## 一、跨系统问题

### CS-1 主线必需事件在日程上的标记与错过即时提示

1. **原文说了什么**：§7.3 规定「错过关键事件的影响包括亏损大量资源、无法获取重要道具、关底事件无法进入真结局、甚至无法抵达关底事件；主线剧情错过的影响严重，支线剧情错过的影响较弱」。B01 4.1① 据此指出「错过关键事件导致整局目标失效」是反感风险最高的一处，建议「主线必需事件在日程上做明确标记；错过时立即提示；局末复盘标出本局未走的节点」。
2. **为什么是问题**：本作卖点是「遗憾感」，但当遗憾升级为「本局已废」且玩家事后才知道时，情绪会归因于「游戏不告诉我」。窗口期与持续时间的参数化设计（§3.1）本身制造了大量错过机会，若不区分「主线必需」与「支线」，玩家无法判断哪次错过是致命的，决策就退化成盲目试错。
3. **需要设计的具体内容**：主线必需事件的判定标准（哪些事件一旦错过就锁死真结局/关底抵达）；这些事件在日程上的标记形态（图标、颜色、层级）；错过时的即时提示时机与文案；局末复盘「本局未走节点」的呈现与线索树写入（§5.2 结算写入）。
4. **争议点与取舍**：a) 标记与提示的「剧透度」——过度标注会破坏条件推断解谜（§9.5）的探索感，不足则挫败；b) 是否只标「主线必需」还是连带标「重要支线」；c) 错过提示是即时强提示还是弱提示，与 CS-2 知情缓冲的边界。
5. **关联与影响**：依赖 S-5/S-6/S-7（日程呈现）、S-9（demo 取舍）、T-2（错过的可见后果）、触发条件 C-5（条件可见性）；影响「世界状态充分呈现」设计原则（§2.3）。
6. **下一步决策**：总监裁定「主线必需事件的标记粒度与提示强度」，并同步决定是否纳入 demo（与 S-9 一并）。

### CS-2 强制事件的知情缓冲 / 预告与收益补偿、插入规则

1. **原文说了什么**：§8.2 定义「强制特殊事件……满足特定要求后强制触发，不容玩家抉择」；§11 规定「强制特殊事件不可拒绝」。B01 4.1④ 指出「不可拒绝的 boss/剧情事件若在玩家精心安排的日程中间强制插入，会破坏计划感」，建议「强制触发前给一个时间段的知情缓冲；强制事件的收益应高于同档可选事件」。
2. **为什么是问题**：强制事件与「日程抉择」的核心卖点直接冲突——计划感是本作招牌，若强制插入毫无预兆，玩家会感到「我的日程被系统强奸」。同时若强制事件收益不高，玩家会视其为惩罚而非世界线的必然节点。
3. **需要设计的具体内容**：强制事件触发前「知情缓冲」的具体形态（提前多少时间段预告、预告的载体）；强制事件在日程上的插入方式（占位、置顶、独立轨道）；强制事件的收益补偿标准（相对同档可选事件的收益上浮幅度）；两类强制事件（错过后果类、失败进入类，见事件系统 4.6）各自的预告需求是否一致。
4. **争议点与取舍**：a) 知情缓冲是「预告不可回避」还是「给玩家一个缓冲时间段」；b) 收益补偿是数值上浮还是内容独有；c) 错过后果类强制事件（因未参与而生）是否需要预告——与「等待期是探索目标而非告知信息」的设计意图（事件系统 4.6）存在张力，需要明确两类强制事件的不同预告口径。
5. **关联与影响**：依赖 E-6（强制事件其他类型）、E-8（错过后果编排）；与 CS-1 的提示体系共用「日程预告」机制；影响 B01 4.1④ 与 4.2（强制剧情频率）。
6. **下一步决策**：总监裁定「强制事件预告的形态与两类强制事件是否区分对待」。

### CS-3 日程簿可视化：横向时间轴 + 事件块的呈现方案

1. **原文说了什么**：B01 4.3② 认为「时间=容量而非成本」是全新心智模型，玩家生活直觉是「走路花时间」，建议「日程簿可视化——横向时间轴 + 事件块（窗口期与持续时间画成甘特图式条块）」。B01 4.5③ 进一步判定它是「时间即路线概念唯一的画面化表达，值得作为 UI 核心投资」。
2. **为什么是问题**：窗口期、持续时间、错过这些抽象参数（§3.1、§4）若只以数字呈现，玩家无法一眼建立「机会成本」的空间直觉，日程张力就兑现不了。这是本作招牌玩法唯一的画面载体，却没有任何已定案形态。
3. **需要设计的具体内容**：时间轴的方向与刻度（时间段为单位的横向条）；事件块的视觉编码（窗口期条、持续时间条、风险/收益/类别）；错过窗口、当前时间段、已锁定强制事件的呈现；日程簿与 S-5/S-6/S-7 三类事件呈现的关系。
4. **争议点与取舍**：a) 甘特图是否过度工程化——是否用更轻的「时间条」即可；b) 日程簿作为「卖点画面」投入多少 UI 资源，与 B01 复杂度控制（4.6）的张力；c) 可视化是「静态时间轴」还是「可交互操作棋盘」。
5. **关联与影响**：与 S-1（日程呈现形式与交互）、S-2（信息呈现）、S-5/S-6/S-7（三类呈现）强耦合，几乎可视为日程系统 UI 设计的母题；影响「世界状态充分呈现」原则。
6. **下一步决策**：总监裁定日程簿的视觉范式（甘特图式 vs 轻量时间条）与投入优先级，作为日程系统填充的 UI 基线。

### CS-4 支线进度阶段化与日程占用的关系

1. **原文说了什么**：§5.5 规定「部分线索树内容的解锁还会直接改变新一局中某些支线的初始进度，避免玩家过多重复同样的前置任务」。C-01-10-04 研讨分析指出「支线进度从之后的阶段开始，但再次进入支线是否仍然占据相同的日程时间段、消耗相同的日程时间，未说明。阶段化简化的是流程内容，日程成本是否同步简化属于事件系统与日程系统的接口问题」。
2. **为什么是问题**：支线阶段化（跳过已做前置）是为了减重复，但若再次进入支线仍占满原时间，阶段化的减负收益会被日程成本抵消，甚至出现「流程变短了但日程占时没变」的不一致。
3. **需要设计的具体内容**：支线阶段化后，该支线事件在日程上占据的时间段是否按阶段缩短；缩短规则（阶段数与日程成本的对应）；对窗口期与后续事件连锁的影响。
4. **争议点与取舍**：a) 日程成本随阶段同步简化 vs 保持固定成本（保持难度平衡）；b) 阶段化是「缩短占用」还是「内容缩短但时间不变」；c) 与「事件持续长度由操作决定」（§7.3、事件系统 4.3）的关系——阶段化省的是哪一段。
5. **关联与影响**：依赖 E-5（推进性特殊事件链式编排）、事件系统 4.3（持续长度由操作决定）；与线索树（§5.5）概率池联动耦合。
6. **下一步决策**：在事件系统填充时，由事件系统与日程系统联调裁定「阶段化是否同步缩短日程占用」。

## 二、时间机制（02-10）

### T-1 "抉择之刻"世界观包装：时间只在有效行为时推进的叙事包装方案

1. **原文说了什么**：§3.1 规定「世界时间只在玩家进入事件时推进，探索、移动、对话完全不消耗时间」；§3.2 提供了重历叙事的合法性。B01 4.4① 指出「时间只在事件中流动反直觉度最高……必须把合法性做进游戏内，以世界观语言包装（例如重历视角中主角处在"抉择之刻"，时间只在做出承诺时启动）；若不做叙事包装，玩家会判定这是技术妥协」。本系统 4.3 已把设计意图（时间只在有效行为时推进、为玩家留思考余地）写入正文，但「用什么世界观语言包装」未定。
2. **为什么是问题**：设计意图（4.3）解决了「系统为什么这么设计」，但没有解决「玩家为什么会相信/接受」。没有叙事包装，「时间只在抉择时流动」会被读成技术妥协，日程紧迫感的成立性受质疑。
3. **需要设计的具体内容**：世界观语言的候选表述（"抉择之刻""承诺启动时间"等）；包装在哪些界面/文本载体出现（开场事件、日程簿、教程）；包装与重历叙事（§3.2）的统一。
4. **争议点与取舍**：a) 是否沿用 B01 的"抉择之刻"候选，还是另起叙事；b) 包装是「轻量文案」还是「完整世界观设定」；c) 与「时间只在有效行为时推进」的精确表述（玩家思考时时间静止）如何自洽。
5. **关联与影响**：依赖时间机制 4.3（设计意图）；影响 B01 4.4① 的学习友好度；与引导与教学（08 域）的时间心智模型教学耦合。
6. **下一步决策**：总监拍板世界观包装用语（沿用"抉择之刻"或另定），定案后回填时间机制 4.3。

### T-2 错过的可见后果设计：错过后果如何让玩家可见

1. **原文说了什么**：§7.3 规定「少数事件在剧情上会继续发展，只是没有主角参与，其后果仍会通过后续事件体现」；B01 4.7 强调「错过的可见后果……必须是玩家能提前看见的后果，而非事后才知」。
2. **为什么是问题**：错过后果若只在事后（后续事件）才暴露，玩家无法把「现在错过」与「未来后果」联系起来，错过感的「机会成本」就退化成「事后懊悔」；反之，后果必须「提前可见」才能构成决策依据。
3. **需要设计的具体内容**：错过后果的可见方式（日程上的预标注、区域形态预告、线索树提示）；「可见」的粒度（只提示「有后果」还是提示「什么后果」）；与强制事件（错过后果类，事件系统 4.6）的衔接。
4. **争议点与取舍**：a) 后果可见度与「等待期是探索目标而非告知信息」（事件系统 4.6）的张力——哪些后果提前告知、哪些留作探索；b) 完全明示会削弱剧情悬念，完全隐藏则违反 B01 4.7；c) 是否对主线/支线区分可见度（呼应 CS-1）。
5. **关联与影响**：与 CS-1（主线标记）、X-11（区域形态转变可见呈现）、事件系统 4.6（错过后果类强制事件）高度耦合；影响「世界状态充分呈现」原则。
6. **下一步决策**：总监裁定「错过后果可见度的分层标准」（哪些提前明示、哪些留待探索）。

### T-3 少数事件"错过但剧情继续发展"的规则与后续体现机制

1. **原文说了什么**：§7.3 规定「窗口期结束后，事件本局消失；少数事件在剧情上会继续发展，只是没有主角参与，其后果仍会通过后续事件体现」；§11 亦有「少数事件剧情继续发展并对后续产生影响」。
2. **为什么是问题**：「少数事件」的判定标准、其「继续发展」如何转化为「后续事件」、以及这一机制与「错过后果类强制事件」（事件系统 4.6）的关系，都未定义，导致错过链的具体规则无法落地。
3. **需要设计的具体内容**：哪些事件属于「错过仍继续发展」的判定规则；后续事件的生成/编排方式（是强制事件还是可选项）；继续发展的世界线变化如何呈现。
4. **争议点与取舍**：a) 「少数」的比例与选例标准；b) 与「错过后果类强制事件」是同一机制还是并列机制；c) 继续发展的后果是否计入错过惩罚体系（§7.3 的亏损资源/锁结局）。
5. **关联与影响**：与 E-8（错过后果编排）、事件系统 4.6（错过后果类强制事件）强耦合；影响 §7.3 的完整兑现。
6. **下一步决策**：事件系统填充时，明确「错过继续发展」与「错过后果类强制事件」的边界，并定「少数事件」的判定规则。

## 三、日程系统（02-20）

### S-1 日程呈现形式与交互：事件清单与日程簿的界面结构、选择与拒绝操作流程

1. **原文说了什么**：§7.1 规定玩家「阅读事件的窗口期与持续时间，结合手头掌握的情况决定是否进入」，§7.3 规定「可以拒绝进入任何已发现的事件」。但「日程」以何种界面承载（清单、时间轴、卡片）、选择与拒绝如何操作，创意文档未定义。
2. **为什么是问题**：日程是本作路线抉择的载体（§4 术语），其呈现与交互形态直接决定「时间即容量」能否被玩家感知；没有已定案的界面结构，日程系统无法进入 UI 细化。
3. **需要设计的具体内容**：日程主界面形态（与 CS-3 日程簿可视化绑定）；发现事件到进入/拒绝的操作链路；多事件并列时的排序与高亮；与探索阶段发现事件的衔接（§7.1）。
4. **争议点与取舍**：a) 清单式 vs 时间轴式 vs 两者结合；b) 选择/拒绝是「点击即决」还是「二次确认」；c) 日程操作是否允许在事件中调整（与 §11-2 确认提示的关系）。
5. **关联与影响**：与 CS-3（可视化）、S-2（信息呈现）、S-3（拒绝反馈）互为母子；影响 X-10（探索发现交互规格）。
6. **下一步决策**：日程系统填充时，先定界面结构骨架（依赖 CS-3 的视觉范式裁定）。

### S-2 日程界面信息呈现：每个事件的窗口期、持续时间、风险与收益的可见度

1. **原文说了什么**：§7.1 要求玩家「阅读事件的窗口期与持续时间」；§2.3 原则「让世界状态充分呈现给玩家」；B01 4.7 要求「错过的可见后果必须是玩家能提前看见的后果」。
2. **为什么是问题**：窗口期、持续时间、风险、收益四项信息若不全或不清晰，玩家无法做机会成本抉择；但信息过载又会加重 B01 反复警告的复杂度。信息呈现的「充分」与「克制」之间需要定边界。
3. **需要设计的具体内容**：每个事件在日程上展示的字段清单（窗口期区间、持续时间、风险、收益、类别）；各字段的呈现形式与层级；信息分级（功能性 vs 氛围性，呼应 B01 4.2 情报分级）。
4. **争议点与取舍**：a) 风险/收益是否「数值化明示」还是「定性暗示」；b) 信息密度与学习友好度（B01 4.3）的平衡；c) 是否与情报分级规范（05-50 情报与解谜）统一。
5. **关联与影响**：与 S-1、CS-3 强耦合；影响「世界状态充分呈现」原则与 B01 复杂度控制。
6. **下一步决策**：日程系统填充时，定「事件卡片信息字段清单与分级」；是否需要与 05-50 情报分级统一由总监确认。

### S-3 拒绝进入事件的交互与反馈规范

1. **原文说了什么**：§7.3 规定「玩家可以拒绝进入任何已发现的事件，拒绝本身是日程决策的一部分」；§11 规定「一般事件可以拒绝进入」。
2. **为什么是问题**：拒绝是日程决策的核心动作之一（主动放弃），但「拒绝的操作形式」「拒绝后的反馈」「拒绝后该事件在日程上的状态」都未定义，导致「拒绝」这一关键决策缺乏清晰的交互闭环。
3. **需要设计的具体内容**：拒绝的操作入口与确认流程；拒绝后事件在日程上的呈现（继续显示至窗口期结束？置灰？）；拒绝是否会触发任何提示（如「你错过了可能影响本局结局的事件」，呼应 CS-1）；拒绝与窗口期结束的关系。
4. **争议点与取舍**：a) 拒绝是否二次确认（误触风险 vs 操作流畅）；b) 拒绝是否区分「普通事件」与「可能重要事件」的提示强度；c) 拒绝的反馈与 CS-1 错过提示的边界。
5. **关联与影响**：与 CS-1（错过提示）、事件系统 4.2（拒绝不改变状态）耦合；影响 §11-2/§11-3 的交互逻辑落地。
6. **下一步决策**：日程系统填充时，定「拒绝的操作与反馈规范」，并与 CS-1 的提示体系统一。

### S-4 转移事件与载具租赁事件的时间消耗在日程上的呈现

1. **原文说了什么**：C-01-10-03 总监裁定「移动事件时间消耗属于日程」「玩家消耗的所有时间都是日程的一部分」。事件系统 4.7 定义转移事件「支付时间」、载具租赁事件「投入金钱和更少的时间成本」。
2. **为什么是问题**：这两类移动事件的时间消耗已裁定「属于日程」，但「在日程上如何呈现」未定——它们是占一个普通时间段，还是以特殊形态（如移动块）呈现？若呈现不清，玩家无法评估「赶路」对窗口期的真实影响。
3. **需要设计的具体内容**：移动事件在日程上的呈现形态（普通事件块 vs 特殊移动标记）；其占用时间段的计算方式（固定 vs 按距离）；与事件池/窗口期的交互（§3.1 时间冲突）。
4. **争议点与取舍**：a) 移动事件是否占用「日程槽位」还是仅消耗时间段；b) 移动时间是否可与目的地事件窗口期联动展示；c) 与 E-13（载具带货）、E-14（封锁通行衔接）的接口顺序。
5. **关联与影响**：依赖事件系统 4.7（移动事件定义）；与 S-2（信息呈现）、X-5（交通站点道路网络）耦合；影响 B01 4.1④ 之外的机会成本体验。
6. **下一步决策**：日程系统填充时，与移动系统（01-10）联调，定「移动事件时间消耗的日程呈现形态」。

### S-5 已经历事件在日程表上的记录粒度与呈现形式（demo 先做）

1. **原文说了什么**：任务书 C-02-bb-01 规定「日程表呈现的信息包括已经历、正在经历、规划未来的事件，demo 阶段先只做已经历的事件」；§4 术语补充「日程表同时记录每段时间经历了哪些事件」。
2. **为什么是问题**：已经历事件是 demo 阶段日程表唯一要做的一类，其「记录粒度」（以事件为单位还是以时间段为单位）与「呈现字段」直接决定 demo 日程表的形态，且必须先行定义才能进入开发。
3. **需要设计的具体内容**：记录粒度（事件级 vs 时间段级）；每条记录包含的字段（事件名、类型、起止时间段、结算结果）；呈现形式（列表 vs 时间轴，依赖 CS-3）。
4. **争议点与取舍**：a) 事件级记录简单但丢失「某时间段重叠/空档」信息，时间段级记录完整但复杂；b) 是否记录「错过」与「拒绝」（呼应 CS-1 局末复盘）；c) demo 范围是否只做最小字段集。
5. **关联与影响**：与 CS-1（局末复盘）、CS-3（可视化）、S-8（世界时间呈现）耦合；是 demo 日程表的直接交付项。
6. **下一步决策**：总监确认 demo 阶段已经历事件的记录粒度（事件级 vs 时间段级）。

### S-6 正在经历事件在日程表上的呈现形式（demo 之后）

1. **原文说了什么**：任务书 C-02-bb-01 规定日程表呈现「正在经历的事件」，但 demo 阶段先只做已经历，正在经历类「demo 之后阶段」再做。
2. **为什么是问题**：正在经历事件是「当前时间段」的唯一内容，其呈现方式（高亮当前块、进度指示）与「时间只在有效行为时推进」（时间机制 4.3）的即时反馈相关，需预留设计避免与已经历事件呈现冲突。
3. **需要设计的具体内容**：正在经历事件在时间轴上的「当前位置」指示；其与已经历事件的视觉区分；事件进行中的时间推进可视化（呼应时间机制 4.5 可见性）。
4. **争议点与取舍**：a) 是否实时显示「当前进行到哪一步」还是只标记「进行中」；b) 与 S-5 已定粒度的统一。
5. **关联与影响**：与 S-5、CS-3、时间机制 4.5（时间推进可见性）耦合；非 demo 阶段，可延后但需预留。
6. **下一步决策**：与 S-5 一并裁定「正在经历」的呈现规格，先出预留方案。

### S-7 规划未来事件在日程表上的呈现形式（demo 之后）

1. **原文说了什么**：任务书 C-02-bb-01 规定日程表呈现「规划未来的事件」，即已发现且仍在窗口期内、尚未决定进入的事件；demo 之后阶段再做。
2. **为什么是问题**：规划未来事件是「机会成本抉择」的直接对象（§3.1），其呈现决定玩家能否一眼比较「做 A 还是做 B」；但它在 demo 不做，设计上最容易被拖延，却又最关键。
3. **需要设计的具体内容**：规划未来事件在时间轴上的位置（按其窗口期区间落位）；窗口期条与持续时间条的可视化（呼应 CS-3 甘特图）；进入/拒绝的入口衔接（呼应 S-1/S-3）。
4. **争议点与取舍**：a) 规划未来事件是否与「已发现未决定」等同（对应事件状态「可进入」）；b) 是否在日程上直接操作进入/拒绝，还是跳转事件详情。
5. **关联与影响**：与 CS-3、S-1、S-3 强耦合；是日程系统最核心的一类呈现。
6. **下一步决策**：与 S-1/S-3 一并定「规划未来事件」的呈现与操作形态（虽 demo 后做，需先定方向）。

### S-8 日程表上世界时间的呈现方式

1. **原文说了什么**：时间机制 4.5 规定「在推进前后向玩家呈现世界时间的当前值，使玩家能判断剩余时间与后续事件窗口期是否还赶得上」；任务书 C-02-bb-01 要求日程表记录时间。
2. **为什么是问题**：世界时间当前值是玩家做「赶窗口」判断的基准，但「以什么形式呈现」（第几时间段、剩余多少、日历日期）未定，呈现不清会导致玩家无法心算窗口。
3. **需要设计的具体内容**：世界时间当前值的显示载体与形式（时间段序号、日历日期、相对窗口期的剩余）；与游戏内日历（时间机制 4.2）的关系。
4. **争议点与取舍**：a) 用「时间段序号」还是「日历时间」做主刻度；b) 是否需要「距某事件窗口结束还剩 X」的辅助换算（呼应 S-2）。
5. **关联与影响**：与时间机制 4.2（日历）、4.5（可见性）、S-2 耦合；影响玩家心算成本（B01 4.3②）。
6. **下一步决策**：日程系统填充时定「世界时间主刻度与辅助换算」。

### S-9 错过即时提示的 demo 阶段取舍（是否列为 demo 必备项）

1. **原文说了什么**：B01 4.1① 要求「错过时立即提示」；§2.3 原则「让世界状态充分呈现给玩家」；但任务书 C-02-bb-01 规定 demo 阶段日程表「先只做已经历的事件」——已经历是事后回顾，无法满足「错过即时提示」的即时性。
2. **为什么是问题**：demo 是验证「错过感」是否成立的关键阶段（B01 P0-1 纸面原型），若 demo 只做事后回顾、不做错过即时提示，「本局已废」的隐性失败风险会在 demo 就暴露，但「错过提示」又与 demo 日程表范围冲突。
3. **需要设计的具体内容**：错过即时提示的承载载体（是否脱离日程表、用独立提示条）；demo 阶段的最小必备提示集；错过提示与 CS-1 主线标记的关系。
4. **争议点与取舍**：a) 错过提示是否必须挂日程表，还是可用世界内提示（视觉/对话）；b) demo 是否「最小化只做主线错过提示」；c) 与「等待期是探索目标而非告知信息」（事件系统 4.6）的口径冲突。
5. **关联与影响**：与 CS-1、T-2、事件系统 4.6 耦合；是 demo 留存的关键变量（B01 P0-3 首小时）。
6. **下一步决策**：总监裁定「错过即时提示是否列为 demo 必备、以何种载体呈现」，并与 S-5 的 demo 范围一并确认。

## 四、事件系统（02-30）

### E-1 强制剧情事件贵精不贵多、触发频率控制

1. **原文说了什么**：§8.2 定义强制特殊事件「boss 事件与剧情事件，满足特定要求后强制触发」。B01 4.2 指出「强制剧情事件若密集出现，会催生反感式跳过。强制剧情贵精不贵多」。
2. **为什么是问题**：强制剧情事件不可拒绝（§11），若频率失控，会持续打断玩家的日程计划感（呼应 CS-2），并催生跳过剧情的习惯，反向损害剧情收集驱动（B01 4.2）。
3. **需要设计的具体内容**：强制剧情事件的每局数量上限/频率基准；与可选剧情事件的配比；强制剧情事件的触发时机分布（避免连续插入）。
4. **争议点与取舍**：a) 频率用「每局数量上限」还是「时间间隔」约束；b) boss 事件与剧情事件是否分别限频；c) 与 B01 4.1④（强制事件收益补偿）的关系。
5. **关联与影响**：与 CS-2（知情缓冲）、E-6（强制事件类型）耦合；影响剧情驱动与复杂度控制（B01 4.2、4.6）。
6. **下一步决策**：事件系统填充时，定「强制剧情事件频率基准」，总监确认。

### E-2 五类事件（战斗/剧情/贸易/探索/委托）的内容模板与编排规范

1. **原文说了什么**：§4 术语定义「事件类型包括战斗、剧情、贸易、探索与委托」；§8.2 将事件按「定位」分为可重复资源获取、推进性特殊、强制特殊三类（分类维度不同）。
2. **为什么是问题**：事件有两个分类维度（类型五类 vs 定位三类），二者如何交叉、每类事件的内容模板（进入后发生什么）如何编排，均未定义，导致事件内容无法批量生产。
3. **需要设计的具体内容**：五类型 × 三定位的交叉矩阵；每类事件的内容模板（结构骨架、可复用的流程模块）；类型与定位的默认映射（哪些类型可重复、哪些推进、哪些强制）。
4. **争议点与取舍**：a) 「探索」与「贸易」类型是否与「定位」重叠造成混乱；b) 模板化程度——过度模板化损叙事，不足则无法量产；c) 委托事件是否拆入 05-20 委托系统独立设计。
5. **关联与影响**：与 E-4（可重复事件参数）、E-5（推进性事件链）、E-6（强制事件类型）耦合；是事件系统填充的起点。
6. **下一步决策**：事件系统填充时先定「五类型 × 三定位矩阵与内容模板」，总监确认。

### E-3 事件进入确认提示的界面形式与文案规范

1. **原文说了什么**：§11 规定「进入会推进时间的事件前必须有界面确认提示，防止误触发」；§8.3 亦规定「进入会推进时间段的事件之前，玩家会收到直接的界面提示」。
2. **为什么是问题**：确认提示是「防止误触发」的安全网，但其界面形式（弹窗/浮层/卡片）、文案结构（事件名、窗口期、持续时间、风险收益摘要）未定义；提示内容过简则玩家仍误入，过繁则打断节奏。
3. **需要设计的具体内容**：确认提示的界面形态与字段；提示中是否复述窗口期/持续时间/风险收益（呼应 S-2）；确认/取消的操作与焦点。
4. **争议点与取舍**：a) 是否只对「推进时间」的事件提示，探索/贸易等是否同规；b) 提示是否内嵌「拒绝」入口（呼应 S-3）；c) 文案与信息分级的统一。
5. **关联与影响**：与 S-1/S-3（进入拒绝流程）、S-2（信息呈现）耦合；是 §11-2 交互逻辑的落地。
6. **下一步决策**：事件系统填充时定「确认提示界面与文案规范」。

### E-4 可重复资源获取事件的程序化生成参数（地点、报酬、敌人配置等）

1. **原文说了什么**：§8.2 定义「可重复资源获取事件是程序化生成的可重复内容，参数例如地点、报酬与敌人配置各不相同，主要承担发育功能」。
2. **为什么是问题**：「参数例如地点、报酬与敌人配置」只是举例（"例如"），参数全集、生成方式（种子扰动 §3.2）与刷新机制都未定义，导致发育内容无法落地。
3. **需要设计的具体内容**：可重复事件的参数全集（地点、报酬、敌人配置、类型、窗口期等）；程序化生成的来源（种子 §3.2）与随机范围；与概率池联动（§5.5）的接口。
4. **争议点与取舍**：a) 参数全集是否「穷举」——按通则「举例仅辅助、不一一枚举」，需定「参数框架」而非枚举值；b) 报酬/敌人配置的具体数值属数值策划（09-10），本阶段只定「有哪些参数、如何生成」；c) 与 E-2 内容模板的分工。
5. **关联与影响**：与 E-2（模板）、概率池联动（07-30）、局生成与种子（09-20）耦合；数值部分归 09-10。
6. **下一步决策**：事件系统填充时定「可重复事件参数框架与生成规则」，数值交 09-10。

### E-5 推进性特殊事件的每局唯一性保障与链式编排

1. **原文说了什么**：§8.2 定义「推进性特殊事件是每局唯一的剧情内容，推进世界线与故事线发展」；§7.3 规定「一局中未触发的支线即本局未走到的世界线分支」。
2. **为什么是问题**：「每局唯一」如何保障（同一事件一局内不重复出现？）、推进性事件如何链式编排（前置/后续关系）、与支线进度阶段化（§5.5、CS-4）如何衔接，均未定义。
3. **需要设计的具体内容**：每局唯一性的保障机制（事件池去重、进度标记）；推进性事件的链式结构（前置事件 → 后续事件）；与支线阶段化的接口（CS-4）。
4. **争议点与取舍**：a) 每局唯一是「内容唯一」还是「节点唯一」；b) 链式编排是否复用触发条件系统（02-30-10 前置事件条件）；c) 与线索树（§5.4 引导、§5.5 概率池）的写入关系。
5. **关联与影响**：与 CS-4（支线阶段化）、E-2（模板）、触发条件 C-2（前置事件条件）耦合；是剧情驱动（B01 4.2）的核心。
6. **下一步决策**：事件系统填充时定「推进性事件链式编排与唯一性机制」。

### E-6 强制事件的其他类型与完整触发要求（失败进入类与错过后果类已定，其余预留）

1. **原文说了什么**：事件系统 4.6 已定义两类强制事件（错过后果类、失败进入类）并预留「其他类型」。§8.2 的强制特殊事件（boss/剧情，满足特定要求强制触发）与这两类的关系未完全对齐。
2. **为什么是问题**：4.6 预留了「其他类型」，但 §8.2 的「满足特定要求强制触发」类（boss/剧情）尚未明确归入 4.6 的哪一类，强制事件的类型全集与触发要求（"特定要求"是什么）未定。
3. **需要设计的具体内容**：强制事件的完整类型清单（失败进入类、错过后果类、剧情推进类 boss/剧情、其他）；各类型的触发要求（"特定要求"的具体化）；与 §8.2 三类定位的对齐。
4. **争议点与取舍**：a) boss/剧情强制事件是否算「第三类」还是并入失败进入/错过后果；b) 强制事件的统一规格（不可拒绝、日程可见性）是否所有类型一致；c) 与 CS-2（知情缓冲）的类型差异。
5. **关联与影响**：与 CS-2、E-1、E-8 耦合；是强制事件机制的完整化。
6. **下一步决策**：事件系统填充时，补齐强制事件类型全集，并把 §8.2 的 boss/剧情强制事件归位。

### E-7 事件内世界状态提示的内容规范

1. **原文说了什么**：§9.4 规定「玩家在事件中会获得关于世界状态的说明，例如某类货物的行情、将发生特殊事件的地点。玩家可据此安排货物买卖、接取委托与日程规划」。
2. **为什么是问题**：世界状态提示是「信息差变现」与「日程规划」的依据，但提示的内容类型（行情、事件地点、线索）、呈现时机（事件内何时）、与情报分级（B01 4.2）的关系都未定义。
3. **需要设计的具体内容**：世界状态提示的内容类别清单；提示在事件内的呈现时机与载体；与线索树写入（§5.2）的衔接（是否结算后可见）。
4. **争议点与取舍**：a) 提示是「功能性情报」需分级排版（B01 4.2），还是普通文案；b) 提示是否与 05-50 情报与解谜的文案管线统一；c) 提示的随机性（种子扰动 §3.2）。
5. **关联与影响**：与 05-50（情报与解谜）、09-20（局生成）、S-2（信息呈现）耦合；影响信息差变现（B01 3.2）。
6. **下一步决策**：事件系统填充时定「世界状态提示内容类别与呈现时机」，与 05-50 情报分级联调。

### E-8 错过后果的内容编排：错过事件后兑现的强制事件如何设计

1. **原文说了什么**：§7.3 规定「少数事件在剧情上会继续发展……其后果仍会通过后续事件体现」；事件系统 4.5 归纳「未进入事件而错过，其后果在世界时间继续推进一段时间后兑现，通常表现为区域形态发生转变」；4.6 定义错过后果类强制事件。
2. **为什么是问题**：错过后果「以强制事件兑现」的机制已定，但「后果内容如何编排」（一个错过对应几个后果事件、后果的叙事与数值、连锁后果）未定义，导致错过链无法落地。
3. **需要设计的具体内容**：错过后果事件的编排结构（单后果 vs 后果链）；后果事件的内容（区域形态转变、资源损失、后续事件锁闭）；与等待期（世界时间推进多少时间段后兑现，时间机制 4.6）的衔接。
4. **争议点与取舍**：a) 后果兑现是否一律「延时」（等待期）还是部分即时；b) 后果内容是否复用 E-2 事件模板；c) 与 T-3（错过但剧情继续）的边界。
5. **关联与影响**：与 T-3、T-2（可见后果）、X-8（区域形态转变规则）耦合；是错过链的编排核心。
6. **下一步决策**：事件系统填充时定「错过后果事件的编排结构」，与 T-3 一并。

### E-9 场景变化包装事件的统一规格（超出四项特征的系统级规格）

1. **原文说了什么**：事件系统 4.4 定义场景变化包装事件「没有流程、日程中不可见、没有投入产出、玩家感知不到的强制事件」；四项特征已在正文定义，但「超出四项特征的系统级规格」（如这些包装事件在状态机、存档、回溯中的统一处理）未定。
2. **为什么是问题**：场景变化「包装为事件」是为了统一执行入口（4.4），但若没有统一的系统级规格，包装事件与常规事件在状态机/结算/存档/线索树写入上的差异会导致管理混乱，失去「统一入口」的意义。
3. **需要设计的具体内容**：包装事件与常规事件共用的规格边界（状态、结算、存档、回溯）；包装事件的「不可感知」在追踪/回溯上的表达（4.4 已提到"可通过事件状态追踪与回溯"）；与区域形态（X-8/X-9）的绑定。
4. **争议点与取舍**：a) 包装事件是否走完整五种事件状态（事件系统 4.2），还是简化状态；b) 「在事件数据中的表达方式」属代码实现，本阶段只定系统级规格；c) 包装事件是否写入线索树/局末结算。
5. **关联与影响**：与事件系统 4.2（状态）、4.4、X-8/X-9 耦合；依赖 07-40（局末结算）边界。
6. **下一步决策**：事件系统填充时定「包装事件的统一规格」（系统级），数据表达留待代码阶段。

### E-10 事件状态迁移的驱动来源与时机（窗口期结束、事件结果、世界时间推进等）

1. **原文说了什么**：事件系统 4.2 定义五状态（未出现/可进入/进行中/已完成/已错过）与迁移主线；触发条件 4.1 说明「条件判定驱动五种事件状态迁移」。但状态迁移的「驱动来源清单」与「时机」（何时检查、谁触发）未系统定义。
2. **为什么是问题**：状态迁移是事件生命周期的基础，若驱动来源（窗口期结束、事件结果、世界时间推进、玩家拒绝等）与时机不清，事件状态机无法实现，错过/强制等机制也会挂错时机。
3. **需要设计的具体内容**：状态迁移的驱动来源全集（窗口期、事件结果、世界时间、玩家行为）；各驱动的触发时机与优先级；与触发条件（C-6）判定的分工。
4. **争议点与取舍**：a) 状态迁移是否全部收敛到触发条件系统统一驱动；b) 「世界时间推进」驱动的等待期检查时机（连续 vs 离散）；c) 「在状态机中的挂载方式」属代码实现，本阶段定驱动来源与时机。
5. **关联与影响**：与触发条件 C-6（状态迁移接口）、事件系统 4.2 耦合；是状态机的系统级底座。
6. **下一步决策**：事件系统与触发条件联调，定「状态迁移驱动来源与时机」全集。

### E-11 事件结算的执行规格：结算时机、结果呈现、与局末结算的职责边界

1. **原文说了什么**：事件系统 4.1 定义「事件结算指在事件结束时，根据结束分支一次性应用本次事件对玩家与世界状态造成的全部结果」；§7.2 规定「局内行为记录与解锁内容在结算时一并写入线索树」。
2. **为什么是问题**：事件结算（退出事件时）与局末结算（07-40 局末结算与写入）的职责边界未定——哪些结果事件退出时立刻应用（资源/时间/世界状态），哪些延迟到局末（线索树解锁），重叠或遗漏都会破坏账目一致性。
3. **需要设计的具体内容**：事件结算的触发时机（退出事件即结算）；结算结果的即时呈现方式（结算面板/浮层）；与局末结算（07-40）的分工清单（事件级 vs 局级）。
4. **争议点与取舍**：a) 线索树解锁是否在事件退出时立即写入还是局末统一写入（§5.2 说"结算时写入"）；b) 结算呈现的粒度（是否逐项列出）；c) 失败/死亡结局的结算差异。
5. **关联与影响**：与 07-40（局末结算）、线索树核心（07-10）耦合；是资源账目一致性（§3.3 资源即战力）的关键。
6. **下一步决策**：事件系统与 07-40 联调，定「事件结算与局末结算的职责边界」。

### E-12 事件结束分支的组合规则与优先级

1. **原文说了什么**：事件系统 4.5 归纳「事件存在多种结束分支，不同分支分别改变区域形态、事件池刷新范围与窗口期长度」；并明确「结束分支的具体数量与组合规则由事件自身设计决定，本阶段不限定分支数量与内容」。
2. **为什么是问题**：多操作组合可能同时满足多个结束分支（如既达成失败又错过），分支的「组合规则与优先级」未定，会出现同一事件走到多个矛盾后果的冲突。
3. **需要设计的具体内容**：结束分支的组合模型（互斥 vs 可叠加）；多分支同时满足时的优先级规则；分支与「事件结果对世界影响」（4.5）的映射。
4. **争议点与取舍**：a) 分支是否「单一出口」还是「多结果叠加」；b) 优先级是固定规则还是事件自定义；c) 与 E-11（结算）的衔接（结算按最终分支）。
5. **关联与影响**：与 E-11、E-8（错过后果）、事件系统 4.5 耦合；是事件结果一致性的保障。
6. **下一步决策**：事件系统填充时定「结束分支组合与优先级规则」。

### E-13 载具租赁事件的带货能力与委托运输接口

1. **原文说了什么**：事件系统 4.7 定义载具租赁事件「投入金钱和更少的时间成本，获得更远的基点位置与活动范围变化」；C-01-10-02 研讨分析指出「载具能否携带货物、委托任务能否使用载具运输」作为经济接口未展开，登记「归 05-20 委托系统」。
2. **为什么是问题**：载具是否带货直接影响「商人」身份的经营玩法（货物运输是商人核心），也影响委托运输类任务的可行性；接口未定会阻断经营与移动两系统的联动。
3. **需要设计的具体内容**：载具带货的容量与规则（是否复用背包/仓库容量，§9.3）；委托运输接口（05-20 委托系统承接）；带货对载具租赁成本的影响。
4. **争议点与取舍**：a) 载具带货是否「有独立载重」还是「复用背包空间」；b) 委托运输是否首版做（B01 4.6③ 建议委托模板化）；c) 与 05-20 委托系统的归属边界。
5. **关联与影响**：与 05-20（委托）、05-30（背包）、05-40（仓库）耦合；影响商人经营循环（§9.1）。
6. **下一步决策**：与 05-20 委托系统联调，定「载具带货与委托运输接口」（可归入委托系统填充）。

### E-14 封锁区域允许通行方式与载具类型的衔接

1. **原文说了什么**：C-01-10-04 裁定「封锁区域携带封锁理由与允许通行方式两个接口」；事件系统 4.7 定义载具租赁「目的地取决于地图上的交通站点与道路网络」。C-01-10-04 研讨分析指出「允许的通行方式与载具目的地规则的接口关系未定义——当站点位于允许地铁通行的封锁区域内时，该站点是否成为地铁载具的合法目的地」。
2. **为什么是问题**：封锁区域的「允许通行方式」（如地铁仍可达）与载具「目的地=交通站点」两个规则叠加时，站点合法性判定缺失，导致移动系统与探索系统的接口空悬。
3. **需要设计的具体内容**：封锁区域站点作为载具目的地的合法性判定；允许通行方式与载具类型的匹配表；地面/地下载具对封锁区域的差异化。
4. **争议点与取舍**：a) 站点位于封锁区时是否「一律不可达」还是「按允许通行方式放行」；b) 与 00-总览/01 交互逻辑 19（未开放区域不可作为目的地）的关系。
5. **关联与影响**：与 X-5（交通站点道路网络）、X-6（封锁机制接口）、移动系统（01-10）耦合；是快速移动与探索的接口。
6. **下一步决策**：探索系统填充交通站点时，与移动系统联调裁定「站点可达性判定」。

## 五、探索系统（02-40）

### X-1 区域解锁规则

1. **原文说了什么**：§8.1 规定「地图划分为若干区域，已开放区域可自由探索，锁定区域随进度解锁，具体解锁规则在后续阶段细化」；§12 将「区域解锁规则」列入后续计划。
2. **为什么是问题**：「随进度解锁」的进度指什么（主线推进？线索树？事件结果？）未定义，区域解锁规则是探索空间开放节奏的底座，缺失会导致地图开放逻辑无法实现。
3. **需要设计的具体内容**：区域解锁的触发条件（进度来源）；解锁与事件/世界线的绑定；锁定区域在玩家侧的呈现（呼应 X-6 封锁机制）。
4. **争议点与取舍**：a) 解锁进度是「主线事件」还是「线索树节点」还是「任意事件结果」；b) 与活动范围/封锁机制（01-10、X-6）是三套锁定还是统一；c) 数值（解锁阈值）归 09-10。
5. **关联与影响**：与 X-6（封锁接口）、移动系统（01-10 活动范围）耦合；影响地图探索节奏（§8.1）。
6. **下一步决策**：探索系统填充时定「区域解锁规则」，并厘清与活动范围、封锁机制的三套锁定关系。

### X-2 区域与事件分布的关系：地点参数的扰动方式

1. **原文说了什么**：§3.2 规定「随机种子扰动本局的环境参数，例如事件分布、窗口期、地点与行情」；§8.1 规定区域划分。
2. **为什么是问题**：事件分布在地图区域上的「地点参数」如何被种子扰动（事件落在哪个区域、密度、类型分布）未定义，直接决定每局探索的新鲜度与「信息差变现」（B01 3.2）的实现。
3. **需要设计的具体内容**：事件地点参数在区域上的分布规则（区域与事件类型的绑定、密度）；种子扰动对这些参数的扰动方式与范围；与概率池联动（§5.5）的分工。
4. **争议点与取舍**：a) 事件分布是「区域绑定」还是「全域随机」；b) 扰动是「参数扰动」还是「事件池重roll」；c) 具体数值归 09-10。
5. **关联与影响**：与 X-9（形态与事件池绑定）、07-30（概率池联动）、09-20（局生成）耦合；影响 §3.2 世界线差异。
6. **下一步决策**：探索系统填充时定「事件分布与地点扰动规则」，与 09-20 局生成联调。

### X-3 地图即战场：战斗状态视觉切换与格子显示方案

1. **原文说了什么**：§10.3 规定「战斗在大世界原地展开，大世界的瓦片格即战斗格」；B01 4.4④ 指出「地图即战场意味着平时自由行走与战时格子判定两套移动规则叠在同一空间，玩家会疑惑为什么格子只在战斗中生效，需要明确的战斗状态视觉切换（格子高亮、射程显示、行动槽浮现）」。
2. **为什么是问题**：探索（自由行走）与战斗（格子判定）共享同一空间，若无明确的「进入战斗」视觉切换，两套移动规则会让玩家困惑；这是 B01 列为「反直觉」的点。
3. **需要设计的具体内容**：战斗状态切换的视觉呈现（格子高亮、射程显示、行动槽浮现）；切换的触发时机与过渡；与战场与战棋规则（06-30）的接口。
4. **争议点与取舍**：a) 切换是「即时切换」还是「过场演出」；b) 视觉切换的归属（探索系统还是 06-30 战场规则）；c) 与 06 战斗 UI 的统一。
5. **关联与影响**：与 06-30（战场与战棋规则）耦合；是 B01 4.4④ 的直接回应；影响战斗学习友好度。
6. **下一步决策**：探索系统与 06-30 联调，定「战斗状态视觉切换规格」，归属需总监确认。

### X-4 区域内容模板（已开放区域中的探索点、贸易点、委托点等分布规则）

1. **原文说了什么**：§8.1 规定已开放区域可自由探索；§9.1 规定委托是随机事件；区域内的探索点、贸易点、委托点等「内容点」如何分布未定义。
2. **为什么是问题**：已开放区域若没有内容点分布规则（哪里能探索、哪里能贸易、哪里接委托），自由探索就退化成空地图，探索的「发现事件」职能（§7.1）无法承载。
3. **需要设计的具体内容**：区域内容点的类型清单（探索点、贸易点、委托点、事件地点等）；各类内容点在区域内的分布与密度规则；与事件分布（X-2）的关系。
4. **争议点与取舍**：a) 内容点是否「区域模板化」（每区域固定构成）还是「随机分布」；b) 密度/数量数值归 09-10；c) 与区域形态（X-8/X-9）的联动。
5. **关联与影响**：与 X-2（事件分布）、X-8/X-9（区域形态）耦合；影响探索节奏（§8.1）。
6. **下一步决策**：探索系统填充时定「区域内容模板」。

### X-5 交通站点与道路网络：载具租赁事件的目的地与路线载体

1. **原文说了什么**：C-01-10-03 裁定「快速移动目的地取决于交通站点与道路网络，事件地点直接传送的设计完全废弃」；事件系统 4.7 定义载具租赁「目的地取决于地图上的交通站点与道路网络」。
2. **为什么是问题**：交通站点与道路网络是载具租赁（快速移动）的空间载体，但站点的布设、道路网络的拓扑、站点与事件点位的关系都未定义，导致快速移动无法落地。
3. **需要设计的具体内容**：交通站点的布设规则（密度、与区域的关系）；道路网络的拓扑（连接关系、路线约束）；站点与事件点位的「最后一程徒步」关系（C-01-10-03 研讨分析：站点密度过高则传送退化为点到点，过低则徒步过长）。
4. **争议点与取舍**：a) 站点密度与「最后一程徒步」的平衡（C-01-10-03 已点名，数值归 09-10）；b) 道路网络是否「区域级」还是「全域级」；c) 与 E-14（封锁通行衔接）、X-6（封锁接口）耦合。
5. **关联与影响**：与 E-14、X-6、移动系统（01-10）耦合；是快速移动的空间底座。
6. **下一步决策**：探索系统填充时定「交通站点与道路网络拓扑」，密度数值交 09-10。

### X-6 封锁机制接口细化（封锁理由与允许通行方式双接口已裁定，交互与实现待设计）

1. **原文说了什么**：C-01-10-03/04 裁定「封锁区域统一携带封锁理由与允许的通行方式两个接口，活动范围机制纳入锁定区代码实现」；00-总览/01 交互逻辑 15、19 记录了该裁定。
2. **为什么是问题**：双接口的「模型」已定，但「交互呈现」（玩家如何看到封锁理由、如何理解可通行方式）与「实现细化」（接口在探索系统内的具体形态）未定；C-01-10-03 研讨分析指出「封锁理由在交互层统一不可通行，玩家侧的呈现未定义」。
3. **需要设计的具体内容**：封锁理由在玩家侧的呈现方式（是否告知理由、如何呈现）；允许通行方式的玩家可读表达；封锁区域与区域解锁（X-1）、活动范围（01-10）的关系。
4. **争议点与取舍**：a) 封锁理由是否完全隐藏（若隐藏，玩家面对不可通行区域缺乏可读性）；b) 三套锁定（封锁、区域解锁、活动范围）是否统一成一个「封锁」概念；c) 实现细节归代码阶段。
5. **关联与影响**：与 X-1（区域解锁）、移动系统（01-10 活动范围/封锁区域）耦合；是探索空间约束的统一。
6. **下一步决策**：探索系统填充时定「封锁理由呈现与三套锁定关系」，总监确认是否统一。

### X-7 安全通道布设

1. **原文说了什么**：C-01-10-03 裁定「安全通道以仅自由探索环节可交互的位置为主要形式」；探索系统 4.2 提及危险地形与安全通道；术语表定义「安全通道：危险地形上供玩家通行的位置，出入口包装为不可见、不可通过的场景道具，f 键交互到达对端」。
2. **为什么是问题**：安全通道的形式（术语表已部分定义）与布设规则（危险地形上如何布设、密度、与战斗封锁的衔接）未完整定义；且其战斗影响已移交 06-30，需厘清探索侧与战斗侧的分工。
3. **需要设计的具体内容**：安全通道在危险地形上的布设规则；通道的探索交互（f 键）完整流程；与战斗环节封锁（06-30 已移交）的接口。
4. **争议点与取舍**：a) 安全通道是「固定布设」还是「种子扰动生成」；b) 与危险地形（06-30 战斗影响）的规则一致性（C-01-10-03 研讨分析已点名）；c) 通道密度数值归 09-10。
5. **关联与影响**：与 06-30（战场与战棋规则）、移动系统（01-10）耦合；影响危险地形通行（§8.1）。
6. **下一步决策**：探索系统填充时定「安全通道布设规则」，与 06-30 战斗影响联调。

### X-8 区域形态转变的通用规则（形态种类、转变条件）

1. **原文说了什么**：任务书 C-02-bb-01 规定「区域形态随事件结果发生转变」；探索系统 4.1 已归纳一般规则（形态变化由事件系统以强制事件执行，形态决定事件池刷新与窗口期），但「形态种类、转变的时间条件与前置事件条件」等通用规则未定。
2. **为什么是问题**：区域形态转变是「事件结果改变世界」的核心载体，若无通用规则（有哪些形态、什么条件触发转变），每个形态转变都要单独设计，无法复用，也无法保证一致性。
3. **需要设计的具体内容**：形态种类的通用框架（形态如何定义、是否每区域独立）；转变的触发条件（时间条件、前置事件条件、事件结果）；形态与场地存在时长的关系。
4. **争议点与取舍**：a) 形态是「全局枚举」还是「区域自定义」；b) 转变是否一律走「强制事件包装」（事件系统 4.4/4.6）；c) 与触发条件（C-7 包装事件条件规格）的分工。
5. **关联与影响**：与 X-9（形态与事件池绑定）、事件系统 4.5/4.6、触发条件 C-7 耦合；是区域形态机制的完整化。
6. **下一步决策**：探索系统填充时定「区域形态转变通用规则」，与事件系统/触发条件联调。

### X-9 区域形态与事件池的绑定规范

1. **原文说了什么**：探索系统 4.1 规定「区域形态决定该区域上事件池的刷新范围与窗口期长度：形态变化后，与新形态对应的事件进入事件池并刷新，新形态相关事件的窗口期受该形态存在时长的约束」。
2. **为什么是问题**：「每种形态允许刷新的事件类别」与「窗口期上限的配置方式」未定，导致形态→事件池的绑定无法落地，形态转变对内容刷新的影响无法实现。
3. **需要设计的具体内容**：每种形态允许刷新的事件类别清单；形态对窗口期上限的约束方式；形态与事件池（07-30 概率池联动）的绑定接口。
4. **争议点与取舍**：a) 绑定是「形态→事件类别白名单」还是「权重调整」；b) 窗口期上限是「形态存在时长」直接约束还是独立参数；c) 与 07-30 概率池联动的分工。
5. **关联与影响**：与 X-8（形态规则）、07-30（概率池联动）耦合；是形态对内容刷新的落地。
6. **下一步决策**：探索系统填充时定「形态与事件池绑定规范」，与 07-30 联调。

### X-10 探索行为与事件发现流程的交互规格

1. **原文说了什么**：§7.1 规定「通过进入区域、对话等交互方式发现事件。发现事件不消耗时间」；探索系统 4.2 归纳「玩家在事件地点发现可进入的事件，阅读窗口期与持续时间并决定是否进入」。
2. **为什么是问题**：发现事件的具体交互流程（如何触发发现、发现后如何阅读、如何发起进入确认）未定义，探索的「发现」职能无法落地，与日程（S-1 进入/拒绝流程）的衔接也未定义。
3. **需要设计的具体内容**：发现事件的触发方式（进入区域、对话、靠近事件地点）；发现后的信息呈现（事件卡片）；发起进入确认的操作流程（衔接 E-3 确认提示）。
4. **争议点与取舍**：a) 发现是「自动」还是「主动交互」；b) 发现信息与日程信息（S-2）是否一致；c) 隐藏事件（术语表：入口不揭露）的发现特殊处理。
5. **关联与影响**：与 S-1（日程进入/拒绝）、E-3（确认提示）耦合；影响 §7.1 局内循环。
6. **下一步决策**：探索系统填充时定「事件发现交互规格」，与日程系统联调。

### X-11 区域形态转变的可见呈现（形态变化后地图与界面变化）

1. **原文说了什么**：探索系统 4.1 规定区域形态随事件结果变化；B01 4.7 要求「错过的可见后果」；形态变化后，地图与界面如何呈现变化未定。
2. **为什么是问题**：区域形态转变若在玩家视觉上不可见，玩家就无法感知「世界因我的选择而改变」，错过后果的可见性（T-2）就落空；但「形态变化前是否预告」又与「等待期是探索目标」（事件系统 4.6）存在张力。
3. **需要设计的具体内容**：形态变化后地图与界面的呈现（视觉变化、区域标识变化、事件池变化提示）；变化前是否预告（与 T-2 可见度分层一致）；与线索树（§5.2 结算写入）的衔接。
4. **争议点与取舍**：a) 「变化后可见」是底线（B01 4.7），「变化前预告」需按 T-2 分层裁定；b) 呈现是「地图图层变化」还是「独立提示」；c) 与 X-8（形态规则）联动。
5. **关联与影响**：与 T-2（错过的可见后果）、X-8（形态规则）耦合；影响「世界状态充分呈现」原则。
6. **下一步决策**：探索系统填充时定「形态变化可见呈现」，与 T-2 可见度分层一致。

### X-12 区域形态转变与进行中事件的关系（强制退出规则）

1. **原文说了什么**：探索系统 4.1 规定区域形态随事件结果变化；若形态转变发生时该区域上有进行中的事件，如何处理未定义。
2. **为什么是问题**：形态转变（如区域变为危险/封锁形态）与进行中事件可能冲突——进行中事件是否被强制打断/退出，直接关系到玩家体验（正在做的事件被形态变化打断）与状态一致性。
3. **需要设计的具体内容**：形态转变发生时该区域进行中事件的处理方式（允许完成、强制退出、延时转变）；强制退出的结算与玩家补偿；与 E-10（状态迁移时机）的衔接。
4. **争议点与取舍**：a) 形态转变是否「等待进行中事件结束」再执行；b) 强制退出的结算是否按 E-11 结算规则；c) 与事件系统 4.6（错过后果类强制事件）的触发时机冲突。
5. **关联与影响**：与 E-10、E-11、X-8 耦合；影响状态一致性。
6. **下一步决策**：探索系统填充时定「形态转变与进行中事件的关系」，与事件系统联调。

## 六、触发条件（02-30-10）

### C-1 线索解锁在条件模块中的一等公民化

1. **原文说了什么**：§8.3 规定事件前置条件「例如时间条件、地点条件、前置事件条件、资源门槛与线索解锁等」；B01 4.2 指出「内容门槛：事件前置条件包含线索解锁，不收集，内容就锁死（内容门槛是剧情收集驱动的五重绑定之一，需在条件模块中一等公民化）」。
2. **为什么是问题**：线索解锁是「剧情收集驱动」的关键门槛（不收集就锁内容），但在条件模块中若只作为普通条件之一，可能被弱化；「一等公民化」意味着它要有独立、完整的表达与联动，而非拼凑。
3. **需要设计的具体内容**：线索解锁条件在条件模块中的独立表达（线索节点、解锁状态）；与线索树（§5.5 概率池联动、§5.4 引导）的联动；线索解锁与其他条件（时间/地点/资源）的组合规则。
4. **争议点与取舍**：a) 线索解锁是「硬门槛」还是「软引导」；b) 与 C-4（条件与线索树联动接口）的分工；c) 一等公民化是否要求「线索解锁条件可单独配置」。
5. **关联与影响**：与 C-2（条件模块）、C-4（线索树联动）耦合；是剧情收集驱动（B01 4.2）的门槛底座。
6. **下一步决策**：触发条件填充时定「线索解锁条件的一等公民化表达」。

### C-2 条件模块清单与组合规则（时间/地点/前置事件/资源门槛/线索解锁）

1. **原文说了什么**：§8.3 规定「不同事件的前置条件各不相同，严格程度也不同，例如时间条件、地点条件、前置事件条件、资源门槛与线索解锁等。触发条件系统必须模块化、可扩展、可组合」。
2. **为什么是问题**：§8.3 列举了五类条件（"例如"表举例），但条件模块的完整清单与「模块化、可组合」的组合规则（如何拼装、逻辑运算）未定义，导致条件系统无法支撑事件触发。
3. **需要设计的具体内容**：条件模块的完整清单（五类 + 可扩展）；各模块的输入/输出契约；组合规则（与/或/非、顺序、嵌套）。
4. **争议点与取舍**：a) 条件清单是否「穷举」还是「框架 + 可扩展」；b) 组合规则是否统一为布尔逻辑；c) 与 C-1（线索解锁一等公民）的从属关系。
5. **关联与影响**：与 C-1、C-3（触发方式）、C-4（线索树联动）耦合；是触发条件系统的底座。
6. **下一步决策**：触发条件填充时定「条件模块清单与组合规则」。

### C-3 触发方式的扩展接口设计

1. **原文说了什么**：§8.3 规定「玩家一般通过地图行为触发事件，触发方式包括进入区域、特定对话选项等，触发方式同样预留可扩展空间」。
2. **为什么是问题**：触发方式（进入区域、对话选项等）已举例，但「可扩展空间」的接口设计（如何新增一种触发方式）未定义，导致触发方式无法按剧情需求扩展。
3. **需要设计的具体内容**：触发方式的扩展接口（新触发方式的注册/配置方式）；已列触发方式（进入区域、对话选项）的完整规格；触发方式与条件判定（C-2）的衔接。
4. **争议点与取舍**：a) 触发方式是「条件的一种」还是独立模块；b) 扩展接口的抽象层级（预留到什么程度）；c) 与信息传递系统（01-20 对话分支图）的触发方式复用。
5. **关联与影响**：与 C-2（条件模块）、01-20（信息传递/对话选项）耦合；影响事件发现的交互（X-10）。
6. **下一步决策**：触发条件填充时定「触发方式扩展接口」，与 01-20 对话系统联调。

### C-4 条件与线索树的联动接口

1. **原文说了什么**：§8.3 规定事件前置条件包含「线索解锁」；§5.2 规定线索树「局内只能看到历史已解锁的内容」；§5.5 规定线索树推进改变概率池。
2. **为什么是问题**：条件判定需要读取线索树的解锁状态（某线索是否已解锁），但「解锁状态如何进入条件判定」的接口未定义，导致线索解锁条件无法真正生效。
3. **需要设计的具体内容**：条件判定读取线索树解锁状态的接口（查询什么、何时查询）；局内可见性（§5.2）对条件判定的约束（局内新解锁是否即时可用）；与概率池联动（§5.5）的关系。
4. **争议点与取舍**：a) 条件判定读的是「局内历史解锁」还是「局外全量解锁」；b) 线索解锁的判定时机（事件生成时 vs 触发时）；c) 与 C-1（线索解锁一等公民）的分工。
5. **关联与影响**：与 C-1、C-2、07-10（线索树核心）耦合；是剧情门槛（B01 4.2）的接口底座。
6. **下一步决策**：触发条件填充时定「条件与线索树联动接口」，与 07-10 联调。

### C-5 条件的玩家可见性（哪些明示、哪些留给玩家推断）

1. **原文说了什么**：§9.5 规定「条件推断式解谜，玩家通过剧情中已有的视觉与文字引导，推断出做好哪些前置条件准备可能会触发一个曾经没触发过的事件」；§5.4 规定线索树提示「保持模糊」。
2. **为什么是问题**：事件触发条件是「明示给玩家」还是「留给玩家推断」，直接决定条件推断解谜（§9.5）的成立——若全部明示，解谜失效；若全部隐藏，玩家无从推断。可见性的分层未定义。
3. **需要设计的具体内容**：哪些条件明示、哪些模糊、哪些完全隐藏的分层规则；模糊条件的呈现方式（呼应 §5.4 线索树模糊提示）；与情报分级（B01 4.2）的关系。
4. **争议点与取舍**：a) 可见性分层是「按条件类型」还是「按事件」；b) 与 T-2（错过后果可见度）、CS-1（主线标记）的分层是否统一；c) 明示度与解谜深度的平衡。
5. **关联与影响**：与 T-2、CS-1、05-50（情报与解谜）、07-10（线索树）耦合；是条件推断解谜（§9.5）的可见性底座。
6. **下一步决策**：触发条件填充时定「条件可见性分层」，与 T-2/CS-1 的可见度裁定统一。

### C-6 条件判定驱动事件状态迁移的接口规范

1. **原文说了什么**：触发条件 4.1 定义「事件状态迁移由触发条件系统的判定结果驱动：条件满足时未出现转可进入，条件不再满足或窗口期结束时可进入转已错过，玩家确认进入后可进入转进行中」。
2. **为什么是问题**：「条件判定结果」如何映射到「五种事件状态」的接口（条件满足度 → 状态迁移的映射表、判定时机）未完整定义，导致状态迁移（E-10）与条件判定（C-2）之间的接口空悬。
3. **需要设计的具体内容**：条件满足度到五种状态的映射关系；判定的触发时机（条件变化时 vs 轮询）；与 E-10（状态迁移驱动来源）的分工。
4. **争议点与取舍**：a) 状态迁移是否「全部由条件驱动」还是「条件 + 事件结果双驱动」；b) 映射表是「固定」还是「事件自定义」；c) 与「拒绝不改变状态」（事件系统 4.2）的交互。
5. **关联与影响**：与 E-10（状态迁移驱动）、事件系统 4.2（状态）耦合；是事件状态机的接口底座。
6. **下一步决策**：触发条件与事件系统联调，定「条件判定→状态迁移的接口规范」。

### C-7 场景变化包装事件的条件规格

1. **原文说了什么**：触发条件 4.1 定义「场景变化包装事件同样由条件驱动：区域形态随事件结果转变，程序上是一次由时间条件与前置事件条件共同驱动的强制事件进入过程」。
2. **为什么是问题**：包装事件的「无流程事件的时间条件与前置事件条件」如何表达（与普通事件条件的差异）未定，导致包装事件（场景变化）无法按条件触发。
3. **需要设计的具体内容**：包装事件的时间条件（等待期）与前置事件条件的表达；与普通事件条件规格（C-2）的差异；与 X-8（区域形态转变条件）的分工。
4. **争议点与取舍**：a) 包装事件条件是否复用 C-2 条件模块，还是特殊处理；b) 等待期的时间条件与「世界时间推进」（时间机制 4.3）的判定方式；c) 与 X-8 的触发条件是否同一套。
5. **关联与影响**：与 C-2、X-8、事件系统 4.4/4.6 耦合；是场景变化触发机制的落地。
6. **下一步决策**：触发条件填充时定「包装事件条件规格」，与探索系统 X-8 联调。
