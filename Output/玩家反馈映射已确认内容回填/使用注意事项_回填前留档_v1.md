# 玩家反馈映射系统：使用注意事项

| 项目 | 内容 |
| --- | --- |
| 文档定位 | 说明反馈主题数据库的浏览、编辑、备份与维护边界 |
| 适用对象 | 需要维护玩家行为与游戏反馈主题，或录入具体操作—程序反馈映射的策划与程序人员 |
| 工具位置 | `Tool/玩家反馈映射系统/` |
| 数据位置 | `Tool/玩家反馈映射系统/数据/玩家反馈映射.sqlite` |
| 前置条件 | Windows 上可运行 Python 3.11 或兼容版本；浏览器可访问本机地址 |
| 更新日期 | 2026-10-09 |

## 1 工具做什么

本工具把 `Output/玩家动作与游戏反馈映射重做/玩家动作与游戏反馈映射重做_反馈依赖清单_v2.md` 的 43 个反馈主题导入 SQLite。网页可浏览、搜索、新增、修改、删除主题，也可在任一主题下维护任意数量的具体映射。

数据库初始状态为 **43 个反馈主题、0 条具体映射**。初始主题的“代码归属”依据 `架构设计文档/架构设计案.md` §2.2、§2.3 的 M01～M10 模块分工填写；跨模块主题列出多个模块，表示待核对的参与范围，使用者可以直接修改。数据库没有“原 v1 坐标”字段，也没有从 v1 导入具体映射。

## 2 目录结构与数据模型

```
Tool/玩家反馈映射系统/
├── database.py              SQLite 表结构与增删改查
├── init_db.py               从 v2 清单建立初始库
├── server.py                本机 HTTP 服务与编辑接口
├── index.html               浏览与编辑页面
├── app.css / app.js         页面样式与交互
├── 使用注意事项.md           本文件
└── 数据/
    └── 玩家反馈映射.sqlite  工作数据库
```

| 表 | 用途 | 关键字段 |
| --- | --- | --- |
| `topics` | 反馈主题主表 | `topic_id`、`player_behavior`、`feedback_topic`、`code_owner`、`source_ref`、`sort_order` |
| `mappings` | 具体映射子表 | `mapping_id`、`topic_id`、`player_action`、`program_feedback`、`context`、`condition_text`、`notes`、`sort_order` |

每个 `FB-xx` 在页面上有自己的“具体映射子表”。数据库使用一张共享的 `mappings` 表，以 `topic_id` 外键关联主题，因此新增主题不需要建新物理表。一个主题能有任意数量的映射，映射编号由数据库自动生成。删除主题会连同其映射一并删除；删除前页面会显示受影响数量并要求确认。

## 3 启动与关闭

在工作区根目录运行：

```powershell
python Tool/玩家反馈映射系统/server.py
```

程序只监听 `127.0.0.1:8788`，默认打开浏览器。若不自动打开：

```powershell
python Tool/玩家反馈映射系统/server.py --no-browser
```

若 8788 被占用，可指定其他本机端口，例如 `--port 8790`。终端会打印实际数据库路径与访问地址。完成编辑后在启动服务的终端按 `Ctrl+C` 停止。

初始库已随本工具创建。只有在数据库丢失且需要从 v2 清单**重新建立空映射库**时才运行：

```powershell
python Tool/玩家反馈映射系统/init_db.py
```

建库脚本遇到既有数据库会拒绝覆盖；它不是更新已有库的命令。已有库中的新增主题与具体映射不会通过重跑脚本恢复。

## 4 浏览与编辑

1. 左侧搜索编号、行为、反馈主题、代码归属、依据或具体映射文字；点选主题后，右侧显示主表字段和该主题的具体映射。
2. 修改主表字段后点“保存主题”。编号是稳定引用，创建后页面不提供改号；需要改变编号时，先创建新主题并迁入映射，再删除旧主题。
3. 点“新建反馈主题”新增主表记录。编号由使用者填写，须以大写字母开头，只用大写字母、数字和连字符，例如 `FB-44`。代码归属可以暂时留空。
4. 点“添加映射”填写具体玩家操作与程序反馈；阶段与上下文、触发条件、备注和排序可按需填写。列表内可编辑或删除单条映射。
5. 点“导出 JSON”可下载全部主题与映射，便于审阅或交换数据。此导出不改变数据库。

主表的“行为范围”与“反馈主题”保持上层粒度；具体按键、鼠标动作、触发条件、程序反馈结果写进子表。子表至少填写“具体玩家操作”和“程序反馈”两项。数据库可保存待讨论的内容，但数据库记录本身不等于正式设计裁定；定案仍按 `Rules/` 回填相应权威文档。

## 5 修改与备份注意事项

| 情形 | 处理方式 |
| --- | --- |
| 日常保存 | 页面每次保存立即写入 SQLite；离开页面前确认出现保存提示 |
| 批量编辑前 | 停止服务，复制 `数据/玩家反馈映射.sqlite` 到本任务允许的备份目录，再启动服务 |
| 只读审阅 | 使用页面浏览与搜索，或用 SQLite 客户端只读打开数据库；可另行导出 JSON |
| 删除主题 | 确认弹窗会显示随主题删除的映射数；需保留内容时先导出 JSON 或备份数据库 |
| 数据库文件移动 | 启动时通过 `--db <工作区内的数据库路径>` 指定；服务拒绝工作区外路径 |
| 并行编辑 | SQLite 会串行处理写入，但网页不会自动合并两人同时修改同一条记录；协作时避免同时编辑同一项 |

JSON 导出用于读取与留档，**不是自动恢复入口**。需要完整恢复时停止服务，用此前复制的 SQLite 文件恢复，并核对主题数与映射数。直接用外部 SQLite 客户端写库可能绕开页面校验，应先备份并检查 `PRAGMA integrity_check`、`PRAGMA foreign_key_check`。

## 6 本机服务与输入边界

本服务只绑定回环地址，不连接外部网站，不上传数据库。编辑请求需要本次服务启动时生成的令牌；终端关闭后令牌失效。静态页面只从本服务加载。服务启动期间，拥有本机浏览器访问权限的人可以查看库并通过页面编辑，使用完毕应停止服务。

具体映射的 `player_action` 与 `program_feedback` 是自由文本，不自动检查是否符合现行系统设计、代码设计案或真实程序行为。代码归属为可编辑文本，也不会自动随着架构文档变化；修订架构模块分工后需逐项复核。
