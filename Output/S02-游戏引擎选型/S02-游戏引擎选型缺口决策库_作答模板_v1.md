## ENG-GAP-001 架构改写的采用范围与强度：本次把 Unity 采用到什么程度、十章中哪些章节整体重写

- 等级：B0；责任方：游戏总监；优先轮次：第一轮 骨架，ENG-Q-001

- **候选 A：全面采用**（推荐）
  - 方案：以 Unity 的机制为骨架重排架构：现行架构中「项目自行实现」的能力逐项重判，Unity 已覆盖的改为直接采用；分层保留，但每层重新说明 Unity 侧的承载方式；第 4、6、7 章整体重写。
  - 代价：重写面最大，下游 42 份文档的架构引用需大面积复核；但这是判据「Unity 已提供且满足需求的能力直接采用」唯一能落实的形态。
- **候选 B：分层保留加表现层采用**
  - 方案：保留现行五层与十个模块不变，只把表现层与基础设施层改为 Unity 机制，领域层与数据层维持纯 C# 自建。
  - 代价：返工面显著缩小，但把资源、场景、输入、序列化等跨层能力排除在重判之外，与任务书「优先判断 Unity 是否已提供满足需求的机制」不符。
- **候选 C：最小改动**
  - 方案：保留现行架构主体，只在第 7 章每项后补一段「Unity 对应实现」，其余章节不改。
  - 代价：改动最小，但等于承认「先设计通用架构再找 Unity 对应实现」，正是任务书第 105 至 115 行明确禁止的方式。

## ENG-GAP-002 对象模型的分工方式：数据侧、表现侧与装配侧对象分别用什么承载

- 等级：B0；责任方：游戏总监；优先轮次：第一轮 骨架，ENG-Q-001

- **候选 A：数据与逻辑纯 C#，引擎对象只做承载与表现**（推荐）
  - 方案：元对象、组件、事件实例、战斗运行状态、线索树等全部运行期数据由普通 C# 对象持有；MonoBehaviour 只用于启动引导、场景与界面对象、表现驱动与帧循环驱动；ScriptableObject 用于静态定义与编辑器配置资产。
  - 代价：需要一条明确的状态同步路径（数据变化如何通知 Unity 对象刷新），要在第 4 章写清；同时满足「数据可序列化、可整体重置、可脱离场景存在、可在无界面环境下测试」四项现行要求。
- **候选 B：静态定义与运行期实例都用 ScriptableObject**
  - 方案：静态定义用 ScriptableObject 资产；运行期实例也以 ScriptableObject 承载，便于在编辑器内检视与序列化。
  - 代价：运行期可变状态放在资产上，会使「随单局创建与销毁」「按域整体重置」两件事变难，且编辑器内检视会诱导把逻辑写进资产。
- **候选 C：不强制定分工**
  - 方案：由各系统按方便选择承载方式，架构层只给原则，不给可机械判定的分工规则。
  - 代价：无法回答任务书第 88 至 104 行要求逐项明确的必答问题，下游 42 份文档的 §2 与 §5 将失去统一判据。

## ENG-GAP-003 常驻对象的持有与创建方式：服务容器、启动物体与引擎场景各自承担什么

- 等级：B0；责任方：游戏总监；优先轮次：第一轮 骨架，ENG-Q-001

- **候选 A：保留纯 C# 服务容器，宿主为入口场景的启动物体**（推荐）
  - 方案：沿用现行的能力登记、依赖图校验、按拓扑创建与逆序销毁；启动物体是 MonoBehaviour，只负责在入口场景驱动容器完成登记与创建并持有容器引用；注册代码由各模块提供。
  - 代价：Unity 不提供依赖注入，容器属项目自建，需在架构案写明自建理由；换来「依赖成环在启动时即报错」与「禁止静态单例就地取用」两条现行约束的保留，下游 31 份依赖行只换承载说法。
- **候选 B：装配声明改为资产，容器不再自建**
  - 方案：常驻对象的装配与依赖关系在编辑器内的资产上声明与校验；运行期由启动物体按声明顺序显式初始化各单元，不设统一容器。
  - 代价：更贴合 Unity 的编辑器工作方式，但会改变下游对 API-M01-001/002 的引用方式，且依赖图的校验时机从运行期启动移到编辑器。
- **候选 C：启动物体直接持有各单元引用**
  - 方案：不设统一容器，初始化顺序写在启动物体的显式调用序列里；跨单元取用经一个只读的单元索引。
  - 代价：实现最省，代价是失去依赖图校验，模块间取用变成隐式约定，现行 8.3 第 1 条与 7.11 的「不允许绕过」失去拦截面。

## ENG-GAP-004 静态数据的载体与生成管线：设计库 13 张扩展配置表与引擎静态数据载体如何对应

- 等级：B0；责任方：游戏总监；优先轮次：第一轮 骨架，ENG-Q-001

- **候选 A：设计库表为权威源、编辑器导入生成资产、运行期只读资产**（推荐）
  - 方案：系统设计文档/ 下的 CSV 扩展配置表继续作为权威来源与评审对象；编辑器侧由导入流程生成 ScriptableObject 资产；运行期只读资产；标识唯一性与表间引用完整性在导入时校验，失败即中止导入。
  - 代价：需要一条导入管线与「表改动到资产重建」的流程约定（属项目自建部分）；同时取得 Unity 的可视化检视与引用能力，并保住 5.1 的「单一来源」约束。
- **候选 B：资产为唯一权威源**
  - 方案：配置内容的维护改在 Unity 编辑器内直接进行，设计库表只作为初始素材，不再作为权威来源。
  - 代价：内容维护更贴近引擎工具链，但设计库表与运行资产出现两个来源，与现行 5.1 第 1 条「单一来源」冲突，也使内容侧评审失去落点。
- **候选 C：运行期直接解析设计库表**
  - 方案：不设资产层，启动时解析 CSV 并构建内存形态。
  - 代价：省掉资产与导入管线，但没有类型检查与编辑器内引用，且离开设计库文本就无法运行与调试。

## ENG-GAP-005 运行期数据的承载与持久化机制：数据域用什么承载、存档用什么序列化、落在哪里

- 等级：B0；责任方：游戏总监；优先轮次：第一轮 骨架，ENG-Q-001

- **候选 A：普通 C# 对象承载 + 通用 JSON 序列化 + 引擎持久化目录落点**（推荐）
  - 方案：数据域条目为可序列化的普通 C# 对象；单局存档、跨局存档、设置数据三份结构各为一个落点并独立提交；配置版本标识写入单局存档；迁移由声明了该切面的域负责。
  - 代价：引入第三方序列化依赖，且需在代码设计案层补「哪些字段入档」的显式声明；换来对嵌套集合、按标识引用与多态的完整支持，与现行 5.2/5.3 的结构最贴合。
- **候选 B：Unity 内置序列化**
  - 方案：数据同样用普通 C# 对象承载，存档序列化改用引擎内置序列化机制，存档结构与可序列化字段直接对应。
  - 代价：无外部依赖，但引擎内置序列化对嵌套集合、按标识引用与多态覆盖有限，很可能需要额外的形态转换层，反而增加一层。
- **候选 C：数据用 ScriptableObject 承载并直接写盘**
  - 方案：三个数据域的内容以资产形态存在，直接用引擎的资产序列化写盘。

## ENG-GAP-006 事件通道的实现方式：跨模块状态广播在引擎侧由什么承载、事件登记表放在哪里

- 等级：B0；责任方：游戏总监；优先轮次：第一轮 骨架，ENG-Q-001

- **候选 A：项目自有事件通道，登记表以资产形态存在**（推荐）
  - 方案：沿用现行登记表与订阅表语义：事件名取自架构案 3.1 词表，载荷字段类别与失败语义在登记项内声明；发布与订阅经统一入口，未登记事件拒绝发布；登记表本身以可检视的资产承载，便于在编辑器内查看全部事件。
  - 代价：仍是项目自建的一层（引擎不提供跨系统事件总线），需写明自建理由与不得绕过；保住下游 38 份文档的「事件名来自词表」「未登记事件不得发布」两条依据。
- **候选 B：每个事件一个资产的事件通道**
  - 方案：采用常见的「事件资产」形态：每个跨模块事件是一份资产，发布方引用并触发，订阅方在编辑器内挂接。
  - 代价：编辑器内连线直观，但失去「一张表回答系统间有哪些事件」的能力，事件名不再是可机械核对的字符串清单，8.4 第 2 条难以核对。
- **候选 C：直接用语言层事件与静态事件**
  - 方案：不设登记表与统一入口，发布方直接触发语言层事件，订阅方直接订阅。
  - 代价：实现最直接，但无法满足 8.4 第 2 条「未登记事件不得发布」，也使事件词表失去权威落点。

## ENG-GAP-007 资源加载与释放的体系：常驻集与场景集如何在引擎资源机制上落地

- 等级：B0；责任方：游戏总监；优先轮次：第一轮 骨架，ENG-Q-001

- **候选 A：分层资源体系**（推荐）
  - 方案：常驻集由启动阶段直接引用并在入口场景预载；事件场景、战斗地图等按需内容经可寻址资源体系加载与释放；发起方仍是界面侧，执行方是引擎的资源机制。
  - 代价：需要维护两套加载路径，要在架构案写明「哪些内容走哪条路径」的判据；与现行 6.2 的常驻集/场景集区分及释放口径一一对应。
- **候选 B：全部资产纳入可寻址资源体系统一管理**
  - 方案：含常驻集在内的全部资产都经可寻址资源体系加载与释放，加载路径只有一条。
  - 代价：统一性最好，但把常驻内容也纳入寻址体系会增加启动期复杂度，收益主要在内容规模大且需要热更时。
- **候选 C：不引入可寻址资源体系**
  - 方案：常驻内容由入口场景直接引用，事件与战斗内容用场景直接引用加运行期实例化。
  - 代价：实现最省，但事件场景与战斗地图只能随构建整包发布，无法满足 6.2「按需加载、随界面退出释放」。

## ENG-GAP-008 界面体系的实现方案：十四个界面的清单、层级与界面栈由什么承载

- 等级：B0；责任方：游戏总监；优先轮次：第一轮 骨架，ENG-Q-001

- **候选 A：统一采用 UI Toolkit**
  - 方案：界面栈为纯 C# 对象；每个界面由一份界面文档资产承载，样式、层级与布局由 UI Toolkit 管理；无 3D 叠层的界面全部用它实现。
  - 代价：是引擎的演进方向，样式复用与数据绑定更好；但在场景内对象叠层、复杂动画与第三方控件生态上仍有取舍。
- **候选 B：采用 uGUI 与 Canvas 预制体**（推荐）
  - 方案：界面栈为纯 C# 对象；界面实体是预制体，层级由 Canvas 排序控制。
  - 代价：本项目的界面以固定版式的面板、列表、信息框与窗口为主，uGUI 在这类形态上生态与案例最成熟，与场景内对象（地图点位、战场单位）的叠层交互最直接；代价是样式与布局复用的维护成本高于 A。
- **候选 C：混合两套界面技术**
  - 方案：固定版式的表格式与列表式界面用 UI Toolkit，需要 3D 表现或场景内叠层的界面用 uGUI。
  - 代价：兼顾两类优势，但全局多一套界面技术栈，样式、输入处理与界面栈的实现都要分两路。

## ENG-GAP-009 场景与界面承载的对应关系：引擎的场景、预制体与运行期组合分别承担哪些范围

- 等级：B0；责任方：游戏总监；优先轮次：第一轮 骨架，ENG-Q-001

- **候选 A：一常驻场景加事件与战斗按需场景**（推荐）
  - 方案：一个常驻场景承载局外与地图阶段；事件场景与战斗地图各自独立成场景按需加载；其余可复用对象用预制体。
  - 代价：需要维护场景清单与事件类型的对应关系，跨场景共享内容需单独安排；最直接地对应设计库「按事件配置启动不同场景」与现行 6.2 的「一次性切换」。
- **候选 B：单一场景加预制体运行期组合**
  - 方案：全场只有一个常驻场景，事件与战斗内容以预制体按需实例化。

  - 方案：局外、地图、事件、战斗各一个场景，阶段切换即场景切换。

## ENG-GAP-010 程序集划分与可测试性口径：纯逻辑与引擎相关代码如何隔离

- **候选 B：直接用引擎自带日志通道**
  - 方案：不做分级与落点管理。
  - 代价：最省，但「内容日志」这一级无处落点，而该级需要长期留存并分发给内容侧，用于记录配置与内容问题。
- **候选 C：引入第三方日志方案，架构成只规定统一入口与三级分级**
  - 方案：实现由技术环节选择。
