## ENG-GAP-018 退出与终止通道：程序退出受理与三类终止情形的落点

| 字段 | 内容 |
| --- | --- |
| 等级 | B1 |
| 责任方 | 游戏总监 |
| 裁定方式 | 自定义方案 |
| 预期方案 | 一、退出侧：不设退出受理能力。

    「退出游戏」即进程终止，与 Alt+F4、任务管理器结束进程、平台强制关闭同义，一律不做任何收尾承诺。
    不新增 M01 的「程序退出受理」能力，不为阶段状态机新增终止态；6.1 的阶段取值仍为六种（地图、事件执行、战斗、收尾窗口、结算、局外）。
    9.4 的「正常退出」序列取消；6.4 的「异常终止不执行销毁序列，以最近一次自动保存的提交结果为准」成为唯一口径。不依赖任何退出回调做存档。
    单局存档的唯一可靠写路径是自动保存的两类节点（时间段推进、战斗轮次推进）；退出时不提交存档，退出也不构成任何提交点。
    验收标准：任意时刻终止进程后重新启动，必须能正常启动并继续游玩；不能保证这一点即为设计失败。由此要求的实现约束有两条：① 单局存档写入必须原子（写临时文件后原子替换）；② 提交过程中断时按 7.1 的失败语义整次作废并保留上一份有效存档。
    读档口径相应确定：自上一个自动保存节点以来的进度不恢复，未确认的操作不恢复（与 9.3 现行约束一致）。此为有意为之的设计决策，不是缺陷；该口径随本项一并写入 9.4 与 5.3。

二、终止侧：三类终止情形一律沿局内循环执行。

    一局游戏结束的唯一入口是「事件结束、提交事件结果」这一环节（即事件结算环节）。任何结局都在该环节成立，不另设入口。
    战斗内只做判定，不成立结局。全队失去行动能力由 M05 判定并写入战斗结果，由 M10 的事件执行器在事件收尾时承接；事件按常规流程打完收尾窗口后进入事件结算环节，结局在该环节成立。现行 9.5.5 的步骤 1 至 4 保留，仅把措辞由「战斗内即时成立」改为「战斗内即时判定」。
    主线中断的两类判定（错失必要主线事件、战斗失败导致主线中断）同样只产生判定结果，结局在事件结算环节成立；删除「本局终止时成立」这一入口。
    6.6 的收敛：结算阶段的进入条件「结局成立」明确为「事件结算环节的事件结果提交」；战斗阶段的「退出到」一栏删除「结算阶段」，战斗只退回收尾窗口阶段或事件执行阶段。
    阶段状态机的两条硬规则不变（阶段切换由当前阶段的拥有方发起、由阶段状态机执行；结算阶段封闭）。
    三类终止情形在结局类型与大关进度两项上的写入内容相同，差异仍只落在达成记录的触发起因字段（T-013）与结算界面文案；同时成立时以即时成立的那一刻为准（现行 07-40 §3.7 口径保留）。

三、不采用：候选 A（M01 增补退出受理）与候选 B（阶段状态机增补终止语义）均不采用。候选 C 的口径采用，但补入第一条第 5 点的验收标准。 |
| 补充要求 | 本项与 REQ-SAVE-05 一并关闭（退出收尾提交与两类自动保存节点的关系按本答复确定为"退出不提交"）。 |
