# 1. 文档定义

## 1.1 文档目的

本文件规定游戏程序作为一个整体如何成立：程序由哪些层与模块组成、各部分负责什么、部分之间允许与禁止怎样依赖、系统之间怎样通信、数据怎样分类与流动、对象与系统的生命周期顺序、有哪些统一的基础设施，以及整个项目必须遵守的全局技术规则。

它回答的问题是"整个程序应该怎样组织"，不回答"玩家应该经历什么"（那是 `系统设计文档/` 系统设计稿的内容），也不回答"某个系统为了实现要求需要哪些程序实体与接口"（那是 `Code_Design/` 代码设计案的内容）。

## 1.2 适用范围

本架构覆盖下列内容。

| 范围 | 内容 |
| --- | --- |
| 程序大循环 | 启动 → 主界面与局外界面 → 开新局或读档 → 局内循环（地图阶段与事件阶段往复）→ 结局成立 → 局末结算与跨局写入 → 回到局外界面 |
| 玩法系统 | `系统设计文档/` 的 6 个系统域共 31 个系统，清单见第 2.3 节的模块划分表 |
| 基础设施 | 服务容器、存档、配置、随机、时间、输入、资源、场景、日志、事件分发共 10 项，另加 7.8 表现通道，见第 7 章 |
| 数据 | 静态配置、运行时数据、持久化数据三类，见第 5 章 |

未覆盖的内容与承接方如下。

| 未覆盖部分 | 承接方 |
| --- | --- |
| 界面内部的布局、字段排版、视觉样式与操作细节 | `系统设计文档/` 各系统设计文档的界面章节（设计决策记录决策 4：界面与操作规格归各系统设计文档承接） |
| 数值取值、难度调制、公式与数值落点 | 后续数值设计阶段（设计决策记录决策 49） |
| 单个系统对外提供的全部接口及其逐项契约 | `Code_Design/` 各系统的代码设计案 |
| 接口内部的执行步骤与算法 | 伪代码层（该层尚未建立） |
| 具体引擎 API、第三方插件选型与部署方式 | 实际代码与技术实现 |
| 剧情与叙事编排、引导提示与事件内容的具体编排 | 关卡与内容策划 |
| 覆盖范围之外的两个库级系统 | `00-总览` 的四份库级台账属文档治理，不是程序系统；本架构只在引用处按编号引用 |
| 05-40 仓库与银行的实现 | 远期占位，当前版本不实现；本架构只在 2.3 的映射表中为其保留归属 |
| 事件结果配置的字段级结构 | 设计决策记录决策 76 悬置，到期日为事件结果落点进入实现设计环节时；本架构只固定结果标识这一层接口 |

## 1.3 与其他设计文档的关系

六层文档的信息流如下。

```
创意需求            Design/ 系统设计稿        本架构设计案          Code_Design/ 代码设计案     伪代码        实际代码
为什么做      →     玩家规则是什么      →     程序整体怎么组织  →   某系统需要什么      →      怎么执行  →   可运行实现
```

| 文档层 | 与本架构的关系 |
| --- | --- |
| `系统设计文档/` 系统设计稿 | 本架构的上游依据。本架构引用其中的系统名与系统编号，不重新定义游戏规则 |
| 本架构设计案 | 规定整个程序允许怎样组织 |
| `Code_Design/` 代码设计案 | 本架构的下游约束对象。代码设计案必须服从本架构的第 3 章与第 8 章；第 2 章的模块划分决定代码设计案的归属与依赖范围 |
| 伪代码与实际代码 | 经代码设计案间接约束 |

架构设计案与代码设计案是两个并列维度，不是同一维度的上下层：架构管"系统之间怎样组成一台机器"，代码设计案管"这台机器中的某个部件具体需要具备什么"。冲突处置按《架构设计案编辑规范》第六章第 3 节执行，不得由下游自行选择更方便执行的一条。

## 1.4 术语的三层归属

本架构使用的词汇分三类，**三类之间不要求同名**。

| 类别 | 定义 | 例 | 谁使用 |
| --- | --- | --- | --- |
| 玩家面向术语 | `系统设计文档/00-总览/02_术语表.md` 登记的标准术语，回答玩家看到与经历什么 | 事件、事件状态、元物品、元效果、背包空间、行动槽 | 策划案、界面文案、面向玩家的说明 |
| 架构术语 | 本文件定义的程序结构用语，回答程序里由什么承担什么 | 事件模板、事件实例、事件变体、元对象、组件、数据域、阶段状态机、意图、表现通道 | 本架构设计案、代码设计案、伪代码与实际代码 |
| 代码术语 | 代码设计案与实际代码中使用的实体名、接口名与字段名 | 由代码设计案定义 | 代码设计案、实际代码 |

三条使用规则：

1. **架构术语可以与玩家面向术语同名，也可以不同名，不要求一一对应。** 例如架构层的「元对象」对应设计库的「元物品」概念并把它扩展到全部局内对象；架构层的「事件实例」在设计库中没有对应术语，但在 `01-50` 的单局状态范围内已隐含存在。
2. **同名不等于同义。** 架构层凡是复用设计库词汇的地方，以第 1.5 节的对应表为准；对应表未登记的同名词，其含义限定在本架构内部，不得反向用于解释游戏规则。
3. **本架构不新增玩家面向术语。** 游戏规则需要新术语时，走 `系统设计文档/00-总览/02_术语表.md` 的登记流程，不由本文件登记。

| 架构术语 | 定义所在 | 设计库对应 | 对应关系 |

| 意图 | 7.4 | 无对应术语 | 架构层对输入的语义化表达 |

# 2. 总体程序架构

## 2.1 整体分层

程序分五层。分层回答的是"某一项能力属于哪一类职责、允许依赖谁"，模块划分（2.2）回答的是"哪些系统属于同一个业务单元"，两者是正交的两个维度。

| 层 | 编号 | 职责 | 不负责 |
| --- | --- | --- | --- |
| 基础设施层 | L1 | 提供与玩法无关的公共能力：服务容器、存档、配置、随机、时间、输入、资源、场景、日志、事件分发，以及 7.8 表现通道 | 任何游戏规则；任何具体玩法状态 |
| 数据层 | L2 | 持有运行期数据（三个数据域）、静态配置的内存形态与持久化数据的读写 | 业务判断；界面呈现；效果的结算规则 |
| 领域层 | L3 | 实现玩法系统的核心规则：事件、时间、日程、探索、战斗、物品、经济、委托、技能、对象与效果、队伍、线索树、概率池、局生成 | 界面呈现；资源加载；输入采集 |
| 游戏逻辑层 | L4 | 编排跨系统的流程与阶段：局内阶段状态机、事件执行与结算、战斗执行、局末结算、局外流程 | 单条规则的实现（由领域层提供）；界面绘制 |
| 表现层 | L5 | 界面栈与场景的生命周期、状态呈现、意图到操作命令的转换 | 直接修改任何游戏数据；业务判断 |

层间允许关系：

```
L5 表现层
      ↓ 只读取状态、只提交意图
L4 游戏逻辑层
      ↓
L3 领域层
      ↓
L2 数据层
      ↓
L1 基础设施层
```

规则是单向向下依赖：上层可以使用下层提供的能力，下层不得引用上层，同层之间按第 3.3 节的允许清单判断。**跨层依赖与反向依赖一律禁止，例外必须登记在第 8.1 节。**

## 2.2 模块划分

模块按玩法主题归并，是代码设计案的归属单位与依赖范围的划定单位。模块不改变系统在 `系统设计文档/` 中的编号与归属域：设计库的域按玩法主题归并，架构的模块按程序结构归并，两者是不同维度的划分，对应关系见 2.3 的映射表。

| 模块 | 编号 | 所在层 | 承担职责 | 包含的系统 |
| --- | --- | --- | --- | --- |

事件界面的管理规则（ARC-GAP-036）：事件配置先确认该事件属于哪个类别（交易事件、战斗事件、对话类等），静态引用其事件数据，再由 M08 的事件界面加载器按类别装配对应界面；新增事件类别时在加载器登记类别，见 8.5.3。

事件属性配置的五个字段类（ARC-GAP-036）：**刷新规则组**（入池条件、权重、上限、一次性与延时）、**呈现配置**（出现方式、点位约束、图标与显示）、**时间配置**（窗口期、持续时间与取整规则）、**界面配置**（界面开放状态、面板展示项）、**锁定配置**（撤退后的窗口期延长与周边事件锁定范围）。字段类之内允许按事件类型扩展字段，新增字段必须先登记字段类。

| 局生成与种子（09-20） | M02 | 管"这一局的世界怎么长出来"：种子加解锁与剪枝状态，生成事件池快照、窗口期与顺序、区域解锁与行情 |

### 2.5.2 架构新增的 11 个单元

这 11 个单元在 `系统设计文档/` 中没有对应系统，是本架构为实现全局规则而设的承载点。它们不是新的游戏系统，不承载新玩法。

| 单元 | 所属模块 | 一句话简介 |
| --- | --- | --- |
| 核心与基础设施（M01） | M01 | 常驻的系统与服务的大本营：服务容器、存档、配置、随机、时间、输入、资源、场景、日志与事件分发都在这里，另外持有三个数据域 |
| 事件与生成（M02） | M02 | 管事件的"配置到运行"：事件模板与变体是静态配置、实例是运行时个体，事件池分两层，生成与刷新由事件调度负责 |
| 探索与推进（M03） | M03 | 管地图层的规则：区域与形态、事件点位、基点与活动范围、跨区域位移事件 |
| 对象与经济（M04） | M04 | 管局内对象：元对象与组件内核、物品与容器、装备与遗物、金钱与交易、委托与背包 |
| 战斗（M05） | M05 | 管一场战斗从启动到收束：时间轴、行动槽、战场、技能、库存联动、敌人与结果 |
| 元进度与结算（M06） | M06 | 管跨局的东西：线索树、剪枝、概率池的内容集合，以及局末结算 |
| 队伍与角色（M07） | M07 | 管队伍编制的来源与重置，以及主角标识；队伍编制每局重置，对成员的构筑也是构筑的一部分 |
| 界面与信息（M08） | M08 | 管界面这一层：界面清单与栈、打开与关闭、场景切换、文案与提示投放；界面只读状态、只提交意图 |
| 全局能力（M09） | M09 | 三处必须统一入口的横切能力：元效果服务、条件求值服务、物品与经济写入服务 |
| 流程编排（M10） | M10 | 管"什么时候轮到谁"：阶段状态机，以及事件执行、战斗执行、结算执行三个执行器 |
| 服务容器 | M01 | 全部常驻对象的唯一持有者：按依赖声明排序创建、注入引用、逆序销毁，成环在启动时即报错 |

### 2.5.3 命名约定

| 约定 | 说明 |
| --- | --- |
| 系统命名 | 一律沿用 `系统设计文档/` 的定义与编号，架构不改名、不改编号、不改变系统在设计库中的归属域 |
| 架构术语与设计库术语 | 可以不同名，不要求一一对应；对应关系见 1.5。例如「元对象」是把设计库的「元物品」升格后的架构用语，「事件模板」对应设计库的「事件」 |
| 模块命名 | 按玩法主题归并，与设计库的系统域是两个维度；一个模块可以容纳多个系统，一个系统只归属一个主模块 |
| 新增单元的命名 | 采用"职能 + 责任"的写法（如"流程编排"），不使用隐喻或代号 |

# 3. 模块与系统边界

## 3.1 各模块职责

各模块按固定字段写成一个单元。字段中「不负责」与「负责」同等重要。

### ARC-M01-001 核心与基础设施

职责：
提供与玩法无关的公共能力，并持有三个运行期数据域。

负责：
- 服务容器的创建、依赖注入与销毁排序
- 存档的分域、切面采集、提交与恢复驱动
- 静态配置的加载、校验与版本绑定
- 随机源与确定性序列
- 世界时间的受理与广播
- 输入采集与意图分发
- 资源与场景的加载释放、常驻集维护
- 分级日志
- 跨系统事件的登记与分发
- 三个数据域的持有

不负责：
- 任何游戏规则的判断
- 战斗、事件、经济等玩法状态的业务含义
- 界面绘制与文案

依赖：
无（本模块是最底层）

对外接口：
服务注册与解析、存档提交与恢复、配置查询、随机序列申请、时间推进受理与订阅、意图订阅、资源请求、日志写入、事件收发

事件：
时间刻度变化、自动保存完成、存档提交完成、存档恢复完成、配置加载完成

生命周期：
服务容器在启动阶段创建，全部常驻对象随进程存活；三个数据域随单局创建与销毁。

### ARC-M02-001 事件与生成

职责：
承载事件从配置到运行、从生成到退出的完整链路，并负责时间刻度与日程记录、本局环境的生成输入。

负责：
- 事件模板、事件变体与事件实例三层结构的数据持有与状态迁移
- 事件池的两层语义：全局事件池的内容集合与当前事件池的刷新集合
- 事件调度：过期剔除、入池判定、配额核算、按权重抽取、变体抽取、点位查重与重试
- 事件的状态迁移规则：进入、推进、达成结束条件、退出与结算条件
- 事件配置的五个字段类与事件类型契约的读取
- 触发条件的模块组合与求值调用
- 世界时间刻度、窗口期与持续时间的时间口径
- 日程记录与事件的界面配置声明
- 种子到本局四项产物的生成流程

不负责：
- 战斗内部的推进（归 M05）
- 事件内执行流程的编排（归 M10）
- 事件内的经济动作（归 M04）
- 事件的界面绘制（归 M08）
- 池成分的内容集合计算（归 M06）

依赖：
M01、M06、M09

对外接口：
事件实例的创建与结束、事件状态查询、事件池刷新、生成流程调用、时间推进请求、日程记录查询

事件：
本局生成完成、事件进入当前事件池、事件刷新到点位、事件进入进行中、事件结算完成、当前事件池刷新完成

生命周期：
常驻。事件实例随事件生命周期创建与销毁。

### ARC-M03-001 探索与推进

职责：
承载地图层的空间规则与事件的呈现取数。

负责：
- 区域的划分、区域形态的推算与区域封锁规则
- 事件点位的布局与绑定
- 基点与活动范围
- 事件在地图上的呈现列表取数
- 跨区域位移事件（转移事件与载具租赁事件）的空间语义
- 地图界面所需的点位与区域数据

不负责：
- 事件的生成与状态（归 M02）
- 地图界面的绘制（归 M08）
- 战斗内的空间判定（归 M05）

依赖：
M01、M02、M06

对外接口：
区域与点位查询、区域形态查询、呈现列表查询、位移事件参数

事件：
区域形态转变、周边事件锁定、呈现列表更新、基点变化

生命周期：
常驻。区域与点位为静态配置，形态与呈现列表为单局状态。

### ARC-M04-001 对象与经济

职责：
承载局内对象模型与全部物品、货币、交易的业务操作。

负责：
- 元对象定义与运行时实例
- 组件注册、挂载、生效与查询
- 物品与容器、装备与遗物、法术书与符文书页的对象侧规则
- 自动装载、溢出与落地物
- 金钱与货物的价值、估价与交易
- 委托的接取、执行与结算
- 背包空间与容器界面操作的业务侧
- 敌方与场地道具的对象定义

不负责：
- 物品状态的最终落库（归 M09 的写入服务）
- 战斗内的行为结算（归 M05）
- 界面绘制（归 M08）

依赖：
M01、M09

对外接口：
对象实例查询、组件能力查询、物品操作、交易提交、委托状态、装载与溢出

事件：
对象实例创建与销毁、物品归属变化、容器内容变化、交易提交完成、委托状态变化

生命周期：
常驻。对象实例、容器与委托为单局状态。

### ARC-M05-001 战斗

职责：
承载一场战斗从启动到收束的全部规则与推进。

负责：
- 战斗的启动、战场加载与初始站位
- 时间轴推进、行动机会与后摇

- 技能定义的使用侧、继承效果求值
- 战斗内库存调取、投掷与法术释放
- 战斗行为的契约与提交
- 敌方行为模板、读招与破招
- 战斗目标判定、战斗结果标识与达成目标清单
- 收尾窗口
- 战斗内时长累计（以秒为单位）

不负责：
- 战斗事件的退出与结算：规则归 M02，执行编排归 M10
- 战斗前后的事件流程（编排归 M10，规则归 M02）
- 战斗界面的绘制（归 M08）
- 结局判定（归 M06）

M01、M04、M09

战斗启动、轮次推进、行为提交、战斗结果查询、战斗状态切面

战斗开始、轮次推进、行为提交完成、单位状态变化、战斗结束、撤退发生

### ARC-M06-001 元进度与结算

职责：
承载跨局数据的记录、封锁、池成分计算与局末写入。

负责：
- 线索树的节点、关系、传闻与节点状态
- 剪枝的封锁集合与封锁标记
- 概率池的内容集合计算与权重输入
- 结算组件的内容定义：每个组件负责哪类跨局数据、取数来源与写入内容
- 结局判定与触发起因
- 大关进度

不负责：
- 局内的界面呈现（归 M08）
- 线索树百科页的绘制（归 M08）
- 局内数据的产生（归各玩法模块）

依赖：
M01

对外接口：
节点与传闻查询、封锁状态查询、池内容集合查询、结算组件清单、大关进度查询

节点解锁、传闻解锁、封锁状态变化、结算完成、结局成立

常驻。跨局数据随存档持久化，局内以只读快照呈现。

- 属性的权威定义（归 M05 的战斗总览侧清单）
- 参战编成规则（归 M05）
- 地图与战斗界面的呈现（归 M08）

依赖：
M01、M04

对外接口：
队伍成员查询、主角查询、成员加入与离队、属性取值

事件：
队伍成员加入、队伍成员离队、主角变化、队伍重置

生命周期：
常驻。队伍编制属单局状态，每局重置。

### ARC-M08-001 界面与信息

职责：
承载全部界面的生命周期、场景切换与信息投放。

M01，以及对其他模块的只读访问与意图提交

界面打开与关闭、界面栈查询、编辑态提交、文案取用

事件：
界面打开、界面关闭、编辑态提交

生命周期：
界面栈常驻，界面实例随打开与关闭创建与销毁。

### ARC-M09-001 全局能力

M01

### ARC-M10-001 流程编排

职责：

- 局外流转：结算提交后的局外阶段流转与开新局入口
- 全局终止通道的受理：全队失去行动能力、主线中断、关底未达标三种情形的收场编排

不负责：
- 事件池的生成与刷新（归 M02）
- 战斗内单条规则的实现（归 M05）
- 跨局数据的写入内容（归 M06）
- 界面呈现（归 M08）

依赖：
M02、M05、M06、M09、M01

对外接口：
阶段查询、阶段切换执行、事件执行入口、战斗执行入口、结算执行入口

事件：
阶段切换、结局成立、结算完成

生命周期：
常驻，无自有数据；阶段取值属世界状态域，随单局创建与销毁。

| 9 | 任何模块向 M01 申请基础设施能力 | 基础设施对所有模块开放 |
| 10 | 任何模块通过 M01 的事件分发器发布与订阅跨系统事件 | 发布方不感知订阅方 |
| 11 | M10 编排 M02、M05、M06 的执行入口 | 流程编排是唯一被允许按阶段调用多个模块执行入口的位置；被编排方不反向调用 M10 的阶段切换之外的能力 |
| 12 | 任何模块查询 M10 的当前阶段 | 阶段判定是所有模块的共同前置，只读查询 |

## 3.4 禁止的依赖

禁止项逐条列出。违反禁止项不会让某个系统立刻出错，但会让整个程序的结构腐化，因此按第 10 章核对。

| # | 禁止的依赖 | 理由 |
| --- | --- | --- |
| 1 | 下层依赖上层：L1 至 L4 引用 L5 的任何类型或界面对象 | 反向依赖会让底层能力无法脱离界面复用，也使界面成为事实上的逻辑层 |
| 2 | 向上依赖与越级调用：任何下层调用其上层的任意层（L3→L5、L2→L4、L1→L3 等） | 绕过中间层会让职责边界失效；向下使用任意下层的公开能力是允许的，例外登记在第 8.1 节 |
| 3 | 界面直接修改任何游戏数据 | 界面是纯表现层（ARC-GAP-017）。界面的全部状态变化必须经命令与服务提交 |
| 4 | 游戏逻辑依赖具体界面实现 | 领域规则必须能在无界面环境下运行与测试 |
| 5 | 领域模块之间互相直接持有对方的数据对象 | 跨域访问只能经持有方的读取与写入能力（ARC-GAP-033） |
| 6 | 任何模块绕过 M01 的存档服务读写存档 | 统一持久化入口是存档一致性的前提 |
| 7 | 任何模块绕过 M09 的物品写入服务改物品状态 | 物品状态变化的唯一入口；绕过会产生无法回滚的部分提交（ARC-GAP-010） |
| 8 | 任何模块绕过 M09 的效果服务自行实现效果叠加 | 效果是唯一表达方式，另立机制会让同名判定与结算顺序不可复现 |
| 9 | 任何模块自行创建随机源 | 确定性序列必须由随机服务统一分流（ARC-GAP-031） |
| 10 | 任何模块直接推进世界时间 | 时间推进只有一个受理入口，且只在事件退出时发生（ARC-GAP-013、ARC-GAP-025） |
| 11 | 基础设施层引用任何具体玩法系统 | 基础设施必须保持与玩法无关 |
| 12 | 循环依赖：两个模块互相直接调用各自的服务 | 循环依赖会让模块无法独立替换；跨模块通知走事件 |
| 13 | 数据层持有业务判断 | 数据层只持有与读写，判定归领域层 |
| 14 | 表现层持有跨局数据或单局数据的权威副本 | 界面持有编辑态允许，持有权威数据会造成双源 |

# 4. 系统通信机制

本章按 S01 裁定 ARC-GAP-024 的口径编写：**架构层只约束禁止的依赖方向（见 3.4），不强制规定通信方式的分类与选择规则。** 各系统与模块在实现层可以按自身特点选择合适的调用方式。

为使各行其是的调用仍能有共同的理解基础，本节列出项目内**可用**的四种通信方式并给出适用场合说明。它们是可选手段，不是强制分类，任何跨模块调用都不要求必须先归入某一类。

## 4.1 直接调用

适用：调用方明确要求被调用方完成一件它职责内的事，且调用方需要立即知道结果。

写法：经服务容器解析接口后同步调用。

约束：
- 被调用方必须是调用方允许依赖的模块（见 3.3）
- 被调用方不得反向调用调用方（见 3.4 第 12 项）
- 一次调用的直接链不跨越两层以上；跨多层的场景通过逐层委托表达，不直接穿透

## 4.2 查询

适用：一方需要读取另一方的状态，但不要求对方做任何事。

写法：向持有方请求只读结果；持有方返回快照、值或只读视图。

约束：
- 查询不得产生状态变化
- 读取方不得缓存跨域结果作为自己的数据（派生缓存只能由来源方维护）
- 高频查询（战斗内每轮次）由持有方提供只读快照，避免每次穿透到对象内部

## 4.3 事件

适用：一次状态变化需要被多个不特定的接收方知晓，或发布方不应感知接收方。

写法：经 M01 的事件分发器发布与订阅。

约束：
- 事件的语义在 M01 登记后才可使用；未登记的跨模块事件不得发布
- 事件只承载"发生了什么"，不承载"要求谁做什么"；要求做事走直接调用
- 订阅方处理失败不得回滚发布方的状态
- 每个事件登记发送方、载荷字段类别与失败语义，逐项契约由代码设计案给出

## 4.4 数据共享

适用：双方约定共读同一份数据，且该数据有明确的所有者。

写法：由所有者持有，其他方按 3.3 与 8.2 的规则读取。

约束：
- 共享数据的写入权只属于所有者
- 只读快照允许跨模块传递，但快照不携带写入口
- 共享数据的分类与所有者见第 5 章

## 4.5 通信选择规则

本节给出可直接判定的选择规则。规则的强制部分在 8.4（六条，违反即按第 10 章核对不通过）；本节回答「默认该用哪一种」，用于在实现时快速定位。

| 情形 | 采用 | 依据 |
| --- | --- | --- |
| 调用方要求对方完成一件属于对方职责的事，且需要立即结果 | 4.1 直接调用 | 明确的命令关系 |
| 只需读取对方状态、不需要对方做任何事 | 4.2 查询 | 同步只读 |
| 需要读取的数据有明确所有者且双方约定共读 | 4.4 数据共享 | 数据所有权见 5.4 |
| 一次状态变化需要被多个不特定接收方知晓，或发布方不应感知接收方 | 4.3 事件 | 状态广播 |
| 跨模块的状态广播 | **必须** 4.3 | 8.4 第 1 条 |
| 界面要求变更游戏状态 | **必须**经意图与命令提交，不得直接调用领域模块改数据 | 8.4 第 5 条 |

判定顺序：先看是否有 8.4 的强制项；没有强制项时，按「要对方做事 → 4.1；只要状态 → 4.2 或 4.4；要多人知道 → 4.3」选取。任一选择都必须同时满足 3.4 的禁止项。

**规范偏离登记。** 《架构设计案编辑规范》第五章第 4 节要求第 4 章给出通信机制的分类与选择规则；S01 裁定 ARC-GAP-024 选择了「只约束禁止项、不规定通信方式分类」的口径。本文件的处置是：把架构层**强制**的部分完整落在 8.4（六条，可直接核对），把第 4 章的四种方式与上表作为**默认指引**保留，两者都不强制要求把每次跨模块调用归入某一类。该偏离在此登记，供后续评审核对。

### 5.2.2 单局状态域

| --- | --- |

**战斗运行状态属于本域**（ARC-GAP-015）：战斗运行状态由 M05 自持，在战斗轮次推进的自动保存节点按 5.3 的切面规则采集入档；读档后由 M05 按记录重建战场与时间轴，恢复到最近一次行动机会开始的时刻，该次行动机会内尚未确认的选择不恢复。战斗内以秒为单位累计的净时长同属本域。

| 项 | 内容 |
| --- | --- |
| 持有者 | M01 的数据域侧；变更入口为 M05、M07 |
| 内容 | 队伍编制与成员、主角标识、角色属性取值、技能配置（四类基础技能各一、五件连携、法术书中的符文书页构成）、装备槽与遗物槽 |
| 生命周期 | 随单局创建并重置；**队伍编制属每局重置的要素，对队伍成员的构筑是玩家构筑的一部分**（ARC-GAP-014） |
| 更新时机 | 玩家数据在事件内实时结算 |
| 派生项 | 继承效果的求值结果、可调取容器范围，按来源状态重建 |

### 5.2.4 技能定义与构筑数据的分离

技能分两层，分属静态数据与玩家状态域（ARC-GAP-005）：

| 层 | 内容 | 归属 |
| --- | --- | --- |
| 技能定义 | 四类基础技能与连携技能的定义、成本串与产出串、后摇参数、继承效果的规则；符文书页承载的法术内容 | 静态数据（5.1 的技能与法术定义行），由 M05 持有；其效果以元效果表达，效果的模型与登记清单由 M09 维护 |
| 玩家技能配置 | 当前携带的四类基础技能各一项、五件连携技能、法术书中符文书页的构成 | 玩家状态域（5.2.3） |

两条约束：

1. **技能定义不随局重置，玩家技能配置随局重置。** 技能通过事件奖励、委托报酬与交易获得，获得动作写入玩家技能配置。
2. **继承效果是派生结果**，在配置变更与进入战斗两个时机求值，只作为派生缓存，不作为数据来源、不入档。

### 5.2.5 两个事件池

事件池在本架构中是两个独立的数据集合，分属两层职责（ARC-GAP-027）。两者都属世界状态域，但计算时机与用途不同。

| 池 | 含义 | 计算时机 | 用途 |
| --- | --- | --- | --- |
| 全局事件池 | 本局游戏中**哪些事件可以出现**的内容集合，即本局允许出现的事件标识清单 | 开新局时按线索树解锁与剪枝状态计算一次并快照入档，局内不再变化 | 为当前事件池提供内容范围的上界 |
| 当前事件池 | **下一次事件刷新时哪些事件可能出现**的刷新集合 | 由 M02 的事件调度在每次刷新时按区域形态与事件属性规则组对全局集合过滤后生成，局内随刷新变化 | 生成抽取的直接输入 |

三条规则：

1. **上界与刷新分离。** 全局集合只回答"能不能出现"，当前集合回答"这次刷新时哪些可能被抽中"；线索树进度作用于全局集合，区域形态与事件属性作用于当前集合，两个过滤条件正交。
2. **形态转变不需要重算全局集合。** 区域形态在局内转变后，下一次刷新即按新形态从全局集合中取子集，全局快照不变。
3. **两个集合都入档。** 全局集合按快照恢复；当前事件池按其快照恢复，读档不重新过滤、不重新抽取。

### 5.2.6 三个域的访问规则

见第 8.2 节的全局技术约束。核心是三条：不直接修改他方数据、跨域变更经过持有方入口、派生结果不作为数据来源。

## 5.3 持久化数据

持久化数据分三份独立结构（ARC-GAP-019）。

| 结构 | 内容 | 提交时机 | 恢复归属 |
| --- | --- | --- | --- |
| 单局存档 | 世界状态域、单局状态域、玩家状态域三个切面，加配置版本标识 | 自动保存的两类节点（时间段推进、战斗轮次推进） | 由 M01 的存档服务驱动，按域顺序恢复 |
| 跨局存档 | 线索树节点状态、传闻解锁状态、事件解锁状态、封锁集合与封锁标记、达成记录与大关进度 | 局末结算的一次提交 | 由 M10 的结算执行器写入，写入内容由 M06 定义，随跨局存档独立提交 |
| 设置数据 | 键位映射、音量分轨、字幕与语言、暂停相关设置 | 设置变更时提交 | 由 M01 的配置与设置侧持有，独立于游戏进度 |

三类持久化数据的边界规则：

1. **局内进行中的交易、委托进度、押金、落地物与未领取奖励不进入跨局数据**，随本局结束废弃；落地物在单局存档内完整保存与恢复（`系统设计文档/01-通用系统/50-存档与持久化/50_存档与持久化设计.md` 第 3、4 节）。
2. **跨局与单局不做同一次提交**：结算写入跨局存档与最近一次自动保存写入单局存档是两个提交点，各自的失败语义独立。
3. **版本号按结构分别维护**，迁移由声明了该切面的域负责。

## 5.4 数据所有权

| 数据类别 | 所有者 | 其他模块的访问方式 |
| --- | --- | --- |
| 静态配置 | M01 配置服务持有内存形态，各定义的所有权归 5.1 表内模块 | 全部模块只读；定义变更走配置更新流程，运行期不改 |
| 世界状态域 | M01（变更入口为 M02、M03 与 M10：M02 写事件池与已刷新事件、M03 写区域形态与呈现、M10 写局内阶段取值） | 只读查询；变更一律经 M02、M03、M10 的入口提交 |
| 单局状态域 | M01（变更入口为 M04 与 M05） | 只读查询；物品写入一律经 M09 的写入服务 |
| 玩家状态域 | M01（变更入口为 M05 与 M07） | 只读查询；变更经 M05 与 M07 的入口提交 |
| 跨局数据 | M06 | 局内只读快照；写入只在局末结算的一次提交内 |
| 存档结构与版本 | M01 | 各域提供自己的切面；存档服务负责结构、顺序与校验 |
| 界面编辑态 | M08 | 仅界面内部可见，提交后转为相应域的数据 |
| 随机序列位置 | M01 | 由随机服务内部维护，其他模块不直接读写 |

## 5.5 数据流向

```
静态配置（启动加载，只读）
        │
        ▼
本局生成（M02）：全局事件池内容集合、窗口期与出现顺序、区域解锁状态、行情
        │
        ▼
世界状态域 ──查询──▶ 领域层各模块 ──写入──▶ 三个数据域
        ▲                                      │
        │                                      ▼
   事件调度刷新 ◀── 事件结束 ◀── 事件执行（M02）◀── 玩家操作（意图 → 命令 → 服务）
        │                                      │
        │                                      ▼
        │                              自动保存（两类节点）──▶ 单局存档
        ▼
结局成立 ──▶ 结算执行器（M10 编排，M06 提供写入内容）──▶ 跨局存档
        │
        ▼
局外界面 ──▶ 开新局 ──▶ 回到"本局生成"
```

跨局数据在局内以只读快照形式参与判定（例如线索解锁条件、呈现列表取数），本局新解锁的内容只在结算写入后进入跨局数据，下一局才生效。

# 6. 生命周期

## 6.1 程序生命周期

程序生命周期分六个阶段，由启动引导器按固定顺序驱动（ARC-GAP-002）。每个阶段声明输入与输出，前一阶段失败即中止启动并给出可读原因，不进入下一阶段。

| 阶段 | 输入 | 动作 | 输出 | 失败处置 |
| --- | --- | --- | --- | --- |
| 1 引导 | 可执行程序 | 创建服务容器；注册全部常驻系统的能力与依赖声明 | 空容器与依赖图 | 依赖成环或声明冲突时中止，报出冲突项 |
| 2 配置装载 | 依赖图 | 加载静态配置、校验标识唯一性与表间引用、确定配置版本标识 | 配置服务可用 | 配置缺失或校验失败时中止，报出具体表与条目 |
| 3 常驻系统创建 | 配置服务 | 按依赖拓扑排创建常驻对象并注入引用 | 常驻对象就绪 | 创建失败时中止，报出模块与阶段 |
| 4 设置与存档索引读取 | 常驻对象 | 读取设置数据与存档索引；设置独立持久化，不随游戏进度 | 主界面可呈现 | 设置损坏时回落默认值；存档索引缺失时只提供开新局 |
| 5 本局装配 | 存档索引或生成输入 | 读档路径：按第 9.3 节恢复；新开局路径：调用本局生成 | 三个数据域就绪 | 读档失败时保留上一份有效存档并提示；生成失败时回到本局装配入口重试 |
| 6 进入可玩状态 | 数据域就绪 | 阶段状态机进入局外阶段，界面栈打开主界面 | 可玩 | — |

## 6.2 场景生命周期

| 阶段 | 动作 | 负责方 |
| --- | --- | --- |
| 场景加载 | 界面栈发起，资源服务与场景管理器执行；加载失败时保留当前界面并提示 | M08 发起，M01 执行 |
| 场景进入 | 场景对象创建，界面按阶段打开，状态订阅建立 | M08 |
| 场景切换 | 一次性切换（地图界面与战斗界面之间）：先加载目标场景，再替换界面栈顶，再释放来源场景的非共享资源 | M08 |
| 场景退出 | 编辑态提交或丢弃，状态订阅解除，场景对象销毁 | M08 |
| 资源释放 | 按界面生命周期释放；常驻集不释放 | M01 资源服务 |

资源策略（ARC-GAP-022）：常驻集在启动阶段加载并全程保留，包含配置、公共资源与主界面所需资源；事件场景、战斗瓦片地图等按需加载，随界面退出释放；战斗与事件场景不并行持有两份场景资源。

## 6.3 系统初始化

初始化顺序由依赖拓扑决定，不由硬编码顺序决定（ARC-GAP-003）。初始化顺序的依据是依赖声明中"我要用谁"，被依赖者先创建。

层内的大致顺序：

1. 基础设施：服务容器 → 日志 → 配置 → 随机 → 时间 → 事件分发 → 资源 → 场景 → 输入 → 存档；
2. 数据层：三个数据域的容器；
3. 领域层：M09 三处全局能力 → M04 对象与经济 → M07 队伍与角色 → M02 事件与生成（含静态配置加载）→ M03 探索与推进 → M05 战斗 → M06 元进度与结算；
4. 游戏逻辑层：M10 阶段状态机 → M02 事件调度器 → M10 事件执行器 → M10 战斗执行器 → M10 结算执行器；
5. 表现层：界面栈与界面栈。

新增系统时按第 8.5 节的接入步骤登记，不在本节改动顺序。

## 6.4 系统销毁

销毁按创建的逆序执行，依据同 6.3。销毁的职责边界：

- 表现层先销毁：界面栈关闭，编辑态按各自规则提交或丢弃，状态订阅解除；
- 游戏逻辑层次之：阶段状态机停止，正在进行的战斗与事件按"退出即结算"或"保留未结状态"规则处理；
- 领域层次之：各模块释放非持久资源；
- 数据层次之：数据域按规定提交一次存档（仅进程正常退出时）；
- 基础设施最后：存档服务完成收尾提交并关闭，日志服务刷新缓冲，资源服务释放全部资源，服务容器析构。

异常终止（崩溃或强制杀死）不执行销毁序列；此时以最近一次自动保存的提交结果为准。

## 6.5 常驻对象

常驻对象的完整清单见 2.4。常驻与非常驻的边界：

| 分类 | 对象 | 约束 |
| --- | --- | --- |
| 常驻对象 | 2.4 表内全部对象 | 进程内唯一实例，跨场景存在；由服务容器创建与销毁 |
| 数据域对象 | 世界状态域、单局状态域、玩家状态域 | 随单局创建与销毁；容器本身常驻，内容按局重置 |
| 场景对象 | 场景实例、战场实例、界面实例 | 随场景与界面的生命周期创建与销毁 |
| 临时运行对象 | 战斗内的结算中间量、条件求值的中间结果、抽样的中间集合 | 单次操作内有效，不跨帧保留，不入档 |
| 存档对象 | 三个切面与三份持久化结构（单局存档、跨局存档、设置数据） | 只在采集与恢复期间存在，采集完成后即释放 |
| 静态配置对象 | 5.1 表内全部定义 | 启动时加载，运行期只读，不销毁直到进程退出 |

## 6.6 阶段状态机

阶段状态机是全部阶段的唯一权威（ARC-GAP-032），与事件状态联动。裁定给出的阶段取五种（地图、事件执行、战斗、收尾窗口、结算）；本架构因覆盖范围扩到大循环（ARC-GAP-001），在其上追加第六种「局外阶段」，用于承载线索树查看、剪枝与开新局。阶段取值属世界状态域，见 5.2.1。

| 阶段 | 进入条件 | 允许的操作 | 退出到 |
| --- | --- | --- | --- |
| 地图阶段 | 无进行中事件 | 按事件类型与界面属性声明（如事件属性配置的界面开放状态） | 事件执行阶段 |
| 事件执行阶段 | 事件实例进入进行中 | 事件类型声明允许的操作（交易操作、物品交付、装备调整等） | 战斗阶段、收尾窗口阶段、地图阶段 |
| 战斗阶段 | M10 的战斗执行器启动 | 按战斗行为表登记的行为集合 | 收尾窗口阶段、事件执行阶段、结算阶段 |
| 收尾窗口阶段 | 战斗结束 | 按战场与战棋规则声明的窗口内操作 | 地图阶段 |
| 结算阶段 | 结局成立 | 无（本阶段不接受任何改变局内状态的输入） | 局外阶段 |
| 局外阶段 | 结算提交完成 | 线索树查看、剪枝提交、规划下一局、开新局 | 地图阶段 |

两条硬规则：

1. **阶段切换只能由当前阶段的拥有方发起，由阶段状态机执行。** 任何模块不得自行切换界面以隐式改变阶段。
2. **结算阶段是封闭的。** 结局成立之后世界时间不再推进，本局不再接受任何改变局内状态的输入（`系统设计文档/07-线索树与元进度/40-局末结算与写入/40_局末结算与写入设计.md` 的 3.13）。

| 退出时推进 | 事件退出时把累计值一次性推进：非战斗事件按整个时间段累加，最小推进单位为**一整个时间段**；战斗事件把以秒计的净时长**向上取整对齐**到时间段边界 |

| 广播 | 每次推进一步广播刻度变化；自动保存节点与界面时间显示由该广播派生 |

# 8. 全局技术约束

## 8.1 依赖方向规则

强制的两条：

## 8.2 数据访问规则

| # | 原则 | 具体含义 |
| --- | --- | --- |
| 1 | 不直接修改他方数据 | 只允许数据所有者写入自己的数据；其他模块只能读取，或经所有者提供的写入能力提交变更 |
| 2 | 跨域变更经过持有方入口 | 任何跨域的状态变化必须经持有方的提交入口，不得直接改对象字段、不得持有对方的可变引用 |
| 3 | 派生结果不作为数据来源 | 派生缓存（背包空间、同名遗物效果、条件求值结果、区域形态推算结果）只能由来源方维护与重建，读取方不得把派生结果当作来源状态使用或缓存 |

具体访问关系由各系统的代码设计案自行声明，并在代码设计案评审时按本节三条核对。评审时的判断基准：

- "直接修改"指持有对方的可变对象并改其字段，或持有对方的内部集合并在其上增删；
- 只读快照的传递不视为直接修改，但快照不得携带写入口；
- 批量查询、跨域只读遍历属于读取，但不得在读取方缓存结果。

## 8.3 生命周期规则

| # | 规则 |
| --- | --- |
| 1 | 常驻对象只能由服务容器创建与销毁，任何模块不得自行创建常驻对象的实例 |
| 2 | 场景对象与界面实例只能由界面栈创建与销毁 |
| 3 | 数据域对象随单局创建与销毁，容器常驻、内容按局重置 |
| 4 | 临时运行对象不得跨帧保留、不得入档 |
| 5 | 结算阶段开始后，任何模块不得创建或销毁单局状态域内的对象 |
| 6 | 常驻对象在其依赖的模块销毁之前不得销毁；销毁按创建逆序执行 |

## 8.4 通信规则

| # | 规则 |
| --- | --- |
| 1 | 跨模块的状态广播必须经 M01 的事件分发器，不得自行实现观察者 |
| 2 | 未在事件分发器登记的事件不得发布 |
| 3 | 事件只承载"发生了什么"，不承载"要求谁做什么" |
| 4 | 订阅方处理失败不得回滚发布方状态 |
| 5 | 界面与游戏逻辑之间的全部交互走意图与命令，界面不得直接修改数据 |
| 6 | 基础设施不得依赖任何具体玩法系统 |

除以上六条外，通信方式的选择由各模块自行判断（ARC-GAP-024）。

# 9. 关键全局流程

全局流程写到模块与能力调用一级，不写能力内部的执行步骤。

## 9.1 游戏启动

```
触发：可执行程序启动
参与：M01（服务容器、配置、日志、随机、时间、输入、资源、场景、存档）、M10（阶段状态机）、M08（界面栈）
序：
  1 服务容器创建 → 各常驻系统登记能力与依赖声明
  2 依赖图校验（成环即中止）→ 按拓扑排序
  3 日志服务就绪 → 配置服务加载并校验静态配置 → 记录配置版本标识
  4 按拓扑创建常驻对象并注入引用
  5 读取设置数据（损坏则回落默认值）→ 读取存档索引
  6 阶段状态机置为局外阶段 → 界面栈打开主界面
状态变化：无游戏状态变化
产生事件：配置加载完成
结束条件：主界面可交互
```

## 9.2 进入场景

```
触发：界面栈发起界面打开请求
参与：M08（界面栈）、M01（资源、场景）、M10（阶段状态机，提供当前阶段供界面判定）
序：
  1 界面栈解析目标界面与其层级 → 判定是否需要新场景
  2 需要时：资源服务加载场景与所需资源 → 场景管理器加载场景
  3 界面实例创建 → 建立状态订阅 → 转换为编辑态（若为可编辑界面）
  4 若是地图与战斗之间的一次性切换：先加载目标场景，再替换栈顶，再释放来源场景的非共享资源
状态变化：界面栈变化；不改变任何游戏数据
产生事件：界面打开
结束条件：界面可交互
失败处置：资源或场景加载失败时保留当前界面，向表现通道给出提示
```

## 9.3 存档加载

```
触发：启动阶段的读档路径，或玩家在局外选择已有存档
参与：M01（存档服务、数据域）、M06、M02、M03、M05、M07、M09、M10（阶段状态机）、M08（界面栈）
序：
  1 存档服务读取单局存档结构与配置版本标识
  2 版本一致则继续；不一致则按迁移规则处理，无法迁移时提示不兼容并停在主界面
  3 装载静态配置（已在启动阶段完成）
  4 创建三个数据域的空结构
  5 按序恢复：世界状态域 → 单局状态域 → 玩家状态域
  6 重建派生缓存：背包空间、同名遗物效果、条件求值结果、区域形态推算
  7 恢复事件池：全局事件池内容集合按快照恢复，当前事件池按快照恢复
  8 恢复战斗未结状态（若有）
  9 恢复界面位置：局内恢复到地图阶段；战斗未结时恢复到最近一次行动机会开始的时刻
状态变化：三个数据域由空转为存档内容
产生事件：存档恢复完成
结束条件：阶段状态机进入地图阶段或战斗阶段，界面可交互
约束：恢复过程不重新抽取任何随机结果；未确认的操作不恢复
```

## 9.4 游戏退出

```
触发：玩家退出，或进程异常终止
参与：M01（存档服务、日志、资源、场景）、M08（界面栈）、M10（阶段状态机）
序（正常退出）：
  1 界面栈关闭全部界面，编辑态按各界面规则提交或丢弃
  2 提交一次单局存档（若处于局内且未结算）
  3 阶段状态机停止
  4 各模块释放非持久资源
  5 存档服务收尾提交并关闭 → 日志刷新 → 资源释放 → 服务容器析构
序（异常终止）：
  不执行销毁序列；以最近一次自动保存的提交结果为准
状态变化：最后一次提交固定
产生事件：无（退出后不再分发）
结束条件：进程结束
```

## 9.5 关键跨系统流程

### 9.5.1 开新局

```
触发：玩家在局外选择开新局
参与：M02（局生成）、M06、M01、M07、M09、M10（阶段状态机）、M08（界面栈）
序：
  1 读取输入：全局事件池内容集合（按线索树解锁与剪枝状态计算）、剪枝状态、已解锁的大关进度
  2 生成四项产物：本局事件池快照、事件的窗口期与出现顺序、区域解锁状态、行情
  3 计算并快照全局事件池的内容集合（本局允许出现的事件标识清单）
  4 初始化三个数据域：队伍编制按生成结果重置，技能配置重置，物品与容器按生成结果建立
  5 初始化当前事件池：由事件调度器执行一次刷新
  6 界面栈切到地图界面，阶段状态机进入地图阶段
状态变化：三个数据域由空转为初始状态
产生事件：本局生成完成、当前事件池刷新完成
结束条件：地图界面可交互且存在可进入的事件
```

### 9.5.2 事件阶段转换（地图 → 事件）

```
触发：玩家在事件信息面板上点击进入
参与：M08（面板）、M10（事件执行器与阶段状态机）、M02（事件状态与数据）、M01（时间服务、输入服务）
序：
  1 玩家点选事件点 → 面板原地展开（窗口期、参考持续时间、强制标记）
  2 点击进入 → 阶段状态机校验当前阶段为地图阶段且事件实例处于可进入
  3 M10 的事件执行器把事件实例置为进行中 → 阶段切换为事件执行阶段（若为战斗事件则进入战斗阶段）
  4 界面栈打开事件界面或战斗界面
状态变化：事件状态迁移；世界时间不在此刻推进
产生事件：事件进入进行中、阶段切换
结束条件：事件界面或战斗界面可交互
```

### 9.5.3 事件阶段转换（事件 → 地图）与八步收束

任务书给出的「事件阶段转地图阶段须完成的八步」对应本流程的第 3 至 10 步：第 3 步时间流逝应用到世界、第 4 步自动保存（时间推进的提交点）、第 5 步过期事件清除、第 6 步事件池检查与权重、第 7 步确认生成数量、第 8 步按权重抽取生成与变体查重、第 9 步生成完毕并展示、第 10 步回到地图阶段。第 1、2 步是事件侧的收尾，不属于任务书八步。

```
触发：事件达成结束条件并退出
参与：M10（事件执行器与阶段状态机）、M02（事件调度器）、M01（时间服务、随机服务、存档服务）、M05、M04、M09、M06、M03、M08
序：
  1 M10 的事件执行器收集事件结果：战斗事件取战斗结果标识与达成目标清单
  2 事件结算：按结果标识查询事件配置，应用本次事件对玩家与世界状态的全部结果
  3 时间结算（ARC-GAP-025）：取出本事件记账上的累计值——非战斗事件为按行为与操作累计的时间之和，战斗事件为 M05 以秒计的净时长；由时间服务在事件退出时一次性推进世界时间（战斗净时长先向上取整对齐到时间段边界）
  4 自动保存：时间推进触发单局存档提交（时间段推进节点）
  5 过期剔除：事件调度器把越过窗口期的事件状态转为已错过并从地图呈现中移除
  6 事件池检查：按事件属性配置判定哪些事件进入、哪些移除、哪些保留，并计算权重；权重由每个事件自己的配置数据填写，抽取时不做难度体系式的层权重调制（ARC-GAP-028）
  7 确认生成数量：按每种事件的当前在场数量与配置上限核算本轮各类别的生成数量
  8 抽取生成：随机服务提供确定性序列 → 按权重抽取模板 → 抽取变体 → 点位查重，冲突则重试，重试超限记为生成失败且不占用点位
  9 呈现：生成结果写入当前事件池 → M03 更新呈现列表 → 界面刷新地图
  10 阶段状态机回到地图阶段
状态变化：事件状态收尾、世界时间推进、当前事件池刷新、事件实例销毁（已完成或已错过）
产生事件：事件结算完成、时间刻度变化、自动保存完成、当前事件池刷新完成、阶段切换
结束条件：地图界面按新事件池刷新完成
```

### 9.5.4 撤退与未完成状态

```
触发：玩家在战斗中发起撤退并成功
参与：M05（撤退判定）、M10（事件执行器）、M02（事件属性配置与状态）、M03、M08
序：
  1 战斗以撤退收场 → 撤退结果写入战斗结果标识
  2 事件状态：技术上仍为可进入状态（ARC-GAP-026），保留战斗内敌人的状态与位置，玩家可以重新进入
  3 事件退出并把控制权交回地图
  4 M10 的事件执行器按事件配置执行两条地图侧结果：该事件的窗口期延长；以该事件为中心锁定一定范围内的其他事件
  5 被锁定的其他事件在该事件完成或过期之前不可进入
状态变化：事件仍可进入；周边事件进入锁定；已获得的战利品保留；世界时间按实际战斗时长推进
产生事件：撤退发生、周边事件锁定
结束条件：回到地图界面
```

### 9.5.5 全队失去行动能力终止本局

```
触发：战斗内全部我方单位同时处于失去行动能力状态
参与：M05（判定）、M10（事件执行器轮询战果、结算执行器、阶段状态机）、M01（存档服务）
序：
  1 M05 判定全队失去行动能力成立 → 写入战斗结果
  2 M10 的事件执行器轮询战斗结果时检测到该终止条件（ARC-GAP-029）
  3 事件继续按常规流程收尾：打完收尾窗口、按常规退出与结算规则处理本场战斗
  4 事件结算环节终止本局：结局成立，结局类型与触发起因按 `系统设计文档/07-线索树与元进度/40-局末结算与写入/40_局末结算与写入设计.md` 的 3.7 与 3.13 与 `06-A0` 的 3.4 取值
  5 阶段状态机进入结算阶段，关闭本局输入通道，世界时间停止推进
  6 M10 的结算执行器接管：收集整局存档快照 → 调度结算组件 → 写入跨局存档
状态变化：本局终止；跨局数据按未通关结局写入
产生事件：结局成立、结算完成
结束条件：结算提交完成并转入局外阶段
```

### 9.5.6 局末结算与跨局写入

```
触发：结局成立（真结局、隐藏关底事件通过、或未通关结局的三种收尾情形）
参与：M10（结算执行器）、M06（跨局写入内容）、M01（存档服务）、M02、M04、M05、M07、M08（结算窗口）
序：
  1 结算执行器读取整局存档快照（不由各系统另行上报）
  2 按结算组件表依次执行本次版本启用的组件
  3 节点解锁检查组件：判定本局解锁的节点与传闻，写入跨局存档
  4 达成记录与大关进度组件（后续版本启用）：写入结局类型、触发起因与大关进度
  5 一次提交完成；提交成功即标记本局已结算，并随最近一次自动保存写入存档
  6 提交失败则整笔回滚，本局保持未结算并保留重试能力，重试不产生重复写入
  7 界面栈打开结算窗口：变更清单 + 结局提示 + 局外循环入口
状态变化：跨局数据更新；本局标记为已结算
产生事件：节点解锁、传闻解锁、结算完成
结束条件：结算窗口可交互
约束：场景变化包装事件默认不写入（事件配置显式声明时才产生节点解锁项）；剪枝的封锁集合与封锁标记不经结算组件
```

### 9.5.7 交易提交

```
触发：玩家在交易事件内确认一笔交易
参与：M08（界面与编辑态）、M09（物品写入服务）、M04（交易与物品）、M01（存档服务）
序：
  1 界面持有玩家选择形成的编辑态
  2 玩家确认 → 界面把编辑态提交给物品写入服务
  3 写入服务按"变更一项一落库"执行（ARC-GAP-010）：逐项校验并落库，任一项无法完成时整笔交易回滚，不产生部分提交
  4 提交成功后界面按新状态刷新
状态变化：物品归属、数量与容器格位变化；撤回与退款的规则见 `系统设计文档/05-运营与经济/10-金钱与货物/10_金钱与货物设计.md` 的 4.1
产生事件：物品变更提交、交易提交完成
结束条件：界面反馈完成
边界：确认前不改变任何物品状态；未确认的选择不产生状态变化
```

### 9.5.8 界面交互与提交

```
触发：玩家在界面上进行操作
参与：M08、M01（输入服务）、M09、各领域模块
序：
  1 输入服务把物理输入映射为意图 → 分发给当前界面
  2 界面把意图转为编辑态变化，或转为一次操作命令
  3 提交位置按粒度判定（ARC-GAP-017）：粗粒度在界面退出指令处提交；细粒度在每次交互处提交；复杂交互在确认处提交
  4 提交经服务（含 M09 的写入服务）执行，数据变化由持有方落库
  5 界面按新状态刷新
状态变化：按提交内容而定
产生事件：界面打开、界面关闭、编辑态提交
结束条件：界面回到可交互状态
约束：界面不直接修改任何游戏数据
```

# 10. 架构约束检查

每个新增或修订的系统在进入代码设计前逐项自查。**前六项为必备项，不得删减**；后四项为本项目按自身架构补充的检查项。

```
[ ] 1  是否产生跨层依赖？
       （对照 2.1 的分层与 3.3 的允许清单）

[ ] 2  是否产生循环依赖？
       （对照 3.4 第 12 项；两模块互相直接调用即为违反）

[ ] 3  是否绕过统一存档系统？
       （对照 7.1；任何自行序列化状态或自行读写存档的行为均为违反）

[ ] 4  是否直接修改其他系统的内部状态？
       （对照 8.2 三条原则；持有对方可变引用并改其字段即为违反）

[ ] 5  是否违反对象生命周期规则？
       （对照 6.5 与 8.3；自行创建常驻对象、临时对象跨帧保留均为违反）

[ ] 6  是否创建了重复的基础设施？
       （对照第 7 章；自行实现随机源、日志、资源加载、事件分发、效果叠加、
         条件判定、物品写入、输入采集、时间推进中的任何一项均为违反）

[ ] 7  是否绕过 M09 的物品写入服务改动物品状态？
       （对照 3.4 第 7 项与 7.11）

[ ] 8  是否在界面层直接改动了游戏数据？
       （对照 3.4 第 3 项与 8.4 第 5 条）

[ ] 9  是否由非持有方推进了世界时间，或在事件未退出时推进了时间？
       （对照 7.5 的推进入口与 8.4）

[ ] 10 是否落在已登记的扩展路径内？
       （对照 8.5 的五类接入步骤；不属于五类之一的扩展先登记再实施）

[ ] 11 是否把派生结果当成了数据来源？
       （对照 8.2 第 3 条；自行缓存跨域结果、或按派生缓存反推来源状态均为违反）

[ ] 12 是否发布了未登记的跨模块事件，或把「要求谁做什么」写进了事件？
       （对照 8.4 第 2、3 条与 4.3）

[ ] 13 是否让订阅方处理失败回滚了发布方状态？
       （对照 8.4 第 4 条）

[ ] 14 是否存在未登记的依赖例外？
       （对照 8.1；例外必须写明双方、理由、失效条件与复核时点）
```
