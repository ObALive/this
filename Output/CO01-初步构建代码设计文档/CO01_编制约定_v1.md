## 二、落点、命名与元信息表

1. 文件落点与命名按 NR-06 §十二.1：`{系统编号}_{系统名}代码设计案.md`；架构单元以模块编号 `M01` 至 `M10` 作系统编号，落在 `Code_Design/00-架构单元/`，该目录是本轮经用户授权新增的库结构，登记在 NR-06 §十二。
2. 元信息表八项按 NR-06 §十二.2 填写。架构单元的字段取值：`系统名` 写单元名；`所属域` 写 `00-架构单元`；`系统编号` 写模块编号；`对应设计文档` 写 `架构设计文档/架构设计案.md` 的对应章节；`关联文档` 写本单元成员系统的代码设计案路径与架构案章节。
3. 系统设计库系统的 `对应设计文档` 写上游设计稿路径（本文 1.2 表格第 8 列）；`关联文档` 写同模块其他单元的代码设计案与架构案相关章节。
4. 文件名、文档标题与元信息表一律不带版本号。

## 三、模块单元文档与系统文档的分工

架构单元文档与系统文档存在天然重叠（例如 M01 与 01-50 都会写到存档），为守住唯一事实来源，分工固定如下：

| 文档 | 写什么 | 不写什么 |
| --- | --- | --- |
| 系统文档（32 份） | 本系统的程序契约：数据对象、状态、对外接口、内部功能、依赖、交互、核心流程、异常、实现约束 | 模块级的公共能力定义（引用模块单元文档的 ID） |
| 模块单元文档（10 份） | 本模块的模块级契约：模块拥有的系统清单与数据、模块对外暴露的能力名与其契约、模块内部装配与初始化顺序、模块级事件、模块级依赖方向限制 | 成员系统已定义的对象与接口（引用其 ID，不重定义）；成员系统的规则细节 |

逐模块的分工补充：

1. **M01 与 01-50、01-60**：数据域与存档服务的能力由 01-50 定义，M01 引用其 ID；服务容器、配置服务、随机服务、时间服务、输入服务、资源服务、场景管理器、日志服务、事件分发器在这些能力上**没有对应的设计库系统**，由 M01 定义。
2. **M02 与 02-10、02-30、02-30-10、09-20**：时间口径由 02-10 定义，时间服务由 M01 定义；事件模板、变体、实例与事件池由 02-30 定义，事件调度由 02-30 定义并在 M02 登记模块能力；条件求值服务由 M09 定义，02-30-10 定义条件的组合与引用侧；局生成由 09-20 定义。
3. **M05 与战斗域十二个系统**：战斗内规则由各系统文档定义，M05 定义战斗的启动、轮次推进与收束这一模块级编排能力；战斗执行器由 M10 定义，M05 提供被调用的入口。
4. **M06 与 07 域四个系统**：结算组件的内容由 07-40 定义，结算流程的执行编排由 M10 定义。
5. **M09 与 06-75、05-05、02-30-10**：元效果服务、条件求值服务、物品与经济写入服务由 M09 定义；提供效果与引用条件的业务语义由对应系统定义。
6. **M10**：没有成员系统，阶段状态机、事件执行器、战斗执行器、结算执行器由 M10 定义。
7. **M08 与 01-20**：界面栈、界面清单、编辑态、文案取用通道由 M08 定义；文案与提示的投放规则、台词索引由 01-20 定义。

任何一处出现同一对象被两份文档定义，以「谁拥有该对象」（架构案 2.4 与 3.2）判定归属，另一份改为引用。

## 四、编号规则

1. 对象 ID 按 NR-06 §九：前缀 `SYS-`、`CLS-`、`API-`，接单元码，再接三位序号，例如 `SYS-SAVE-001`、`CLS-SAVE-003`、`API-SAVE-002`；架构单元用模块编号作单元码，例如 `CLS-M01-004`。
2. 单元码见本文 1.1 与 1.2 的「单元码」列。单元码一经分配不修改，ID 在全库唯一且不复用。
3. 每份文档在第一节给出本单元的 `SYS-` ID，写法 `SYS-{单元码}-001 {单元名}`，全库唯一；再对全部数据对象给 `CLS-` ID，对全部对外接口给 `API-` ID。文档未声明 `SYS-` ID 时，全库核对无法判定该文档的单元归属。
4. 功能要求编号 `F-{单元码}-01`、实现要求编号 `I-{单元码}-01`，两位递增。
5. 引用其他单元的对象时写 `ID 名称`，例如 `API-SAVE-002 SaveService.Submit()`，不复制对方内容。引用设计库术语时按 NR-05 §四.3 加注 `（术语表 T-XXX）`。
6. 单元内 ID 由本单元的编制方分配；跨单元引用按下列顺序取用：先查附录 A 的公共能力 ID 表；表内没有的，写 `{名称}（{对方单元码}，ID 待补）`。收口时由全库核对统一回填真实 ID，编制方不得为对方单元编造 ID。
7. 向量表的固定列：对外接口表写 `接口 ID | 接口 | 调用者 | 输入 | 输出 | 状态变化 | 副作用`；外部依赖表写 `依赖对象 | 所属单元 | 依赖类型 | 用途 | 使用接口 | 对象 ID | 接口 ID`（后两列未知时写「待补」）。列名固定，供全库机械核对。
8. 待登记事件的标记写作 `【待架构登记】{事件名}`，事件名紧随标记；标记后不接事件名时视为格式不合规。

## 五、事件词表与登记口径

1. 跨模块事件只使用架构案 3.1 各模块单元「事件」栏已登记的名称，词表如下（括号内为登记模块）：

| 模块 | 已登记事件 |
| --- | --- |
| M01 | 时间刻度变化、自动保存完成、存档提交完成、存档恢复完成、配置加载完成 |
| M02 | 本局生成完成、事件进入当前事件池、事件刷新到点位、事件进入进行中、事件结算完成、当前事件池刷新完成 |
| M03 | 区域形态转变、周边事件锁定、呈现列表更新、基点变化 |
| M04 | 对象实例创建与销毁、物品归属变化、容器内容变化、交易提交完成、委托状态变化 |
| M05 | 战斗开始、轮次推进、行为提交完成、单位状态变化、战斗结束、撤退发生 |
| M06 | 节点解锁、传闻解锁、封锁状态变化、结算完成、结局成立 |
| M07 | 队伍成员加入、队伍成员离队、主角变化、队伍重置 |
| M08 | 界面打开、界面关闭、编辑态提交 |
| M09 | 效果附加、效果移除、物品变更提交 |
| M10 | 阶段切换、结局成立、结算完成 |

2. 代码设计案可以细化事件的**载荷字段类别与失败语义**（架构案 4.3 把逐项契约留给代码设计案），但事件名必须来自上表；同一事件的多处描述必须一致。
3. 确需上表之外的事件时，在文档内按 `【待架构登记】事件名` 标注，并同时写入本文第九章的上游缺口申报，不得当作已登记事件使用。
