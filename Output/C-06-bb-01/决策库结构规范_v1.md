# 决策库创建规范（v1）

| 项目 | 内容 |
| --- | --- |
| 文档定位 | 各章节信息缺口分析的配套决策库的建库规范与填写器接入约定；按本规范建库即可直接使用同一套网页填写器 |
| 适用范围 | `Dsh/Output/{任务编号}/` 下由信息缺口分析产出的全部决策库 |
| 首个实例 | `Dsh/Output/C-06-bb-01/C-06-bb-01_战斗系统缺口决策库_v1.sqlite`，45 项缺口 |
| 配套工具 | `Dsh/Output/C-06-bb-01/.artifact_runtime/建库工具/` 与 `Dsh/Output/C-06-bb-01/.artifact_runtime/填写器/` |
| 维护人 | 首席主策划 |
| 版本 | v1 |
| 更新日期 | 2026-09-24 |

## 1 决策库要解决的问题

信息缺口分析产出的 GAP 清单是一份需要人逐项拍板的待决清单。把清单放进数据库有三个直接好处。第一，裁定结果有唯一的结构化落点，回答不再散落在对话、文档与邮件里。第二，同一个网页填写器可以服务任意章节，只要新库符合本规范即可直接打开填写，不需要为每个章节改界面。第三，裁定状态可查询，能随时回答"还有多少项没有拍板、哪些项卡住了正文编写"。

决策库只承载待决清单与裁定结果。系统设计正文、候选方案的长篇论证、任务报告都不进数据库，它们仍按现有规则存放在 `Dsh/Design`、`Dsh/Output` 与 `Dsh/Report`。

## 2 文件位置与命名

| 项目 | 约定 |
| --- | --- |
| 存放目录 | `Dsh/Output/{任务编号}/`，与同任务的信息缺口分析文档同级 |
| 文件命名 | `{任务编号}_{系统或域名称}缺口决策库_v{版本}.sqlite` |
| 首个实例 | `C-06-bb-01_战斗系统缺口决策库_v1.sqlite` |
| 版本规则 | 按 `Dsh/Rules.md` 的默认禁止覆盖原则，结构或内容整体重做时新建 `_v2.sqlite` 并保留旧版；仅在原有条目上继续填写不升级版本 |
| 建库工具位置 | `Dsh/Output/{任务编号}/.artifact_runtime/建库工具/`，包含模板模块与建库脚本 |

填写器在 `Dsh/Output` 下按文件名自动发现决策库，文件名的后缀必须是 `.sqlite`，且文件名包含"决策库"或位于任务目录下。同一工作区内可以存在多个决策库，填写器在页面顶部以下拉框列出全部库并支持切换。

## 3 库结构

决策库由四张表与一张视图构成。表名、列名与列的含义由本规范固定，任何新增章节都沿用同一套结构，不得为单个章节改动列名或语义。

### 3.1 meta 自述表

| 列 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| key | TEXT | 主键 | 元信息键 |
| value | TEXT | 非空 | 元信息值 |

约定的键如下，填写器读取 `title` 作为库的显示名。

| 键 | 是否必需 | 说明 |
| --- | --- | --- |
| title | 必需 | 库的显示名称，例如 `C-06-bb-01 战斗系统缺口决策库` |
| chapter | 必需 | 章节或任务编号，与文件名中的任务编号一致 |
| domain | 建议 | 所属系统域，例如 `06-战斗` |
| analysis_doc | 必需 | 对应信息缺口分析文档的库内路径 |
| created_at | 建议 | 建库日期 |
| created_by | 建议 | 建库脚本名 |
| meta_added_at | 条件 | 为早期无 meta 表的库补建时写入的时间 |

### 3.2 gaps 缺口主表

| 列 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| gap_id | TEXT | 主键 | 缺口编号，形如 `CBT-GAP-001`，前缀由章节自定并全库统一 |
| title | TEXT | 非空 | 缺口陈述，一句话说清缺什么、影响什么 |
| level | TEXT | 非空 | 阻塞等级，取 `B0`、`B1`、`B2` |
| status | TEXT | 非空 | 缺口自身的登记状态，例如 `待裁定`、`本轮部分关闭` |
| source_ref | TEXT | 非空 | 来源依据，文档路径与章节号 |
| impact_scope | TEXT | 非空 | 受影响系统编号清单 |
| close_condition | TEXT | 非空 | 关闭条件，写清满足什么即可认为该缺口关闭 |
| owner | TEXT | 非空 | 责任方，例如 `游戏总监`、`主策划` |
| priority_round | TEXT | 可空 | 所属优先轮次与问题编号，未列入本轮问题包的缺口留空 |
| analysis_doc | TEXT | 非空 | 分析文档路径，与 meta 中的同名字段一致 |

### 3.3 solution_options 候选方案表

| 列 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| option_id | TEXT | 主键 | 候选编号，规则为 `{gap_id}-OPT-{字母}`，自定义预留行为 `{gap_id}-OPT-CUSTOM` |
| gap_id | TEXT | 外键指向 gaps | 所属缺口 |
| seq | INTEGER | 非空 | 显示顺序，候选从 1 递增，自定义预留行固定为 99 |
| option_label | TEXT | 非空 | 显示用短标签，候选取 `A`、`B`、`C`；自定义预留行取 `自定义` |
| summary_title | TEXT | 非空 | 候选标题，一句话点明该候选的核心做法 |
| detail | TEXT | 非空 | 方案正文，写清规则是什么、适用范围、状态变化与与既有系统的衔接 |
| tradeoff | TEXT | 非空 | 代价与影响，写清选它要付出什么、放弃了什么 |
| is_recommended | INTEGER | 非空，默认 0 | 是否推荐，每个缺口至多一条为 1 |
| is_selected | INTEGER | 非空，默认 0 | 是否已被选定，由填写器维护 |
| is_custom | INTEGER | 非空，默认 0 | 是否为自定义预留行，自定义行必须为 1 |

### 3.4 decisions 裁定表

| 列 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| gap_id | TEXT | 主键，外键指向 gaps | 与缺口一一对应，建库时为每个缺口插入一行 |
| chosen_option_id | TEXT | 可空 | 采用的候选编号；采用候选时写这里 |
| answer_text | TEXT | 可空 | 预留的空白字段；候选都不符合时把预期方案写这里 |
| decision_basis | TEXT | 可空 | 裁定理由 |
| extra_requirement | TEXT | 可空 | 补充要求，候选未覆盖的例外与细节 |
| decided_by | TEXT | 可空 | 裁定人 |
| decided_date | TEXT | 可空 | 裁定日期 |
| status | TEXT | 非空，默认 `待裁定` | 裁定状态，取值见 4.2 |
| filled_at | TEXT | 可空 | 最后一次写入时间，由填写器写入 |
| needs_followup | INTEGER | 非空，默认 0 | 候选与预期方案同时存在时置 1，提示复核以哪一项为准 |

### 3.5 v_gap_decision 裁定进度视图

视图把缺口与裁定拼成一行，供查询与导出使用，列包括 `gap_id`、`level`、`owner`、`priority_round`、`gap_status`、`title`、`decision_status`、`chosen_option_id`、`candidate_count`、`final_answer`、`needs_followup`。其中 `final_answer` 按预期方案优先、候选次之的顺序给出最终答案。

## 4 内容规则

### 4.1 候选数量与写法

1. 每项缺口给出 **2 至 3 条候选**，候选之间必须互斥，不能是同一条规则的强弱两档。
2. 每条候选的 `detail` 是一段可以直接落成规则的完整表述，需要覆盖四件事：规则是什么、适用范围、触发后的状态变化、与既有系统的衔接方式；必要时补充边界与例外。只写方向不写规则的候选不满足要求。
3. 每条候选的 `tradeoff` 写清选择它要付出的代价与被放弃的替代方案，避免出现只有优点没有代价的候选。
4. 每项缺口 **至多标记一条推荐候选**，也可以不标记；推荐只表达倾向，不改变候选的平等地位。
5. 建库时无论候选给几条，都自动追加一条 `is_custom = 1` 的自定义预留行，使填写器始终呈现"候选若干加一个自定义输入框"的形态。
6. 缺口陈述 `title` 不写候选倾向，只陈述缺什么。

### 4.2 裁定状态取值

| 取值 | 含义 | 写入方式 |
| --- | --- | --- |
| 待裁定 | 尚未作出决定 | 建库初始值；清除裁定后回到该值 |
| 已选候选 | 采用了某条候选 | `chosen_option_id` 写入候选编号 |
| 自定义方案 | 候选都不符合，采用自己写的方案 | `answer_text` 写入方案文本 |

填写器按"有预期方案文本即为自定义方案、否则有候选编号即为已选候选"的顺序判定状态。候选编号与预期方案文本同时存在时状态取自定义方案，并把 `needs_followup` 置 1。

## 5 建库流程

1. 完成该章节的信息缺口分析，产出 GAP 清单与优先问题包。
2. 在 `Dsh/Output/{任务编号}/.artifact_runtime/建库工具/` 下编写建库脚本，脚本从模板模块导入结构，只负责提供本任务的数据。
3. 运行建库脚本生成 `.sqlite` 文件到 `Dsh/Output/{任务编号}/`，脚本结束时应打印自检结果。
4. 用校验命令确认结构：`python decision_db_template.py --check {库文件路径}`。
5. 启动填写器：`python .artifact_runtime/填写器/decision_server.py`，在页面顶部选择新建的库。
6. 逐项裁定，页面实时写入；裁定完成后用页面右上角的导出链接得到 Markdown 复核稿。
7. 把裁定结果作为下一轮任务书或系统设计正文的输入，并同步更新缺口分析文档中的 GAP 状态列。

### 5.1 模板模块的最小调用

```python
from decision_db_template import GapRecord, OptionRecord, build_decision_db

build_decision_db(
    path="Dsh/Output/C-aa-bb-01/C-aa-bb-01_某系统缺口决策库_v1.sqlite",
    meta={
        "title": "C-aa-bb-01 某系统缺口决策库",
        "chapter": "C-aa-bb-01",
        "domain": "02-时间与事件",
        "analysis_doc": "Dsh/Output/C-aa-bb-01/C-aa-bb-01_某系统信息缺口分析_v1.md",
        "created_at": "2026-09-24",
    },
    gaps=[
        GapRecord(
            gap_id="XXX-GAP-001",
            title="缺口陈述",
            level="B0",
            source_ref="来源文档与章节",
            impact_scope="受影响系统编号清单",
            close_condition="关闭条件",
            owner="游戏总监",
            priority_round="第一轮 骨架，XXX-Q-001",
        ),
    ],
    options={
        "XXX-GAP-001": [
            OptionRecord("A", "候选 A：短标题", "方案正文", "代价与影响", True),
            OptionRecord("B", "候选 B：短标题", "方案正文", "代价与影响"),
            OptionRecord("C", "候选 C：短标题", "方案正文", "代价与影响"),
        ],
    },
)
```

### 5.2 模板模块提供的四个能力

| 能力 | 入口 | 说明 |
| --- | --- | --- |
| 建库 | `build_decision_db(path, meta, gaps, options)` | 建表、写入元信息、缺口、候选与自定义预留行，返回自检结果 |
| 校验 | `verify_decision_db(path)` 或命令行 `--check` | 检查必需表与视图、引用完整性、候选数量、推荐数量、空正文与孤儿候选 |
| 补建自述 | `ensure_meta(path, meta)` 或命令行 `--ensure-meta` | 为早期没有 meta 表的库补建自述表，不改动其余数据 |
| 示例 | `python example_build.py` | 从零建一个两项缺口的示例库并自检，运行后自动删除，用作回归测试 |

## 6 填写器接入约定

填写器是本地服务，不依赖外部网络，只在 `127.0.0.1` 上监听。启动方式与目录结构如下。

| 项目 | 内容 |
| --- | --- |
| 启动命令 | `python .artifact_runtime/填写器/decision_server.py` |
| 默认地址 | `http://127.0.0.1:8777/`，端口被占用时自动向后顺延 |
| 目录结构 | `填写器/decision_server.py`、`填写器/index.html`、`填写器/app.css`、`填写器/app.js` |
| 库的发现范围 | `Dsh/Output` 下的 `.sqlite` 文件，逐个尝试读取，结构不符的自动跳过 |
| 界面结构 | 顶部为数据库选择器、进度条与筛选；主体为缺口卡片；每张卡片内含若干候选与一个自定义输入框，每项前面一个单选框，共四个单选框 |

填写器使用的接口如下。新章节不需要改动接口，只要库结构符合第 3 节即可。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/databases` | 列出全部决策库及其裁定进度与自述标题 |
| POST | `/api/select` | 切换当前库 |
| GET | `/api/questions?db=库路径` | 返回缺口、候选、裁定状态 |
| POST | `/api/decision` | 写入一项裁定，接受 `db`、`gap_id`、`chosen_option_id`、`answer_text`、`decision_basis`、`extra_requirement` |
| POST | `/api/clear` | 清除一项裁定，回到待裁定 |
| GET | `/api/export?db=库路径` | 导出已裁定项的 Markdown 复核稿 |

写入接口有三条校验规则。缺口必须存在于 `gaps`；候选编号必须存在且属于该缺口；库路径必须落在工作区之内。任一不满足时接口返回 400 与具体原因，界面提示保存失败并回滚单选框状态。

## 7 与文本流程的兼容

网页填写与文本填写共用同一份库，两条路径可以混用。

| 路径 | 操作 | 适用场景 |
| --- | --- | --- |
| 网页填写 | 启动填写器，勾选候选或填写自定义输入框 | 逐项决策、需要横向比对候选正文时 |
| 文本模板 | 编辑 `{任务编号}_缺口作答模板_v1.md` 后运行 `建库工具/import_answers.py` | 离线思考、批量粘贴长方案、需要版本管理对比时 |
| 直接改库 | 用任意 SQLite 工具写 `decisions` 表 | 批量脚本处理或与其他系统对接时 |

无论走哪条路径，裁定结果的权威落点都是 `decisions` 表。作答模板与候选清单属于过程性产物，可从库中随时重新导出。

## 8 版本与兼容规则

1. 本规范的结构变更必须升版本，并同步升级填写器与模板模块；旧库只做补建字段处理，不重建。
2. 允许的向后兼容变更包括新增可空列、新增 meta 键、新增视图；这些变更不改变第 3 节已列列的含义。
3. 不允许的变更包括改动既有列名或含义、改动 `option_id` 与 `gap_id` 的编号规则、把自定义预留行改为多条。
4. 新增章节建库时，若发现本规范缺少某项必需字段，先在本文件登记变更，再改模板模块，最后建库，避免各章节各自扩展结构。

## 9 自检清单

建库完成后逐项核对本节。模板模块的校验能力已覆盖其中第一至第六项。

| # | 检查项 | 通过标准 |
| --- | --- | --- |
| 1 | 必需表与视图 | `meta`、`gaps`、`solution_options`、`decisions` 与 `v_gap_decision` 齐备 |
| 2 | 引用完整性 | 完整性检查为 ok，外键检查无错误，无孤儿候选 |
| 3 | 候选数量 | 每项缺口 2 至 3 条候选，另有且仅有一条自定义预留行 |
| 4 | 推荐数量 | 每项缺口恰好一条推荐候选 |
| 5 | 内容完整 | 候选正文与代价说明均非空 |
| 6 | 裁定初始状态 | `decisions` 全部为 `待裁定`，`chosen_option_id` 与 `answer_text` 为空 |
| 7 | 自述信息 | meta 含 title、chapter、analysis_doc |
| 8 | 填写器可读 | 启动填写器后能在下拉框中看到该库，缺口数与候选数与清单一致 |
