## 一、建议采用的总体方向

建议整体重写 NR-06，并联动调整相关规范，把代码设计案重新定义为：

> 在既定游戏规则和全局架构约束下，完成 Unity/C# 技术实现设计，确定类型、实例、数据、成员、装配、通信和执行机制，交付可独立编写单类伪代码的实施规格。

本轮建议改变的核心，是代码设计阶段必须承担的决策责任。旧规范主要规定系统应有的能力，把类型与技术选择留给后续；新定位要求在进入伪代码之前，完成影响类结构及类间协作的决定。

建议用以下结果衡量重构：执行者收到单一类的交付稿后，能够写出该类的伪代码，无需重新拆类、选择事件机制、寻找数据字段、发明依赖方法或决定 Unity 承载方式。

这允许保留函数内部的编写空间。局部变量名、简单循环的写法和不改变契约的私有辅助逻辑，可以在伪代码阶段确定。影响方法结果、数据所有权、确定性、复杂度要求或跨类协议的算法选择，应在代码设计阶段先决定。

## 二、先重订阶段分工与决策权限

### 2.1 六层体系可以保留，但需要改写第四至第六层的职责

| 阶段 | 建议负责的决定 | 交付给下一阶段的结果 |
| --- | --- | --- |
| 系统设计 | 游戏行为、玩家规则、状态含义、数值关系与业务边界 | 可解释游戏行为的规则输入 |
| 架构设计 | 全局约束、程序集方向、模块边界、公共机制、全局所有权与生命周期原则 | 实现方案必须遵守的结构约束 |
| 代码设计 | 具体类型与成员、实例装配、数据结构、引擎与语言机制、跨类协议、必要算法策略 | 已完成关键技术决定的类级实施规格 |
| 伪代码 | 在既定签名、数据结构和机制下，展开方法体、分支、循环、状态更新与清理路径 | 可翻译成实际代码的函数执行逻辑 |
| 实际代码 | 按已定方案完成语法、工程接线、编译、调试和运行验证 | 可执行且经过验证的实现 |

保留系统设计与架构设计作为两种输入来源。代码设计承担二者到具体实现的转化；伪代码不再承接遗留的系统结构设计任务，实际代码阶段也不再首次决定核心技术栈。

现有 NR-01 §二、NR-03 §七及 NR-06 §二中“实际代码才决定用什么技术”“代码设计只确定要有什么”等表述，应随之重订。

### 2.2 明确三类决策的处理权

| 遇到的问题 | 建议处理责任 | 是否需要逐项请示 |
| --- | --- | --- |
| 现有架构范围内的类拆分、字段、容器、参数、回调、局部实现机制 | 由代码设计执行者比较并作出结论，写明关键理由 | 已授权技术设计任务内自行完成 |
| 修改公共接口、公共异步机制、全局装配或数据域边界 | 在受影响范围统一设计，识别兼容影响；超出现有授权时单列变更建议 | 按实际授权判断，不把每项普通选型都升级为用户裁定 |
| 改变游戏规则、取消用户已定要求、违反明确架构约束 | 保留问题与影响，提交有权决定者裁定 | 不能以“实现方便”为由自行改变 |

建议在 NR-01、NR-03 中明确：“不得擅自创造游戏设计”与“按授权完成技术设计”是不同范围。否则即使 NR-06 允许选型，执行者仍可能以“上游没写”为由回避职责。

技术设计的依据可以是上游规则、既有架构、官方技术资料以及有说明的工程取舍。新方案不必全部从策划文字中唯一推导出来；但技术选择必须能说明它满足哪些约束。

## 三、取消以玩法系统为唯一实施单位

### 3.1 玩法系统与程序类型采用多对多映射

建议废除“代码设计与系统设计一一对应、不合并不拆分”“拆代码前先拆玩法系统”。保留系统编号用于追踪来源，不再用它限制软件类型划分。

一个玩法系统可以由多个类共同实现；一个通用类可以承接多个系统的需求。代码设计需要回答每项功能落在哪个类的哪个方法，同时确认这些类如何共同工作。

建议用“变更原因、持有状态、生命周期、执行机制、依赖边界”判断是否拆类。例如编辑器资产维护与运行期事件分发具有不同执行环境，不能仅因都与事件相关就默认属于同一执行类。反过来，两个同生命周期且共同维护一个不变量的小功能，也不必为了增加类数量而拆开。

### 3.2 保留三种文档视图，全部属于代码设计这一层

| 视图 | 用途 | 内容边界 |
| --- | --- | --- |
| 实现总览 | 解释一组类如何完成需求 | 功能到方法映射、类型清单、实例装配、关键协作链、共用技术决定 |
| 类型设计稿 | 描述具体类、接口、结构体等 | 精确成员、职责、数据与行为协议；有行为的类是独立实施单元 |
| 共用契约定义 | 统一跨类使用的接口、载荷、请求、结果、标识与枚举 | 唯一声明及语义，避免使用方分别发明 |

“单类分发稿”由类型设计稿加必要依赖摘录形成，是交付视图，不另建一套手工维护的权威设计。总览也不再重复全部字段和方法契约。

三种视图不表示同一个接口要写两份：共享接口或载荷自身的类型稿可以就是它的共用契约定义；实现类注明实现关系和本类行为，使用方附只读摘录，均不另立声明权。具体成员契约应能指向一个明确的维护位置。

建议目录按程序模块或能力组织，模块内按类型命名，保留程序集和目标源码路径的登记。域目录与系统编号可以用于需求索引，无需继续决定物理文件结构。具体目录命名和模板由第三步统一规定，本轮不直接迁移文件。

原则上一个行为类有一份主设计稿；仅供它使用的简单数据类型可以在稿内附属声明。跨类共享或可单独维护的数据类型应有明确的唯一落点。这样既能按类分发，也不会把每个枚举和值对象机械扩成一份长文档。

## 四、把类型设计从“名称与用途”提升为可声明的结构

建议取消所有类型统一套系统十节的模板，采用“共同信息 + 按类型适用的内容”。文档长短由实施信息决定，不设字符数下限。

### 4.1 所有类型应能确定的信息

| 信息 | 建议达到的深度 |
| --- | --- |
| 类型身份 | 明确名称、命名空间、所属程序集、目标源码路径；区分 class、interface、struct、enum 等 |
| 职责与需求 | 职责可归属于这个类型；标出承接的功能和方法，不再笼统写“本系统处理” |
| 类型关系 | 基类、实现接口、泛型约束、组合和引用关系；不使用继承时也要能确定组合结构 |
| 字段与属性 | 所有持久于方法调用之外的成员的名称、类型、可变性、初始来源、约束与读写归属 |
| 集合与标识 | 元素类型、索引键、顺序语义、重复与缺项处理、ID 与对象引用的关系 |
| 方法和事件 | 名称、可见性、参数与返回类型、事件或回调签名、同步或异步形式 |
| 不变量 | 哪些关系在一次成功或失败操作后始终成立，何处维护 |
| 外部依赖 | 精确使用面、取得方式、是否拥有其生命周期、调用限制 |

这里要求的是足以声明结构的设计，不要求先写完实际类代码。允许使用 C# 声明片段和类型名表达签名；“出现语法”不再是越界判据。

### 4.2 按类型补充适用内容

- 行为类：方法契约、必要内部状态、调用顺序、异常与清理职责。
- Unity 承载脚本：挂载位置、序列化引用、业务初始化入口、启停和场景生命周期的关联。
- 配置资产：资产类型、编辑器维护方式、校验与读取路径、运行期内存形态。
- 数据对象：逐字段定义、不变量、复制与可变性；需要持久化时补 DTO、标识恢复和版本兼容边界。
- 接口、请求、结果与事件载荷：完整使用协议和取值语义；不强套一个没有意义的运行期状态机。

“无”只用于确实不适用的内容。关键字段、签名或所有者尚未决定时，应登记为缺口，而不是写“由伪代码决定”后标记完成。

### 4.3 方法契约要补齐能改变协作方式的信息

建议在原有前后置条件基础上，明确以下适用内容：

1. 参数类型、单位、有效范围、空值含义以及输入对象是否允许被修改。
2. 读取和写入的具体成员、数据来源及访问入口。
3. 返回类型、成功与拒绝的区别、可预期失败和异常的区分。
4. 外部调用目标及其先后关系，状态提交与通知的时点。
5. 同步完成、接受请求后返回、跨帧等待、回调完成等执行语义。
6. 幂等、重入、取消、部分成功、回滚和释放责任。

完整公开协议和重要内部方法应先确定。伪代码可以增加不改变这些协议的局部私有辅助逻辑；若需要新增跨类调用、持有状态或改变成员可见性，就应回到设计稿补充，而非各执行者自行扩张。

## 五、实例与装配从附表提升为设计主干

建议将“类型怎么定义”与“运行中有哪些实例”明确分开。每个行为类型都要能确定实例数量规则、作用域、创建者、依赖注入方式、引用持有者和终止路径。

| 实例问题 | 建议输出 |
| --- | --- |
| 多少个、何时存在 | 每进程、每局、每场战斗、每实体或每次操作的数量规则；无实例的静态能力单独说明 |
| 谁创建、谁初始化 | 具体装配类、工厂或拥有者及其入口；区分对象分配、引用注入和业务启动 |
| 谁持有谁 | 具体字段或集合，以及拥有关系和借用关系 |
| 何时可用 | 初始化前能否调用、就绪条件、初始化失败后的状态 |
| 如何终止 | 正常完成、取消、读档替换、场景退出或池回收时的处理 |
| Unity 如何接线 | 挂载 GameObject 或 Prefab 的位置、引用绑定方式、引擎回调与显式业务调用的分工 |

装配总览要给出实际类型和实例角色的关系，不能只写“M01 创建 M02”。相关单类稿必须包含本类需要的那部分装配信息。

需要特别区分四组概念：

- C# 类型继承与 GameObject/Transform 父子层级；
- 玩法组件与 Unity Component；
- 配置资产、运行期权威状态、存档 DTO 与表现实例；
- 常驻的服务实例与它拥有的可按局替换的数据。

对角色、物品、技能的“元对象 + 组件”设计，建议进一步写清组件由哪种结构承载、谁执行行为、谁拥有组件状态、如何挂载和查询、如何保存恢复。仅列能力类别还不能作为实施完成。

## 六、技术选型改为代码设计的必交结果

### 6.1 先有可核验的技术基线

现架构已规定 Unity 6 长期支持版。本方案不重新选择引擎，也不凭空指定补丁版本。建议在进入相关实现设计时，明确实际 Unity 版本、目标平台、与该能力有关的包及版本、API 可用性和程序集限制。

项目尚无实际工程时，可以登记拟采用的基线并说明依据。依赖特定 API 的类，在适用版本未核实前不能声称已可实施；与该缺口无关的普通逻辑类可以继续完成设计。无需为写一个普通类穷举所有可能使用的插件。

### 6.2 按实际需求决定机制

| 设计主题 | 建议必须明确的选择 |
| --- | --- |
| 运行承载 | 普通 C# 类、MonoBehaviour、ScriptableObject 等各自承担什么；具体对象与绑定方式 |
| 发布与订阅 | 项目事件通道、C# 委托或事件、UnityEvent 等分别用于何处；载荷、签名、订阅与解除责任 |
| 跨帧与异步 | 采用哪种机制、由谁执行、如何等待、取消、合并请求与清理；同步逻辑也应明确为同步 |
| 生命周期 | 哪些 Unity 回调承担绑定和释放，哪些业务动作只能显式调用；不得用未定义的回调顺序掩盖依赖 |
| 数据组织 | 关键集合、索引、排序和复制方式；依据查询与更新需求确定，不默认全部使用同一种容器 |
| 继承与组合 | 基类与接口的实际协议、扩展点和替代关系；组件化不等于必须采用某一种 Unity 技术框架 |
| 资产与持久化 | 编辑器配置、运行状态、存档结构之间的转换；实际序列化机制及可保存的引用种类 |
| 资源和场景 | 具体加载 API 或项目适配接口、句柄和实例的所有权、失败与取消后的释放 |

涉及共享基础设施的机制应统一决定，其余类引用确定的协议。采用自建薄封装、第三方包或引擎原语时，都应解释项目职责与引擎职责，不把“已有原语”理解为禁止任何项目适配层。

### 6.3 技术名称必须连到实际语义

例如使用 Unity 协程，就不能只写“协程加载”：需要写出宿主、入口、等待条件和中止后的清理。Unity 文档说明协程可跨帧恢复，且并非线程；宿主 GameObject 停用与仅禁用 MonoBehaviour 的停止行为也不同。因此，宿主与启停关系会直接影响设计是否正确。[Unity 协程文档](https://docs.unity3d.com/6000.0/Documentation/Manual/Coroutines.html)

使用 ScriptableObject 时，要说明配置资产与运行实例的关系；它是可以被多个对象引用的数据资产载体，不应仅因“能保存数据”就推导为局内状态或存档方案。[Unity ScriptableObject 文档](https://docs.unity3d.com/6000.0/Documentation/Manual/class-ScriptableObject.html)

使用 C# 事件时，需要确定如何取得发布者引用、处理器签名以及解除时机；发布者持有处理器引用，订阅对象的释放与解除协议有关。[Microsoft 订阅与解除文档](https://learn.microsoft.com/en-us/dotnet/csharp/programming-guide/events/how-to-subscribe-to-and-unsubscribe-from-events)

上述是要求技术设计达到的深度，不是本轮替全项目定下协程、资产或事件实现。规范应要求选出可执行方案，而非规定每个类都必须使用这些机制。

## 七、彻底解决单类稿的独立阅读问题

建议同时区分“权威维护稿”和“交付给执行者的单类分发稿”。

权威维护稿保持唯一声明。分发稿包含目标类本体及它实施所需的必要契约摘录，摘录标明来源、符号和内容标识，作为只读交付内容。可先用普通文档整理，无需先建设专用生成工具。

建议分发时保证以下信息在本份交付中可得到：

- 本类实际适用的玩法规则、公式、限制与异常结果；不能只写上游章节号。
- 本类完整字段、签名、状态、不变量和技术机制。
- 每项外部依赖实际用到的方法、参数、结果和失败语义。
- 这些签名涉及的必要自定义类型、枚举、取值、单位和约束，直到不再需要追读其他项目设计。
- 本类的实例来源、依赖绑定和终止职责。
- 用来判断本类行为正确的具体输入与期望结果。

不要求复制其他类的实现，也不要求重写 C# 或 Unity 教程。标准库和框架类型可以沿用已声明的技术基线；但本次选择所依赖的特殊生命周期或线程语义，要在稿内说明。

摘录的维护规则建议是：只有来源能修改契约；执行者发现缺口时反馈来源；来源改变后重新核对受影响的分发稿。已有分发稿只代表生成或整理时的那一组内容，不能与另一个来源状态的材料混用。这样满足单类阅读要求，同时避免多个使用方各自维护不同定义。

这需要把 NR-06 的“只引用、不得复制”改为：维护定义只在唯一位置，交付允许带来源的受控摘录。游戏规则的引用同样处理；不能把“唯一事实来源”理解为执行者必须不断跳转。

## 八、把方法流程和算法选择的边界重画清楚

建议撤销“出现遍历、查找、排序就越界”的词语式禁令。判断应看这项决定是否会改变程序结构、可观察行为或协作协议。

| 内容 | 建议落点 |
| --- | --- |
| 提交状态后再发布事件；失败时不发成功通知 | 代码设计必须确定 |
| 分发前取订阅者快照，回调期间修改订阅表如何生效 | 代码设计必须确定 |
| 路径选择策略、等价路径的稳定顺序、随机消费点 | 影响玩法结果或确定性，代码设计必须确定 |
| 关键索引结构、算法复杂度目标、批量与逐项提交的取舍 | 影响实施结构，代码设计必须确定 |
| 在已定策略下怎样展开 for/while、如何命名局部变量 | 伪代码展开 |
| 逐行填完全部函数体 | 不作为代码设计的普遍交付要求 |

核心流程应从模块级接口串联推进到“具体实例的方法调用与状态提交”。需要跨帧时标出等待边界；需要原子性时标出提交点和回滚范围。这样保留伪代码的工作，同时不会把关键结构决策再次后移。

## 九、用一个局部示例检验重订方向

以下只用于说明新要求的实施深度，不是事件总线的项目定案。

旧稿写“Subscribe 接收事件名、订阅方标识和响应职责，随后按订阅表通知”，仍然缺少可调用协议。新要求下，可以讨论如下候选：

```csharp
SubscriptionToken Subscribe<TEvent>(Action<TEvent> handler);
void Unsubscribe(SubscriptionToken token);
PublishResult Publish<TEvent>(TEvent payload);
```

如果采用该候选，就还需要把这些决定写完：

| 问题 | 示例中的候选决定 |
| --- | --- |
| 类型和实例 | 运行期分发器为普通 C# 类，由装配对象创建并注入；资产维护工具独立承担编辑期职责 |
| 订阅标识 | 由分发器生成不重复的订阅标识；token 的具体字段与跨分发器误用行为有唯一声明 |
| 订阅方持有什么 | 订阅方持有 token，并在其作用域结束时显式解除；重复解除无副作用 |
| 线程与分发时点 | 候选为主线程同步分发；其他线程不得直接调用；是否采用这一限制须结合发布来源核查 |
| 回调期间修改订阅 | 当前发布使用已取得的订阅快照；新增订阅从下一次发布生效；已经排入当前快照的订阅本次仍被调用 |
| 嵌套发布 | 示例候选拒绝分发期间的嵌套发布，并返回明确结果；实际选择要结合调用链决定 |
| 处理失败 | 单个处理器异常被记录，继续通知剩余项；不回滚发布方状态 |
| 结果与约束 | `PublishResult` 给出成功送达和失败项的明确字段；事件登记与唯一发布方约束仍需另行闭合 |

这里的签名也不是完整单类稿：token、结果类型、字段结构、依赖和发布权限还没有全部声明，所以不能把这个示例直接标为“可实施”。它展示的是需要作出决定的内容，而不是用一段代码片段替代完整设计。

对资源服务也应采用同一判断。尤其要重新检查“在途加载记录不跨帧保留”：若真实加载跨帧完成，就必须明确等待状态存于何处以及由谁终止，不能同时保留互相矛盾的生命周期要求。

## 十、把验收改为可独立实施与可共同集成

建议保留编号、链接、结构检查，将主验收改为以下四项：

| 验收 | 具体检查方式 | 未通过意味着什么 |
| --- | --- | --- |
| 功能覆盖 | 从上游功能逐项追到具体类型与方法；从方法反查实现依据 | 存在无人实现的功能或没有依据的新增职责 |
| 单类阅读 | 仅给出单类分发稿，尝试声明字段、方法、依赖并展开一条成功与失败路径 | 仍需要其他设计材料或新的结构决策，不能交付 |
| 双方契约 | 将调用、返回、事件发布与订阅两端逐项比对；核对自定义类型和结果语义 | 单类各自看似完整，但无法连接 |
| 实例与生命周期 | 沿创建、注入、运行、替换、取消和释放走查；按需求补存档恢复等路径 | 存在未创建的对象、引用悬空、重复订阅、资源无归属或状态丢失 |

建议选择能暴露真实分支的场景走查，例如重复订阅、回调中解除、两个请求共享一次加载、等待方取消、读档替换状态。只为相关能力选择适用场景，不要求每份数据声明都附一套无意义的异常流程或执行测试。

完成状态至少区分“仍有设计缺口”和“可独立分发”。影响本类字段、签名、所有权或执行机制的待定项存在时，本类不能进入后一个状态。一个无关系统的远期未决不应阻塞全部文档。

“可独立分发”只证明设计输入充分；仍须在后续实际代码阶段编译、测试和运行验证。不能把文档自检写成已经证明代码可运行。

### 11.3 架构案中需要核查的相关约束

第一步保留的架构边界仍应遵守，但本次目标允许重新审查妨碍实施的抽象条款。建议在后续架构变更范围内核查：

- “第三方包和版本留给实际代码”是否需要改为在技术实施设计完成前确定相关依赖。
- “临时运行对象不得跨帧”应限定到真正的同步临时量；异步操作上下文需要有可表达的所有者与终止条件。
- “不得重复引擎能力”应区分重复造机制与必要的项目协议适配、生命周期管理和业务集成。
- 事件类型契约、唯一发布方、登记表、运行期分发与测试检查之间，是否存在相互冲突的执行要求。

这些是建议核查和变更的对象，不表示当前约束已自动失效。发现实质冲突时，应给出具体影响与替代方案，不能在类稿里静默绕过。

## 十二、重构规模与第三步的交付边界

建议采用“重建结构、复用事实”的方式处理旧库：需求、状态、所有权与经核实的行为结论进入新稿；重复的原则说明、同义契约和纯编号堆叠不按原结构搬运。旧 `CLS-*` 逐项判断它究竟对应类型、字段、资产记录还是派生结果；一个旧编号拆成多个类型时登记明确映射，不能按数量硬凑类。

建议第三步的新规范至少解决八件事：新的阶段职责、类型拆分依据、实例与装配要求、准确成员协议、Unity 技术选型深度、共用契约与独立分发、未决与完成状态、实施与集成验收。并附少量可判断正误的技术示例，避免第三步再次只交一套抽象章节标题。

后续可选事件分发、资源加载和一个元对象组件族验证规范覆盖面：它们分别暴露通信、异步生命周期和组合模型问题。这样的局部验证用于检验新规范是否足够，不代表本轮已开始代码设计案重构。

应同时避免三种新的偏差：每个能力都建独立服务与工厂、每个类都挂场景脚本、每份简单数据稿都套完整系统模板。重构的完成尺度是关键决定已经落定，且单类输入可独立使用，文档数和类数量都不作为成果指标。

本轮第二步到此完成。下一步是据此编制新规范正文；全库重构命令及实际分发安排仍属于第四步。
