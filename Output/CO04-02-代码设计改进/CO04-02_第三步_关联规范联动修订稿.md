## 5. 游戏规则、技术设计与规范的边界

替换正文：

# 七、六层文档的职责边界

## 1. 阶段与产物

| 阶段 | 核心问题 | 核心产物 |
| --- | --- | --- |
| 创意需求稿 | 为什么做，追求什么体验 | 理念、体验与产品特征 |
| 系统设计稿 | 游戏规则与玩家行为是什么 | 完整规则、状态含义与业务边界 |
| 架构设计案 | 程序作为整体应遵守什么结构 | 全局模块、程序集、公共机制、所有权和生命周期约束 |
| 代码设计案 | 在约束内怎样落实到具体实现 | 类型、实例、成员、装配、技术机制与准确协议 |
| 伪代码 | 已定程序结构中的方法体怎样执行 | 分支、循环、状态更新、调用与清理步骤 |
| 实际代码 | 怎样完成工程并确认可运行 | 实际源码、工程绑定、编译与运行验证 |

## 2. 输入关系

系统设计提供游戏规则，架构设计提供全局结构约束。代码设计同时依据两者，形成类级实施规格；伪代码依据已定类型与协议展开方法体；实际代码完成工程实现。

代码设计必须遵守现行架构。局部类型与技术选择由代码设计完成，共享机制按架构统一约束。发现冲突时，明确影响和变更建议，不能在类型稿中静默绕过，也不能把所有局部技术问题推回游戏策划。

## 3. 内容归属

| 内容 | 主要定义位置 |
| --- | --- |
| 体验理念 | 创意需求稿 |
| 游戏规则、玩家状态含义、公式 | 系统设计稿 |
| 全局模块、程序集方向、公共入口、跨域所有权和生命周期约束 | 架构设计案 |
| 实际类型、接口、字段、容器、继承与组合、实例装配、引擎调用机制 | 代码设计案 |
| 方法协议、必要算法策略、确定性与提交时序 | 代码设计案 |
| 函数体的具体分支、循环和局部辅助步骤 | 伪代码 |
| 语法、工程接线、平台实现、编译与运行证据 | 实际代码及其验证记录 |

跨层引用不转移定义权。下一层可以整理其实施所需的已定内容，不得改变上层规则。单类材料的只读契约摘录按《代码设计案编辑规范》第十二章执行。

## 4. 各层边界

系统设计稿不得提前绑定具体工程和引擎 API。架构设计案不承担全部类型与成员的详细定义。代码设计案必须确定影响结构和协作的选择，不以“具体实现”之名整体后移。

代码设计允许 C# 类型与声明、容器、引擎基类、回调签名及必要算法说明。是否越界根据该内容承担的职责判断，不按“出现语法、查找或遍历”等词语判断。

伪代码可以决定不改变成员、状态结构及跨类协议的局部写法；需要改变已定结构时先更新设计。实际代码阶段仍须验证设计，不能以设计已可分发替代编译与运行结果。

## 5. 落点与规范

| 文档 | 落点 | 规范 |
| --- | --- | --- |
| 创意需求稿 | Input 与 Output 下的相关材料 | 本规范相应体裁要求 |
| 系统设计稿 | 系统设计文档 | 本规范及《文档库组织规范》 |
| 架构设计案 | 架构设计文档 | 《架构设计案编辑规范》 |
| 代码设计案 | Code_Design | 《代码设计案编辑规范》及《文档库组织规范》第七章 |
| 伪代码 | 具体任务指定的交付位置 | 已定类型与协议，以及相应任务要求 |
| 实际代码 | 目标源码工程 | 工程规范与实际验证要求 |

### 2. 整体替换第七章

替换正文：

# 七、代码设计案库的组织

代码设计案库位于 `Code_Design/`，内容、交付与验收按《代码设计案编辑规范》执行。本章规定目录、命名与索引。

## 1. 目录结构

```text
Code_Design/
├── README.md
└── {模块编号}-{模块名}/
    ├── 00_实现总览.md
    ├── Types/
    │   └── {类型文件键}代码设计案.md
    └── Contracts/
        └── {契约文件键}契约.md
```

模块沿用架构已登记的模块；跨模块使用的通用能力放在其明确的所属模块，不为方便放文件而擅自新增架构模块。模块目录是维护归属，不等同于程序集；程序集在类型元信息中登记。

`Types/` 放主要实现类型，`Contracts/` 放共享接口、请求、结果、载荷、标识及枚举的唯一声明。一个共享类型的契约文件就是它的类型稿，不再在 `Types/` 复制一份。

仅服务单一主要类型的简单附属声明可以写在其稿内。规模不需要时可以省去空目录，也不要求每模块都有公共契约文件。

## 2. 文件键与命名

类型文件键使用类型名；本目录存在同名类型时加命名空间区分，泛型名称使用名称加 `_g{参数个数}` 表达，避免将尖括号写入文件名。若仍冲突，采用明确且唯一的文件键，并在索引中登记与完整类型名的映射。

文件名、标题与权威维护稿的元信息不带历史版本号。文件历史由 git 承载；交付材料的内容标识用于识别来源集合，不是另建历史副本的理由。

## 3. 索引与状态

库 README 必须能定位实现总览、类型稿和共用契约。类型索引至少列出：主要类型完整名、所属模块、程序集、定义文件、预期或实际源码路径、状态和主要依赖来源。一个符号只能有一个权威定义落点。

状态取值和可分发条件由《代码设计案编辑规范》第十四、十五章定义，索引只登记现状。新增、改名、拆分、停用和改变状态时同步索引与实际使用点。

## 4. 与上游的关系

玩法系统与程序类型采用多对多映射，映射写在实现总览。系统编号用于追踪规则来源，不能限制类拆分，也不要求为了拆类先改变系统设计库结构。

## 5. 分发视图与过渡

权威类型稿已经含足够依赖摘录时可以直接分发。任务需要整理独立分发稿时，放在该任务的 Output 子目录，按《代码设计案编辑规范》第十二章登记来源和内容标识；权威定义不能反向依赖一次性交付文件。

既有系统稿目录和旧状态在实际迁移前据实保留，不因采用目录规则而宣称已重构。旧条目应标明尚未按新规范核验；实际迁移、停用和删除须在相应任务授权范围内执行。

### 3. 补充 §四.7 引用边界

新增正文：

## 四、NR-07《架构设计案编辑规范》

### 1. 更新 §三.7 的第三方选型说明

### 2. 修改 §四 禁止项表中的算法说明

原第三项改为：

| 3 | 展开函数体 | 逐行描述某类型方法的全部执行步骤 | 架构确定跨模块协作与全局策略；类型的必要算法选择由代码设计确定，方法体由伪代码展开 |

### 3. 替换 §六.1 的衔接例子及说明

替换正文：

架构设计规定全局结构与公共入口约束；代码设计把这些约束落到具体类型、准确接口与实例装配；伪代码在既定结构中展开方法体。

例如架构规定存档必须经过公共服务，代码设计需要确定本类所使用的存档接口及其参数、结果、失败语义和取得方式，伪代码再展开本类对该接口的调用与分支处理。接口名与箭头本身不能代替完整契约。

### 4. 整体替换 §八.4

替换正文：

架构设计案提供全局约束。代码设计案按实际类型组织，玩法系统与程序类型可以多对多对应；两者通过模块归属、程序集边界、所有权、技术机制和需求映射联系。

架构的模块边界与技术约束是具体实施设计的输入。代码设计不得改写架构约束；发现现行抽象约束妨碍必要实现时，应提出有具体影响和替代方案的变更建议。

## 六、与实际架构和旧代码设计库的边界

上述文本解决规范分工与目录冲突，不自动改变实际架构案中的全局决定，也不自动迁移 Code_Design。尤其是第三方版本归属、临时对象跨帧、引擎机制与项目封装的分工及事件登记语义，须在后续实际设计重构中逐项核实并处理。

本轮仅提供规则正文与联动替换稿，不编制第四步的执行命令、不分发子代理任务，也不将示例接口当作项目公共契约。
