## 一、目标与完成尺度

代码设计案必须完成影响程序结构和对象协作的技术决定。其输出必须使执行者能够仅凭收到的单类分发稿，编写目标类的伪代码。

可独立分发的类稿必须同时回答：

1. 该类承接什么需求，采用什么类型、成员和数据结构。
2. 运行中存在多少实例，谁创建、初始化、持有和终止它们。
3. 每个方法怎样进入，读取和修改什么，何时完成，成功和失败产生什么。
4. 如何调用外部依赖、收发事件、等待异步结果及完成清理。
5. 采用哪些语言、引擎或包机制，以及相应技术基线和约束。
6. 用哪些具体输入与期望结果判断设计是否正确。

不能回答其中适用问题时，必须登记具体缺口及其影响，不能以篇幅、模板齐备或对象编号数量判定完成。

## 二、阶段边界与决策责任

### 1. 相邻阶段分工

| 阶段 | 承担的决定 |
| --- | --- |
| 系统设计 | 玩家规则、游戏行为、状态含义、公式和业务限制 |
| 架构设计 | 全局模块、程序集方向、公共机制、数据所有权和全局生命周期约束 |
| 代码设计 | 具体类型、实例、成员、数据结构、技术机制、协作协议及必要算法策略 |
| 伪代码 | 在已定结构和协议内展开方法体、分支、循环、状态更新和清理逻辑 |
| 实际代码 | 完成语法、工程绑定、编译、测试、调试和运行验证 |

系统设计与架构设计分别提供规则与结构约束。代码设计必须结合两种输入，不能仅将系统设计稿改写为程序术语，也不能用一个模块名代替模块内的类型设计。

### 2. 技术决策

在已授权的技术设计范围内，执行者必须自行完成类拆分、字段、容器、方法签名及适用机制的选择。重要取舍写明约束、采用结论、理由和受影响类型；简单且无争议的选择不要求另写方案比较报告。

涉及公共契约或全局机制的选择，必须在其共同影响范围内统一决定。不得由多个类的执行者分别发明互不兼容的协议。

改变游戏规则、取消用户决定或超出现有架构约束的方案，必须单列冲突和变更建议；未取得相应授权时不得作为正式实现前提。冲突只阻止受影响的设计完成，不要求无关类型一律停工。

### 3. 方法体边界

允许使用 C# 类型、声明、容器、继承、回调签名、算法名称和必要的顺序说明。影响可观察结果、确定性、所有权、复杂度或跨类协议的算法策略必须先确定。

伪代码可以决定局部变量、循环写法，以及不增加持有状态、不改变外部协议的私有辅助逻辑。若需要改变签名、状态成员、跨类依赖或执行机制，必须先更新设计来源。不得把这类改动隐含在方法体中。

## 三、设计单位与文档视图

### 1. 类型与系统的关系

代码设计以具体类型为结构单位，以有行为的类为主要实施单位。玩法系统与程序类型允许多对多对应，系统编号用于需求追踪，不限制类型拆分与组合。

拆分依据包括职责变化原因、持有状态、生命周期、执行环境和依赖边界。不得为满足文件数量而拆类，也不得把多个独立职责全部压入一个系统服务。

类、接口、结构体、枚举、委托、配置记录和某类字段必须区别登记。一个旧数据项并不必然对应一个新类。

### 2. 三种视图

| 视图 | 必须交付的内容 | 定义权 |
| --- | --- | --- |
| 实现总览 | 需求到类型与方法的映射、类型清单、实例装配、关键协作、共用技术决定及未决影响 | 维护该范围的协作与共同决定 |
| 类型设计稿 | 一个主要类型的结构、成员、生命周期和行为，及其独立实施所需的局部规则 | 维护该类型及成员 |
| 共用契约 | 跨类使用的接口、标识、请求、结果、枚举、载荷及其语义 | 维护每个共享符号的唯一声明 |

共用接口或数据类型自身的类型稿可以就是共用契约。不得同时为同一接口建立两个独立维护的声明。

单类分发稿是类型稿加必要摘录的交付视图，其具体内容按第十二章。实现总览不是单类稿的替代物；分发稿也不另立一套设计权威。

### 3. 附属类型与身份

仅供一个主要类型使用的简单数据类型，可以在该类型稿内声明。跨类共享或独立维护的类型必须有明确的唯一来源。

类型身份至少包括完整限定名、泛型参数和所属程序集；方法身份包括所属类型、方法名及参数类型，重载不得混淆。既有 `CLS-*`、`API-*` 编号可以作为稳定追踪标识，不能代替实际类型和签名。

对象撤销或拆分时必须登记承接关系，旧编号不复用。一个概念只对应某字段或配置记录时，应指明其落点，不能继续伪装成可实例化类型。

## 四、实现总览与需求覆盖

实现总览必须包含下列内容：

| 内容 | 要求 |
| --- | --- |
| 范围与输入 | 列出覆盖功能、上游规则和适用架构约束；说明相关缺口 |
| 技术基线 | 引用已定基线和本范围补充选择，内容见第五章 |
| 需求映射 | 每个功能指向实际类型和方法；多个参与者必须明确主要实现方与协作职责 |
| 类型清单 | 类型名、类型种类、程序集、设计落点、目标源码路径、负责内容和状态 |
| 实例装配 | 创建、注入、持有、就绪和终止的具体关系 |
| 关键协作 | 至少覆盖该范围的主成功路径及会改变协议的失败路径，写到实例角色与方法一级 |
| 未决影响 | 哪些类型受影响、缺少什么决定、关闭条件是什么 |

需求映射应当能双向核对。每个已定功能都有承接方法；每个新增业务职责能说明依据。构造、释放、适配和校验等工程职责可以依据结构与技术约束，不要求伪造策划需求编号。

总览可以按模块或能力组织。跨模块功能要明确协作关系，但不得因其跨模块而重复定义对方类型的成员。

## 五、技术基线与机制选择

### 1. 技术基线

基线必须写明与本范围有关的 Unity 版本、目标平台、编译与运行约束、相关包及版本。项目已有工程时以实际工程为依据；尚未建立工程时登记拟采用基线和可用性核查依据，不得伪称已安装或已验证。

只要求登记实际采用的技术。使用版本敏感 API 的类型，在适用版本未确认前不能标记可分发；无关普通逻辑类型可以依据已明确的编译环境继续完成。

### 2. 选择结果

每个相关能力必须确定具体机制或准确的项目适配接口，并标明由哪个类型实现。只写“使用引擎能力”“广播通知”“异步处理”不构成选择结果。

| 主题 | 必须写明的适用决定 |
| --- | --- |
| 类型承载 | 普通 C# 类型、MonoBehaviour、ScriptableObject 或其他机制各承担什么 |
| 继承与组合 | 具体基类、接口及其协议，组合对象和替换边界 |
| 通信 | 直接调用、事件通道、委托、UnityEvent 等的实际使用位置与签名 |
| 跨帧执行 | 采用的机制、执行宿主、完成通知、取消与清理 |
| 数据与算法 | 关键集合、键、顺序、索引、查询和更新策略；需要确定性的顺序与随机消费点 |
| 配置与存档 | 配置载体、运行期形态、存档机制和标识恢复规则 |
| 资源与场景 | 具体加载入口、句柄与实例归属、释放和失败处理 |

选型必须符合架构中的程序集与数据边界。引擎提供原语时，项目仍可承担必要的协议适配、记账与生命周期管理，但必须说明职责差异。不能用自建实现绕过已定公共入口。

### 3. 技术证据

版本敏感能力和不确定的引擎行为应核对适用版本的官方资料或实际工程证据。记录足以支撑所采用语义的出处，不能用一个 API 名称或搜索摘要代替可用性结论。

使用协程、引擎回调、线程或异步机制时，必须把影响设计的启动、恢复、终止及线程语义写入相关类型稿。标准库和 Unity 基础知识不要求全文抄录。

## 六、类型结构与数据成员

### 1. 类型元信息

每份类型稿至少包含以下元信息：

| 字段 | 内容 |
| --- | --- |
| 主要类型 | 完整限定名与泛型参数 |
| 类型种类 | class、interface、struct、enum、delegate 等；相关修饰符 |
| 所属范围 | 程序模块或能力；上游系统可以列多个 |
| 所属程序集 | 实际或已决定的目标程序集及引用限制 |
| 目标源码路径 | 实际路径或已决定的预期路径，不能伪称文件已存在 |
| 定义来源与需求 | 上游来源、实现总览及已有追踪编号 |
| 状态 | 按第十四章登记 |
| 更新日期 | 最后实质修改日期 |

### 2. 类型关系

必须准确列出基类、实现接口、泛型约束及关键组合关系。不采用某种关系时说明为无，不得留下多种候选供伪代码执行者选择。

继承必须能说明基类提供的成员和派生类负责的实现。泛型必须说明参数的语义及可用操作。采用普通对象组合时，必须给出持有成员和创建来源。

### 3. 字段与属性

所有跨方法调用存续的设计状态必须有明确成员归属。每项列出名称、准确类型、可见性、可变性、初值来源、含义与不变量；属性还要说明是否可写和计算来源。

标识要说明有效范围、唯一性、缺省值与比较规则。数值要说明单位、范围、取整或溢出处理。对象引用要说明空值、借用或拥有关系，以及能否跨作用域保留。

集合必须说明键与元素类型、是否允许重复、缺项语义、顺序保证、复制方式及修改入口。依赖稳定顺序时必须定义该顺序，不能依赖未承诺的集合枚举行为。

派生缓存必须说明来源、有效期、失效和重建触发，以及能否持久化。不得同时把一项数据称为派生结果又让其成为另一个权威来源而不说明依据。

### 4. 数据类型

数据类、结构体、枚举和载荷必须列全本协议要求的字段、值及含义。请求和结果必须区分接受、完成、拒绝、失败等适用状态，不能只给一个没有字段的 `Result` 名称。

附属类型按同样标准声明，但可以使用简短表格。纯数据类型不要求编造内部服务、场景挂载或独立状态机。

## 七、实例、生命周期与装配

每个可实例化的行为类型必须明确以下内容；无实例的静态能力说明调用与状态范围。

| 项目 | 必须回答 |
| --- | --- |
| 数量与作用域 | 每进程、每局、每战斗、每实体、每操作等实例数量规则及唯一性范围 |
| 创建与注入 | 哪个具体类型或调用者的哪个入口创建；依赖经构造、绑定方法或其他已定方式取得 |
| 持有关系 | 哪个成员保存引用；哪些对象由本类拥有，哪些仅借用 |
| 业务初始化 | 分配对象、注入引用与业务启动的先后顺序；就绪条件 |
| 正常使用 | 谁可以调用、从什么状态进入、是否允许重入 |
| 终止与替换 | 正常结束、取消、读档替换、场景退出或池回收时的适用处理 |
| 失败清理 | 初始化或运行失败后，订阅、句柄、状态和等待方由谁处理 |

必须将 C# 类型继承、Transform 父子层级、玩法组件与 Unity Component 分开描述。

Unity 脚本必须说明具体挂载位置、序列化引用和绑定方式，以及适用回调承担的职责。显式业务初始化不能仅写为“在 Awake/Start 中处理”而不说明依赖顺序和就绪条件。

普通 C# 规则对象必须说明与承载脚本或装配对象的连接；“不依赖场景”不能替代创建与持有关系。配置、运行状态、存档 DTO 和表现实例必须通过明确标识或引用关联。

涉及异步操作时，跨帧上下文必须有实际所有者和终止条件。若现行架构不允许其存续，登记冲突并提出替代或修订方案，不能假装上下文不存在。

## 八、成员签名与行为契约

### 1. 成员清单

行为类必须列出构造、初始化、业务方法、事件与回调、关键内部方法和适用的终止入口。每项明确可见性、静态或实例、参数、返回值、泛型约束，以及同步、迭代器或异步形式。

接口契约必须说明实现方的责任。实现类说明如何满足协议，不另行维护一份不一致的接口声明。

### 2. 方法契约模板

每项公开方法及会决定状态、协作或生命周期的重要内部方法，按以下内容展开。可以合并表达重复信息，但不能省略适用语义。

| 项目 | 内容 |
| --- | --- |
| 准确签名 | 所属类型、成员名、参数类型、参数修饰符及返回类型 |
| 职责与触发 | 谁在何时调用，本次方法负责的结果 |
| 输入与读取 | 参数、成员状态、配置和外部查询；单位、范围、空值及读写权限 |
| 前置与拒绝 | 允许状态、输入校验、拒绝结果；是否发生任何变化 |
| 成功结果 | 返回值、修改成员、创建或释放对象及不变量 |
| 协作顺序 | 准确依赖方法、状态提交点、通知时点及必要算法策略 |
| 执行语义 | 何时返回与完成；线程、等待、重入和并发约束 |
| 失败与清理 | 可预期失败、异常传播或转换、部分成功、回滚、取消及释放责任 |
| 验收场景 | 决定性输入及期望输出和状态；可以引用本稿内的统一场景表 |

状态修改、事件、副作用和异常不得在不同段落采用相互冲突的解释。前置条件未满足时究竟拒绝、忽略、排队或抛异常必须确定。

### 3. 算法与协作深度

必须确定影响结果与协作的策略，例如稳定排序、路径的等价选择、随机消费顺序、提交与通知先后、批量原子性和回调期间修改集合的生效时点。

函数内部逐行步骤不是统一必交内容。只有为消除关键歧义需要时，才附局部伪代码或声明片段。方法体允许怎样展开以第二章的边界为准。

## 九、依赖、事件与交互协议

### 1. 外部依赖

每项依赖必须给出实际类型或接口、使用的准确成员、取得方式、读写权限、生命周期责任及失败语义。调用方的声明必须能在来源中找到对应定义。

程序集依赖与运行期对象引用需要分别核对。接口抽象的放置必须符合项目架构；不得让纯逻辑类型仅为调用一个服务就引用被禁止的承载或表现程序集。

### 2. 事件协议

每类事件和每组订阅必须说明：

- 事件或载荷类型、完整字段、语义、发布入口与有权发布者。
- 订阅方式、处理器签名、订阅凭证、重复订阅的定义与结果。
- 建立与解除订阅的拥有者及生命周期时点，重复解除的处理。
- 同步或延后分发、处理线程、顺序保证及嵌套发布规则。
- 分发期间新增和解除订阅对当前及后续发布的影响。
- 单个处理器失败后是否继续、错误如何报告、是否影响发布方。

“响应职责”不能代替回调协议。“随界面解除”不能代替准确的解除入口、凭证和调用者。采用回调集合、C# event、UnityEvent 或项目通道时，都要按相同语义要求描述。

### 3. 跨类流程

流程按“触发 → 实例方法 → 结果与状态提交 → 通知或下一调用 → 完成/失败”书写。涉及异步的步骤标出等待与恢复边界，涉及事务的步骤标出提交和回滚范围。

不得只用模块名、系统名和箭头证明接口已经闭合。

## 十、跨帧、异步、资源与取消

只有涉及这些能力的类型需要本章内容；纯同步类型声明同步完成即可。

| 主题 | 必须确定的内容 |
| --- | --- |
| 执行机制 | 具体协程、异步 API、回调或项目接口；执行宿主与线程 |
| 操作身份 | 操作或请求怎样识别，同一请求是否可以重复发起 |
| 跨帧状态 | 在途对象的字段、拥有者、可用期限和结束清理 |
| 完成结果 | 接受与完成的区别；成功、失败、取消何时通知、能否重复通知 |
| 共享操作 | 合并哪些请求，每个等待方如何登记；一个等待方取消是否影响其他方 |
| 取消与迟到结果 | 谁发起取消、传播到哪里、底层不能取消时怎样丢弃结果或释放资源 |
| 资源归属 | 谁持有句柄、谁实例化、谁释放、重复释放如何处理 |
| 异常和中断 | 超时、依赖失败、宿主启停及场景切换时的适用路径 |

采用引用计数或租约时，增加与减少计数、去重与重复释放的依据必须能由具体操作身份解释。不得把“两个请求共用加载”误写为只有一份使用责任，也不得在回调已失去接收者后仍无条件写入其状态。

只有需求或技术约束需要时才设超时与重试；一旦采用，必须写清触发条件、计时依据、次数或终止条件，不能在文档中暗示自动重试却不给出协议。

## 十一、配置、组件模型与持久化

### 1. 配置与运行状态

配置资产、运行期只读内存形态、运行期可变状态及存档数据必须区分。说明加载、校验、转换、版本关联与数据所有者。共享配置不能因实例变化被意外修改。

采用 ScriptableObject 或其他配置形式时，应说明资产与运行实例的关系，不能仅以“可序列化”推导其就是存档方案。

### 2. 组件模型

对于元对象、元技能等组合模型，必须明确组件定义、运行状态与行为执行器是否为不同类型，采用什么挂载结构，怎样查询能力、建立初值、启用停用及恢复。

组件类别、允许挂载集合、互斥或重复规则、写入入口及新增组件时需要改变的落点必须明确。仅给一个组件族名称不能判为完成；也不强制每种能力对应一个 Unity 场景组件。

### 3. 持久化

需要保存的类型必须列出字段或明确的保存投影、DTO 类型、静态定义引用、判别值和恢复入口。明确不保存项、默认值、派生重建和版本不兼容处理。

同一字段是否入档只能有一个确定结论。需要恢复引用时说明标识解析与恢复顺序；需要稀疏增量时说明缺项如何解释和如何与静态定义合成。

保存与恢复的失败处理必须与项目的统一存档入口和提交语义一致。不能在类型稿内自行增加架构未允许的直接文件写入路径。

## 十二、单类分发稿与依赖摘录

### 1. 自足内容

单类分发稿必须包含：目标类型稿、本类适用的规则与公式、必要装配信息、全部实际使用的外部契约，以及验收场景。执行者应能只读本稿完成本类伪代码，不需要阅读其他项目设计文档。

依赖摘录必须覆盖参数和返回值中必要的自定义类型、枚举、字段、取值和约束，直到不再隐含“去别处查定义”。可以省去没有使用的成员，但不能省去理解已用成员所需的不变量和生命周期语义。

标准库及引擎通用知识按技术基线引用，不要求复制教程；影响本类行为的特殊时序、线程和生命周期限制必须在本稿可见。

### 2. 来源与一致性

摘录标明来源文件、章节或符号及内容标识。已提交内容可以使用提交标识；包含工作区改动时使用实际文本摘要或明确的交付批次标识，不能把 HEAD 当作未提交内容的标识。

执行者不得为补齐缺口而发明公共方法、字段、事件或结果类型。发现材料不充分时，返回具体缺项及其影响；已定的本类内部方法体工作可以继续。

## 十三、编制与修订方法

编制应当按以下依赖顺序完成，各项可合并执行，不要求每项另建一份过程文档：

1. 读取规则与架构，定位需求、既有技术决定和冲突。
2. 将功能分配到类型和成员，确认数据所有权与职责边界。
3. 统一共享契约和技术机制，决定实例装配与执行方式。
4. 完成类型结构、方法契约、必要策略和失败清理。
5. 核对关键协作链，补齐单类实施所需的依赖摘录。
6. 按第十五章验收，登记状态和影响范围。

共享契约与使用方可以协同完善。分发前必须形成一致的交付内容，不能把循环依赖的设计责任交给下游自行协商。

旧稿重构必须识别可保留的规则、状态、所有权和已验证技术决定，重新分配到具体类型。旧稿的十节、编号行数和文件边界都不作为新结构的硬约束。

## 附录 B：自足单类分发示例

### B.1 示例身份与边界

以下是独立教学示例 `WritingExamples.OrderedSubscribers<TEvent>`，不属于游戏代码，也不是项目事件总线定案。它只展示一份类稿如何把结构、实例与行为说清楚。可依据本附录编写该示例的伪代码，无需其他项目设计。

类型：`public sealed class OrderedSubscribers<TEvent>`，无项目基类、接口或泛型约束。命名空间 `WritingExamples`；示例程序集 `WritingExamples.Core`；预期源码 `WritingExamples/OrderedSubscribers.cs`，文件并未在本任务创建。

技术范围为 C# 7.3、.NET Standard 2.0 兼容基线下的普通同步类，使用 `System` 与 `System.Collections.Generic`，不引用 Unity、项目事件框架、资产、存档或外部服务。只接受单线程串行调用；调用者负责线程约束。`TEvent` 可以为值类型或引用类型，引用类型载荷允许为 null，类自身不修改载荷；订阅者应按只读输入使用它。

### B.2 需求与字段

需求：维护有序回调集合；发布时按订阅序号调用；各订阅独立解除；单个回调失败不阻止其余回调；不递归分发嵌套发布。

| 字段 | 类型与可见性 | 初值 | 语义 |
| --- | --- | --- | --- |
| `_handlers` | `private readonly Dictionary<long, Action<TEvent>>` | 构造时创建空集合 | 正数订阅号到非空处理器的映射 |
| `_lastId` | `private long` | 0 | 已分配的最大号，仅增加、不复用；上界为 `long.MaxValue` |
| `_isPublishing` | `private bool` | false | 从外层 Publish 进入分发直到退出期间为 true |

不变量：已登记号均在 1 至 `_lastId` 之间；一个号只对应一个处理器；同一委托重复订阅获得不同号；解除不会回退 `_lastId`。

附属公开类型放在同一示例源码内，且由本附录唯一声明：

| 类型 | 完整定义 |
| --- | --- |
| `WritingExamples.DispatchStatus` | `public enum`；`Completed = 0`、`ReentrantRejected = 1` |
| `WritingExamples.DispatchReport` | `public readonly struct`；公开只读属性 `DispatchStatus Status`、`int Attempted`、`int Succeeded`、`int Failed`；构造签名 `public DispatchReport(DispatchStatus status, int attempted, int succeeded, int failed)`，将四个参数原样写入属性，不自行验证组合 |

`DispatchReport` 由 Publish 保证：Completed 时 Attempted 等于本次快照长度且 Succeeded + Failed = Attempted；ReentrantRejected 时三个数量全为 0。非本类调用者自行构造的不合法报告不属于该保证。

### B.3 实例与生命周期

调用者通过 `public OrderedSubscribers()` 创建，构造完成即就绪；可以创建多个互不共享状态的实例。构造者持有引用并将同一实例提供给其订阅与发布调用者。

订阅号只在产生它的实例内有意义，调用者必须保存“实例引用 + 订阅号”，不能把另一个实例的号当作凭证。本类不尝试检测这种误用。

订阅者在其作用域结束前调用该实例的 Unsubscribe。集合持有处理器引用；本类没有 Unity 挂载、池回收或显式 Dispose。整个实例不再使用时，调用者结束对它的引用；本类不承诺进程退出时执行回调或收尾。

### B.4 完整成员契约

`public long Subscribe(Action<TEvent> handler)`：

- handler 为 null 时抛 `ArgumentNullException`，状态不变。
- `_lastId == long.MaxValue` 时抛 `InvalidOperationException`，状态不变。判断顺序为先判 handler，再判号耗尽。
- 成功时 `_lastId` 加一，将新号与 handler 加入 `_handlers`，返回新号。
- 允许同一处理器多次订阅；允许在回调中调用 Subscribe，新项不加入当前 Publish 的已有快照。

`public bool Unsubscribe(long subscriptionId)`：

- 删除该号当前对应的项；实际删除时返回 true，号不存在或非正数时返回 false。
- 重复解除不抛预期业务异常、不改变其他项；不减少 `_lastId`。
- 允许在回调中解除自己或其他项；当前快照已包含的处理器本次仍被调用，下次发布不再包含已解除项。

`public DispatchReport Publish(TEvent payload)`：

- `_isPublishing == true` 时立即返回 ReentrantRejected 及三个零值，不调用任何处理器、不改变外层分发标记。
- 否则设置 `_isPublishing = true`，复制当前 `_handlers` 为方法局部 `List<KeyValuePair<long, Action<TEvent>>>`，按 Key 升序形成快照。
- 逐个同步调用快照中的处理器，每个都接收同一个 payload。正常返回计 Succeeded；单项抛出 `Exception` 时计 Failed，继续处理其余项；本示例不调用日志服务，失败由报告计数表示。
- 快照为空时返回 Completed 及三个零值。正常完成时返回 Completed、快照长度与两项计数。
- 从设置标记后的整个范围都必须通过 finally 将标记恢复为 false。快照建立或排序等本类内部操作发生的非处理器异常不转换为报告，清理标记后向调用方传播；本类不承诺从内存耗尽或进程终止等情形恢复。

没有其他必需公共方法、事件或依赖。私有辅助函数可在伪代码阶段提取，但不得改变这些成员与语义。

### B.5 本稿内验收场景

| 输入及先前状态 | 期望结果 |
| --- | --- |
| 新实例依次订阅 A、B，再发布 | 返回号 1、2；按 A、B 调用；报告 Completed、2、2、0 |
| 订阅同一 A 两次，再发布 | 得到两个不同号；A 调用两次 |
| 解除号 1 两次，再发布 | 两次解除分别 true、false；已解除项不调用 |
| A 在回调中解除 B 并订阅 C | 本次仍按已有快照调用 A、B；下次快照包含 A、C |
| A 抛 Exception，B 正常 | B 仍被调用；报告 Completed、2、1、1；结束后可再次发布 |
| A 在回调中调用 Publish | 内层报告 ReentrantRejected、0、0、0；外层仍继续，不发生递归分发 |
| 新实例 Subscribe(null) | ArgumentNullException，集合与 `_lastId` 不变 |
