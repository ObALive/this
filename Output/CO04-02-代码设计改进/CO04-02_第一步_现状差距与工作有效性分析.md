## 一、核心判断

当前代码设计案已经积累了大量系统行为契约，但距离本次要求的“对象与实例层面的 Unity/C# 实现方案”仍缺一个完整的软件设计环节。

问题首先来自产物定位。现行规范要求编写者说明某个系统“必须有什么”，同时禁止固定类、容器类型和引擎基类。因此，执行者即使严格遵守规范，也会把关键结构决策留给伪代码编写者。用户希望下一阶段直接分发单一类，现行规范却把下一阶段设定成继续设计整个系统，两个完成判据不同。

这不是简单增加篇幅就能解决的问题。目前的进展大致是：游戏规则已有对应的状态、数据和接口描述；部分模块已有对象分类与生命周期描述；但具体类型、成员归属、实例装配、依赖注入、事件签名和异步执行方式尚未形成足够明确的实施契约。

“无效工作”在本文中指不能按当前目标直接形成交付价值，或持续投入会把文档带向错误方向。已有行为分析、对象识别和边界澄清仍有复用价值，不应整库抛弃。

## 二、差距具体在哪里

### 1. 系统职责已描述，系统内部的软件职责尚未分配完

现行 NR-06 第四章明确规定“基本单位是系统，不是类”，把“一个类 = 一个章节”判为错误；第十二章又要求与系统设计稿一一对应，不合并、不拆分。

证据：[NR-06 第四章](<D:/myspace/Git/this/Rules/06_代码设计案编辑规范.md:139>)、[第十二章](<D:/myspace/Git/this/Rules/06_代码设计案编辑规范.md:670>)；相同要求还存在于 [NR-05](<D:/myspace/Git/this/Rules/05_文档库组织规范.md:303>)。

这种组织有助于核对玩法覆盖，但不能直接代表代码分工。一个玩法系统可能需要定义对象、实例对象、规则服务、工厂、存储接口、界面适配器和异步宿主；一个通用类也可能服务多个玩法系统。把代码文档强制锁在玩法系统边界内，会让这些职责继续混在“本系统”中。

例如背包案列出了背包空间、调取范围、格位占用结论、写入目标序列和装载试算结果，并给出了“目标计算 → 试算 → 溢出组装 → 提交”的关系。但这些主要是数据或结果对象，尚不能据此判断哪个具体类负责执行计算、哪个类持有缓存、哪个实例接收调用，以及这些方法是否属于同一服务。

证据：[背包数据定义](<D:/myspace/Git/this/Code_Design/05-运营与经济/30_背包系统代码设计案.md:71>)、[内部功能关系](<D:/myspace/Git/this/Code_Design/05-运营与经济/30_背包系统代码设计案.md:246>)。

差距是“程序能力 → 实际类型及其成员”的映射尚未完成。列出许多 `CLS-*` 数据项，并不等于已设计出全部执行对象。

### 2. 对象分类已有，类型、实例和挂载关系仍混在一起

M01 拆成十一份成员对象文档，是有效进展。但“成员对象”仍可能是一组功能与多个类型的集合。例如 M01-02 一份文档同时承载三个数据域持有者，其接口定义还指向 01-50。它已经比通稿容易定位，却仍不是一份可直接分配给单一类的设计稿。

证据：[M01-02 单元说明与数据表](<D:/myspace/Git/this/Code_Design/00-架构单元/M01-02_数据域持有代码设计案.md:14>)。

现有生命周期表通常回答“常驻、随单局、随战斗、是否依赖场景”，但还需要能够回答以下实现问题：

- 这是具体类、接口、结构体、配置记录，还是某个类里的字段？
- 一个类型对应一个全局实例、每局一个实例，还是每个实体一个实例？
- 实例由哪个工厂或装配对象创建，谁保存引用，谁释放？
- 普通 C# 对象与 Unity 承载脚本之间怎么绑定？创建与业务初始化是否为同一时点？
- 同一对象的配置、运行状态、存档 DTO 和表现对象通过什么标识关联？
- 需要父子类时继承什么，不需要继承时采用什么组合关系？

“由常驻场景承载”不能单独回答以上问题；“不依赖普通场景”也不能说明具体承载类是否为 Unity 组件。

架构已经给出可保留的技术边界：权威状态由普通 C# 对象持有，Unity 对象承担承载、表现与编辑器配置职责，纯逻辑程序集不引用承载与表现程序集。这里缺的是边界内的具体实现分配，不应把所有领域类改成场景脚本。

证据：[程序集划分](<D:/myspace/Git/this/架构设计文档/架构设计案.md:183>)、[引擎侧约束](<D:/myspace/Git/this/架构设计文档/架构设计案.md:1408>)。

### 3. 技术环境确定了，关键技术机制未确定

Unity/C#、可寻址资源、显式初始化、状态与表现分离等已经出现在架构和代码设计案中，不能评价为完全没有技术决策。

但现行 NR-06 禁止引擎基类、容器类型，并称代码设计不涉及具体语言；CO04-01 的临时撰写口径继续禁止继承关系、字段类型、事件回调签名和具体序列化库，只允许增加承载类别与生命周期表。

证据：[NR-06 技术禁止项](<D:/myspace/Git/this/Rules/06_代码设计案编辑规范.md:123>)、[CO04-01 技术深度口径](<D:/myspace/Git/this/Output/CO04-01-代码设计改进/CO04-01_M01子文档撰写规范_v1.md:125>)。

这解释了上轮改进的上限：它补充了对象归属和存续范围，却有意避开本次要求明确的那些决策。

本轮对 `Code_Design/` 做关键词检索，未发现 `MonoBehaviour`、`ScriptableObject`、`UnityEvent`、`IEnumerator`、`Coroutine`、`协程`、`Dictionary`、`List<`、`Action<`、`Addressables`、`Resources.`、`SceneManager.` 的命中。关键词缺失本身不是不合格的充分证据；结合现行禁令与具体接口，说明文档目前主要停留在机制类别的表述。

例如资源服务规定了并发加载去重、同句柄返回、成组释放和失败结果，但 `Request` 没有具体返回类型、完成通知方式、等待方的保存方式、取消语义和执行宿主。对于已经存在的异步场景切换，执行者仍需自行决定这些对象与协议。

证据：[资源接口](<D:/myspace/Git/this/Code_Design/00-架构单元/M01-08_资源服务代码设计案.md:169>)、[架构异步切换](<D:/myspace/Git/this/架构设计文档/架构设计案.md:1148>)。

明确技术选型不意味着每个功能都要使用协程、继承或 Unity 事件。需要的是：需要这些机制的地方有明确决定，不需要的地方也能确定普通对象和显式调用如何完成工作。

### 4. 接口有行为含义，但缺少可执行的成员协议

最清楚的例子是事件分发器。

现有 `Subscribe` 输入为“事件名、订阅方标识、响应职责声明”，返回“订阅受理结果”。文档同时要求解除订阅，但接口和内部功能没有定义解除操作的区分参数、订阅凭证或独立解除接口。也没有说明“响应职责声明”如何映射为可以调用的回调或接收者接口。

证据：[Subscribe 契约](<D:/myspace/Git/this/Code_Design/00-架构单元/M01-11_事件分发器代码设计案.md:195>)、[内部订阅功能](<D:/myspace/Git/this/Code_Design/00-架构单元/M01-11_事件分发器代码设计案.md:278>)、[解除流程](<D:/myspace/Git/this/Code_Design/00-架构单元/M01-11_事件分发器代码设计案.md:437>)。

读者知道“发生订阅与解除”，却不能直接写出两个操作的伪代码签名。此外，“并发保护”未明确执行线程和重入规则，订阅方在回调内修改订阅表时如何处理也没有定案。

这些决定会影响调用方、数据结构和生命周期，不能由各个类的执行者分别选择。函数内部遍历的具体写法可以留给伪代码阶段，但回调协议、参数类型、解除方式和完成语义应先确定。

### 5. 引用可追溯，但单一类的阅读输入不自足

NR-06 要求引用外部对象 ID 与出处，不复制对方内容。这能减少重复定义，但对当前目标而言，仅有 ID 和路径还不够。

例如 M01-02 声明存档结构、切面和域入口在 01-50 定义；事件分发器使用 `API-SAVE-008` 读取阶段状态。如果单类稿只给出这些编号，执行者仍需打开别的文档，确认依赖方法的参数、返回类型、失败值和数据字段。

证据：[NR-06 引用要求](<D:/myspace/Git/this/Rules/06_代码设计案编辑规范.md:680>)、[M01-02 外部定义引用](<D:/myspace/Git/this/Code_Design/00-架构单元/M01-02_数据域持有代码设计案.md:83>)。

“唯一事实来源”和“独立编写单类伪代码”并不必然冲突。前者决定谁拥有定义权；后者要求交付给执行者的材料包含本类需要的准确契约。当前文档完成了追溯，尚未完成面向单类任务的契约整理。

独立性也不等于让一个类脱离全部依赖运行，更不等于复制依赖实现。需要自足的是编写本类所需的规则、依赖表面和协作协议。

### 6. 文档检查较强，实施完备性检查较弱

现行验收包含十节齐备、编号、输入输出分类、依赖引用和状态一致性。这些是有用的质量检查，但还不能证明每个功能已有具体类承接，或单类稿已经无需新的结构决策。

本轮发现的实际矛盾进一步说明了这一点：

| 对象 | 当前正文证据 | 实现影响 |
| --- | --- | --- |
| 事件订阅 | `Subscribe` 前置条件要求事件已有登记，异常条款却允许未登记事件继续受理；核心流程又要求先校验登记 | 执行者无法判断未登记事件应拒绝还是允许；解除协议也不完整 |
| 瓦片装配 | 数据表与 §2.7.3 把装配入口写成 `API-FIELD-114`，内部功能中该编号是 `BuildPresentationView`，装配接口为 `API-FIELD-115`；`CLS-FIELD-014` 至 `018` 的数据表行重复出现 | 同一对象可能调用错误能力；重复条目增加修订漂移风险 |

| 技能定义归属 | 库 README 声明 `CLS-SKILL-001` 至 `005`、`009` 停用；当前技能案仍在职责与数据表中使用这些编号，包括定义 `SkillDefinition` | 索引与正文对定义权的描述不一致，按类分发会遇到重定义风险 |

证据：[订阅异常](<D:/myspace/Git/this/Code_Design/00-架构单元/M01-11_事件分发器代码设计案.md:223>)、[订阅流程](<D:/myspace/Git/this/Code_Design/00-架构单元/M01-11_事件分发器代码设计案.md:441>)；[瓦片数据表](<D:/myspace/Git/this/Code_Design/06-战斗/30_战场与战棋规则代码设计案.md:107>)、[接口区分](<D:/myspace/Git/this/Code_Design/06-战斗/30_战场与战棋规则代码设计案.md:656>)；[类型码不入档](<D:/myspace/Git/this/Code_Design/01-通用系统/30_元对象与组件代码设计案.md:104>)、[序列化条款](<D:/myspace/Git/this/Code_Design/01-通用系统/30_元对象与组件代码设计案.md:153>)；[技能停用登记](<D:/myspace/Git/this/Code_Design/README.md:181>)、[技能案数据表](<D:/myspace/Git/this/Code_Design/06-战斗/40_技能系统代码设计案.md:92>)。

## 三、哪些工作有效，值得保留

| 已有工作 | 实际价值 | 按当前目标如何使用 |
| --- | --- | --- |
| 系统职责、边界和上游需求回指 | 保护玩法语义，核对需求遗漏，限制职责漂移 | 作为对象拆分的需求输入和覆盖依据 |
| 静态定义、运行实例、存档与派生数据的区分 | 已识别不同数据的来源、存续范围和持久化需求 | 保留结论，并落实到具体类型和字段 |
| 数据所有权与访问约束 | 已限制跨系统直接修改、绕过提交入口等行为 | 映射为持有成员、只读接口和变更方法 |
| 接口前后置条件、状态转换和失败语义 | 很多行为契约已有分析基础，无需重新发明 | 分配给具体类的方法，再补参数与结果类型 |
| 模块依赖方向、程序集边界和显式初始化 | 为实现结构提供了现成的全局约束 | 保留其约束，明确具体装配与调用关系 |
| 元对象与组件、元技能的通用抽象 | 从按用途建黑箱向共用对象模型推进 | 保留组合理念，继续完成具体组件类型与行为承接 |
| 瓦片规格、静态地图、逐格声明、运行状态和稀疏增量 | 已经发生实质性的数据设计，不只是重述玩法 | 保留可确认的结构，解决矛盾并确定字段、索引、更新入口与表现绑定 |
| M01 主案加成员对象子文档 | 已降低检索负担，能看出公共能力与装配关系 | 保留导航与协作总览，把多类型子文档继续落到可分发的类设计 |
| 对象与接口 ID、缺口登记、库索引 | 有助于追溯、交叉核对和识别未决问题 | 作为查找与校验工具，不代替具体类型和签名 |

这些成果多数属于“可复用的中间成果”。“有效”不等于已经满足最终验收。特别是元对象与瓦片设计，仍需解决本文列出的冲突后才能作为确定的下游输入。

## 四、哪些工作方向错误，不能继续沿用

### 1. 把系统设计稿机械转换为同构的系统契约

继续按每个玩法系统套同一套十节，只会让功能描述更完整，无法自动产生合理的代码对象。系统主案可以存在，但不应成为唯一实施单元；代码划分也不应以先拆玩法系统为前提。

### 2. 以“保留实现自由”为由回避所有关键技术决策

禁止继承、字段类型、回调签名等，直接阻止本次要求完成的技术落地。实现自由应保留在不会改变跨类契约的函数内部细节，不能覆盖影响所有调用者的结构决定。

### 3. 把承载类别和生命周期表当作完整技术方案

表本身有效；把它视为已经回答“采用什么封装、多少实例、如何挂载和执行”，则高估了完成程度。常驻、随战斗等是存续分类，不能替代具体类型、实例创建路径和方法协议。

### 4. 给功能族改名为“组件”，但仍只在系统级描述其行为

组件族清单是中间成果。若未定义组件的类型、配置、状态、挂载和行为执行入口，“组件化”就仍停留在词汇层。一个新增能力究竟是增加数据记录、具体组件类、处理器，还是注册项，当前材料还不足以统一决定。

### 5. 用大量 ID、出处和长篇契约替代准确字段与成员归属

编号让对象可追踪，不能决定谁持有谁、方法属于谁以及参数有什么字段。反复要求读者回看上游，和用户要求的单类稿独立编写能力存在直接差距。

### 6. 用固定篇幅和结构完整证明完成

CO04-01 临时撰写口径要求每份子文档控制在 12000 至 25000 字符。这个要求会鼓励扩写，却不能保证补上关键协议。一份很短但完整的单类稿，比反复陈述边界和生命周期的长稿更接近当前目标。

证据：[CO04-01 篇幅要求](<D:/myspace/Git/this/Output/CO04-01-代码设计改进/CO04-01_M01子文档撰写规范_v1.md:168>)。

结构、编号和引用检查应继续使用，但只能证明文档卫生与追溯能力，不能单独证明可进入独立伪代码编写。

## 五、根因与后续工作的输入

根因可归为三层：

1. **规范目标错位**：NR-06 把代码设计定位为系统级行为契约，把类型和技术实现决策推向更下游；NR-03、NR-05 中也保留同方向的条款。
2. **对象设计缺层**：功能已列出，却没有完整分配到类型、成员、实例和装配关系；M01 拆文件改善了组织，没有完全补上这一层。
3. **验收对象错位**：当前检查偏重系统章节完备，用户要求检查单类任务是否能独立执行。现有未决项还需要区分玩法缺口、全局架构冲突和代码技术设计缺口，不能全部推给策划上游。
