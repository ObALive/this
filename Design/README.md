# 游戏设计文档库（系统 Wiki）

本目录是**全局性、持续维护**的游戏设计文档库，定位为开发团队使用的"系统 wiki"。它与 `Dsh/Input`、`Dsh/Output`、`Dsh/Report`、`Dsh/Task` 同级，但职责不同：

| 目录 | 职责 |
| --- | --- |
| `Dsh/Task/` | 任务书 |
| `Dsh/Output/` | 各任务的过程性文件（一次性产出） |
| `Dsh/Report/` | 各任务的执行报告 |
| `Dsh/Design/`（本目录） | **全局设计文档**：各系统的设计内容长期在此生长、修订、维护，跨任务共享 |

## 一、本库承载的内容

本库承接策划流程第 2～5 步（游戏设计纲要 → 系统架构设计 → 系统关系设计 → 功能需求拆分）的全部落盘文档，回答三个问题：

1. **做什么**：游戏整体与每个系统的设计内容；
2. **有哪些系统**：全量系统清单与分层结构（本库的目录结构即该清单的物理载体）；
3. **有哪些注意的交互逻辑和细节**：跨系统的关键交互逻辑与每个界面的交互方式细节。

设计依据（只读来源）：`Dsh/Output/A04-fix/A04-fix_创意需求文档_v2.1.md`（以下简称"创意文档"）、`Dsh/Input/战斗增量思路.md`、`Dsh/Output/B01-游戏创意研讨/` 下两份研讨文档。

分层约定：

- **域目录**（`00`～`09`）：按"独特系统 / 通用系统 / 局外系统 / 支撑系统"归并的系统域，编号即稳定排序；
- **系统目录**（域内 `10`、`20`、`30`……）：一个系统一个目录，为该系统的后续多文档扩展预留空间；
- **子系统目录**（系统内 `{系统编号}-{序号}`，如 `30-10-触发条件`）：子系统在设计上从属于宿主系统、两者设计不可分割时使用，编号为 `{系统编号}-{系统内序号}`；库内当前唯一实例是 30-事件系统下的 30-10 触发条件；
- **文档**：每系统当前一张主设计文档，后续可拆分子文档（如规则表、UI 规范）放在系统目录内；
- **扩展配置表**（`{序号}_{表名}.csv`）：承载枚举会持续增长、且被多个系统共同引用的结构化定义。表内以 ID 标识每条记录，并保留一条"待补充"记录声明扩展契约；新增条目时同步登记到系统设计文档。库内当前实例是 `05-运营与经济/05-物品系统/05_物品词条表.csv`、`05-运营与经济/05-物品系统/05_物品操作总表.csv`、`05-运营与经济/05-物品系统/05_商人原型配置表.csv`、`02-时间与事件/30-事件系统/30_事件类型表.csv`、`06-战斗/10-战斗总览/10_角色属性表.csv`、`06-战斗/75-元效果系统/75_元效果表.csv`、`06-战斗/80-技能与库存联动/80_投掷组件表.csv`、`06-战斗/85-战斗行为系统/85_战斗行为表.csv`、`07-线索树与元进度/10-线索树核心/10_节点类型表.csv`、`07-线索树与元进度/10-线索树核心/10_节点关系表.csv`、`07-线索树与元进度/10-线索树核心/10_传闻表.csv`、`07-线索树与元进度/30-概率池联动/30_概率池表.csv` 与 `07-线索树与元进度/40-局末结算与写入/40_结算组件表.csv`；
- **交互与 UI 归属**（C03）：不单独成立章节，各系统界面与操作的规格由各系统设计文档承接；跨系统的全局交互规范归 `00-总览/01_设计原则与跨系统交互逻辑.md` 维护。

全量系统清单与关系见 `00-总览/00_系统全景图.md`。

## 三、文档状态约定

| 状态 | 含义 |
| --- | --- |
| 占位 | 结构已建、要点已摘录，完整设计待填充 |
| 草稿 | 设计已展开，未评审 |
| 评审中 | 提交总监/顾问评审 |
| 定稿 | 评审通过，可作为下游（架构、功能拆分）依据 |

每张文档头部元信息表中必须标注状态：系统名、所属域、状态、设计依据、关联文档、维护人、更新日期。元信息表不设版本字段。

## 四、命名与版本控制

- 目录：`{序号}-{系统名}`；系统目录内文件：`{序号}_{系统名}{文档类型}.md`；扩展配置表：`{序号}_{表名}.csv`；
- 文件名、文档标题与元信息表**一律不带版本号**。本库采用 **git 版本控制**：修订历史、修订原因与历史版本全部由提交记录承载，本库内不保留归档文件，也不在文档内登记版本号与更改历史；
- **域编号**：两位数字 `00`~`99`。`0X` 只是单位数时的补零对齐（`00` 保留给库级总览文档）；第 10 个及以后的域直接使用 `10`、`11`……，词典序天然正确（`09` < `10`）；
- **系统编号**：域内以 `10`、`20`……`90` 为锚点（以 0 结尾，共 9 个锚点）。新增系统插在相邻锚点之间取中值（如 `15`、`25`），避免整域重编号。系统不使用 `0X` 连续编号的原因：`01` 与 `02` 之间没有任何整数插入位，插入新系统必然引发整域重编号与全库引用更新；锚点编号把插入成本降为取一个中值、不波及既有系统。域可以使用 `0X`，是因为域数量少、新域只会追加在末尾（`10`、`11`……），不存在"两域之间插队"的需求；
- **系统编号扩容规则**（域内系统数达到 10 个时）：优先**拆分该域**（10 个系统挤在一个域是复杂度过高的信号）；若不拆，则整域重编号为三位补零（`010`、`020`……`100`），保证字典序 = 数字序。禁止 2 位与 3 位混排（混排时 `100` 会排在 `90` 之前，排序失效）。当前唯一超限的 06-战斗域，第 10 个子系统暂用 `A0` 记号（`A` > `9` 保序），待"拆分或重编号"定案后处理。

## 五、术语与引用规范

1. **唯一术语来源**：`00-总览/02_术语表.md` 是全库术语的权威清单。同一概念只使用一个标准术语，禁止同义词、别名与缩写混用；新术语必须先登记入表再用于各系统文档。
2. **允许的简称**：仅当术语表条目显式标注「文档中可简称」时，正文才可使用该简称，且须在同一文档内标准术语首次出现之后使用；未标注的写法一律改为标准术语。
3. **定义优先级**：术语的定义以文档正文为准。正文已有定义的，术语表只做一句话概括并标注概念来源（文档与章节）；正文没有定义的，才由术语表补充一句话定义，并标注"定义来源：术语表补充"。
4. **引用标注**：凡跨文档、跨章节引用，或某术语在当前处出现但其定义在别处时，必须在引用处加注术语表编号，写作 `术语名（术语表 T-XXX）`。
5. **反向可追溯**：术语表条目必须标明概念来源（首次给出定义的文档与章节）并给出一句话简介，使任意引用点都能回溯到定义处。
6. **停用术语**：术语表「停用术语」一节登记已撤销或已更名的表述，全库禁止再使用，其位置以标准术语或承接方为准。

## 六、维护流程（供后续任务使用）

1. 每次任务只在其任务书授权的系统范围内新建或修订文档；
2. 修订文档前先读现行文档与对应索引；修订直接在原文件上进行，历史由 git 提交承载，不另存历史版本、不保留归档副本；
3. 同步更新：所属域索引与 `00-总览/00_系统全景图.md` 中的状态列；
4. 跨系统的交互逻辑与设计原则变更，必须同步登记到 `00-总览/01_设计原则与跨系统交互逻辑.md`；
5. 新术语写入 `00-总览/02_术语表.md`，并按第五节规范维护编号、概念来源与定义来源；
6. 重大取舍（砍掉/不做/悬置）必须登记 `00-总览/03_设计决策记录.md`，"不做"与"砍掉"须记录理由与复活条件，"悬置"须记录到期日；
7. 任务的过程性产出仍按规则放 `Dsh/Output/{任务编号}/`，本库只存放长期维护的设计文档；
8. 本阶段范围约束（C-01-10-04 总监重申）：本库当前只承载系统级设计——各系统做什么、系统间如何交互；属性定义、数值规格与代码实现落地细节不属于本阶段讨论内容，禁止写入文档正文与待设计清单。
