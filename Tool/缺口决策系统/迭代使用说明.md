# 迭代使用说明：如何归档审阅内容并推进下一轮

| 项目 | 内容 |
| --- | --- |
| 文档定位 | 指导一轮提问到归档收口的完整流程，以及归档后如何开出下一轮 |
| 适用对象 | 执行缺口分析的负责人 |
| 工具位置 | `Dsh/Tool/缺口决策系统/` |
| 前置条件 | 已按 `建库说明.md` 建好决策库 |
| 更新日期 | 2026-09-26 |

## 1 一轮迭代的五步

每一轮提问到收口都是同一条链路，工具只负责中间三步，首尾两步由人完成。

| 步骤 | 动作 | 责任 | 产物 |
| --- | --- | --- | --- |
| 1 出题 | 分析现状，把信息缺口写成缺口记录与候选方案 | 分析负责人 | 决策库中的未裁定项 |
| 2 提问 | 导出候选清单与作答模板，交给总监 | 分析负责人 | `{base}_候选清单_v{n}.md`、`{base}_作答模板_v{n}.md` |
| 3 回收 | 把总监的裁定导入决策库 | 工具 | `decisions` 表更新 |
| 4 归档 | 已裁定项移入归档表，主表只留未澄清项 | 工具 | `gaps_archived` 表更新 |
| 5 落地 | 按裁定回填设计稿，登记设计决策记录 | 分析负责人 | 新版设计稿与决策记录 |

第 5 步不属于本工具范围，但它是归档的前提：归档表里的 `landed_at` 字段应当在设计稿回填完成后填写，只有结论真正落到文档里，一条缺口才算闭合。

## 2 步骤 2：导出提问材料

```powershell
python Dsh/Tool/缺口决策系统/建库工具/export_catalog.py --db <库路径> --out-dir <输出目录>
```

命令在输出目录生成两个文件。候选清单面向总监阅读，每项缺口给出等级、责任方、影响范围、关闭条件与三条候选的完整正文。作答模板是回填载体，每项缺口一个作答区，区内四个标记行。

```markdown
## CBT2-GAP-001 缺口标题

[候选]
[预期方案]
[裁定理由]
[补充要求]
```

回填规则只有两条：选候选就在 `[候选]` 后写候选字母（`A`、`B`、`C`）；候选都不合就在 `[预期方案]` 后写自己的方案。两行可以同时写，此时以预期方案为准并标记需要复核。`[裁定理由]` 与 `[补充要求]` 是可选补充，后者常用于记录候选正文没覆盖的例外。

留空即视为未裁定，不会被写入。不要把候选正文抄进模板，导入脚本只读取标记后的同行内容。

## 3 步骤 3：导入裁定

先校验，再写入。

```powershell
python Dsh/Tool/缺口决策系统/审阅工具/import_answers.py --db <库路径> --answers <模板路径> --check
python Dsh/Tool/缺口决策系统/审阅工具/import_answers.py --db <库路径> --answers <模板路径>
```

`--check` 输出写入项数、未填写项数与冲突清单，不改变库。确认无误后去掉 `--check` 执行写入。

导入脚本的判定规则：

| 填写情况 | 写入结果 |
| --- | --- |
| 只填候选字母 | `chosen_option_id` 记为对应候选，状态为 `已选候选` |
| 只填预期方案 | `answer_text` 记为方案文本，状态为 `自定义方案` |
| 两者都填 | 以预期方案为准，状态为 `自定义方案`，`needs_followup` 置 1 |
| 候选字母无法识别 | 判为冲突，跳过该项并计入报告 |

出现冲突时必须先查清原因再重跑，不要手工改库绕过。冲突通常来自候选字母写成了候选编号、候选标题或被改写过，此时以候选清单为准回填。

作答结果也可以直接以 JSON 提供。

```json
{"answers": [
  {"gap_id": "CBT2-GAP-001", "chosen_option": "B",
   "answer_text": "", "decision_basis": "与决策 27 保持一致", "extra_requirement": ""}
]}
```

`chosen_option` 只写字母，不要写 `CBT2-GAP-001-OPT-B` 或候选标题。

### 3.1 候选与预期方案同时填写时

导入脚本按「预期方案优先」写入，状态记为自定义方案，并把 `needs_followup` 置 1。此时不要直接当作替换关系处理：先读两段文本，判断它们是**互相冲突**还是**分别约束不同规则**。

| 情况 | 处理 |
| --- | --- |
| 两段文本互不冲突，各自约束不同的规则 | 可以在设计稿中并存落地，两段都写进对应章节，并在归档文档中登记该判定，提请下一轮确认 |
| 两段文本互相冲突 | 不得自行取舍，回到总监确认以哪一项为准 |

判定的依据写进归档文档，不要只留在对话里。

## 4 步骤 4：归档

归档分两步，推荐分开执行以便留存凭证。

### 4.1 导出结论留存

```powershell
python Dsh/Tool/缺口决策系统/审阅工具/dump_decisions.py --db <库路径> --markdown --out <归档目录>/回答归档_v{n}.md
```

这份输出是本轮裁定的可读凭证，归档目录按任务编号组织的惯例存放。它是人写的归档文档的素材，不是替代品：归档文档还要记录本轮之后新增了哪些缺口、哪些既有结论被取代。

### 4.2 执行归档

```powershell
python Dsh/Tool/缺口决策系统/审阅工具/archive_decided.py --db <库路径> --check
python Dsh/Tool/缺口决策系统/审阅工具/archive_decided.py --db <库路径> --by <任务编号>
```

`--check` 先预览将归档的项与归档后主表保留的项。确认后执行写入，脚本把已裁定项写入 `gaps_archived`，并把它们从 `gaps`、`solution_options`、`decisions` 三张主表中移出。

### 4.3 归档后修正设计落点

归档脚本写入 `gaps_archived.landed_at` 时，早期版本会把缺口的关闭条件写进该字段。该字段的语义是结论落到哪份文档，修正方式是按设计稿的实际落点改写，不必重开缺口。

做法：在任务输出目录的 `.artifact_runtime` 内写一份映射文件，形如 `LANDING = {"XXX-GAP-001": "07-10 §3.6；术语表新增……"}`，再用小脚本按映射更新归档表。参考实现见 `Dsh/Output/C-07-bb-01/.artifact_runtime/set_landing.py` 与同目录的 `landing_round2.py`。

修正好落点之后重新导出归档 Markdown，使归档文档与库内落点一致。

归档后的库语义只有一句话：主表只保留尚未澄清的问题，填写器只呈现这些项；归档表保留已澄清问题连同裁定结果与结论摘要。

两个可选项的适用场合：

| 选项 | 作用 | 何时使用 |
| --- | --- | --- |
| `--keep-gaps` | 只同步归档表，不从主表移出 | 需要在填写器里继续看到这些项，或本轮只做阶段性留痕 |
| `--conclusion <文本>` | 为本次归档的全部项补一条统一结论摘要 | 本轮裁定可以用一句话概括时 |

`archive_decided.py` 与 `import_answers.py --archive` 的区别：后者只把当前状态同步进归档表、不动主表，等价于 `--keep-gaps`；前者执行完整归档。两者产出的归档记录结构一致，可以先跑 `--check` 核对。


## 5 步骤 1：开下一轮

归档执行完后主表只剩下没有拍板的问题。下一轮的做法有三种，通常混合使用。

### 5.1 追问未裁定项

主表中剩下的项就是遗留问题，直接进入下一轮导出即可。若某项已经问过两轮仍无结论，应当在归档文档中记录它为何难以拍板，而不是原样再问一遍。

### 5.2 把方向性回答转成新缺口

总监的回答里如果只有意图与举例、没有可落地的规则，不要自行补全。把它拆成新的缺口重新建库，新缺口编号沿用本域前缀并递增序号，`source_ref` 指向那条方向性回答。

### 5.3 因新裁定产生的新缺口

一条裁定常常打开新的问题面。例如某个约束被放开后，依赖该约束的子系统需要重新确认口径。这类缺口要在归档文档里写明由哪条裁定引出，便于追溯。

新一批缺口按 `建库说明.md` 第 4 节的方式构造 JSON 后导入既有库。导入是追加语义：已归档的项不会被重新写入主表，重复编号会被拒绝或覆盖，编号必须递增。

## 6 归档的边界

归档不改写历史，只追加结论。以下做法都属于越界：

| 越界做法 | 后果 | 正确做法 |
| --- | --- | --- |
| 用归档表覆盖前几轮的结论 | 失去裁定演变过程，无法追溯 | 保留旧记录，新结论另起编号并标注被取代 |
| 把推断当作裁定写入归档 | 未经确认的规则进入设计稿 | 转成新缺口提问 |
| 直接改设计稿再补归档 | 文档与决策记录脱节 | 先归档、再回填设计稿 |
| 用复制文件的方式做版本快照 | 占用空间且与版本管理重复 | 交给版本管理，按 `第 7 节` 取用历史版本 |

归档信息不保留副本。本项目使用版本管理，历史版本按需取用即可。

## 7 取用历史版本

需要查看某轮归档之前的库或文档时，用版本管理读取，不要留快照副本。

```powershell
git log --oneline -- Dsh/Output/C-06-bb-01
git show <提交>:<路径>
git cat-file blob <提交>:<路径> > <临时文件>
```

读取二进制库同样有效：

```powershell
git show <提交>:Dsh/Output/C-06-bb-01/C-06-bb-01_战斗系统缺口决策库_v1.sqlite > 旧库.sqlite
```

取出的临时文件用完后删除，不要留在工作区。

## 8 填写器接口约定

填写器由本地 HTTP 服务提供，接口在迭代中也被脚本使用。

| 接口 | 方法 | 用途 |
| --- | --- | --- |
| `/api/databases` | GET | 列出工作区内可选的决策库与各自进度 |
| `/api/select` | POST | 切换当前库，请求体为 `{"db": "<库路径>"}` |
| `/api/questions` | GET | 返回当前库的全部缺口、候选与已有裁定 |
| `/api/decision` | POST | 提交单项裁定，立即写回库 |
| `/api/clear` | POST | 清空单项裁定，状态回到待裁定 |
| `/api/export` | GET | 导出当前库的裁定结果为 Markdown 文本 |

启动：

```powershell
python Dsh/Tool/缺口决策系统/填写器/decision_server.py --port 8777
```

`--port` 缺省为 8777，端口被占用时自动向后顺延，最多试 12 个；`--db` 可指定启动时选中的库，`--no-browser` 阻止自动打开浏览器。库的发现范围由 `建库工具/db_locator.py` 决定：扫描 `Dsh/Output` 下所有子目录中文件名含「决策库」的 sqlite 文件，以及工具自带的示例目录。库放在任务输出目录下才会被自动发现，放在别处时用 `--db` 显式指定；`--db` 与网页上的切换都只接受工作区内的路径。

网页端每次裁定会立即写回库，不需要额外保存动作。`needs_followup` 标记在页面上有提示，需要复核的项应当在下一轮开始前处理掉。

## 9 每轮自检清单

归档完成前逐条核对。

1. `dump_decisions.py --pending` 的输出是否为 0；不为 0 时是否已记录原因。
2. 是否存在 `needs_followup` 为真的项；有则是否已向总监确认。
3. 本轮新增缺口是否都已建库并导出，编号是否递增且无重复。
4. 被本轮裁定取代的既有结论是否在设计决策记录中登记。
5. 归档文档是否写清了本轮裁定的结论、新增缺口与遗留问题。
6. 归档能否从版本管理复原：库文件与归档文档是否都已提交。
7. 主表是否只留下确实尚未澄清的问题。
