# 读库说明：如何读取并审阅总监给出的决策

| 项目 | 内容 |
| --- | --- |
| 文档定位 | 指导如何读出决策库中的裁定结果，并把它用于下一步设计工作 |
| 适用对象 | 需要按总监裁定继续设计的人，以及需要复核裁定完整性的人 |
| 工具位置 | `Dsh/Tool/缺口决策系统/审阅工具/` |
| 前置条件 | 决策库中已有填写的裁定结果 |
| 更新日期 | 2026-09-26 |

## 1 裁定的两种形态

总监给出的决策在库中只有两种落地形态，读库时必须先分清。

| 形态 | 落点 | 含义 |
| --- | --- | --- |
| 采用候选 | `decisions.chosen_option_id` 写入候选编号，状态为 `已选候选` | 总监在三条候选里选了一条，该候选的方案正文就是规则 |
| 自定义方案 | `decisions.answer_text` 写入方案文本，状态为 `自定义方案` | 三条候选都不符合，总监写了自己的方案，该文本就是规则 |

两个字段的优先级是预期方案高于候选。两者同时存在时状态记为自定义方案，并把 `needs_followup` 置 1，提示需要复核以哪一项为准。读到 `needs_followup` 为真的记录时，不要自行判断，应当向总监确认。

除裁定本身外，还有两个可选字段需要一并读取：`decision_basis` 是裁定理由，说明为什么这样选；`extra_requirement` 是补充要求，记录候选未覆盖的例外或细节。补充要求往往包含候选正文里没有的规则，回填设计稿时不能漏。

## 2 读取方式

### 2.1 终端速览

```powershell
python Dsh/Tool/缺口决策系统/审阅工具/dump_decisions.py --db <库路径>
```

输出每项缺口的编号、等级、裁定方式与答案摘要，末尾给出整体进度，适合快速判断这一轮回答到什么程度。

### 2.2 只看未裁定项

```powershell
python Dsh/Tool/缺口决策系统/审阅工具/dump_decisions.py --db <库路径> --pending
```

输出未裁定项的编号清单与数量。用于判断是否还有阻塞项没有拍板；数量为 0 时说明这一轮可以收口。

### 2.3 结构化读取

```powershell
python Dsh/Tool/缺口决策系统/审阅工具/dump_decisions.py --db <库路径> --json --out <文件>
```

导出 JSON，结构与填写器读取的一致，包含每项缺口的元信息、候选清单、裁定结果与所需字段。用于脚本处理，例如批量回填设计稿或生成归档文档。

### 2.4 导出裁定结论 Markdown

```powershell
python Dsh/Tool/缺口决策系统/审阅工具/dump_decisions.py --db <库路径> --markdown --out <文件>
```

导出人类可读的结论表，每项包含等级、责任方、裁定方式、采纳方案或预期方案、裁定理由与补充要求。这份输出可以直接作为回答归档的素材，也是向总监复核时的凭证。

### 2.5 网页填写器复核

```powershell
python Dsh/Tool/缺口决策系统/填写器/decision_server.py
```

填写器顶部可以切换库，页面按缺口逐项展示候选与自定义输入框，已裁定的项带状态标记。用于需要横向比对候选正文、或需要现场改动个别项的场合。接口约定见 `迭代使用说明.md` 第 5 节。

## 3 读取后的判断顺序

按以下顺序处理一轮回答，可以避免漏项。

1. **先看进度**：未裁定项是否为 0。不为 0 时先确认这些项是本轮遗漏还是有意留到下一轮，遗漏的按 `迭代使用说明.md` 补充提问。
2. **再看复核标记**：是否有 `needs_followup` 为真的记录。有则先向总监确认以哪一项为准，不要带着歧义回填设计稿。
3. **再读补充要求**：把 `extra_requirement` 逐条列出，与所选候选的方案正文合并理解，形成该缺口的完整规则。
4. **再区分两类回答**：采用候选的项直接以候选方案正文为规则；自定义方案的项需要通读文本，从中提炼规则，不要把临时描述或举例原样写进设计稿。
5. **最后核对自洽**：把本轮全部裁定放在一起看，检查是否互相矛盾。例如某一项放开了某个约束而另一项依赖该约束，两者不能同时成立。

## 4 冲突与歧义的识别

读库时需要主动识别的三类情况。

| 类型 | 表现 | 处理 |
| --- | --- | --- |
| 回答之间的矛盾 | 本轮两项裁定对同一条规则给出不同口径 | 停下来确认优先级，在归档中记录以哪一项为准 |
| 回答推翻既有结论 | 新裁定与前几轮的归档结论相反 | 在设计决策记录中登记新决策并在归档表标注被取代，不直接改写历史结论 |
| 回答只给方向 | 文本里只有意图与举例，没有可落地的规则 | 转成新的缺口并给出候选，见 `迭代使用说明.md` 第 3 节 |

这三类情况都不能靠自行推断解决。前两类影响已定内容，第三类影响后续开发，都必须以提问的方式回到总监。

## 5 直接查询数据库

需要精确查询时可以直接打开库，常用查询如下。库是标准 SQLite 文件，可用任意 SQLite 客户端只读打开。

```sql
-- 裁定进度总览
SELECT * FROM v_gap_decision;

-- 未裁定项
SELECT gap_id, title, level FROM v_gap_decision WHERE decision_status = '待裁定';

-- 采用候选的项及其候选正文
SELECT g.gap_id, g.title, d.chosen_option_id, o.detail
FROM gaps g
JOIN decisions d ON d.gap_id = g.gap_id
JOIN solution_options o ON o.option_id = d.chosen_option_id
WHERE d.status = '已选候选';

-- 自定义方案与补充要求
SELECT gap_id, answer_text, extra_requirement
FROM decisions WHERE answer_text IS NOT NULL AND TRIM(answer_text) <> '';

-- 已归档问题的结论与落点
SELECT gap_id, decision_status, conclusion, landed_at, archived_by FROM gaps_archived;
```

## 6 审阅边界

读库只负责读出与核对，不负责改变裁定内容。以下动作不属于本环节：修改候选方案正文（属于建库环节）；替总监选择候选（属于授权范围问题，必须回到提问）；把未确认的推断写进设计稿（属于越权，见 `迭代使用说明.md` 第 6 节）。

## 7 需要总监确认的两种记录

读库时除裁定本身，还要挑出两类需要回到总监的记录，不要自行判定。

| 形态 | 判据 | 处理 |
| --- | --- | --- |
| 候选与预期方案同时存在 | `needs_followup` 为 1 | 先确认以哪一项为准。若两段文本互不冲突、分别约束不同的规则，可以在设计稿中并存落地，但必须在归档文档中登记该判定并提请下一轮确认 |
| 归档落点与结论不匹配 | `gaps_archived.landed_at` 的内容看起来是关闭条件或结论摘要，而不是文档章节 | 该字段的语义是结论落到哪份文档。历史库在归档时可能写入过关闭条件，迁移时按设计稿的实际落点改写即可，不需要重开缺口 |
