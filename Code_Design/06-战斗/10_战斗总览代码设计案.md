## 1. 系统定义

### 1.1 系统目的

战斗总览是战斗域的纲领系统：程序上持有三份权威登记（角色属性台账、单位状态模型、战斗行为类别与职责），并给出伤害类别口径与战斗界面取数契约，使战斗域各子系统共用同一份属性清单、同一套单位状态判定与同一套行为分类，而不各自复制规则。本单元的系统标识为 SYS-BATTLE-001 战斗总览。本系统只产生判定与查询结论：全队失去行动能力等收尾情形在战斗内**只产生判定并写入战斗结果**，由事件执行器在事件收尾时承接；结局成立的**唯一入口是事件结算环节的事件结果提交**，战斗阶段不直接退出到结算阶段（架构案 3.1 ARC-M05-001 与 6.6 第 3 条、9.5.5；设计决策记录决策 90）。

### 1.2 系统职责

- 持有角色属性台账：属性定义的唯一权威清单（属性类别、含义、取值范围出处、生效系统、生效方式、关联机制、Demo 状态与扩展说明）。运行期配置的权威载体是**引擎编辑器内的配置资产**，经 M01 配置服务取得其内存形态；`系统设计文档/06-战斗/10-战斗总览/10_角色属性表.csv` 是属性的**设计侧认领台账**，用于设计评审与枚举契约登记，**程序侧不直接读表**（架构案 5.1、7.9、8.6 第 10 条；设计决策记录决策 93）；
- 持有属性读取关系登记：逐属性登记读取方与用途，作为新增属性的受理条件与读取侧的唯一依据；
- 判定生命状态（术语表 T-114）三档 正常／受伤／失去行动能力，与伤势状态三档 轻伤／重伤／致残；
- 判定单位状态迁移：生命值低于配置限度时进入受伤并使伤势档提升一档；生命值归零时进入失去行动能力；轻伤档下生命值归零时置击倒标记；
- 维护伤势恢复进程：处理伤势后随世界时间推进逐步恢复；进入战斗时终止恢复进程并保留当时的恢复进度；
- 提供队伍行动能力判定：全部我方单位同时处于失去行动能力状态的聚合判定，只给出结论与依据项，供 06-A0 写入战斗结果与事件结算环节的结局判定取用；本系统不在战斗内成立结局；
- 持有战斗行为（术语表 T-135）的类别与职责登记：技能释放、移动、容器搜刮、场景交互、撤退与防御待机六类，含「一次行动机会只执行一项行为、行为之间不能合并」的类别口径与「行动槽内无可用操作时须提供防御待机与撤退」的类别级要求；兜底项的清单、触发条件与呈现顺序归 06-85 战斗行为系统的兜底项登记（`CLS-BATTLEACT-005`、`API-BATTLEACT-003`）；
- 持有伤害类别登记（直接伤害与持续伤害两类，含判定时点与结算位置；结算分层的层序归 06-75 的效果定义，架构案 5.1）与战斗界面取数契约（战斗 HUD、行动槽、时间轴与技能面板四个区块的取数归属，以及「以当前行动者为中心、只对当前行动者可操作」的呈现规则）；技能面板区块的取数来源为 06-40 的 `API-SKILL-007`，本系统只登记汇总关系；
- 受理新增属性、行为类别与伤害类别的登记校验，核对三处同步的完整性；
- 维护单位状态条目：按战斗与队伍事件建立、保留与销毁条目；
- 提供上述登记与单位状态的只读查询，并在单位状态迁移时发布 单位状态变化。

### 1.3 系统边界

本系统不负责：

- 战斗的启动、轮次推进与收束的执行编排：归 M10 的战斗执行器（`API-M10-004` 战斗执行入口）；本系统只提供被其编排调用的判定与查询能力；
- 战场加载、初始站位、参战编成、射程与地形判定、收尾窗口（术语表 T-123）：归 06-30 战场与战棋规则；
- 时间轴（术语表 T-117）推进、行动机会（术语表 T-118）与行动后摇（术语表 T-119）计算：归 06-20；行动槽序列、连携条件与字母追加：归 06-50；
- 技能定义、技能效果与继承效果（术语表 T-145）求值：归 06-40 技能系统与 M09 的元效果服务；
- 战斗行为的权威清单与逐行为契约字段（术语表 T-137）：归 06-85 战斗行为系统，本系统只登记类别与职责；
- 元效果的构成、同名判定、叠加顺序与生命周期：归 06-75 元效果系统与 M09 的效果服务（`API-M09-001`～`API-M09-003`）；本系统不实现效果叠加，也不实现条件判定；
- 伤害与恢复的具体数值计算与换算：归发起行为的子系统与数值侧；本系统只登记伤害类别口径，并对结果做单位状态判定；
- 属性取值的产生与持有：取值来源为 01-40 角色与小队（`API-M07-004` 属性取值）；属性的取值范围给出归数值侧；本系统只维护属性定义与读取关系；
- 战斗目标（术语表 T-129）判定、战斗结果标识（术语表 T-131）与达成目标清单（术语表 T-130）：归 06-A0；全队失去行动能力只产生判定并写入战斗结果，由事件执行器在事件收尾时承接，结局成立的唯一入口是事件结算环节的事件结果提交，本系统不成立结局（架构案 3.1 ARC-M05-001、6.6 第 3 条、9.5.5；设计决策记录决策 90）；
- 战斗界面的绘制、布局、信息优先级、键位与操作方式：归 M08 与后续界面设计阶段；本系统只给出取数归属与呈现规则；
- 战斗未结状态的入档与恢复驱动：归 M01 的存档服务与单局状态域侧；本系统只声明可持久化内容与重建口径；
- 世界时间的持有与推进：唯一受理入口是 M01 时间服务（`API-M01-005`），本系统不推进也不改写世界时间。

### 1.5 功能要求

- F-BATTLE-01 角色属性只有一份权威清单，登记属性类别、含义、取值范围出处、生效系统、生效方式与关联机制；新增属性先登记定义与读取关系，再由数值侧给出取值范围。
- F-BATTLE-02 单位状态由生命状态与伤势状态两层构成，生命状态三档、伤势三档，两层各自独立判定。
- F-BATTLE-03 生命值低于配置限度时进入受伤状态并使伤势档提升一档；生命值归零时进入失去行动能力状态。
- F-BATTLE-04 轻伤档下生命值归零的单位视为被击倒：不能行动、仍在时间轴上保留位置、可以恢复，生命值恢复到受伤限度以上时恢复行动能力。
- F-BATTLE-05 全部我方单位同时处于失去行动能力状态时，战斗模块**只产生判定并写入战斗结果**，不在战斗内结束本局；判定对象是整支队伍而不是主角（术语表 T-018）一人，判定结果由事件执行器在事件收尾时承接，结局成立的唯一入口是事件结算环节的事件结果提交（架构案 3.1 ARC-M05-001、6.6 第 3 条、9.5.5；设计决策记录决策 90）。
- F-BATTLE-06 生命与伤势不随战斗结束自动清除；处理伤势后随世界时间推进逐步恢复，下一次进入战斗终止恢复进程并保留当时的恢复进度。
- F-BATTLE-07 战斗行为由战斗行为系统规范化管理，分类为技能释放、移动、容器搜刮、场景交互、撤退与防御待机六类，各自独立占用一次行动机会，行为之间不能合并。
- F-BATTLE-08 新增战斗行为必须同时更新战斗行为表、本系统的行为类别与职责登记、发起该行为的子系统文档三处。
- F-BATTLE-09 行为的前置条件不满足时不产生任何状态变化；行动槽内无可用操作时提供防御待机与撤退作为兜底选项。
- F-BATTLE-10 伤害分直接伤害与持续伤害两类，两类的判定时点与结算位置相同，单位状态的变化在事件内实时结算。
- F-BATTLE-11 装备（术语表 T-107）、遗物（术语表 T-110）、道具与技能提供的效果统一以元效果（术语表 T-132）表达，不另立效果机制。
- F-BATTLE-12 战斗界面固定四个区块；以当前行动者为中心，其他单位只可查看、不可操作，且其行动槽标注为不可操作状态。

| 生命状态 正常 → 受伤 | `API-BATTLE-004` 受理已提交的行为结果后，`API-BATTLE-101` 判定生命值低于受伤限度 |
| 生命状态 受伤 → 失去行动能力 | 同一路径判定生命值归零 |
| 生命状态 受伤 → 正常 | 判定生命值恢复到受伤限度以上 |
| 生命状态 失去行动能力（已击倒）→ 正常 | 判定生命值恢复到受伤限度以上，且 `API-BATTLE-103` 清除击倒标记 |
| 伤势状态 升档（未受伤 → 轻伤 → 重伤 → 致残） | 每发生一次生命值低于受伤限度的判定使档位提升一档；已达致残时为最高档，不继续提升 |
| 伤势状态 降档（致残 → 重伤 → 轻伤 → 未受伤） | `API-BATTLE-104` 按世界时间推进累计的恢复进度达到该档位的恢复限度 |
| 击倒标记 未击倒 → 已击倒 | `API-BATTLE-103` 判定处于轻伤档且生命值归零 |
| 击倒标记 已击倒 → 未击倒 | 生命值恢复到受伤限度以上 |
| 伤势恢复进程 未在途 → 恢复中 | `API-BATTLE-004` 受理收尾窗口或事件治疗机会提出的伤势处理请求 |
| 伤势恢复进程 → 已终止 | 订阅到 战斗开始（M05）后由 `API-BATTLE-108` 置位 |
| 伤势恢复进程 已终止 → 恢复中 | 再次受理伤势处理请求 |
| 属性台账 未装配 → 已装配 | `API-BATTLE-105` 装配完成且 `API-BATTLE-107` 校验通过 |
| 属性台账 未装配 → 校验不通过 | 存在属性未登记读取关系或生效系统字段为空 |
| 取数契约 未装配 → 已装配 | `API-BATTLE-106` 装配完成且四区块取数来源全部登记（与属性台账共用 配置加载完成 触发点） |
| 判定结果 各取值 | 由 `API-BATTLE-004` 的单次判定给出；被拒绝时单位状态与恢复进程均不变 |
| 本单元装配 未初始化 → 初始化中 → 已初始化 | 启动物体读取并校验单元装配声明后，在初始化序列第 3 步按声明顺序显式调用本单元初始化；本单元在初始化时显式复位自身状态，不依赖引擎的启动回调顺序与域重载（架构案 6.1 阶段 1 与阶段 3、8.3 第 7 条、8.6 第 4、5 条） |
| 本单元装配 已初始化 → 已销毁 | 程序结束时的逆序销毁；进程终止不执行销毁序列、不做任何收尾承诺，也不提交存档（架构案 6.4、8.3 第 6、8 条、9.4） |

### 4.2 接口详细定义

### API-BATTLE-001 AttributeLedger.QueryAttribute 属性定义查询

职责：按属性ID 或属性类别返回属性定义记录，作为属性读取与配置校验的唯一依据。输入：参数输入：属性ID 或属性类别；状态输入：属性台账装配状态 `CLS-BATTLE-003`；数据输入：属性定义 `CLS-BATTLE-001`；外部事件输入：无。读取：`CLS-BATTLE-001`、`CLS-BATTLE-003`。输出：返回值：属性定义记录或未登记结论；状态输出：无；事件输出：无；外部系统调用：无。产生的状态变化：无。前置条件：本单元已完成初始化（架构案 6.1 阶段 3、8.3 第 1 条；由启动物体按单元装配声明顺序显式初始化）；属性台账已装配；查询的属性ID 或类别已在 `CLS-BATTLE-001` 登记。后置条件：返回值与配置资产的内存形态一致，不返回推算值。副作用：无。异常情况：台账未装配；属性ID 未登记；属性类别为空；定义缺少生效系统字段。

### API-BATTLE-002 AttributeLedger.QueryReaderBinding 属性读取关系查询

### API-BATTLE-003 UnitState.Query 单位状态查询

职责：返回指定单位的单位状态快照，不提供写入口。输入：参数输入：单位标识集合；状态输入：单位状态 `CLS-BATTLE-004`；数据输入：无；外部事件输入：无。读取：`CLS-BATTLE-004`。输出：返回值：单位状态快照集合；状态输出：无；事件输出：无；外部系统调用：无。产生的状态变化：无。前置条件：本单元已完成初始化（架构案 6.1 阶段 3、8.3 第 1 条）；查询范围内的单位已建立单位状态条目。后置条件：快照为只读且不携带写入口；读取方不得把快照缓存为自身数据。副作用：无。异常情况：单位标识未建立条目；单局状态域未就绪；查询发生在读档恢复期间。

### API-BATTLE-004 UnitState.ApplyChange 单位状态结算

职责：受理已提交行为结果或伤势处理请求，判定生命状态、伤势档与击倒标记的迁移并落库。输入：参数输入：单位标识、变更类别（伤害／恢复／伤势处理）、变更量或处理请求、来源行为标识；状态输入：`CLS-BATTLE-004`、当前阶段（`API-M10-001`）；数据输入：`CLS-BATTLE-005`、属性取值（`API-M07-004`）；外部事件输入：无。读取：`CLS-BATTLE-004`、`CLS-BATTLE-005`、属性取值（`API-M07-004`）、当前阶段（`API-M10-001`）。输出：返回值：单位状态判定结果 `CLS-BATTLE-009`；状态输出：`CLS-BATTLE-004` 按判定迁移，恢复进程按伤势处理与战斗开始迁移，生命值数值变更经 `API-SAVE-009` 提交到玩家状态域切面；事件输出：单位状态变化；外部系统调用：`API-SAVE-009` 单局状态域变更提交与玩家状态域属性取值（生命）变更提交、`API-M01-011` 事件分发器.Publish、`API-M01-010` 日志服务.Write。产生的状态变化：生命状态、伤势档、击倒标记与恢复进程按 3.2 迁移；被拒绝时不产生任何状态变化。前置条件：本单元已完成初始化（架构案 6.1 阶段 3、8.3 第 1 条）；当前阶段允许改变局内状态（非结算阶段）；单位已建立条目；变更来自已确认提交的行为结果或已受理的伤势处理请求；变更量取值合法。后置条件：成功时单位状态等于当次判定结果且已落库；被拒绝或失败时单位状态与落库内容保持受理前内容。副作用：发布 单位状态变化；生命值变更提交到玩家状态域切面；落库被拒绝时经日志服务记录。异常情况：结算阶段受理；单位无条目；变更量非法；未确认或已取消的行为结果提交；属性取值缺失；落库提交被拒绝；玩家状态域切面不可写；同一单位并发变更。

职责：判定一次生命值低于受伤限度是否使伤势档提升，以及恢复进度是否使档位下降。输入：参数输入：单位标识、判定方向（提升／下降）；状态输入：`CLS-BATTLE-004` 的当前伤势档；数据输入：`CLS-BATTLE-005`；外部事件输入：无。读取：`CLS-BATTLE-004`、`CLS-BATTLE-005`。输出：返回值：目标伤势档与判定依据；状态输出：无；事件输出：无；外部系统调用：无。产生的状态变化：无。前置条件：单位条目已建立；档位限度已登记。后置条件：一次判定最多提升一档，已达致残时为最高档，不继续提升；下降逐档进行。副作用：无。异常情况：档位限度待上游补充（REQ-BATTLE-01）；初始档位取值待上游补充（REQ-BATTLE-02）；同一批次内重复提升同一档。

### API-BATTLE-103 EvaluateActionCapability 击倒与行动能力判定

职责：判定单位是否可行动、是否置击倒标记，并给出击倒单位保留时间轴位置的结论。输入：参数输入：单位标识；状态输入：`CLS-BATTLE-004`、当前阶段（`API-M10-001`）；数据输入：`CLS-BATTLE-005`；外部事件输入：无。读取：`CLS-BATTLE-004`、`CLS-BATTLE-005`、当前阶段（`API-M10-001`）。输出：返回值：可行动标记、击倒标记与依据；状态输出：无；事件输出：无；外部系统调用：无。产生的状态变化：无。前置条件：生命状态与伤势档已判定。后置条件：击倒只由「轻伤档且生命值归零」置位；击倒不清除时间轴位置。副作用：无。异常情况：生命状态与伤势档的组合未定义（重伤或致残档下生命值归零，REQ-BATTLE-02）；敌方单位的击倒处置待上游补充（REQ-BATTLE-07）。

### API-BATTLE-104 AdvanceWoundRecovery 伤势恢复推进

职责：按世界时间推进量推进在途的恢复进度，并在达到档位限度时使伤势档下降。输入：参数输入：世界时间推进量；状态输入：`CLS-BATTLE-004` 的恢复进程与恢复进度；数据输入：`CLS-BATTLE-005`；外部事件输入：时间刻度变化。读取：`CLS-BATTLE-004`、`CLS-BATTLE-005`。输出：返回值：推进后的恢复进度与伤势档；状态输出：`CLS-BATTLE-004` 的恢复进度与伤势档；事件输出：单位状态变化（档位下降时）；外部系统调用：`API-SAVE-009`、`API-M01-011`。产生的状态变化：恢复进度累加；达到档位限度时伤势档下降一档并重置该档进度。前置条件：恢复进程为恢复中；世界时间已由时间服务推进。后置条件：已终止的恢复进程不因时间推进而累计进度。副作用：档位下降时发布 单位状态变化。异常情况：恢复推进口径待上游补充（REQ-BATTLE-03）；恢复进程为已终止；推进量为零或刻度变化缺失。

### API-BATTLE-105 BuildAttributeLedger 属性台账装配

职责：在配置加载完成后把属性定义与读取关系登记装配为可查询台账，并校验两者成对存在；定义内容取自引擎编辑器内的配置资产的内存形态。输入：参数输入：无；状态输入：无；数据输入：`CLS-BATTLE-001`、`CLS-BATTLE-002`；外部事件输入：配置加载完成。读取：`CLS-BATTLE-001`、`CLS-BATTLE-002`。输出：返回值：装配结果与不通过项；状态输出：属性台账 未装配→已装配或校验不通过；事件输出：无；外部系统调用：`API-BATTLE-107`、`API-M01-010`。产生的状态变化：`CLS-BATTLE-003` 生成或标记为校验不通过。前置条件：本单元已完成初始化（架构案 6.1 阶段 3、8.3 第 1 条）；配置加载完成已发布且配置资产已由配置服务加载为内存形态（架构案 5.1、7.9）。后置条件：台账覆盖全部已成对登记的属性；未成对登记的属性不进入台账。副作用：不通过项经日志服务记录。异常情况：属性未登记读取关系；生效系统字段为空；待补充属性记录（ATTR-TBD-001）只有占位字段。

### API-BATTLE-106 BuildPresentationContract 取数契约装配

职责：按行为类别登记与各子系统登记的取数入口装配四区块的取数契约。输入：参数输入：无；状态输入：无；数据输入：`CLS-BATTLE-006`、各子系统的取数入口登记；外部事件输入：配置加载完成。读取：`CLS-BATTLE-006`、子系统取数入口登记项。输出：返回值：装配结果；状态输出：取数契约 未装配→已装配；事件输出：无；外部系统调用：`API-M01-010`。产生的状态变化：`CLS-BATTLE-008` 生成。前置条件：本单元已完成初始化（架构案 6.1 阶段 3、8.3 第 1 条）；配置加载完成已发布且静态配置资产已加载为内存形态；四区块的取数来源均已登记。后置条件：契约只登记来源标识与呈现规则，不登记数据本体。副作用：缺失来源经日志服务记录。异常情况：区块取数来源未登记（SKILL、SKILLITEM、ACTIONSLOT、TIMELINE、FIELD 的接口 ID 待补）；界面设计阶段的布局与操作规格缺失（REQ-BATTLE-08）。

### API-BATTLE-107 ValidateRegistration 登记受理与扩展校验

职责：受理新增属性、行为类别与伤害类别的登记校验，给出三处同步的缺失项。输入：参数输入：登记类别（属性／行为类别／伤害类别）、登记项；状态输入：`CLS-BATTLE-003`、`CLS-BATTLE-006`、`CLS-BATTLE-007`；数据输入：`CLS-BATTLE-001`、`CLS-BATTLE-002`；外部事件输入：无。读取：`CLS-BATTLE-001`、`CLS-BATTLE-002`、`CLS-BATTLE-006`、`CLS-BATTLE-007`。输出：返回值：受理结论与缺失项清单；状态输出：无；事件输出：无；外部系统调用：战斗行为表查询（BATTLEACT，`API-BATTLEACT-001` BehaviorRegistry.QueryBehavior 行为契约查询）、`API-M01-010`。产生的状态变化：无（登记内容由静态配置承载，在配置加载后经 `API-BATTLE-105` 生效）。前置条件：登记项字段齐备；行为类别的登记项在 06-85 的行为表内存在对应行为标识。后置条件：受理结论给出三处同步的缺失项清单。副作用：缺失项经日志服务记录。异常情况：行为类别在行为表内无对应标识；属性缺少读取关系；伤害类别口径为空；登记项引用的子系统未登记。

### API-BATTLE-108 MaintainUnitState 单位状态条目维护与落库提交

职责：按战斗与队伍事件与后续波次入场建立、保留与销毁单位状态条目（含撤退收场的保留分支），并执行单位状态的落库提交。输入：参数输入：条目操作（建立／保留／销毁）、单位标识集合；状态输入：`CLS-BATTLE-004`、当前阶段（`API-M10-001`）；数据输入：无；外部事件输入：战斗开始、战斗结束、队伍成员加入、队伍成员离队、队伍重置、后续波次入场（06-90 的 `API-ENEMY-114` 经 M05 的波次入场路径请求）。读取：`CLS-BATTLE-004`、当前阶段（`API-M10-001`）。输出：返回值：条目操作结果；状态输出：`CLS-BATTLE-004` 的条目集合变化；事件输出：无；外部系统调用：`API-SAVE-009`、`API-M01-010`。产生的状态变化：我方条目按队伍事件建立与销毁；敌方条目随战斗建立，后续波次单位在其入场时建立条目（与 06-90 的 REQ-ENEMY-09 合并处置），常规与全队失去行动能力收束时敌方条目在收束后不再保留，随单局状态域在**结算提交完成时释放**；我方条目在战斗结束时保留（生命与伤势不清除）；撤退后事件在技术上仍为可进入，敌方条目连同其生命状态、伤势档、击倒标记与恢复进度随事件保留，玩家可以重新进入（架构案 9.5.4；设计决策记录决策 92）；恢复进程在战斗开始时转已终止。前置条件：当前阶段允许建立或销毁单局状态域对象（非结算阶段）。后置条件：条目集合与最近一次战斗状态、队伍状态一致；已建立条目的内容不因重复事件重置。副作用：条目建立与销毁结果经日志服务记录。异常情况：结算阶段收到建立或销毁请求；重复的 战斗开始 事件；事件载荷缺少单位集合；撤退后调用方请求销毁敌方条目；落库提交被拒绝。

### 5.3 功能之间的关系

- `API-BATTLE-004` 依次调用 `API-BATTLE-101`、`API-BATTLE-102`、`API-BATTLE-103`，再由 `API-BATTLE-108` 落库并发布 单位状态变化；任一环节判定为被拒绝时不做落库。
- `API-BATTLE-005` 复用 `API-BATTLE-103` 的判定结果对我方集合做聚合，只返回结论、不落库、不发事件。
- `API-BATTLE-104` 调用 `API-BATTLE-102` 的下降方向判定与 `API-BATTLE-108` 的落库，只发布档位下降引发的 单位状态变化。
- `API-BATTLE-105` 先调用 `API-BATTLE-107` 完成成对校验，再产出 `CLS-BATTLE-003`；`API-BATTLE-106` 与它共用 配置加载完成 触发点，产出 `CLS-BATTLE-008`。
- `API-BATTLE-001`、`API-BATTLE-002` 只读 `CLS-BATTLE-003`；`API-BATTLE-006`、`API-BATTLE-007` 只读静态登记，不触发装配；`API-BATTLE-107` 是属性、行为类别与伤害类别的唯一受理入口。

### 6.4 使用方式

- 启动阶段：本单元在单元装配声明中登记依赖关系并由启动物体按声明顺序注入相互引用（框架侧承担，不构成本单元的运行期依赖）；本单元由启动物体在初始化序列第 3 步显式完成初始化后，订阅 配置加载完成，由 `API-BATTLE-105` 与 `API-BATTLE-106` 装配台账与取数契约（架构案 2.4.1、6.1、8.3 第 1 条）。
- 运行期：单位状态结算由调用方直接调用 `API-BATTLE-004`；队伍行动能力判定由 06-A0 与 M10 直接调用 `API-BATTLE-005`；属性与类别口径查询由读取方直接调用 `API-BATTLE-001`、`API-BATTLE-002`、`API-BATTLE-006`、`API-BATTLE-007`。
- 事件侧：条目维护与恢复推进不轮询，由 战斗开始、战斗结束、队伍成员加入、队伍成员离队、队伍重置 与 时间刻度变化 经 `API-M01-012` 订阅后触发，本系统不解析事件的业务分支。
- 落库与告知：一切单位状态写入经 `API-SAVE-009`；拒绝与不通过项经 `API-M01-010` 记录；状态广播经 `API-M01-011`；配置对象运行期只读，不得就地修改（架构案 7.9）。

### 6.5 依赖方向限制

分层与模块是架构案的**描述性分类**，不承担数据隔离、交互隔离与依赖方向约束职责（架构案 1.6）。本节只用于阅读导航：列出本单元实际依赖的模块与方向，以及仍然成立的少量硬规则。调用是否合法的判据是架构案 3.3 的允许清单、3.4 的禁止清单与 8.1 的依赖方向规则；**同层只读查询按 3.3 第 5 项的通则成立，不需要逐条登记、不需要逐条例外申报**（架构案 8.1、8.2）。

- 实际依赖与方向：M01（基础设施：配置服务、日志服务、事件分发器、单局状态域）；01-50 存档与持久化（单局状态域的切面声明与提交接口，属基础设施）；01-40 角色与小队（属性取值的只读查询，架构案 3.3 第 5.1 项已登记；反向的属性台账只读查询同属第 5 项通则）；M09（元效果登记与结算分层层序的只读引用）；M10（编排方：战斗的启动、推进与收束由其编排，本系统只查询阶段并提供被其调用的判定与查询）；06-85 与 06-75（行为契约字段与效果定义的只读引用）；M05（本系统的宿主模块，战斗状态切面只在取数契约中引用其标识）。单元装配由启动物体与编辑器维护，不构成运行期跨单元依赖（架构案 2.4.1、6.1、8.3 第 1 条）。
- 不依赖 M08 及任何界面对象：战斗界面的绘制、布局、信息优先级、键位与操作方式归 M08 与后续界面设计阶段；本系统只给出四区块的取数归属与呈现规则，界面不得经本系统或绕过本系统修改任何游戏数据（架构案 3.4 第 3 项）。全量界面清单的权威来源是 `架构设计文档/界面索引.md`（界面 8 战斗界面；架构案 2.4、设计决策记录决策 94）。
- 不得被越权依赖：其他模块不得持有单位状态的**可变引用**，不得绕过 `API-BATTLE-004` 改写生命状态或伤势档；读取侧只允许经 `API-BATTLE-003` 取只读快照（快照不携带写入口、不得被缓存为自身数据来源），界面侧只允许经取数契约取数（架构案 3.4 第 5 项、8.2）。
- 与 M09 的往来：效果必须以元效果为唯一表达，任何模块不得绕过 M09 自行叠加效果或自行判定条件（架构案 3.4 第 8 项、7.11）。
- 与 M10 的往来：本系统只查询阶段（`API-M10-001`），战斗的启动与推进由 M10 编排并调用本系统的判定与查询（架构案 3.3 第 11、12 项）；本系统不反向调用 M10 的执行入口，不推进世界时间、不创建随机源、不读写存档文件（架构案 3.4 第 6、9、10、12 项与第 7 章）。

### 7.2 事件关系

跨模块事件的契约以**类型契约**的形式确定：本表逐事件登记事件名、方向、对方、载荷字段类别与失败语义；登记表以可检视的资产承载、按**即用即定**登记（需要新事件时直接在登记表补一行，不设审批、编号申领或版本流程）。契约的强制方式是**一条对账测试**：测试遍历代码中的全部事件发布点并与登记表逐项比对，出现未登记事件即测试失败；事件名不在契约登记表内属于契约缺口，由对账测试在测试期发现，不在运行期拦截，受理侧不做运行期登记校验（架构案 4.3、7.6、8.4 第 2 条、8.6 第 10 条；设计决策记录决策 95）。

| 事件 | 方向 | 对方 | 载荷字段类别 | 失败语义 |
| --- | --- | --- | --- | --- |
| 单位状态变化 | 发布 | 全部订阅方（M08、06-A0、06-85、06-90、01-50） | 单位标识、变化前后的生命状态与伤势状态（术语表 T-114）、起因行为标识（与 M05 §7.2 的登记同一组字段类别） | 订阅方处理失败不回滚单位状态 |
| 配置加载完成 | 订阅 | 配置服务（M01） | 配置版本标识 | 处理失败时属性台账与取数契约保持未装配，查询按未装配返回 |
| 时间刻度变化 | 订阅 | 时间服务（M01） | 世界时间刻度、推进量 | 处理失败不回滚时间推进；该次推进不计入恢复进度 |
| 战斗开始 | 订阅 | 战斗（M05） | 战斗实例标识、事件实例标识、战场标识、参战方清单、战斗目标清单（与 M05 §7.2 的登记同一组字段类别；本系统取用其中我方参战单位集合与敌方单位集合） | 处理失败不回滚战斗启动；条目在查询时按未建立返回 |
| 战斗结束 | 订阅 | 战斗（M05） | 战斗标识、战斗结果标识 | 处理失败不回滚战斗结束；生命与伤势不因战斗结束变更 |
| 队伍成员加入 | 订阅 | 队伍与角色（M07） | 成员标识 | 处理失败不影响成员加入，条目在战斗开始时补建 |
| 队伍成员离队 | 订阅 | 队伍与角色（M07） | 成员标识 | 处理失败不回滚离队，该成员移出我方集合 |
| 队伍重置 | 订阅 | 队伍与角色（M07） | 重置后的成员标识集合 | 处理失败不回滚重置，条目按重置结果在战斗开始时重建 |

## 8. 核心流程

### 8.1 战斗内的单位状态结算

- 触发：玩家在战斗界面确认一次行为，行为结果结算出伤害、恢复或伤势处理。参与者：本系统、行为结算方（06-40、06-80、06-30、06-A0）、元效果服务（M09）、01-40、单局状态域、事件分发器。
- 调用顺序：1 结算方按 `API-BATTLE-007` 取伤害类别口径；2 调用 `API-BATTLE-004`；3 `API-BATTLE-101` 判定生命状态；4 `API-BATTLE-102` 判定伤势档是否提升；5 `API-BATTLE-103` 判定击倒与行动能力；6 `API-BATTLE-108` 经 `API-SAVE-009` 落库；7 发布 单位状态变化。
- 状态变化：生命状态、伤势档、击倒标记按 3.2 迁移。产生的事件：单位状态变化。结束条件：判定结果已落库并发布事件；被拒绝时单位状态与落库内容保持受理前内容。

### 8.2 全队失去行动能力判定与事件收尾的承接

- 触发：单位状态结算使某个我方单位进入失去行动能力，或战斗目标判定需要全队行动能力结论。参与者：本系统、06-A0、M10（战斗执行入口 `API-M10-004`、事件执行器、结算执行器、阶段状态机）、M01 存档服务。
- 调用顺序：1 `API-BATTLE-003` 取我方单位状态快照；2 `API-BATTLE-005` 判定集合是否全部失去行动能力；3 判定成立时由 06-A0 写入战斗结果标识——战斗模块在全队失去行动能力时**只产生判定并写入战斗结果**，不在战斗内成立结局；4 M10 的战斗执行入口按战斗结果推进收尾窗口与事件退出（架构案 3.1 ARC-M05-001、9.5.5）；5 由 M10 的事件执行器在事件收尾时承接该判定结果，并在事件结算环节经事件结果提交成立结局、进入结算阶段。
- 状态变化：本系统只做只读判定，不改变单位状态；**不在战斗内成立结局**，本局终止不作为结局成立的入口。产生的事件：单位状态变化（已由 8.1 发布）；战斗结束由 M05 发布，结局成立由 M10 在事件结算环节发布。结束条件：判定结论与依据项返回；其后的收尾、结算与跨局写入不由本系统参与。
- 边界：结局成立的**唯一入口是事件结算环节的事件结果提交**，三种未通关收尾情形统一在该环节成立；结算阶段的进入条件是事件结果提交，不是「结局成立」；战斗阶段不直接退出到结算阶段（架构案 3.1 ARC-M05-001 与 ARC-M10-001、6.6 第 3 条、9.5.5；设计决策记录决策 90）。

### 8.3 伤势恢复随世界时间推进

- 触发：事件退出时由时间服务把事件内的记账一次性推进世界时间并广播 时间刻度变化（事件内只做时间记账、不动世界时间；架构案 7.5；设计决策记录决策 91）。参与者：本系统、M01 时间服务、收尾窗口与事件治疗入口、单局状态域、事件分发器。
- 调用顺序：1 经 `API-M01-012` 订阅 时间刻度变化；2 取出恢复进程为恢复中的单位条目；3 `API-BATTLE-104` 按推进量累计恢复进度；4 达到档位限度时由 `API-BATTLE-102` 给出下降后的伤势档；5 `API-BATTLE-108` 经 `API-SAVE-009` 落库；6 档位下降时发布 单位状态变化。
- 状态变化：恢复进度累加，伤势档逐档下降至未受伤；已终止的恢复进程不累计。产生的事件：单位状态变化（档位下降时）。结束条件：全部在途条目的恢复进度推进完毕；该次推进不构成额外的存档提交节点。

### 8.4 属性台账与登记扩展

- 触发：初始化序列第 2 步发布 配置加载完成（静态配置资产已由配置服务加载为内存形态），或新增属性、战斗行为与伤害类别的登记。参与者：本系统、M01 配置服务、06-85、数值侧、日志服务。
- 调用顺序：1 经 `API-M01-012` 订阅 配置加载完成；2 `API-BATTLE-107` 校验属性定义与读取关系成对、行为类别与 06-85 行为表一一对应、伤害类别口径非空；3 `API-BATTLE-105` 装配属性台账；4 `API-BATTLE-106` 装配战斗界面取数契约；5 不通过项经 `API-M01-010` 记录。
- 状态变化：属性台账 未装配→已装配或校验不通过；取数契约 未装配→已装配。产生的事件：无。结束条件：台账与取数契约可查询；不通过项已记录并等待上游补齐。

### 8.5 战斗界面的取数与呈现刷新

- 触发：界面栈打开战斗界面（`API-M08-001`），或收到 单位状态变化、轮次推进 后刷新。参与者：M08（战斗界面装配侧）、本系统、M05 战斗状态切面、06-20、06-30、06-40、06-50、06-80。
- 调用顺序：1 M08 调用 `API-BATTLE-008` 取四区块的取数归属与呈现规则；2 按契约从 `API-M05-005` 战斗状态切面与各子系统取数入口取数据本体；3 调用 `API-BATTLE-003` 取单位状态快照；4 调用 `API-BATTLE-006` 取技能面板的类别与职责；兜底选项经 06-85 的 `API-BATTLEACT-003` 取数，本系统不返回兜底项清单。
- 状态变化：界面呈现随数据刷新；界面不改变任何游戏状态。产生的事件：无（由 M08 订阅 单位状态变化 与 轮次推进）。结束条件：四区块可交互，且只有当前行动者显示可操作按钮。

## 9. 异常与边界情况

| # | 情形 | 判定条件 | 期望结果 |
| --- | --- | --- | --- |
| 1 | 结算阶段的状态变更 | 当前阶段为结算阶段（`API-M10-001`）且变更类别改变局内状态 | `API-BATTLE-004` 拒绝受理，单位状态与落库内容不变，记日志 |

| 4 | 集合为空或含非我方单位 | `API-BATTLE-005` 收到空集合，或集合中出现敌方单位、非参战单位 | 前置条件不满足，拒绝受理并返回缺失项，不按部分集合给出结论 |

| 13 | 落库提交被拒 | `API-SAVE-009` 拒绝或失败 | 判定结果不落库，返回值标记失败，单位状态保持受理前内容并可重试 |
| 14 | 读档恢复期间的状态写入 | 单局状态域处于装载或恢复期间 | 拒绝受理，恢复完成后按快照内容重建条目与恢复进度 |

| 16 | 取数来源未登记 | 四区块中的某个取数来源接口 ID 待补 | 该区块取数契约标记来源缺失，界面按缺失提示处置，不以内置数据代替 |

| 18 | 战斗内要求成立结局 | 收束路径要求本系统成立结局，或要求把阶段直接从战斗阶段切入结算阶段 | 拒绝：本系统只产生判定并写入战斗结果，由事件执行器在事件收尾时承接；结局成立的唯一入口是事件结算环节的事件结果提交，战斗阶段不直接退出到结算阶段（架构案 6.6 第 3 条、9.5.5；设计决策记录决策 90） |

## 10. 实现约束

### 10.1 实现约束条目

- 角色属性必须只有一份权威清单，取值由 01-40 提供、台账由本系统维护；运行期权威载体是引擎编辑器内的配置资产（设计库的 `10_角色属性表.csv` 只是设计侧的认领台账，用于设计评审与枚举契约登记，程序侧不直接读表）；属性定义与读取关系登记必须成对存在，未成对登记的属性不得进入台账，也不得被读取方使用（架构案 5.1、7.9、8.6 第 10 条；设计决策记录决策 93）。
- 常驻对象由常驻场景承载，只能由启动物体按单元装配声明顺序显式初始化并按逆序销毁；**不设统一的持有容器，不设解析入口，不设静态单例就地取用**（架构案 2.4.1、2.4.2、6.1、7.11、8.3 第 1 条）。
- 单位状态必须分生命状态与伤势状态两层独立登记；两层不得合并为单一取值，也不得由其他系统另立等价机制。
- 单位状态的一切变更必须经 `API-BATTLE-004`，落库必须经单局状态域的提交入口；任何模块不得持有单位状态的可变引用并改其字段，本系统不得自行序列化状态或读写存档（架构案 3.4 第 5、6 项、7.1、8.2）。
- 单位状态必须可序列化；存档序列化采用**判别字段式多态序列化**——序列化结果中只出现自定义的字符串判别值，不写入运行时类型名，多态类型按判别值映射；不得使用已被运行时移除实现的二进制序列化机制；单局存档的写入必须原子，读档时未确认的操作不恢复（架构案 5.3 第 4、5 项、7.1、8.6 第 8 条）。判定结果、台账与取数契约属派生项，只按来源重建，不入档。
- 退出游戏即**进程终止**，退出不提交存档、不构成任何提交点、不依赖任何退出回调完成存档或收尾；单位状态的唯一可靠写路径是时间段推进与战斗轮次推进两类自动保存节点（架构案 3.4 第 17 项、5.3、7.1、9.4；设计决策记录决策 89）。
- 全队失去行动能力时只产生判定并写入战斗结果，不在战斗内成立结局；结局成立的唯一入口是事件结算环节的事件结果提交，结算阶段的进入条件是事件结果提交，战斗阶段不直接退出到结算阶段（架构案 3.1 ARC-M05-001、6.6 第 3 条、9.5.5；设计决策记录决策 90）。
- 单位状态条目与恢复进程在结算阶段不得建立、销毁或变更；单局状态域内容随单局创建，结算提交完成时释放，开新局时全部重建（架构案 6.6、8.3 第 3、5 条）。
- 战斗行为的类别与职责由本系统登记，逐行为契约字段归 06-85；两者必须双向一一对应，任何一处不得重复登记对方的字段，且不得登记允许行为合并的类别（一次行动机会只执行一项行为）。
- 效果必须以元效果为唯一表达；本系统不得实现效果叠加，也不得实现条件判定（架构案 3.4 第 8 项、7.11）。
- 属性取值必须经 01-40 的取值能力取得；本系统不得持有取值的副本，也不得按派生结果反推来源状态（架构案 8.2 第 3 项；架构案 3.3 第 5.1 项已登记该只读依赖）。
- 本系统不得创建随机源、不得推进世界时间（架构案 3.4 第 9、10 项）。
- 含常驻集在内的**全部资产**经引擎的可寻址资源机制加载与释放，加载路径**只有一条**；本单元不发起资源加载与场景装卸，任何模块不得自行加载资源文件（架构案 7.2）。
- 跨模块事件契约以**类型契约**的形式确定并由**一条对账测试**强制：测试遍历全部事件发布点并与登记表逐项比对，出现未登记事件即测试失败；受理侧不做运行期登记校验（架构案 4.3、7.6、8.4 第 2 条）。
- 战斗界面取数契约只登记取数归属与呈现规则，不得携带数据本体与写入口；全量界面清单的权威来源是 `架构设计文档/界面索引.md`；界面不得经本系统修改任何游戏数据（架构案 2.4、3.4 第 3 项；设计决策记录决策 94）。
- 待上游补充的字段（单位状态限度取值、伤害类别口径、恢复推进口径）为空时，相关判定必须返回拒绝而非取默认值。

### 10.2 实现要求

- I-BATTLE-01 属性定义与属性读取关系登记必须成对登记，未成对登记的属性不得进入属性台账。
- I-BATTLE-02 单位状态必须以生命状态与伤势状态两个独立状态集登记，不得合并为单一状态。
- I-BATTLE-03 单位状态变更必须经 `API-BATTLE-004`，其他模块只读；落库必须经单局状态域的提交入口。
- I-BATTLE-04 单位状态必须可序列化；序列化采用判别字段式多态序列化，序列化结果中只出现自定义的字符串判别值、不写入运行时类型名，多态类型按判别值映射；单局存档的写入必须原子；单位状态判定结果、属性台账与取数契约不得入档，只按来源重建。
- I-BATTLE-05 结算阶段不得建立、销毁或变更单位状态条目与恢复进程；单局状态域内容在结算提交完成时释放，开新局时全部重建。
- I-BATTLE-06 战斗行为类别登记必须与 06-85 的行为表双向一一对应，不得重复登记逐行为契约字段。
- I-BATTLE-07 行为类别不得提供行为合并的登记项，一次行动机会只执行一项行为。
- I-BATTLE-08 效果必须经元效果表达，本系统不得实现效果叠加与条件判定。
- I-BATTLE-09 属性取值必须经 01-40 的取值能力取得，不得缓存或反推。
- I-BATTLE-10 取数契约不得携带数据本体与写入口，界面不得经本系统修改游戏数据。
- I-BATTLE-11 待上游补充字段为空时相关判定必须返回拒绝，不得以默认值代替。
- I-BATTLE-12 不得重复实现引擎已提供的能力：对象池与集合池、异步任务、设备到动作的输入映射、音频与本地化与特效动画的播放原语、资产载体与序列化原语、资源加载、场景装卸与日志通道一律使用引擎提供的能力，本单元只做架构案 7.12「项目实现」栏登记的部分（架构案 7.12、8.6 第 1 条）。
- I-BATTLE-13 权威游戏状态由普通 C# 对象持有，引擎对象只承担承载、呈现与编辑器配置职责；本单元不得把单位状态、属性台账与取数契约等权威状态放在随场景销毁的对象上（架构案 8.6 第 2 条）。
- I-BATTLE-14 不依赖引擎的启动回调顺序、脚本执行顺序或帧回调顺序满足初始化与推进的顺序要求；顺序由单元装配声明与显式调用序列决定，本单元在初始化序列第 3 步按声明顺序完成初始化（架构案 6.1、6.3、8.6 第 4 条）。
- I-BATTLE-15 本单元在初始化时显式复位自身状态，不依赖引擎的域重载提供初始状态（架构案 6.1、8.3 第 7 条、8.6 第 5 条）。
- I-BATTLE-16 影响游戏状态的判定不得使用帧时间；本作为半回合制，玩家不操作时游戏状态不推进，**不设暂停概念**，本单元不得以暂停为由冻结数据或引入暂停语义（架构案 3.4 第 16 项、7.4、8.6 第 6 条；设计决策记录决策 87、88）。
- I-BATTLE-17 空间判定归 06-30 的网格与坐标逻辑，本单元不承担空间判定；物理与动画只用于表现，表现对象与数据对象分离（架构案 8.6 第 7 条）。
