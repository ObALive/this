单元说明：本系统是 `01-通用系统` 域新增的通用系统之一，承载**元对象加组件的统一构建规范**：元对象是什么、组件是什么、标识怎么发、组件怎么挂载与查询、生命周期与存档粒度怎么定、扩展怎么登记。角色、物品、装备、遗物、技能与场地道具的**具体组件族**不在本系统定义，由各自所属系统按本规范写下（`SYS-ITEM-001` 物品系统、`SYS-EQUIP-001` 装备系统、`SYS-RELIC-001` 遗物系统、`SYS-PARTY-001` 角色与小队、`SYS-SKILLDEF-001` 元技能、`SYS-FIELD-001` 战场与战棋规则）。本系统只提供底座与登记处，不提供任何具体玩法功能。对象与组件的登记表原由 M04 模块单元文档承载（`CLS-M04-001`、`CLS-M04-002`），按「元对象编入通用系统」的口径迁入本系统，迁移与编号处置见 2.6 与第 10.3 节的缺口 `REQ-OBJ-01`。

## 1. 系统定义

### 1.1 系统目的

本系统的对象标识为 `SYS-OBJ-001 元对象与组件`。

本系统为全部「由组件组合出功能的程序实体」提供同一套构建规范与同一个登记处：谁有标识、标识怎么发、组件怎么登记、怎么挂、怎么查、状态存在哪、生命周期跟谁走、存档存到什么粒度。它存在的理由是避免每一类实体各自发明一套「定义加实例加能力」的模型：角色、物品、装备、遗物、技能与场地道具都是元对象定义加组件构成，能力差异全部由组件组合表达，不由实体类别决定。

### 1.2 系统职责

- 持有并维护**对象与组件注册表**：登记元对象定义与组件定义的标识、能力类别与挂载契约，是「新增组件必须先登记」的唯一落点（架构案 7.11）；
- 持有**组件能力描述项**：逐组件登记能力类别、适用条件声明与挂载契约，供实例的组件构成解析与能力判定取数；
- 定义**实体类型登记**：实体类型码的登记与查询，使「哪些实体属于同一套元对象模型」有唯一清单，且新增实体类型不改动内核；
- 定义**实体标识发布规则**：实体标识的构成、唯一性范围、跨系统引用的书写方式，以及标识与实体类型、元对象定义的对应关系；
- 定义**组件挂载与生效契约**：组件在元对象定义侧与实例侧的挂载关系、挂载前置条件、同类别组件的并存与互斥口径、挂载变更时的启停口径；
- 定义**组件状态归属与存储位置**：哪些组件状态属于实例、哪些属于元对象定义、哪些是派生缓存；
- 定义**元对象实例的生命周期与存档粒度**：实例随什么创建、随什么销毁、入不入档、入档时的切面归属与判别字段式多态序列化的口径；
- 提供**组件能力查询**：按实例或元对象标识与能力类别返回能力可用性与配置取值的只读结果，供各系统判定前取数；
- 定义**派生缓存的统一口径**：由组件状态派生的结果按来源状态重建、不入档、不作为数据来源（架构案 8.2 第 3 条）；
- 受理**登记项校验**：标识唯一性、挂载契约完整性、能力类别已登记、类型码已登记，校验失败即拒绝该登记项（架构案 7.9、8.6 第 10 条）。

### 1.3 系统边界

本系统不负责：

- 任何具体组件族的定义与规则：容器、堆叠、价值、装备槽适配、遗物词条、投掷、符文书页、角色属性、装备槽等组件的判定与状态变化归各自所属系统（见 1.2 的落点清单）；
- 元效果（术语表 T-132）的构成、同名判定、强度方向、叠加顺序与生命周期：归 M09 的效果服务（`API-M09-001` 至 `API-M09-003`）与 06-75 元效果系统；
- 条件求值：归 M09 的条件求值服务（`API-M09-004`），本系统不自行实现条件判定；
- 物品状态变化的落库：唯一写入入口是 M09 的物品与经济写入服务（`API-M09-005`），本系统不落库、不自行序列化状态（架构案 3.4 第 7 项、7.11）；
- 实体归属、容器格位与嵌套关系的具体规则：归 05-05 与 05-30；
- 装备槽、遗物槽的槽位模型与占用：归 06-60 与 06-70；
- 角色属性取值、主角标识与队伍成员：归 01-40，属性集合与含义的权威清单归 06-10；
- 技能定义的构筑骨架、成本串与产出串、继承效果：归 `SYS-SKILLDEF-001` 元技能，技能的使用侧归 06-40 技能系统；
- 存档结构、切面采集与提交：归 M01 的存档服务与 01-50，本系统只声明实例状态的切面归属与序列化口径；
- 资源加载与元对象定义资产的装载：归 M01 的资源服务与配置服务（`API-M01-003`、`API-M01-008`），本系统不自行加载资源；
- 引擎已提供能力的重复实现：对象的池化使用引擎的通用池与集合池，项目只保留薄封装层（架构案 7.12）。

### 1.5 功能要求

- F-OBJ-01 角色、物品、装备、遗物、技能与场地道具一律由「元对象定义 + 组件」构建，能力差异由组件组合表达，不按用途或类别建立互斥判断，也不为某一类实体另立一套「定义加实例加能力」的模型（`05_物品系统设计.md` 1 与 2.2；`06_装备系统设计.md` 1；`06_遗物系统设计.md` 1 与 4）。
- F-OBJ-02 新增一项能力时优先扩展组件；只有无法由现有组件组合表达的稳定能力，才新增组件类型，且必须先登记后使用（架构案 5.1 第 1 条、7.11）。
- F-OBJ-03 实体标识在全库唯一、一经分配不再变更、不复用；跨系统引用一律以实体标识书写，不以实体类别名或用途名书写。
- F-OBJ-04 元对象定义与组件定义是引擎编辑器内的配置资产，运行期只读，不带热重载（架构案 5.1、7.9、8.6 第 10 条）。
- F-OBJ-05 由组件状态派生的结果按来源状态重建、不入档、不作为数据来源（架构案 8.2 第 3 条）。
- F-OBJ-06 新增组件类型、实体类型或挂载契约时，先在本系统的注册表内登记，登记项校验不通过即拒绝（架构案 7.11、8.6 第 10 条）。

| `PROP` | 场地道具 | 05-05 定义组件、06-30 定义战场条目 | 06-30（战场侧条目） |

**类型码本身是扩展点**：新增实体类型时按 8.3 登记类型码与允许挂载的组件类别，内核不改动。类型码不写进存档，存档只写实体标识与组件状态。

### 2.3 外部数据引用

本系统只引用下列数据的标识与只读内容，不重新定义其职责与结构：

- 静态配置资产与配置版本标识（M01，`API-M01-003`）：元对象定义、组件定义与类型码登记的取数来源；运行期只读（架构案 5.1、7.9）；
- 单局状态域结构与切面（M01，接口由 01-50 给出，`API-SAVE-001`、`API-SAVE-008`、`API-SAVE-009`）：实例与组件状态的入档与恢复；
- 物品与经济写入服务（M09，`API-M09-005`）：物品侧实例状态变化的唯一落库入口；
- 元效果服务（M09，`API-M09-001` 至 `API-M09-003`）：组件所声明的效果以元效果标识引用，效果的施加与移除归该服务；
- 条件求值服务（M09，`API-M09-004`）：组件挂载前置条件中的条件判定归该服务；
- 各实体类型系统已定义的对象：物品侧 `CLS-ITEM-*`（05-05）、装备侧 `CLS-EQUIP-*`（06-60）、遗物侧 `CLS-RELIC-*`（06-70）、角色侧与小队侧 `CLS-PARTY-*`（01-40）、战场侧 `CLS-FIELD-*`（06-30）、技能侧 `CLS-SKILLDEF-*`（`SYS-SKILLDEF-001`）与 `CLS-SKILL-*`（06-40）。本系统只定义这些对象**共用的形态与登记**，不重定义其业务规则。

### 2.4 数据关系

- 包含：`CLS-OBJ-001` 收录 `CLS-OBJ-002` 与各系统的元对象定义标识；`CLS-OBJ-005` 聚合 `CLS-OBJ-006`。
- 派生：`CLS-OBJ-008` 由 `CLS-OBJ-001` 的装配派生；`CLS-OBJ-009` 由 `CLS-OBJ-005` 的组件状态与 `CLS-OBJ-002` 的契约派生；由组件状态派生的一切结果（背包空间、同名遗物效果、继承效果、价值评估、可调取范围等）按来源状态重建、不入档、不作为数据来源（架构案 8.2 第 3 条）。
- 引用：`CLS-OBJ-004` 引用 `CLS-OBJ-003` 的类型码与 `CLS-OBJ-002` 的组件定义；`CLS-OBJ-005` 引用 `CLS-OBJ-004`；`CLS-OBJ-006` 按 `CLS-OBJ-007` 的契约校验。
- 并列：元对象定义（静态）与元对象实例（运行时）严格分离，同一实体的定义不随局重置、实例随局创建与释放；本系统不提供把定义写入存档的路径。
- 迁移：`CLS-M04-001` 与 `CLS-M04-002` 两个对象的定义权由 M04 模块单元文档迁入本系统，编号改为 `CLS-OBJ-001` 与 `CLS-OBJ-002`，原编号按 NR-06 §九.4 停用不复用（见 2.6）。

### 2.5 数据生命周期

- 常驻对象：`CLS-OBJ-001` 由常驻场景承载，由启动物体按单元装配声明顺序显式初始化、按逆序销毁，进程内唯一实例（架构案 2.4.1、2.4.2、6.1、6.3、8.3 第 1 条）。
- 静态配置对象：`CLS-OBJ-002`、`CLS-OBJ-003`、`CLS-OBJ-004`、`CLS-OBJ-007` 按引擎编辑器内的配置资产在启动阶段经 `API-M01-003` 取得内存形态，运行期只读，进程退出前不销毁（架构案 5.1、7.9）。
- 数据域对象：`CLS-OBJ-005` 与 `CLS-OBJ-006` 随单局创建，结算提交完成时随单局状态域释放，开新局时全部重建（架构案 5.2.2、6.6、8.3 第 3 条）；实例的常规销毁由所属业务系统按其受理接口触发。
- 临时运行对象：`CLS-OBJ-008`、`CLS-OBJ-009` 在单次装配或单次查询内有效，不跨帧保留、不入档（架构案 6.5）。
- 状态复位：本系统常驻对象在初始化时显式复位自身状态，不假定引擎已提供初始状态（架构案 6.1、8.3 第 7 条）。

### 2.6 持久化要求

| 需入档的数据 | 切面归属 | 恢复时的重建步骤 |
| --- | --- | --- |
| `CLS-OBJ-005` 元对象实例与 `CLS-OBJ-006` 组件状态 | 单局存档的单局状态域切面（架构案 5.2.2；经 `API-SAVE-001` 登记） | 按单局状态域次序恢复；恢复后由各系统按自身对象重建归属链、容器格位与槽位占用；派生结果按来源重建，不参与入档 |
| 实例与组件状态的序列化形态 | 与三个域切面同一份结构 | 采用**判别字段式多态序列化**：序列化结果中只出现自定义的字符串判别值（实体类型码与组件类别判别值），**不写入运行时类型名**，多态组件状态按判别值映射（架构案 7.1、8.6 第 8 条）；实体标识与类型码的对应关系按 `CLS-OBJ-003` 的登记解析 |

不入档项：`CLS-OBJ-001` 至 `CLS-OBJ-004`、`CLS-OBJ-007` 按启动阶段重建；`CLS-OBJ-008`、`CLS-OBJ-009` 为临时运行对象；由组件状态派生的一切结果按来源重建，不作为数据来源。本系统不自行序列化状态，采集与提交一律经 01-50 的存档服务与数据域入口（`API-SAVE-001`、`API-SAVE-009`）。

**对象与组件登记表的迁移说明**：M04 模块单元文档原持有的 `CLS-M04-001 对象与组件注册表` 与 `CLS-M04-002 组件能力描述项` 两项，自本轮起改由本系统定义，编号为 `CLS-OBJ-001` 与 `CLS-OBJ-002`。原编号不再分配、不复用（NR-06 §九.4）。M04 的 `API-M04-002 组件能力查询` 的**登记侧定义**随之一并迁入本系统的 `API-OBJ-002`；`API-M04-002` 的编号保留，改为只承载物品侧的组件能力取数口径（能力类别取值的物品侧解释），不重复登记处。此项迁移需上游确认，见缺口 `REQ-OBJ-02`。

## 3. 状态定义

### 3.1 状态

| 对象 | 状态取值 |
| --- | --- |
| 对象与组件注册表 `CLS-OBJ-001` | 未登记 → 校验中 → 已就绪；校验中 → 冲突中止 |
| 组件能力描述项 `CLS-OBJ-002` | 无自身状态（登记项校验通过／不通过） |
| 实体类型登记 `CLS-OBJ-003` | 已登记／待补充 |
| 元对象定义 `CLS-OBJ-004` | 已登记／待补充 |
| 元对象实例 `CLS-OBJ-005` | 已创建 → 已归属 → 已销毁 |
| 组件状态 `CLS-OBJ-006` | 未生效 → 已生效 → 已停用 |
| 挂载契约 `CLS-OBJ-007` | 已登记／契约缺项 |
| 登记校验结果 `CLS-OBJ-008` | 校验中 → 通过／不通过 |
| 能力查询结果 `CLS-OBJ-009` | 可用／不适用 |

### 3.2 状态转换

```
对象与组件注册表：未登记 → 校验中 → 已就绪 ／ 校验中 → 冲突中止（中止启动）
元对象实例：已创建 → 已归属 → 已销毁
组件状态：未生效 → 已生效 ⇄ 已停用
登记校验结果：校验中 → 通过 ／ 校验中 → 不通过
能力查询结果：可用 ／ 不适用（单次查询内取值，不跨次保持）
```

### 3.3 状态转换触发条件

| 转换 | 触发行为或事件 | 对应接口 |
| --- | --- | --- |
| 未登记 → 校验中 → 已就绪 | 启动阶段按配置资产登记元对象定义与组件定义，校验标识唯一性、能力类别已登记、类型码已登记与挂载契约完整性 | `API-OBJ-003`（登记侧装配）；事件「配置加载完成」 |
| 校验中 → 冲突中止 | 登记项标识重复、能力类别未登记或挂载契约缺项 | 无（中止启动并报出不通过项，架构案 7.9、8.6 第 10 条） |
| 已创建 → 已归属 | 实例经装载、拾取、交易或构建受理获得归属 | 各实体类型系统的受理接口（物品侧 `API-ITEM-006`、`API-M04-003`） |
| 已归属 → 已销毁 | 数量减至零、被交付耗尽或所属业务对象销毁 | 各实体类型系统的受理接口 |
| 未生效 → 已生效 ⇄ 已停用 | 组件随实例归属、装备槽占用或触发条件变化而启停 | 各实体类型系统的受理接口；效果类组件的启停经 `API-M09-001`、`API-M09-002` |
| 校验中 → 通过／不通过 | 登记项校验执行完成 | `API-OBJ-003` |
| 可用／不适用 | 一次能力查询的判定结论 | `API-OBJ-002` |

状态转换与第 4 节接口表的状态变化列一致；组件状态的启停由各实体类型系统受理，本系统不提供启停入口。

### 4.2 接口详细定义

#### API-OBJ-001 元对象定义查询

职责：按定义类别、实体类型码与元对象标识返回元对象定义的只读快照。

输入：
- 参数输入：定义类别、实体类型码、元对象标识或筛选条件、查询用途上下文
- 状态输入：注册表就绪状态
- 数据输入：`CLS-OBJ-004` 元对象定义、`CLS-OBJ-002` 组件能力描述项、`CLS-OBJ-003` 实体类型登记
- 外部事件输入：无

读取：`CLS-OBJ-001` 对象与组件注册表、`CLS-OBJ-002` 组件能力描述项、`CLS-OBJ-003` 实体类型登记、`CLS-OBJ-004` 元对象定义。

输出：
- 返回值：元对象定义只读快照（标识、类型码、组件定义清单与逐组件的配置取值）
- 状态输出：无
- 事件输出：无
- 外部系统调用：无

产生的状态变化：无。

前置条件：注册表处于已就绪状态；实体类型码已在 `CLS-OBJ-003` 登记；查询方落在架构案 3.3 允许的依赖方向内。

后置条件：返回内容为只读形态，不携带写入面（架构案 7.9）；快照不含任何跨系统的业务判定结论。

副作用：无。

异常情况：注册表尚未就绪（返回失败并记录日志）；类型码或元对象标识未登记；请求写入（拒绝，运行期配置只读）；结算封闭期间请求影响局内状态的写入面（拒绝，架构案 6.6）。

#### API-OBJ-002 组件能力与登记查询

职责：按元对象标识或实例标识与能力类别，返回能力是否可用、配置取值与登记契约的只读结果。

输入：
- 参数输入：元对象标识或实例标识、能力类别（容器、堆叠、价值、装备槽适配、遗物词条、投掷、符文书页、消耗使用、地形、角色属性、技能成本串等）、查询用途上下文
- 状态输入：`CLS-OBJ-005` 的组件构成与 `CLS-OBJ-006` 的组件状态
- 数据输入：`CLS-OBJ-002` 组件能力描述项、`CLS-OBJ-007` 组件挂载契约
- 外部事件输入：无

读取：`CLS-OBJ-001` 对象与组件注册表、`CLS-OBJ-002` 组件能力描述项、`CLS-OBJ-005` 元对象实例、`CLS-OBJ-006` 组件状态、`CLS-OBJ-007` 组件挂载契约。

输出：
- 返回值：能力可用性与配置取值的只读结果；未登记时给出登记缺口说明（能力类别未登记或该类型码不允许挂载该类别）
- 状态输出：无
- 事件输出：无
- 外部系统调用：无

产生的状态变化：无（`CLS-OBJ-009` 为单次查询内的临时结果）。

前置条件：注册表处于已就绪状态；能力类别已登记；实例存在或元对象定义已登记。

后置条件：结论只依据登记项与实例的组件状态，不引入未登记的能力推断。

副作用：无。

异常情况：实例不存在；能力类别未登记；该类型码不允许挂载该类别组件（返回不适用并给出类型码与类别）；同一实例存在多个同类别组件且契约未声明并存口径（返回契约冲突并记录日志，架构案 5.1 第 1 条）。

#### API-OBJ-003 登记项校验与装配受理

职责：在启动阶段受理登记项集合，校验标识唯一性、能力类别已登记、类型码已登记与挂载契约完整性，产出校验结论与不通过项清单。

输入：
- 参数输入：待校验的登记项集合（元对象定义标识、组件定义与能力类别、实体类型码、挂载契约）
- 状态输入：`CLS-OBJ-001` 注册表状态
- 数据输入：引擎编辑器内的配置资产（经 `API-M01-003` 取得内存形态）
- 外部事件输入：配置加载完成

读取：`CLS-OBJ-001` 至 `CLS-OBJ-004`、`CLS-OBJ-007`。

输出：
- 返回值：校验结论与不通过项清单（逐条给出登记项、字段与原因）
- 状态输出：注册表由未登记经校验中到已就绪或冲突中止
- 事件输出：无（校验结论并入「配置加载完成」的载荷）
- 外部系统调用：`API-M01-010` 日志服务.Write

产生的状态变化：注册表与登记项建立；不通过项标注。

前置条件：配置服务可用；登记项集合自配置资产给出。

后置条件：已就绪时全部登记项的标识唯一、能力类别与类型码均已登记、挂载契约字段齐备。

副作用：不通过项经日志服务记录。

异常情况：标识重复；能力类别未登记；类型码未登记；挂载契约缺项（缺挂载前置条件、并存与互斥口径、启停口径或状态归属之一）；登记项引用的元对象定义不存在；结算阶段受理新增登记（拒绝，架构案 6.6）。

#### API-OBJ-004 组件挂载受理

职责：受理实例或元对象定义上的组件挂载与卸下，按挂载契约校验并改变组件状态。

输入：
- 参数输入：实例或元对象标识、组件定义标识、挂载操作类别（挂载／卸下）
- 状态输入：`CLS-OBJ-005` 元对象实例、`CLS-OBJ-006` 组件状态、当前阶段取值
- 数据输入：`CLS-OBJ-002` 组件能力描述项、`CLS-OBJ-007` 组件挂载契约
- 外部事件输入：无

读取：`CLS-OBJ-002` 组件能力描述项、`CLS-OBJ-004` 元对象定义、`CLS-OBJ-005` 元对象实例、`CLS-OBJ-006` 组件状态、`CLS-OBJ-007` 组件挂载契约。

输出：
- 返回值：受理结论与失败原因
- 状态输出：`CLS-OBJ-006` 新增、生效或停用；实例的组件构成变化
- 事件输出：无（变更事实由所属系统的受理接口发布，物品侧发布「物品归属变化」「容器内容变化」）
- 外部系统调用：物品侧落库经 `API-M09-005`；效果类组件的启停经 `API-M09-001`、`API-M09-002`；挂载前置条件中的条件判定经 `API-M09-004`

产生的状态变化：组件状态新增、由未生效到已生效或由已生效到已停用。

前置条件：注册表已就绪；待挂载的组件定义已登记；实例存在或元对象定义可解析；挂载前置条件满足。

后置条件：组件构成与登记契约一致；被卸下的组件状态保留在实例内且标记为已停用（供装备槽切换、卸下后重新启用等场景使用）。

副作用：卸下后组件所提供的效果停止生效，由效果服务执行；不改变实例的归属与容器内容。

异常情况：组件未登记（拒绝，架构案 7.11）；该类型码不允许挂载该类别；同类别组件互斥冲突；挂载前置条件不满足；实例不存在；结算阶段受理影响局内状态的挂载变更（拒绝，架构案 6.6）；运行期请求新增组件定义（拒绝，配置运行期只读）。

#### API-OBJ-005 能力类别登记查询

职责：返回已登记的能力类别清单与其定义方，供新增组件时的查重与登记填写。

输入：
- 参数输入：能力类别标识（可选，缺省时返回全部清单）
- 状态输入：注册表就绪状态
- 数据输入：`CLS-OBJ-002` 组件能力描述项
- 外部事件输入：无

读取：`CLS-OBJ-001` 对象与组件注册表、`CLS-OBJ-002` 组件能力描述项、`CLS-OBJ-003` 实体类型登记。

输出：
- 返回值：能力类别清单（类别标识、定义方、允许挂载的类型码集合）
- 状态输出：无
- 事件输出：无
- 外部系统调用：无

产生的状态变化：无。

前置条件：注册表已就绪。

后置条件：清单与登记表逐项一致。

副作用：无。

异常情况：注册表尚未就绪；能力类别未登记（返回空结果并提示未登记，不隐式创建类别）。

## 5. 内部功能

### 5.1 功能列表

| 功能 | 对外暴露 | 说明 |
| --- | --- | --- |
| 登记项装配与唯一性校验 | 部分是（经 `API-OBJ-003`） | 按配置资产装配元对象定义、组件定义、类型码与挂载契约，校验标识唯一性与字段齐备 |
| 能力类别与类型码一致性校验 | 否（经 `API-OBJ-003`） | 校验每个类型码允许挂载的组件类别均已登记，且每个组件的能力类别有定义方 |
| 挂载契约解析 | 否（经 `API-OBJ-003`、`API-OBJ-004`） | 解析挂载前置条件、并存与互斥口径、启停口径与状态归属 |
| 组件构成解析 | 否（经 `API-OBJ-001`、`API-OBJ-002`） | 由元对象定义与实例的组件状态组装只读的组件构成视图 |
| 能力判定 | 否（经 `API-OBJ-002`） | 按能力类别与组件状态判定可用性，产出可用或不适用与理由 |
| 挂载变更受理与启停联动 | 否（经 `API-OBJ-004`） | 挂载与卸下的校验与执行，联动效果类组件的启停 |
| 类型码登记查询与扩展受理 | 部分是（经 `API-OBJ-005`；扩展按 8.3 登记） | 新增实体类型时登记类型码与允许挂载的组件类别 |
| 实例状态的切面声明与重建口径维护 | 否 | 声明实例与组件状态的切面归属与判别字段口径，配合 01-50 的采集与恢复 |

### 5.2 功能之间的关系

- 启动序：登记项装配与唯一性校验 → 能力类别与类型码一致性校验 → 挂载契约解析 → 注册表已就绪；以上由 `API-OBJ-003` 在启动阶段一次完成，失败即中止启动（架构案 6.1 阶段 2、8.6 第 10 条）。
- 运行序：组件构成解析 → 能力判定；两者由各实体类型系统的受理接口在判定前触发，本系统只出结论、不做业务判定。
- 变更序：挂载变更受理与启停联动由各实体类型系统的实例构建与构建变更触发；卸下只停用组件状态，不删除条目。
- 切面序：实例与组件状态的切面声明在系统初始化时登记，采集与恢复由 01-50 驱动；派生结果不参与。
- 扩展序：新增能力类别或实体类型时先经 `API-OBJ-005` 查重，再在编辑器内的配置资产补登，启动校验通过后生效。

### 6.4 使用方式

- 静态配置：元对象定义与组件定义在启动阶段经 `API-M01-003` 取得内存形态，本系统只做结构与登记一致性校验，不解释条目业务含义（架构案 5.1、7.9）。
- 登记与校验：登记在编辑器内维护，运行期只读；校验由 `API-OBJ-003` 在启动阶段一次完成，失败即中止启动（架构案 7.11、8.6 第 10 条）。
- 实例状态：本系统拥有实例与组件状态的形态契约，写入一律经各实体类型系统自身的受理接口；物品侧的落库经 M09 的写入服务，本系统不落库、不自行序列化（架构案 3.4 第 7 项、7.11）。
- 效果类组件：效果的构成与生命周期归 M09 与 06-75，本系统只在挂载变更时联动其启停调用。
- 条件与派生：挂载前置条件与派生结果一律经 M09 的条件求值服务或按来源重建，不自行实现判定。

### 6.5 依赖方向限制

- 被依赖方向：全部实体类型系统经本系统查询元对象定义与组件能力；本系统是它们的共同底座，处于比各实体类型系统更低的依赖位置。
- 依赖方向：本系统只依赖 M01、01-50 与 M09，不依赖任何具体玩法系统；对 ITEM、EQUIP、RELIC、PARTY、SKILLDEF、FIELD 的引用是**定义引用的反向说明**（本系统不调用它们，只在 2.1 的类型码表中登记定义方）。
- 禁止方向：任何实体类型系统不得把自身的组件族规则写进本系统；本系统不得出现对具体玩法系统的运行期调用；任何模块不得绕过本系统自行登记或挂载组件（架构案 3.4 第 6 至 11 项、7.11）。
- 硬规则：
  1. 不写入他方数据、不持有对方的可变引用（架构案 3.4 第 5 项、8.2）；
  2. 不重复实现引擎已提供的能力（架构案 7.12、8.6 第 1 条）；
  3. 权威游戏状态由普通 C# 对象持有，引擎对象只承担承载、呈现与编辑器配置职责（架构案 8.6 第 2 条）；
  4. 不形成循环依赖；跨模块状态广播走事件通道（架构案 3.4 第 12 项、8.4 第 1 条）。

### 7.3 数据流

- 运行：各实体类型系统的受理接口 → `API-OBJ-004` 挂载变更 → `CLS-OBJ-006` 状态变化 → 效果类组件经 `API-M09-001`、`API-M09-002` 启停；判定前经 `API-OBJ-002` 取能力结论。
- 存档：`CLS-OBJ-005`、`CLS-OBJ-006` 经 01-50 的切面能力流入单局存档；恢复时按实体标识与判别值重建，派生结果不参与（架构案 5.2.2、7.1）。

## 8. 核心流程

### 8.1 启动阶段的登记项装配与校验
触发：启动阶段配置装载完成（架构案 6.1 阶段 2）。
参与者：启动装配序列、本系统、各实体类型系统的定义方。
调用顺序：配置服务装载配置资产 → 本系统经 `API-OBJ-003` 受理登记项集合 → 校验标识唯一性、能力类别已登记、类型码已登记与挂载契约完整性 → 不通过项经 `API-M01-010` 记录 → 通过则注册表置为已就绪。
状态变化：注册表由未登记经校验中到已就绪；`CLS-OBJ-008` 产出。
产生的事件：无（结论并入「配置加载完成」）。
结束条件：注册表已就绪且全部登记项字段齐备；不通过时中止启动并报出具体登记项。

### 8.2 实例构建与组件挂载
触发：某一实体类型系统受理一次实例创建或构建变更（物品获得、装备穿戴、技能获得等）。
参与者：该实体类型系统、本系统、M09。
调用顺序：实体类型系统解析元对象定义（`API-OBJ-001`）→ 经 `API-OBJ-002` 校验可挂载的组件类别 → 经 `API-OBJ-004` 受理挂载 → 建立 `CLS-OBJ-005` 与 `CLS-OBJ-006` → 效果类组件经 `API-M09-001` 施加 → 实例状态经所属系统的写入路径落库（物品侧 `API-M09-005`）。
状态变化：实例由已创建到已归属；组件状态由未生效到已生效。
产生的事件：无（变更事实由所属系统的受理接口发布）。
结束条件：实例的组件构成与元对象定义一致，能力查询可返回预期结论。

### 8.3 能力判定与派生结果的取数
触发：任一系统在判定前需要确认某个实体是否具备某项能力（投掷资格、即时取用、槽位适配、同名遗物判定等）。
参与者：调用方系统、本系统。
调用顺序：调用方给出实例或元对象标识与能力类别 → 本系统经 `API-OBJ-002` 解析组件构成为能力结论 → 调用方按结论执行自身规则；涉及效果求值经 `API-M09-001` 至 `API-M09-003`，涉及条件经 `API-M09-004`。
状态变化：无（`CLS-OBJ-009` 为单次查询内的临时结果）。
产生的事件：无。
结束条件：返回可用或不适用的结论与理由；调用方不自行推断未登记的能力。

### 8.4 新增组件类型或实体类型的登记
触发：内容侧或程序侧需要引入一项现有组件无法组合表达的能力，或引入一类新的元对象实体。
参与者：能力提出方、本系统、配置资产维护方。
调用顺序：提出方经 `API-OBJ-005` 查重能力类别 → 若需新增能力类别则先在配置资产补登 → 登记组件的适用条件与挂载契约（`CLS-OBJ-007`）→ 若需新增实体类型则登记类型码与允许挂载的组件类别（`CLS-OBJ-003`）→ 启动阶段经 `API-OBJ-003` 校验通过后生效。
状态变化：注册表登记项新增；校验通过后置为已就绪。
产生的事件：无。
结束条件：新能力可经 `API-OBJ-002` 查询到，且挂载契约字段齐备。**新增组件必须先登记后挂载**（架构案 7.11）。

### 8.5 读档后的实例与组件状态重建
触发：启动阶段的读档路径（架构案 9.3）。
参与者：01-50 的存档服务与数据域入口、本系统、各实体类型系统。
调用顺序：存档服务按单局状态域次序恢复 → 判别值映射为实体类型码与组件类别 → 重建 `CLS-OBJ-005` 与 `CLS-OBJ-006` → 各实体类型系统按自身对象重建归属链、容器格位与槽位占用 → 派生结果按来源重建。
状态变化：实例与组件状态由空结构转为就绪。
产生的事件：无（恢复完成由存档侧发布「存档恢复完成」）。
结束条件：实例标识可解析、组件状态与登记契约一致、派生结果重建完成；不重新抽取任何随机结果。

## 9. 异常与边界情况

| 情形 | 判定条件 | 期望结果 |
| --- | --- | --- |
| 登记项标识重复 | 同一标识在注册表内出现两次 | 校验不通过并中止启动，报出标识与两个登记项 |
| 能力类别未登记 | 组件声明的能力类别不在 `CLS-OBJ-002` 内 | 校验不通过；该组件不得挂载（架构案 7.11） |
| 类型码未登记 | 元对象定义引用的类型码不在 `CLS-OBJ-003` 内 | 校验不通过并中止启动 |
| 挂载契约缺项 | 缺挂载前置条件、并存与互斥口径、启停口径或状态归属之一 | 校验不通过并中止启动 |
| 同类别组件互斥冲突 | 同一实例上挂载两个同类别组件且契约声明互斥 | 拒绝受理挂载，返回冲突的两项 |
| 运行期新增组件定义或改动登记 | 运行期请求新增或修改登记项 | 拒绝；登记项在编辑器内维护、运行期只读（架构案 7.9） |
| 请求写入元对象定义 | 调用方请求取得写入面 | 拒绝；返回内容一律只读（架构案 7.9） |
| 结算阶段受理挂载变更 | 当前阶段为结算阶段且变更改变局内状态 | 拒绝（架构案 6.6、8.3 第 5 条） |
| 实例不存在或已销毁 | 查询或挂载时实例标识解析不到 | 返回失败并记录日志，不隐式创建实例 |
| 未登记能力的推断请求 | 调用方要求对未登记的能力给出结论 | 返回不适用并说明能力类别未登记，不推断（架构案 5.1 第 1 条） |
| 派生结果被当作数据来源 | 调用方要求派生结果参与存档或作为判定来源 | 拒绝；派生结果按来源重建（架构案 8.2 第 3 条） |
| 存档中的组件判别值无法解析 | 读档时判别值不在登记的类型码或组件类别内 | 判定为版本或内容不匹配，交 01-50 的迁移规则处理（架构案 7.1） |
| 注册表尚未就绪时受理查询 | 启动阶段尚未完成校验 | 返回失败并记录日志，不返回部分结果 |

| I-OBJ-10 | 相同功能的组件只有一处定义；跨系统引用按 ID 书写，不得重定义他方对象（NR-06 §八.2） |
| I-OBJ-11 | 本系统不得依赖任何具体玩法系统，不得出现对实体类型系统的运行期调用；对实体类型系统的登记是定义归属登记，不构成调用（架构案 3.4 第 11 项） |
| I-OBJ-12 | 效果的构成、叠加、同名判定与生命周期一律经 M09 的元效果服务，本系统不实现效果叠加，也不自行实现条件判定（架构案 7.11） |
| I-OBJ-13 | 本系统的常驻对象在初始化时显式复位自身状态，不依赖引擎的域重载（架构案 6.1、8.3 第 7 条、8.6 第 5 条） |

## 11. 对象承载与生命周期

本表逐功能单元登记实现归属，承载形态取架构案 6.5 的六类之一。一句话概括：**常驻的只有注册表一个对象，其余全是随配置装载的静态对象、随单局创建的数据域对象与单次操作内有效的临时对象**。

| 功能单元 | 承载形态 | 生命周期归属 | 创建触发 | 销毁触发 | 是否依赖场景 |
| --- | --- | --- | --- | --- | --- |
| 对象与组件注册表 `CLS-OBJ-001` | 常驻对象 | 常驻（进程内唯一实例） | 启动阶段由启动物体按单元装配声明顺序显式初始化 | 进程退出时的逆序销毁；进程终止不执行销毁序列 | 否（由常驻场景承载，规则部分为普通对象） |
| 登记项装配与唯一性校验 `API-OBJ-003` | 临时运行对象（结论并入注册表状态） | 启动阶段内有效 | 启动阶段配置装载完成后触发 | 校验结论落定即释放 | 否 |
| 登记校验结果 `CLS-OBJ-008` | 临时运行对象 | 单次装配内有效 | `API-OBJ-003` 受理时建立 | 结论并入注册表状态后释放 | 否 |
| 组件能力描述项 `CLS-OBJ-002`、实体类型登记 `CLS-OBJ-003`、挂载契约 `CLS-OBJ-007` | 静态配置对象 | 运行期只读，不销毁直到进程退出 | 启动阶段经 `API-M01-003` 取得内存形态 | 进程退出 | 否 |
| 元对象定义 `CLS-OBJ-004` | 静态配置对象 | 运行期只读，不随局重置 | 启动阶段经 `API-M01-003` 取得内存形态 | 进程退出 | 否 |
| 元对象定义查询 `API-OBJ-001` | 临时运行对象（返回值快照） | 单次查询内有效 | 任一实体类型系统或界面侧发起查询 | 返回即释放 | 否 |
| 组件能力与登记查询 `API-OBJ-002` | 临时运行对象（返回值快照） | 单次查询内有效 | 判定前的取数请求 | 返回即释放 | 否 |
| 能力查询结果 `CLS-OBJ-009` | 临时运行对象 | 单次查询内有效 | 查询受理时建立 | 返回即释放 | 否 |
| 组件构成解析 | 临时运行对象 | 单次查询内有效 | `API-OBJ-001`、`API-OBJ-002` 受理时触发 | 返回即释放 | 否 |
| 组件挂载受理 `API-OBJ-004` | 数据域对象（写入 `CLS-OBJ-006`） | 与所属实例同步 | 各实体类型系统的实例构建或构建变更受理触发 | 随实例销毁 | 否 |
| 元对象实例 `CLS-OBJ-005`、组件状态 `CLS-OBJ-006` | 数据域对象 | 随单局创建；结算提交完成时随单局状态域释放，开新局全部重建 | 各实体类型系统受理实例创建时建立 | 所属业务对象销毁或单局状态域释放 | 否（权威状态由普通 C# 对象持有） |
| 能力类别登记查询 `API-OBJ-005` | 临时运行对象（返回值清单） | 单次查询内有效 | 新增组件时的查重请求 | 返回即释放 | 否 |
| 类型码登记与扩展受理 | 静态配置对象 | 运行期只读；扩展在编辑器内完成 | 编辑器内维护，启动阶段校验 | 进程退出 | 否 |
| 实例状态的切面声明与重建口径维护 | 常驻对象（声明随注册表持有） | 常驻 | 启动阶段随注册表初始化登记 | 进程退出 | 否 |

**两条口径**：其一，本系统**没有任何随场景创建销毁的脚本**——引擎对象只承担承载与编辑器配置职责，权威状态一律由普通对象持有（架构案 8.6 第 2 条）。其二，组件状态的写入不产生新的对象层级，一律落在 `CLS-OBJ-006` 的条目上，因此新增一项能力不新增承载对象（这是「功能由组件组合表达」在承载层面的体现）。
