## 1. 系统定义

### 1.1 系统目的

以整局存档快照为唯一输入完成一局游戏的收口：在事件结算环节的事件结果提交之后判定本局结局，按结算组件（术语表 T-177）的分工把本局解锁内容与达成记录写入跨局数据，并向局外循环交接。

结局成立的**唯一入口是事件结算环节的事件结果提交**；结算阶段不接受任何改变局内状态的输入，世界时间停止推进（架构案 6.6 第 2、3 条、9.5.5；设计决策记录决策 90）。本系统只提供跨局写入内容与其设计侧契约登记，结算流程的执行编排归 M10 的结算执行器（架构案 2.3 的跨列说明）。

本系统的对象标识：`SYS-SETTLE-001 局末结算与写入`。

### 1.2 系统职责

- 提供结算组件的定义清单契约：每个组件负责哪类跨局数据、取数来源、写入对象与生效时点；
- 维护结算组件划分与写入边界的设计侧登记契约：组件编号、负责的跨局数据、取数来源、写入对象与生效时点的登记以 `40_结算组件表.csv` 为准；运行期配置的权威内容以引擎编辑器内的配置资产为准，新增组件时两处都要登记（架构案 5.1、8.5.5；设计决策记录决策 93）；
- 按组件分工从整局存档快照取数，产出写入项并把跨局数据变更写入写入对象的持有者；
- 判定本局结局类型与未通关结局的触发起因（术语表 T-013），产出结局判定取值；结局成立的唯一入口是事件结算环节的事件结果提交（架构案 3.1 ARC-M05-001 与 ARC-M10-001、6.6 第 3 条、9.5.5；设计决策记录决策 90）；
- 执行节点解锁检查组件（术语表 T-179）：节点解锁（术语表 T-163）、传闻解锁与事件解锁状态（术语表 T-166）的判定与写入发起；
- 在节点解锁写入完成后对被解锁节点的下游中仍处于锁定状态的节点（术语表 T-164）执行一次开放阈值（术语表 T-165）判定；
- 在达成记录与大关进度组件（术语表 T-180）启用后写入达成记录与大关进度；
- 维护本局结算状态与结算执行记录，受理结算提交结果的登记；
- 向结算窗口提供本局写入的变更清单与结局数据；
- 向存档服务声明本系统的跨局数据切面；跨局写入提交完成、进入局外阶段时释放的是**世界状态域、单局状态域、玩家状态域三个数据域**，开新局时三个域全部重建；本系统的结算运行对象不写入三个域的内容，按各自生命周期在下一次本局装配前释放（架构案 5.2、8.3 第 3 条、9.5.6；变更 J）。

### 1.3 系统边界

本系统不负责：

- 结算流程的执行编排：快照收集时点、组件调度顺序、提交动作与阶段流转，归 M10 的结算执行器（引用 `API-M10-005 结算执行入口`）；本系统只提供跨局写入内容与结算窗口数据（架构案 2.3 的跨列说明）；
- 存档文件与三份持久化结构的读写、提交点管理与失败处置，归 01-50 的存档服务（引用 `存档服务（CLS-SAVE-001）`）；跨局存档的提交由 M10 的结算执行器经存档服务发起；
- 结局判定源的事实采集：关底事件（术语表 T-009）是否以额定条件通过由事件结算给出，全队失去行动能力由战斗模块只产生判定并写入战斗结果、由事件执行器在事件收尾时承接（见设计稿 3.13 与 `系统设计文档/06-战斗/A0-战斗目标与结果/A0_战斗目标与结果设计.md` 的 3.4；架构案 3.1 ARC-M05-001 与 ARC-M10-001、6.6 第 3 条、9.5.5；设计决策记录决策 90）；
- 线索树节点与关系、传闻文本、空行占位（术语表 T-161）数量的持有与推导，归 07-10 线索树核心；
- 剪枝封锁集合（术语表 T-167）与节点封锁标记（术语表 T-168）的写入，归 07-20 剪枝系统，不经结算组件；
- 全局事件池（术语表 T-169）与概率池内容集合的计算，归 07-30 概率池联动；
- 结算窗口的绘制、结局提示文案的投放与局外循环入口的交互，归 M08（引用 `结算窗口（M08，ID 待补）`）；
- 向其他模块索取结算输入：结算的输入只有整局存档快照，本系统不读取其他模块的运行时状态（架构案 3.1 ARC-M06-001）；
- 结算阶段的任何局内状态变更：结算阶段不接受改变局内状态的输入，世界时间停止推进（架构案 6.6 第 2 条）；
- 战斗内成立结局：战斗模块在全队失去行动能力时只产生判定并写入战斗结果，不在战斗内成立结局；战斗阶段不直接退出到结算阶段（架构案 6.6 第 3 条、9.5.5；设计决策记录决策 90）。

提交点与序列化口径（架构案 5.3、7.1、8.6 第 8 条；设计决策记录决策 89）：

- **跨局提交不是单局提交**：跨局存档的写入只发生在局末结算的一次提交内，它不占用也不依赖单局自动保存的两个节点（时间段推进、战斗轮次推进）；跨局存档的提交与最近一次自动保存写入单局存档是**两个提交点，各自的失败语义独立**（架构案 5.3 边界规则第 2 条、9.5.6）。
- **提交失败则整笔回滚**：本局保持未结算并保留重试能力，重试不产生重复写入（设计稿 3.4、架构案 9.5.6）。
- **退出不构成提交点**：退出游戏即进程终止，与强制关闭、平台关闭、异常终止同义；退出时不提交存档、不执行销毁序列、不依赖任何退出回调完成存档或收尾（架构案 3.4 第 17 项、5.3、6.4、9.4；设计决策记录决策 89）。
- 入档数据采用**判别字段式多态序列化**：序列化结果中只出现**自定义的字符串判别值**，**不写入运行时类型名**；多态类型按判别值映射，不接受任意类型名；不得使用已被运行时移除实现的二进制序列化机制（架构案 7.1、8.6 第 8 条）。
- 数据域的持久化随单局存档：单局存档的写入必须原子（写临时文件后原子替换，提交过程中断时整次作废并保留上一份有效存档）；读档时未确认的操作不恢复（架构案 5.3 第 4、5 条）。
- 切面登记、采集、装载与提交一律经存档服务；本系统不自行序列化状态、不自行读写存档文件（架构案 7.1、3.4 第 6 项）。

## 3. 状态定义

### 3.1 状态

| 状态实体 | 取值 |
| --- | --- |
| CLS-SETTLE-003 本局结算状态 | 未结算／结算中／已结算 |
| CLS-SETTLE-001 组件生效状态 | 已确认／后续版本／待补充 |
| CLS-SETTLE-004 结局类型 | 真结局／隐藏关底事件／未通关结局 |
| CLS-SETTLE-004 触发起因 | 关底未达标／主线中断／全队失去行动能力 |
| CLS-SETTLE-002 执行结论 | 执行中／成功／失败 |
| 三个数据域的持有者（M01 持有） | 空结构／就绪／结算封闭／已释放 |

### 3.2 状态转换

```
未结算 → 结算中 → 已结算
              └→ 未结算（提交失败，整笔回滚）
执行中 → 成功／失败（组件执行返回时一次性置值）
（三个数据域，M01 持有）空结构 → 就绪 → 结算封闭 → 已释放
```

已结算为本局的终态：已完成结算的本局不重复结算（设计稿 3.4）。组件生效状态由设计侧登记表与配置资产的登记内容共同决定，运行期不转换；执行结论在组件执行返回时一次性置值，执行期间不存在中间取值。

数据域持有者状态：`空结构 → 就绪 → 结算封闭 → 已释放`。释放范围为**世界状态域、单局状态域、玩家状态域三个域**，在跨局写入提交完成、进入局外阶段时释放；开新局时三个域**全部重建**（架构案 5.2、6.6、8.3 第 3 条、9.5.6；变更 J）。本系统的结算运行对象不写入三个域的内容：CLS-SETTLE-002、CLS-SETTLE-008 为运行记录与呈现用派生量，保留供结算窗口在局外阶段取数；CLS-SETTLE-003 与 CLS-SETTLE-004 的域归属与切面归属待上游补充（REQ-SETTLE-01）。

### 3.3 状态转换触发条件

| 转换 | 触发行为或事件 | 执行接口 | 与接口表「状态变化」列一致 |
| --- | --- | --- | --- |
| 未结算 → 结算中 | 事件结算环节的事件结果提交、结算阶段建立后，M10 的结算执行器首次调用组件执行（架构案 6.6、9.5.5；设计决策记录决策 90） | API-SETTLE-001 | 一致 |
| 结算中 → 已结算 | 一次提交成功并由结算执行器登记提交结果 | API-SETTLE-003 | 一致 |
| 结算中 → 未结算 | 一次提交失败并由结算执行器登记提交结果 | API-SETTLE-003 | 一致 |
| 已结算 → 已结算 | 对本局重复调用组件执行 | API-SETTLE-001 | 拒绝执行，状态不变（见第 9 节） |
| 执行中 → 成功／失败 | 组件执行返回时一次性置值 | API-SETTLE-001 | 一致 |
| 组件生效状态 | 由设计侧登记表与配置资产的登记内容共同决定 | API-M06-004 | 一致 |
| 结算封闭 → 已释放 | 跨局写入提交完成、进入局外阶段 | 域释放归 M01 的数据域持有者，由 M10 的结算执行器在登记为成功后进入局外阶段触发 | 不适用（域释放不由本系统接口触发） |
| 已释放 → 空结构 → 就绪 | 开新局时三个数据域全部重建（架构案 8.3 第 3 条、9.5.1） | 归 M01 的数据域持有者与 M10 的开新局编排 | 不适用 |

### 4.2 接口详细定义

### API-SETTLE-001 结算组件执行 ExecuteSettlementComponent()

职责：
按指定结算组件的取数来源从整局存档快照提取数据，产出写入项并把该组件负责的跨局数据变更写入写入对象的持有者。

输入：
- 参数输入：组件标识；整局存档快照（SAVE，ID 待补），只读传入
- 状态输入：CLS-SETTLE-003 本局结算状态；CLS-SETTLE-001 中该组件的生效状态
- 数据输入：CLS-SETTLE-001；节点关系表与传闻表
- 外部事件输入：无

读取：
- 整局存档快照（SAVE，ID 待补）中的事件实例结果（EVENT，ID 待补）与节点解锁结果
- CLS-SETTLE-001、CLS-SETTLE-003
- 节点解锁状态与传闻解锁状态（经 API-M06-001）、封锁状态（经 API-M06-002）

输出：
- 返回值：组件执行结果，含组件标识、执行结论、写入项条数与失败原因
- 状态输出：CLS-SETTLE-003 由未结算转为结算中；CLS-SETTLE-002 追加一条执行结论
- 事件输出：无：节点解锁与传闻解锁由线索树核心在写入成功后发布
- 外部系统调用：线索树写入接口（API-CLUETREE-001）、API-M01-010 日志服务.Write

产生的状态变化：
- 本局结算状态由未结算转为结算中
- 写入对象的跨局数据按写入项更新：节点解锁、传闻解锁、事件解锁状态
- 结算执行记录新增一条组件执行结论

前置条件：
- 本单元已完成初始化（架构案 6.1 阶段 3、8.3 第 1 条）
- 本局结算状态为未结算
- 组件标识在 CLS-SETTLE-001 中登记且生效状态为已确认
- 传入的整局存档快照是本局的一份完整快照

后置条件：
- 组件执行结论已登记；成功时该组件负责的跨局数据与写入项一致
- 执行失败时不产生部分写入，本局结算状态可回退

副作用：
- 触发线索树核心发布节点解锁与传闻解锁
- 写运行日志，记录结算开始、组件结论与失败原因

异常情况：
- 组件标识未登记或生效状态不是已确认时拒绝执行
- 本局结算状态不是未结算时拒绝执行，不产生重复写入
- 在结算阶段之外（含战斗阶段内）调用时拒绝执行：结局成立的唯一入口是事件结算环节的事件结果提交，本系统不在战斗内成立结局（架构案 6.6 第 3 条；设计决策记录决策 90）
- 快照缺少该组件所需数据时执行失败并返回失败原因
- 写入对象校验不通过（节点标识不存在）时该写入项失败，按整笔回滚处理
- 一次提交失败时由 API-SETTLE-003 回退本局结算状态

### API-SETTLE-002 结局判定执行 EvaluateOutcome()

职责：
按本局终止情形与整局存档快照中的事件实例结果判定结局类型与未通关结局的触发起因，产出结局判定取值；结局成立的唯一入口是事件结算环节的事件结果提交，本系统不在战斗内成立结局（架构案 6.6 第 3 条、9.5.5；设计决策记录决策 90）。

输入：
- 参数输入：整局存档快照（SAVE，ID 待补），只读传入；终止情形，取关底事件结算、主线中断、全队失去行动能力三者之一
- 状态输入：本局已解锁的节点与事件解锁状态（经 API-M06-001 只读查询）
- 数据输入：关底事件配置与节点关系表，经 API-M01-003 配置服务.Query 读取
- 外部事件输入：无

读取：
- 整局存档快照（SAVE，ID 待补）中的事件实例结果（EVENT，ID 待补）
- 节点解锁状态与事件解锁状态（经 API-M06-001）
- 关底事件配置中的额定条件与节点关系

输出：
- 返回值：结局判定结果，含结局类型、触发起因与大关推进标记
- 状态输出：CLS-SETTLE-004 生成并置值
- 事件输出：无：结局成立由 M10 的结算执行器在事件结算环节发布，本系统只提供判定取值
- 外部系统调用：无

产生的状态变化：
- 结局判定结果生成；判定取值供 M10 的结算执行器在事件结算环节发布 结局成立 并落定结算阶段

前置条件：
- 本单元已完成初始化（架构案 6.1 阶段 3、8.3 第 1 条）
- 受理请求来自 M10 的结算执行器，且时点在事件结算环节的事件结果提交之后；结算阶段的进入条件是事件结果提交，不是「结局成立」（架构案 6.6 第 3 条、9.5.5；设计决策记录决策 90）
- 终止情形取自设计稿 3.13 的三种收尾情形之一
- 传入的整局存档快照包含关底事件的结果记录

后置条件：
- 结局类型取真结局、隐藏关底事件、未通关结局三者之一
- 未通关结局的触发起因取关底未达标、主线中断、全队失去行动能力三者之一，且只有一个取值

副作用：
- 判定结果随返回值交回 M10 的结算执行器，由其发布 结局成立 并据阶段状态机切换阶段

异常情况：
- 快照缺少关底事件结果记录时判定不产出，返回失败原因并写内容日志
- 终止情形取值不在三者之内时拒绝执行
- 在事件结算环节之外请求判定（含战斗内请求成立结局）：拒绝执行，并把拒绝事实记入运行日志；战斗模块只产生判定并写入战斗结果，本系统不在战斗内成立结局（架构案 6.6 第 3 条、9.5.5；设计决策记录决策 90）
- 对本局重复调用时返回同一判定结果，不重复产生判定

### API-SETTLE-003 结算提交结果登记 AcceptSettlementCommit()

职责：
受理一次结算提交的结果，把本局结算状态置为已结算或回退为未结算。

输入：
- 参数输入：提交结果，取成功或失败；失败原因
- 状态输入：CLS-SETTLE-003 当前取值应为结算中
- 数据输入：无
- 外部事件输入：无

读取：
- CLS-SETTLE-002 本次结算的组件执行结论

输出：
- 返回值：登记后的本局结算状态
- 状态输出：结算中转为已结算，或结算中回退为未结算
- 事件输出：无：结算完成由 M10 的结算执行器在登记为成功后发布，本系统只提供提交结果登记
- 外部系统调用：API-M01-010 日志服务.Write

产生的状态变化：
- 本局结算状态更新；失败时本局保持未结算并保留下一次启动重试的能力

前置条件：
- 本单元已完成初始化（架构案 6.1 阶段 3、8.3 第 1 条）
- 本局结算状态为结算中
- 提交结果由 M10 的结算执行器按存档服务的回执给出

后置条件：
- 已结算时本局不重复结算；提交成功是进入局外阶段与释放三个数据域的前提（架构案 9.5.6；变更 J）
- 未结算时重试路径可用，重试不产生重复写入
- 跨局提交与最近一次自动保存的单局提交是两个独立提交点，各自的失败语义独立；**退出不构成提交点**，本接口不受理以退出为触发条件的登记（架构案 5.3 边界规则第 2 条、9.4；设计决策记录决策 89）

副作用：
- 写运行日志；登记后的本局结算状态是 M10 的结算执行器发布 结算完成、进入局外阶段与释放三个数据域的依据

异常情况：
- 本局结算状态不是结算中时拒绝登记
- 登记为成功但存在失败的组件执行结论时按失败处理并返回原因
- 重复登记同一提交结果时不改变状态，登记结果不重复交回调用方

### 5.2 功能之间的关系

- 组件清单提供先于组件执行，为结算执行器提供调度依据；
- 结局判定与组件执行只在事件结算环节的事件结果提交、结算阶段建立之后受理；结算阶段的进入条件是事件结果提交，不是「结局成立」（架构案 6.6、9.5.5；设计决策记录决策 90）；
- 组件执行由 API-SETTLE-001 触发，内部依次使用事件解锁判定；事件解锁判定在节点解锁写入完成后执行一次；
- 组件执行的结论汇入 CLS-SETTLE-002，结算窗口数据汇总按 CLS-SETTLE-002 重建 CLS-SETTLE-008；
- 结局判定由 API-SETTLE-002 触发，排在组件执行之前，其产出被达成记录与大关进度写入取用；
- 达成记录与大关进度写入经组件执行参与，调用位置与其他组件一致，生效状态为后续版本时跳过；
- 结算状态维护由 API-SETTLE-003 触发，在全部启用的组件执行完成并由 M10 完成一次提交之后调用；登记为成功后由 M10 进入局外阶段，三个数据域随之释放；
- 结算窗口数据汇总由 API-SETTLE-004 触发，只读，不触发任何写入；结算窗口在局外阶段取数呈现，数据域释放不影响本汇总（变更 J）。

### 6.5 依赖方向限制

分层与模块是架构案的**描述性分类**，不承担数据隔离、交互隔离与依赖方向约束职责（架构案 1.6）。本节只用于阅读导航：列出本单元实际依赖的模块与方向，以及仍然成立的少量硬规则。调用是否合法的判据是架构案 3.3 的允许清单、3.4 的禁止清单与 8.1 的依赖方向规则；**同层只读查询按 3.3 第 5 项的通则成立，不需要逐条登记、不需要逐条例外申报**（架构案 8.1、8.2）。

阅读导航：

- 本系统实际依赖的模块与方向：向 M01 取配置查询、日志写入、存档服务与数据域入口；向同模块的 07-10 与 07-20 只读查询并写入线索树解锁数据；向 M09 请求条件判定；M10 的结算执行器是本系统的编排方（`API-M10-005` 由 M10 自身受理，本系统为被编排方）。
- 被依赖方向：M10 的结算执行器经 `API-M06-004` 取结算组件清单并编排 `API-SETTLE-001` 至 `API-SETTLE-003`；结算窗口（M08）经 `API-SETTLE-004` 只读取数；09-20 与 07-30 经 `API-M06-005` 取大关进度。
- 禁止方向：不调用 M10 的阶段切换与三个执行入口；不调用 M08 的界面能力，也不持有界面对象；不读取 M02、M04、M05、M07 等模块的运行时状态（只经整局存档快照读取）。

硬规则：

1. 不写入他方数据、不持有对方的可变引用；跨域变更经持有方入口（架构案 3.4 第 5 项、8.2）。
2. 不绕过统一入口（存档、物品写入、效果叠加、随机源、世界时间、资源、场景、输入、日志）（架构案 3.4 第 6 至 10 项、第 7 章）。
3. 基础设施不依赖任何具体玩法系统（架构案 3.4 第 11 项）。
4. 不形成循环依赖；跨模块状态广播走事件通道（架构案 3.4 第 12 项、8.4 第 1 条）。
5. 不使用系统基础库的随机源、不在游戏状态判定中使用帧时间、不依赖引擎的退出回调（架构案 3.4 第 15 至 17 项）。
6. 不重复实现引擎已提供的能力（架构案 8.6 第 1 条、7.12）。

| 事件 | 发布方 | 订阅方 | 载荷字段类别 | 失败语义 |
| --- | --- | --- | --- | --- |
| 结局成立 | M10 的结算执行器（本系统只提供结局判定取值） | M10 的阶段状态机 | 结局类型、触发起因、本局标识 | 订阅方处理失败不回滚判定结果 |

节点解锁与传闻解锁由写入对象的持有者在写入接口执行成功后发布，本系统是写入的发起方。本系统不发布也不订阅跨模块事件：结局成立与结算完成由 M10 的结算执行器发布，本系统只提供结局判定取值与提交结果登记；结局成立的唯一入口是事件结算环节的事件结果提交（架构案 6.6、9.5.5；设计决策记录决策 90）。事件的载荷字段类别按本表细化，事件名取自架构案 3.1 的已登记词表。

跨模块事件的契约以**类型契约**的形式确定：登记事件名、唯一发布方、载荷字段类别与失败语义；登记表以可检视的资产承载、按**即用即定**登记（需要新事件时直接在登记表补一行，不设审批、编号申领或版本流程）。契约的强制方式是**一条对账测试**：测试遍历代码中的全部事件发布点并与登记表逐项比对，出现未登记事件即测试失败。事件名不在契约登记表内属于契约缺口，由对账测试在测试期发现，**不在运行期拦截**（架构案 4.3、7.6、8.4 第 2 条、8.6 第 10 条）。

## 8. 核心流程

### 8.1 结局成立判定

触发：事件结算环节的事件结果提交（三种未通关收尾情形统一在该环节成立；全队失去行动能力由战斗模块只产生判定并写入战斗结果，由事件执行器在事件收尾时承接）。

参与者：M05（战斗内的判定）、M10 的事件执行器与结算执行器、本系统、01-50 存档服务。

调用顺序：
1. 判定与承接：战斗模块在全队失去行动能力时只产生判定并写入战斗结果（战斗内的判定由战斗执行器轮询战果后转交）；主线中断与关底未达标由各自系统即时判定；M10 的事件执行器在事件收尾时承接判定结果（架构案 9.5.5）；
2. 收场：事件按常规流程打完收尾窗口、按常规退出与结算规则处理本场战斗；**战斗内不成立结局，战斗阶段不直接退出到结算阶段**（架构案 6.6 第 3 条、9.5.5；设计决策记录决策 90）；
3. 事件结算环节：事件结果提交，本局结束在此刻落定；结局成立的唯一入口是该环节；
4. M10 的阶段状态机经 API-M10-002 阶段切换执行进入结算阶段；结算阶段的进入条件是事件结果提交，不是「结局成立」（架构案 6.6）；结算阶段不接受任何改变局内状态的输入，世界时间停止推进；
5. M10 的结算执行器接管并取得整局存档快照（SAVE，ID 待补），调用 API-SETTLE-002 结局判定执行，传入快照与终止情形；
6. 本系统按快照中的事件实例结果（EVENT，ID 待补）与关底事件配置的额定条件判定结局类型与触发起因；结局类型与触发起因按设计稿 3.7 与 3.13 与 `06-A0` 的 3.4 取值；
7. M10 的结算执行器受理判定取值并发布 结局成立（本系统只提供判定取值）。

状态变化：结局判定结果生成；结算阶段建立，世界时间停止推进，本局输入通道关闭。

产生的事件：结局成立（由 M10 的结算执行器发布）。

结束条件：结算阶段建立且结局成立已发布，进入 8.2 的组件执行。

### 8.2 局末结算与跨局写入

触发：结算阶段建立后，M10 的结算执行器调用 API-M10-005 结算执行入口。

参与者：M10、本系统、01-50 存档服务、07-10 线索树核心。

调用顺序：
1. M10 取得整局存档快照，并经 API-M06-004 取得本次版本启用的组件清单与顺序；
2. M10 对每个启用组件调用 API-SETTLE-001，传入组件标识与快照；
3. 本系统按组件登记的取数来源从快照提取数据，构造写入项，经线索树写入接口写入节点解锁与传闻解锁项；
4. 节点解锁写入完成后，本系统对被解锁节点的下游中仍处于锁定状态的节点执行一次事件解锁判定并写入事件解锁项；
5. 本系统返回组件执行结果，结算变更清单按结算执行记录重建；
6. M10 经存档服务以一次提交写入跨局存档（跨局提交与最近一次自动保存的单局提交是两个独立提交点，各自的失败语义独立，架构案 5.3 边界规则第 2 条；**退出不构成提交点**，架构案 9.4）；
7. M10 调用 API-SETTLE-003 登记提交结果；
8. 登记为成功后，界面栈打开结算窗口（变更清单 ＋ 结局提示 ＋ 局外循环入口），阶段状态机进入局外阶段，世界状态域、单局状态域、玩家状态域三个数据域随之释放（架构案 8.3 第 3 条、9.5.6；变更 J）。

状态变化：本局结算状态由未结算转为结算中再转为已结算；跨局数据按写入项更新；三个数据域由结算封闭转为已释放。

产生的事件：节点解锁、传闻解锁（由线索树核心发布）、结算完成（登记为成功时由 M10 的结算执行器发布）。

结束条件：本局结算状态为已结算，结算窗口在局外阶段可查询。

### 8.3 提交失败回滚与重试

触发：一次提交返回失败回执。

参与者：M10、本系统、01-50 存档服务、07-10 线索树核心。

调用顺序：
1. M10 收到失败回执并调用 API-SETTLE-003，传入失败结果与失败原因；
2. 本系统把本局结算状态回退为未结算，并在结算执行记录中保留失败原因；
3. 存档服务按失败语义保留上一份有效存档（架构案 7.1）；本局不进入局外阶段，三个数据域不释放（变更 J）；
4. 下一次启动或重试时，重新执行 8.2 的调用顺序；重试不产生重复写入（设计稿 3.4）；
5. 进程在提交前终止时不触发任何收尾提交：退出即进程终止，不构成提交点，本局保持未结算并保留重试能力（架构案 3.4 第 17 项、9.4；设计决策记录决策 89）。

状态变化：本局结算状态由结算中回退为未结算；跨局数据不产生部分写入；三个数据域维持结算封闭。

产生的事件：无。

结束条件：本局结算状态回到未结算，重试路径可用且不产生重复写入。

| 情形 | 判定条件 | 期望结果 |
| --- | --- | --- |
| 重复结算 | 本局结算状态为已结算时调用 API-SETTLE-001 | 拒绝执行，不产生重复写入 |
| 重复达成同一结局 | 达成记录中该结局类型已有条目 | 只更新次数与最近时间，不重复推进大关进度 |
| 提交失败 | 存档服务回执为失败 | 整笔回滚，本局结算状态回退为未结算，保留重试能力 |
| 组件标识未知 | 组件标识不在 CLS-SETTLE-001 中 | 拒绝执行并返回失败原因 |
| 组件未启用 | 组件生效状态不是已确认 | 该组件不参与本次结算，不产出写入项 |
| 快照数据缺失 | 快照缺少该组件登记项所需的取数来源 | 该组件执行失败，不产生部分写入 |
| 结局判定事实缺失 | 快照中缺少关底事件结果记录 | 判定不产出，返回失败原因并写内容日志 |
| 终止情形非法 | 终止情形不在三种收尾情形之内 | 拒绝执行 |
| 节点标识不存在 | 线索树写入接口校验不通过 | 该写入项失败，按整笔回滚处理 |
| 同一次结算内重复解锁项 | 同一节点出现多条同内容标识的写入项 | 按内容标识去重，不产生重复条目 |
| 场景变化包装事件 | 节点解锁项来源为包装事件且事件配置未声明写入标记 | 不产生写入项 |
| 剪枝封锁数据 | 写入项涉及封锁集合或节点封锁标记 | 不经结算组件，由剪枝系统自行维护 |
| 空行占位数量 | 写入项涉及未解锁传闻的空行占位 | 不作为独立写入项，数量按传闻表登记条数推导 |
| 结算阶段的局内输入 | 结算阶段内收到改变局内状态的请求 | 本系统不接受该输入，不产生状态变化；结算阶段世界时间停止推进（架构案 6.6 第 2 条） |
| 结算窗口超前查询 | 本局结算状态为未结算时调用 API-SETTLE-004 | 返回未结算标记与空清单 |
| 战斗内请求成立结局 | 战斗阶段内请求结局判定或组件执行 | 拒绝执行：战斗模块在全队失去行动能力时只产生判定并写入战斗结果，由事件执行器在事件收尾时承接；结局成立的唯一入口是事件结算环节的事件结果提交（架构案 6.6 第 3 条、9.5.5；设计决策记录决策 90） |
| 提交前进程终止 | 进程在跨局提交完成前终止（主动退出、强制关闭、平台关闭、异常终止按同一口径处理） | 不执行收尾提交、不触发退出回调驱动的流程，退出不构成提交点；本局保持未结算，重试路径保留，以最近一次自动保存的提交结果为准（架构案 3.4 第 17 项、9.4；设计决策记录决策 89） |
| 数据域已释放后请求写入 | 局外阶段（三个数据域已释放）收到组件执行或域内容写入请求 | 拒绝执行并返回失败原因，不隐式重建数据域；开新局时三个数据域全部重建（架构案 8.3 第 3 条、9.5.6；变更 J） |
| 组件登记两处不一致 | 设计侧登记表与引擎编辑器内配置资产的登记内容不一致 | 以配置资产为准并记内容日志；新增组件必须两处都登记（架构案 5.1、8.5.5 第 1 步与第 5 步；设计决策记录决策 93） |
