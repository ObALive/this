本单元承载三处必须统一入口的横切能力——元效果服务、条件求值服务、物品与经济写入服务（架构案 2.2、3.1 ARC-M09-001）；本单元**无自有数据**（架构案 3.2）：效果、条件输入与物品变更分别落在 L2 的数据域，其中效果状态与物品状态落单局状态域与玩家状态域（架构案 3.1、5.2.2、5.2.3、5.4），本文档只登记引用并定义服务侧的模块级契约。约定附录 A 的 `API-M09-001` 至 `API-M09-005` 由本文档逐项定义八项契约；成员系统 06-75 的效果语义、05-05 的物品语义与 02-30-10 的条件引用侧规则一律按其 ID 引用，本文档不重定义（约定 §三）。

## 1. 系统定义

### 1.1 系统目的

本单元的系统标识为 `SYS-M09-001 全局能力`。

为全部领域与逻辑模块提供三处不可绕过的统一入口：效果的施加、移除与求值，条件的无状态判定，物品状态变化的唯一写入，使同名效果判定、条件判定与物品变更的原子性在全工程内只有一份实现，可复现且可回滚。

### 1.2 系统职责

- 元效果服务：受理元效果（术语表 T-132）的施加、移除与来源状态同步，维护效果生命周期判定，给出按结算层组织的求值结果（架构案 3.1 ARC-M09-001、7.11）。
- 条件求值服务：以一份已提交状态与当前上下文为输入执行无状态判定，自身不持有状态（架构案 7.11、ARC-GAP-012）。
- 物品与经济写入服务：物品状态变化的唯一写入入口，逐项校验并逐项落库，任一变更项无法完成时整笔回滚（架构案 3.4 第 7 项、9.5.7）。
- 模块装配与封闭校验：本单元在单元装配声明中登记依赖关系，由启动物体按声明顺序显式初始化并注入相互引用、按逆序销毁（架构案 2.4.1、2.4.2、6.1 阶段 3、6.4、8.3 第 1、6 条）；进入结算阶段后拒绝改变局内状态的请求（架构案 6.6、8.3 第 5 条）。
- 事件发布：发布「效果附加」「效果移除」「物品变更提交」三个事件；事件契约以类型契约形式确定，契约一致性由对账测试在测试期核对（架构案 3.1 事件栏、4.3、7.6、9.5.7）。

### 1.3 系统边界

- 效果的业务语义与数值取值：某个道具、装备（术语表 T-107）、遗物（术语表 T-110）或技能提供什么效果、数值多少，由来源系统与数值侧给出；效果定义在引擎编辑器内的配置资产中维护，归成员系统 06-75（架构案 5.1、7.9）。
- 判定条件的业务含义、条件引用的组合规则与引用侧登记（归 02-30-10 与引用条件的各系统）；物品的业务规则：组件能力、物品词条（术语表 T-079）匹配、容器允许内容约束（术语表 T-083）、估价与行情、经营范围与买卖价差、任务关联物品提示规则（归 05-05、05-10、05-20、05-30）。
- 交易事件的商品与定价的确定（归 M02 与 M04）、自动装载顺序与溢出处置的判定（归 05-30）；写入服务只受理已解析的变更项清单。
- 界面的编辑态持有、提交粒度与呈现（归 M08）；战斗内的结算时机与层内结算执行（归 M05）。
- 存档结构、切面采集、提交点与恢复顺序（归 M01 与成员系统 01-50）；世界时间推进、随机抽取、配置加载、日志落点与事件分发通道本身（归 M01）。
- 阶段取值的持有与阶段切换（归 M10）。本单元不新增玩法内容，不产生新的数据域。

功能要求（编号前缀 `F-`，来源为上游设计）：

- F-M09-01 道具、装备、遗物与技能产生的全部增益、状态与持续影响以元效果统一表达；同名效果只生效强度最高的一条，其余条目保留但不重复结算，有效项被移除后立即重新比较（06-75 3.2、3.3）。
- F-M09-02 不同类别与来源的元效果按结算分层处理，前一层结果确定后才进入下一层；效果生命周期由来源配置决定：随装备启停者在卸下时移除，限时者到期移除，投掷（术语表 T-146）类效果在动作结算结束时一次性移除，技能继承效果（术语表 T-145）随基础技能被替换同步重算，战斗外继续生效者随角色写入存档（06-75 3.4、3.5）。
- F-M09-03 条件支持与、或、非组合并读取当前已提交数据判定；判定作用于事件生成，玩家进入事件时不进行条件判定（02-30-10 4.1、4.2）。
- F-M09-04 物品条件读取已提交存档中的物品实例（术语表 T-076）、组件与归属，不改变物品状态（02-30-10 4.6）。
- F-M09-05 交易确认时全部资源变化一次提交完成，任一部分无法完成时整笔不产生状态变化；确认后不可撤回、不可退款（05-05 5.2、`05-10_金钱与货物设计.md` 4.1）。
- F-M09-06 无效操作不改变任何物品状态；需要玩家确认的操作在确认前不得提交状态变化；物品满足持续任务（术语表 T-095）要求且将离开角色时，必须在提交操作前提示玩家（05-05 5、5.3）。
- F-M09-07 物品始终归属一个明确载体；直接获得物品的系统调用自动装载流程，空间不足的未装入部分生成在事件点位（术语表 T-063）的世界掉落载体中（05-05 3、6）。

### 2.3 数据关系

- 包含与派生：CLS-M09-002 包含一笔提交的全部变更项与逐项校验结果；CLS-M09-001 登记本单元的依赖关系与初始化结果并引用三处入口的接口；CLS-M09-003 由已提交状态与条件引用派生，以状态版本为键，状态提交时统一失效、按来源重建、不入档（架构案 5.2.2、7.11、8.2 第 3 条）。
- 受理与引用：本单元的元效果服务是效果实例与来源绑定变化的唯一提交面，写入服务是物品归属、堆叠数量、容器格位与嵌套关系变化的唯一提交面（架构案 3.4 第 7、8 项）；CLS-M09-002 引用物品与容器状态的只读结果。
- 并列与不持有：三处入口互不包含、互不调用（效果服务不判定条件，条件服务不改变状态，写入服务不产生效果）；本单元**无自有数据**，不拥有任何数据域条目，三项自有对象均属非数据域对象；本单元不持有任何域内条目的可变引用，也不缓存跨域查询结果作为数据来源（架构案 3.1、3.2、8.2 第 2、3 条）。

### 2.4 数据生命周期

- 常驻与临时：CLS-M09-001 由常驻场景承载、随进程存活，由启动物体按单元装配声明顺序在初始化序列第 3 步显式初始化、按逆序销毁（架构案 2.4.1、2.4.2、6.1 阶段 3、6.5、8.3 第 1 条）；CLS-M09-002 在单次写入受理内有效，受理结束即释放，不跨帧保留、不入档（架构案 6.5、8.3 第 4 条）；CLS-M09-003 按状态版本建立与失效，读档后按新状态版本重建（架构案 9.3 第 6 步）。
- 数据域对象：效果实例与来源绑定、物品与容器状态随单局创建、按局重置，并在跨局写入提交完成、进入局外阶段时随世界状态域、单局状态域、玩家状态域三个域一并释放，开新局时三个域全部重建；其定义与切面由 06-75 与 M04 声明（架构案 5.2、6.6、8.3 第 3 条、9.5.6）。本单元不持有域内条目，不参与释放驱动。
- 结算与销毁：进入结算阶段后本单元不受理改变局内状态的请求，也不创建或销毁单局状态域内的对象（架构案 6.6、8.3 第 5 条）；本单元无入档数据，销毁按初始化逆序执行，**进程终止（主动退出、强制关闭、平台关闭、异常终止同义）不执行销毁序列、不提交存档、不依赖任何退出回调完成收尾**（架构案 6.4、9.4；设计决策记录决策 89）。

## 3. 状态定义

### 3.1 状态

| 对象 | 状态取值 |
| --- | --- |
| 单元初始化登记项（CLS-M09-001） | 未初始化 → 初始化中 → 已初始化 → 已销毁 |
| 单笔写入事务（CLS-M09-002） | 收集中 → 校验中 → 已提交；校验中 → 已回滚 |
| 条件求值缓存（CLS-M09-003） | 未建立 → 有效 → 已失效；派生缓存，以状态版本为键，状态提交时统一失效、不入档 |
| 三处受理面 | 无自身状态（架构案 3.1、7.11）；元效果实例的生命周期状态（已施加 → 生效／保留 → 已移除）与来源绑定状态归成员系统 06-75，物品与容器取值归 M04 与单局状态域，本文档不重新定义 |

### 3.2 状态转换

```
单元初始化登记项：未初始化 → 初始化中 → 已初始化 → 已销毁
单笔写入事务：收集中 → 校验中 → 已提交 ／ 校验中 → 已回滚
条件求值缓存：未建立 → 有效 → 已失效 → 有效（按新状态版本重建）
```

本单元无自有数据域对象：世界状态域、单局状态域、玩家状态域三个域的持有者状态（`空结构 → 就绪 → 结算封闭 → 已释放`）归 M01，本文档只在 2.4 与 3.3 登记其对本单元受理面的影响（架构案 5.2、6.6、8.3 第 3 条）。

### 3.3 状态转换触发条件

转换条件与第 4 节接口表的「状态变化」列一致；接口表中出现的域内状态变化（元效果实例、物品与容器）按 3.1 末行归成员系统与数据域。

| 转换 | 触发行为或事件 | 对应接口 |
| --- | --- | --- |
| 未初始化 → 初始化中 → 已初始化 | 启动物体读取并校验单元装配声明后，按初始化顺序显式调用本单元的初始化方法并完成相互引用；本单元在初始化时显式复位自身状态 | 无（不经本表接口；架构案 6.1 阶段 1、3，8.3 第 1、7 条） |
| 已初始化 → 已销毁 | 程序结束时的逆序销毁；进程终止不执行销毁序列、不提交存档、不做任何收尾承诺 | 无（架构案 6.4、8.3 第 6 条、9.4） |
| 收集中 → 校验中 → 已提交 | 写入服务受理变更项清单，全部校验通过并逐项落库完成 | API-M09-005，事件「物品变更提交」 |
| 校验中 → 已回滚 | 任一项校验不通过或落库无法完成 | API-M09-005（返回逐项失败原因，不发布事件） |
| 未建立 → 有效 → 已失效 → 有效 | 同一状态版本内首次判定建立缓存；任一数据域提交状态变更即统一失效；新版本下按来源重建（结果不入档） | API-M09-004；失效由状态提交触发（架构案 5.2.2、7.11） |
| 效果实例与来源绑定状态变化 | 施加、移除、来源状态同步与来源注销 | API-M09-001、API-M09-002（取值归 06-75） |

域内数据的持有者状态归 M01：`空结构 → 就绪 → 结算封闭 → 已释放`，在跨局写入提交完成、进入局外阶段时释放，开新局时三个数据域全部重建（架构案 5.2、6.6、8.3 第 3 条、9.5.6）。本单元不持有域内条目，数据域释放后三处受理面不再受理写入请求，也不隐式重建域结构。

### 4.2 接口详细定义

### API-M09-001 效果施加
职责：受理一批元效果的施加或来源状态同步，按效果标识完成同名判定与强度方向解释，划分生效项与保留项。

输入：参数输入：来源标识、来源类别、承载对象标识、效果清单（效果标识、效果数值、作用对象范围、持续信息）；状态输入：承载对象名下现有的元效果实例与来源绑定、当前阶段取值；数据输入：`CLS-EFFECT-001` 元效果定义；外部事件输入：无。

读取：`CLS-EFFECT-002` 元效果实例、`CLS-EFFECT-003` 效果来源绑定、`CLS-EFFECT-001` 元效果定义。

输出：返回值：施加结果（本次登记或更新的实例清单、生效项与保留项划分）；状态输出：实例由已施加转为生效或保留、来源绑定登记、效果生效判定结果失效；事件输出：效果附加；外部系统调用：事件分发器 `API-M01-011`。

产生的状态变化：元效果实例与来源绑定变化（单局状态域，本单元为唯一变更入口；入口登记见 REQ-M09-08）；不改变其他域数据。

前置条件：本单元已完成初始化（架构案 6.1 阶段 3、8.3 第 1 条；由启动物体按单元装配声明顺序显式初始化）；效果标识与来源类别已在元效果定义中登记；承载对象标识在单局状态域内有效；结算阶段未开始；调用方落在架构案 3.3 第 8 项的调用范围内。

后置条件：同一来源与同一效果在同一承载对象上至多一份实例；同名条目中按强度方向解释后强度最高的一条生效、其余标记为保留且不重复结算（06-75 3.3）。

副作用：发布「效果附加」；订阅方处理失败不回滚本次施加（架构案 8.4 第 4 条）。

异常情况：效果标识未登记；来源类别缺失；结算封闭期间受理（拒绝）；同一来源同一效果的重复施加（幂等受理，不新增实例）；效果强度方向缺失（按数值越高越强处理，06-75 3.3）；承载对象在结算阶段被创建或销毁（拒绝，架构案 8.3 第 5 条）。

### API-M09-002 效果移除
职责：按移除定位移除承载对象名下的元效果实例，并在同名范围内重新划分生效项与保留项。

输入：参数输入：承载对象标识、移除定位（按来源／按实例／按到期／按消耗）、移除原因；状态输入：现有实例与来源绑定、当前阶段取值；数据输入：`CLS-EFFECT-001` 元效果定义；外部事件输入：无（到期与消耗的时点由调用方给出，战斗内时点归 M05）。

读取：`CLS-EFFECT-002` 元效果实例、`CLS-EFFECT-003` 效果来源绑定、`CLS-EFFECT-001` 元效果定义。

输出：返回值：移除结果与重新划分后的生效项；状态输出：实例转已移除、生效项重算、来源绑定按需注销、效果生效判定结果失效；事件输出：效果移除；外部系统调用：事件分发器 `API-M01-011`。

产生的状态变化：元效果实例与来源绑定变化（单局状态域，本单元为唯一变更入口；入口登记见 REQ-M09-08）。

前置条件：本单元已完成初始化（架构案 6.1 阶段 3、8.3 第 1 条）；移除定位命中至少一项实例或来源绑定；结算阶段未开始。

后置条件：同名声明的剩余条目中重新启用强度最高的一条（06-75 3.3）；来源名下实例全部移除时该来源绑定注销。

副作用：发布「效果移除」；订阅方处理失败不回滚本次移除。

异常情况：移除定位未命中（返回空结果并记录日志，不视为异常）；结算封闭期间受理（拒绝）；来源注销时仍有剩余实例（按来源移除全部实例并注销绑定）；承载对象不存在。

### API-M09-003 效果求值
职责：按求值上下文取用承载对象名下的生效项，按结算分层给出只读的求值结果。

输入：参数输入：承载对象标识、求值上下文（战斗内外、结算层、用途）；状态输入：现有实例与来源绑定、当前阶段取值；数据输入：`CLS-EFFECT-001` 元效果定义、`CLS-BATTLE-007` 伤害类别登记（结算分层口径）；外部事件输入：无。

读取：`CLS-EFFECT-002` 元效果实例、`CLS-EFFECT-003` 效果来源绑定、`CLS-EFFECT-001` 元效果定义、`CLS-BATTLE-007` 伤害类别登记。

输出：返回值：按结算层组织的求值结果（逐层聚合值与生效项清单）；状态输出：效果生效判定结果由失效转为有效；事件输出：无（只读求值不产生事件，架构案 4.5）；外部系统调用：无。

产生的状态变化：仅派生结果按来源重建（效果求值结果为派生缓存，不入档）；不改变实例、来源绑定与任何域内数据。

前置条件：本单元已完成初始化（架构案 6.1 阶段 3、8.3 第 1 条）；承载对象存在；求值上下文落在已登记的结算层与用途内；结算分层登记可用。

后置条件：返回只读结果、不携带写入口；调用方不得把结果作为数据来源缓存（架构案 8.2 第 2、3 条）。

副作用：无。

异常情况：结算分层登记缺失（待上游补充，见缺口 REQ-M09-03）；承载对象名下无生效项（返回空结果，不视为异常）；求值上下文与登记的用途不符（拒绝）；请求战斗内的层内结算执行（拒绝，交 M05 按其伤害与结算条款处理）。

### API-M09-004 条件判定
职责：以一份已提交状态与当前上下文为输入执行无状态判定，返回条件引用的成立情况。

输入：参数输入：条件引用（与或非组合的引用项）、判定上下文（判定场合与时机：事件入池、物品交付检测、编排点分支、结算侧条件）；状态输入：三个数据域的已提交状态只读视图与其状态版本、跨局数据的局内只读快照、当前阶段取值；数据输入：`CLS-CONDITION-001` 条件模块、`CLS-CONDITION-002` 条件组合节点、`CLS-ITEM-004` 词条定义与物品池、`CLS-TIME-001` 时间段刻度与历法换算规则；外部事件输入：无（判定由调用方发起）。

读取：`API-SAVE-008` 数据域只读查询、`CLS-M06-004` 跨局数据只读快照、`CLS-CONDITION-005` 条件引用声明、`CLS-M09-003 条件求值缓存`。

输出：返回值：判定结果（成立／不成立）与逐条命中情况；状态输出：CLS-M09-003 按状态版本建立或取用、状态提交时统一失效；事件输出：无（只读查询不产生事件，架构案 4.5）；外部系统调用：无（不反向调用引用条件的系统）。

产生的状态变化：条件求值缓存按状态版本建立或失效；不改变任何域内数据；判定结果为派生缓存，不入档（架构案 5.2.2、7.11）。

前置条件：本单元已完成初始化（架构案 6.1 阶段 3、8.3 第 1 条）；条件引用已在引用侧登记；判定上下文已声明；判定所需状态快照可用（读档完成、本局数据域已就绪）。

后置条件：输入状态不变；返回结果不携带写入口，且判定结果不作为数据来源被缓存（架构案 8.2 第 3 条）。

副作用：无。

异常情况：条件引用未登记或引用项缺失（拒绝该次判定并记录日志）；判定上下文与引用项的场合不符（拒绝）；状态快照不可用（读档未完成、局外阶段无本局数据，返回不可判定）；结算封闭期间受理（判定只读，照常受理，但调用方不得据其结果发起写入，架构案 6.6）。

### API-M09-005 物品变更提交
职责：受理一笔物品状态变化，逐项校验并逐项落库，任一变更项无法完成时整笔回滚。

输入：参数输入：变更项清单（变更类别、目标载体标识、物品或组件标识、数量或格位、来源与目标归属）、提交来源类别（交易确认、事件交付与交换、自动装载、投掷与消耗、溢出落地）、业务类别；状态输入：目标载体与容器的当前内容与格位、`CLS-INVENTORY-001` 背包空间派生结果、`可调取容器范围（PARTY，ID 待补）`、当前阶段取值与结算封闭标记；数据输入：`物品操作总表（ITEM，ID 待补）`、`CLS-ITEM-004` 词条定义与物品池、`CLS-ITEM-001` 元物品定义、`CLS-ITEM-002` 组件定义、`CLS-INVENTORY-007` 装载与溢出规则项、`CLS-TRADE-001` 基准价值定义、`CLS-TRADE-004` 行情数据、`CLS-QUEST-002` 持续任务；外部事件输入：无。

读取：`CLS-ITEM-005` 至 `CLS-ITEM-009`（物品实例、组件运行状态、容器状态、归属引用、落地物载体）、上述配置与规则引用、`CLS-M09-002 单笔写入事务记录`。

输出：返回值：提交结果（整笔成功，或整笔回滚并给出逐项失败原因）；状态输出：物品归属、堆叠数量、容器格位与嵌套关系、落地物变化（单局状态域，本单元为变更入口；入口登记见 REQ-M09-08）、背包空间等派生结果失效待重建；事件输出：物品变更提交（整笔成功后发布）；外部系统调用：`API-SAVE-009` 数据域变更提交、事件分发器 `API-M01-011`、日志服务 `API-M01-010`。

产生的状态变化：一笔提交内的全部变更项一次生效或全部不生效，不存在部分提交（架构案 9.5.7）；确认前不改变任何物品状态（05-05 5.2）。

前置条件：本单元已完成初始化（架构案 6.1 阶段 3、8.3 第 1 条）；变更类别已在物品操作总表内登记；目标载体存在且可写；涉及容器时满足允许内容约束与容量限制；涉及持续任务关联物品时已完成提交前提示并取得确认（05-05 5.3）；结算阶段未开始。

后置条件：整笔成功时全部变更项已落库并已发布「物品变更提交」，事务记录释放；整笔失败时物品状态与提交前一致、不发布事件。

副作用：发布「物品变更提交」；成功后由持有方在下一个自动保存提交点纳入单局存档切面，**退出不构成提交点**；整笔落库经 `API-SAVE-009` 提交，本单元为该域的变更入口（登记见 REQ-M09-08）；本单元不自行序列化状态、不自行读写存档文件（架构案 3.4 第 6 项、5.3 第 4 项、7.1、9.4）。

异常情况：变更项类别未登记（拒绝整笔，05-05 7）；目标载体不存在或不可写（整笔回滚）；容量不足且无溢出目标（整笔回滚，溢出处置归 05-30）；容器允许内容约束不匹配（整笔回滚，05-05 2.4）；任务关联物品离开角色未取得确认（整笔回滚，05-05 5.3）；重复提交同一笔（幂等拒绝）；结算封闭期间受理（拒绝）；落库过程中任一项无法完成（整笔回滚并记录日志，不发布事件）。

### 5.2 功能之间的关系

- 装配序：初始化登记与依赖关系声明建立 → 结算封闭校验就绪 → 三处受理面可用（架构案 6.1 阶段 3、6.3 第 3 项，领域层中本单元先于 M04、M07、M02、M03、M05、M06）。

- 写入序：变更项受理与逐项校验 → 逐项落库与整笔回滚 → 写入结果通知与事件发布；任一步失败即整笔回滚，不进入事件发布。
- 数据域序：效果实例与来源绑定、物品与容器状态随单局创建，在跨局写入提交完成、进入局外阶段时随三个数据域一并释放，开新局时全部重建；本单元不持有域内条目，写入一律经数据域变更提交入口（架构案 5.2、6.6、8.3 第 3 条）。
- 间接关系：结算封闭校验为三项写入口与 `API-M09-004` 的前置；效果相关事件由来源系统与订阅方各自响应，本单元不承担其后续动作。

### 6.4 使用方式

- 启动阶段：常驻对象由常驻场景承载；启动物体按单元装配声明顺序在初始化序列第 3 步显式初始化本单元并注入相互引用，一次性完成；**不设统一的持有容器，不设解析入口，不设静态单例就地取用**（架构案 2.4.1、2.4.2、6.1、7.11、8.3 第 1 条）。
- 每次受理内：直接调用配置服务（读取引擎编辑器内的配置资产）、日志服务、事件分发器与数据域入口，并只读查询阶段取值；日志记录拒绝与回滚，事件经分发器发布，阶段用于结算封闭判定；不持有可变引用、不缓存跨域结果（架构案 5.1、7.9、8.2 第 1、2 条）。
- 按需读取：效果定义与实例面为模块内部使用，不构成跨模块调用；定义引用与跨局只读快照按需读取只读内容，跨局快照为同层只读查询，只读、不写入、不缓存（架构案 3.3 第 5、5.3 项、5.5、8.2 第 3 条）。

### 6.5 依赖方向限制

分层与模块是架构案的**描述性分类**，不承担数据隔离、交互隔离与依赖方向约束职责（架构案 1.6）。本节只用于阅读导航：列出本单元实际依赖的模块与方向，以及仍然成立的少量硬规则。调用是否合法的判据是架构案 3.3 的允许清单、3.4 的禁止清单与 8.1 的依赖方向规则；**同层只读查询按 3.3 第 5 项的通则成立，不需要逐条登记、不需要逐条例外申报**（架构案 8.1、8.2）。

- 被依赖方向：M09 被全部游戏逻辑与领域模块调用，三处统一入口对所有层开放，但**不反向依赖调用方**（架构案 3.3 第 8 项）。这是本单元成立的前提，也是本节保留的硬规则之一。
- 依赖方向：M01 是模块外唯一运行期依赖——配置服务、数据域读取与变更提交入口、日志服务、事件分发器（架构案 3.3 第 9、10 项）；M10 的阶段取值为只读查询（第 12 项）；M06 的跨局数据局内只读快照按 3.3 第 5.3 项与第 5 项通则成立（架构案 5.5）；模块内成员系统 06-75 的效果定义与实例面在模块内部使用，不计入跨模块依赖。装配不构成运行期依赖：依赖关系在单元装配声明内登记，由启动物体按声明顺序显式初始化（架构案 2.4.1、2.4.2、6.1、8.3 第 1 条）。
- 显式标注的双向调用面：M04 调用本单元的写入服务落库，本单元经 M01 的数据域入口只读物品与容器状态，不直接调用 M04 的接口；该结构按架构案 8.2 第 1、2 条成立，不构成循环依赖。本单元是单局状态域中效果实例与来源绑定、物品与容器状态的变更入口，架构案 5.4 已登记该身份；`API-SAVE-009` 的调用者栏同步见缺口 REQ-M09-08。
- 硬规则：
  1. 不写入他方数据、不持有对方的可变引用；跨域变更经持有方入口（架构案 3.4 第 5 项、8.2）。
  2. 不绕过统一入口：写入服务与效果服务不得被任何模块绕过；本单元也不得绕过存档、物品写入、效果叠加、随机源、世界时间、资源、场景、输入与日志等统一入口（架构案 3.4 第 6 至 10 项、第 7 章）。
  3. 不依赖任何具体玩法系统，也不反向依赖调用方（架构案 3.4 第 11 项）。
  4. 不形成循环依赖；跨模块状态广播走事件通道（架构案 3.4 第 12 项、8.4 第 1 条）。
  5. 不使用系统基础库的随机源、不在游戏状态判定中使用帧时间、不依赖引擎的退出回调完成存档或收尾（架构案 3.4 第 15 至 17 项）。
  6. 不重复实现引擎已提供的能力（架构案 7.12、8.6 第 1 条）。
- 唯一事实来源：本文档只定义 §2 的自有对象与 §4 的五项接口契约；成员系统与引用单元已定义的对象与接口一律引用其 ID（约定 §三）。

| 效果附加 | 本单元发布 | 承载对象标识、效果标识、来源标识与来源类别、生效项与保留项划分 | 每次 `API-M09-001` 受理成功后；订阅方处理失败不回滚本次施加（架构案 8.4 第 4 条），记录日志 |
| 效果移除 | 本单元发布 | 承载对象标识、移除定位、移除原因、重新划分后的生效项 | 每次 `API-M09-002` 受理成功后；失败语义同上 |
| 物品变更提交 | 本单元发布 | 提交来源类别、变更项类别汇总、涉及载体标识、整笔提交结果 | `API-M09-005` 整笔成功后；整笔回滚时不发布，按逐项失败原因返回调用方 |
| 阶段切换 | 本单元订阅（发布方 M10） | — | 进入结算阶段（进入条件为事件结果提交，架构案 6.6）时置三处写入口为封闭；进入局外阶段后三个数据域释放、本局数据不再保留，本单元不保留任何状态（架构案 6.6、8.3 第 3 条） |
| 存档恢复完成 | 本单元订阅（发布方 M01） | — | 清空 CLS-M09-003 求值缓存并按新状态版本重建，释放 CLS-M09-002 事务记录（架构案 9.3 第 6 步） |

跨模块事件的契约以**类型契约**的形式确定：登记事件名、唯一发布方、载荷字段类别与失败语义；登记表为 M01 的 `CLS-M01-014 事件契约登记表`，以可检视的资产承载、按**即用即定**登记（需要新事件时直接在登记表补一行，不设审批、编号申领或版本流程）。契约的强制方式是**一条对账测试**：测试遍历代码中的全部事件发布点并与登记表逐项比对，出现未登记事件即测试失败（架构案 4.3、7.6、8.4 第 2 条、8.6 第 10 条）。**受理侧不做运行期校验**：事件名不在契约登记表内属于契约缺口，由对账测试在测试期发现，不在运行期拦截。

一致性说明：`交易提交完成` 由 M04 金钱与货物发布（架构案 9.5.7 事件栏），不是本单元的事件；本单元只在整笔落库成功后发布「物品变更提交」，两者不互相替代。

### 7.3 数据流

- 效果与条件：来源系统 → `API-M09-001`／`API-M09-002` → 元效果实例与来源绑定（单局状态域，本单元为变更入口）→ `API-M09-003` 求值结果 → M05、M07、M08、M10，两个事件经 `API-M01-011` 广播；三个数据域的已提交状态与 M06 的跨局只读快照（架构案 3.3 第 5.3 项）→ `API-M09-004` → 判定结果 → 调用方（M02 入池、M04 交付检测、M06 结算侧、M10 编排点），CLS-M09-003 只在同一状态版本内复用、状态提交即失效，结果为派生缓存、不入档（架构案 5.2.2、7.11）。
- 物品：界面编辑态经 `API-M08-003` 提交 → `API-M09-005` 逐项校验与逐项落库到单局状态域（本单元为变更入口）→ 派生结果（背包空间）失效待重建 → 事件「物品变更提交」→ M04 与 M08 各自刷新；下一个自动保存提交点由 M01 的存档侧采集切面（架构案 5.3、9.5.7）。**退出不构成提交点**，本单元不自行序列化状态、不自行读写存档文件（架构案 3.4 第 6 项、7.1、9.4）。
- 装配与不流动项：CLS-M09-001 在启动物体按单元装配声明顺序显式初始化本单元时建立，配置与定义的可用性由「配置加载完成」驱动本单元完成自身绑定与自检；本单元不产生、不缓存也不转发任何跨域权威数据，条件求值结果与效果求值结果均为派生缓存、按来源状态重建、不入档，均不携带写入口（架构案 4.2、5.2.2、7.11、8.2）。

## 8. 核心流程

### 8.1 效果施加、移除与生效项重算

触发：穿戴或卸下装备、遗物词条启停、技能释放或替换、道具使用与投掷结算、来源停用、持续到期、被消耗（06-75 3.2、3.5）。
参与者：来源系统（M04、M05 各来源系统）、本单元元效果服务、成员系统 06-75、事件分发器（M01）、订阅方（M05、M07、M08）。
调用顺序：来源系统经 `API-M09-001` 提交来源标识、来源类别、承载对象标识与效果清单 → 读取 `CLS-EFFECT-001` 元效果定义校验登记 → 与承载对象名下现有实例与绑定比对，来源状态同步按差额产出施加与移除两个方向 → 按效果标识完成同名判定并按强度方向解释数值 → 划分生效项与保留项并登记实例与来源绑定（经数据域变更提交入口）→ 移除方向经 `API-M09-002` 置实例为已移除、按需注销来源绑定 → 在剩余条目中重新划分生效项 → 发布「效果附加」或「效果移除」。
状态变化：实例由已施加转为生效或保留、或转已移除；来源绑定登记或注销；效果生效判定结果失效（取值归 06-75）。
产生的事件：效果附加、效果移除。
结束条件：结果返回、生效项划分确定；重复施加不新增实例，定位未命中返回空结果并记录日志。待上游补充：效果作用对象覆盖场地、区域与事件（架构案 7.11）时承载对象标识的口径（承接方：架构案 3.1、5.2.2；见缺口 REQ-M09-05）。

### 8.2 效果求值（结算分层取用）

触发：战斗内结算取用（M05）、属性取值重算（M07）、界面只读呈现（M08）、编排点取用（M10）、来源系统自检。
参与者：调用方、本单元元效果服务、成员系统 06-75。
调用顺序：调用方经 `API-M09-003` 提交承载对象标识与求值上下文 → 按 `CLS-BATTLE-007` 伤害类别登记的结算分层口径逐层取用生效项并聚合 → 返回按层组织的只读结果 → 调用方在其自身位置使用结果（战斗内的层内结算执行归 M05）。
状态变化：效果生效判定结果由失效转为有效；不改变实例、绑定与域内数据。
产生的事件：无（只读求值不产生事件，架构案 4.5）。
结束条件：结果返回；本流程不执行层内结算。待上游补充：结算分层的层序与同层内确定性顺序的登记字段（承接方：06-75 3.4 与 06-10 的伤害与结算条款；见缺口 REQ-M09-03）。

### 8.3 条件判定（事件入池与编排点）

触发：事件池刷新的入池条件判定（架构案 9.5.3 第 6 步）、物品条件与交付检测、编排点分支判定、结算侧条件（02-30-10 4.1、4.6）。
参与者：调用方（M02、M04、M06、M10 等）、本单元条件求值服务、数据域读取入口（M01）、跨局只读快照（M06）。
调用顺序：调用方经 `API-M09-004` 提交条件引用与判定上下文 → 取用三个数据域的已提交状态只读视图与状态版本，按需取用跨局只读快照 → 命中 CLS-M09-003 时直接返回，未命中时按与或非组合逐条求值并写入缓存 → 返回判定结果与逐条命中情况。
状态变化：CLS-M09-003 按状态版本建立或失效，结果为派生缓存、不入档；不改变任何域内数据。
产生的事件：无（只读查询不产生事件，架构案 4.5）。
结束条件：判定结果返回；判定作用对象是事件生成，玩家进入事件时不重新判定（02-30-10 4.1）。待上游补充：判定输入中「已提交状态」的时点口径（承接方：架构案 7.11 与 02-30-10 4.2 的一致化；见缺口 REQ-M09-01）。

### 8.4 物品变更提交与整笔回滚

触发：界面确认一笔交易（架构案 9.5.7）、事件内的物品交付与交换、自动装载与溢出落地、投掷与消耗的扣除、事件结算的物品结果（05-05 5、6）。
参与者：提交方（M08 界面经 `API-M08-003`、M10 事件执行器、M02 事件结算、M04 各系统）、本单元写入服务、数据域入口（M01）、事件分发器（M01）。
调用顺序：提交方整理变更项清单（含目标载体、数量或格位、溢出目标）并经 `API-M09-005` 提交 → 建立 CLS-M09-002 事务记录并逐项执行受理校验（变更类别登记、目标载体可写、组件能力、容量与允许内容约束、任务关联提示、结算封闭）→ 任一项不通过则整笔回滚、返回逐项失败原因、不改变物品状态、不发布事件 → 全部通过则经数据域变更提交入口逐项落库（变更一项一落库，架构案 9.5.7 第 3 步）→ 落库中任一项无法完成则整笔回滚到提交前状态并释放事务记录 → 整笔成功则释放事务记录、发布「物品变更提交」，提交方按其职责刷新（架构案 9.5.7 第 4 步）。
状态变化：物品归属、堆叠数量、容器格位与嵌套关系、落地物按整笔全部生效或全部不生效；背包空间等派生结果失效待重建。
产生的事件：物品变更提交（整笔成功后发布）。
结束条件：提交结果确定；不存在部分提交；确认前不改变任何物品状态。

### 8.5 模块装配、初始化与销毁顺序

触发：程序启动、常驻场景加载完成后的常驻单元初始化（架构案 6.1 阶段 1、3、6.3）。
参与者：装配侧（常驻场景、启动物体、单元装配声明）、本单元三处入口、成员系统 06-75。
调用顺序：常驻场景加载 → 启动物体读取单元装配声明并校验（缺失引用或循环依赖即中止）→ 推导初始化顺序 → 按顺序显式调用本单元的初始化方法；本单元在初始化时显式复位自身状态并在单元装配声明内登记其依赖关系（配置服务、数据域入口、日志服务、事件分发器；M10 的阶段查询；06-75 的效果定义与实例面）→ 完成相互引用（领域层中本单元先于 M04、M07、M02、M03、M05、M06，架构案 6.3 第 3 项）→ 收到「配置加载完成」后完成自身定义绑定与自检 → 三处入口可用。**不设独立的启动引导单元，也不设统一的持有容器**（架构案 2.4.1、6.1）。
状态变化：本单元装配状态由未初始化经初始化中到已初始化；CLS-M09-001 与三处受理面建立。
产生的事件：无（自检由「配置加载完成」驱动）。
结束条件：三处入口可用；程序结束时按初始化逆序销毁，本单元无入档数据、不提交存档、不做任何收尾承诺，事务记录与求值缓存直接释放（架构案 6.4、8.3 第 6 条、9.4）。

## 9. 异常与边界情况

- 效果标识未登记或来源类别缺失：拒绝本次施加并记录日志，不登记任何实例；同一来源同一效果的重复施加为幂等受理；效果强度方向缺失时按数值越高效果越强处理（06-75 3.3、3.6）。
- 移除定位未命中、承载对象名下无生效项：返回空结果并记录日志，不视为异常，不改变状态。
- 求值上下文与登记的用途不符，或请求执行战斗内的层内结算：拒绝该次请求，交 M05 按其结算条款处理；结算分层登记缺失时拒绝求值并记录日志，不以空结果代替拒绝。
- 条件引用未登记或引用项缺失：拒绝该次判定并记录日志，不按「不成立」静默返回；判定上下文与引用项的场合不符时同样拒绝。
- 判定输入不可用（读档未完成、局外阶段无本局数据、跨局快照缺失）：返回不可判定，调用方不得据此进入事件或写入。
- 条件求值缓存的状态版本已被提交推进：判定为缓存失效，按新状态版本重建，不复用旧结果；求值结果作为派生缓存不入档（架构案 5.2.2、7.11）。
- 结算封闭期间的效果施加、效果移除与物品变更提交：一律拒绝，不改变任何局内状态（架构案 6.6、8.3 第 5 条）；条件判定只读，照常受理但其结果不得用于发起写入。
- 结算提交完成、进入局外阶段后收到写入请求：三个数据域（世界状态域、单局状态域、玩家状态域）已释放，拒绝受理并不隐式重建域结构；开新局时三个域全部重建（架构案 6.6、8.3 第 3 条、9.5.6）。
- 程序终止（主动退出、强制关闭、平台关闭、异常终止按同一口径处理）：不执行销毁序列、不提交存档、不依赖任何退出回调完成收尾，本单元不保留任何状态，以最近一次自动保存的提交结果为准（架构案 6.4、9.4；设计决策记录决策 89）。
- 变更项类别未在物品操作总表内登记：拒绝整笔提交并记录日志（05-05 7）。
- 目标载体不存在或不可写、容量不足且无溢出目标、容器允许内容约束不匹配：逐项校验不通过，整笔回滚；溢出处置归 05-30（05-05 2.4、第 6 节）。
- 涉及持续任务关联物品离开角色而未取得玩家确认：整笔回滚，不产生物品状态变化（05-05 5.3）。
- 落库过程中任一项无法完成或同一笔提交被重复提交：前者整笔回滚到提交前状态、不产生部分提交、不发布「物品变更提交」（架构案 9.5.7、8.4 第 4 条）；后者幂等拒绝。
- 界面未经编辑态提交直接调用写入服务：拒绝并记录日志（架构案 3.4 第 3 项、8.4 第 5 条）；事务记录在受理异常中断时按受理边界释放，不跨帧保留、不入档（架构案 8.3 第 4 条）。
- 效果作用对象为场地、区域或事件而承载对象标识不可解析：拒绝受理并记录日志（口径待上游补充，见缺口 REQ-M09-05）。
- 发布的事件名不在事件契约登记表内：属契约缺口，由对账测试在测试期发现，不在运行期拦截；载荷字段类别不符时拒绝发布并记录日志（架构案 7.6、8.4 第 2 条）。
- 调用方把效果求值结果或条件判定结果缓存为自己的数据来源：违反架构案 8.2 第 3 条，按第 10 章核对处理。

## 10. 实现约束

程序实现要求（编号前缀 `I-`）：

- `I-M09-01` 三处能力的契约以本文档 §4 为唯一落点（约定附录 A）；成员系统 06-75 与引用单元只按 ID 引用，不重定义 `API-M09-001` 至 `API-M09-005`。
- `I-M09-02` 物品状态变化只能经 `API-M09-005` 提交，效果状态变化只能经 `API-M09-001`、`API-M09-002`（或成员系统内同源的来源同步）提交，任何模块不得绕过（架构案 3.4 第 7、8 项、7.11）。
- `I-M09-03` 一笔物品变更提交必须整笔生效或整笔回滚：逐项校验、变更一项一落库，任一项无法完成即整笔回滚，不得出现部分提交（架构案 9.5.7）。
- `I-M09-04` 需要玩家确认的操作在确认前不得提交状态变化；无效操作不改变任何物品状态（05-05 5）。
- `I-M09-05` 效果同名判定与叠加只能由本单元的效果服务给出，任何模块不得自行实现效果叠加或另立效果表达（架构案 3.4 第 8 项、7.11）。
- `I-M09-06` 条件判定只能经 `API-M09-004`；本单元不自行定义条件的业务含义，判定结果不得作为数据来源对外提供（架构案 7.11、8.2 第 3 条）。
- `I-M09-07` 条件求值服务必须保持无状态：判定结果只以状态版本为键缓存于 CLS-M09-003，状态提交时统一失效，不入档、不跨帧保留；求值结果作为派生缓存，不得作为数据来源（架构案 5.2.2、7.11、6.5、8.2 第 3 条）。
- `I-M09-08` 本单元无自有数据：效果、条件输入与物品变更分别落在 L2 的数据域，效果与物品状态一律经 M01 的数据域入口读写，不持有域内条目的可变引用，不缓存跨域查询结果（架构案 3.2、8.2 第 1 至 3 条）。
- `I-M09-09` 结算阶段封闭：进入结算阶段后三处写入口拒绝改变局内状态的请求，本单元不创建或销毁单局状态域内的对象（架构案 6.6、8.3 第 5 条）。
- `I-M09-10` 常驻对象由常驻场景承载，只能由启动物体按单元装配声明顺序显式初始化并注入相互引用、按逆序销毁（架构案 2.4.1、2.4.2、6.1、6.3、8.3 第 1、6 条）；本单元在领域层中先于 M04、M07、M02、M03、M05、M06 装配；不设统一的持有容器，不设解析入口，不设静态单例就地取用（架构案 7.11）。
- `I-M09-11` 跨模块状态广播必须经事件分发器；事件契约以**类型契约**的形式确定（登记事件名、唯一发布方、载荷字段类别与失败语义），登记表以可检视的资产承载、按即用即定登记；契约一致性由**一条对账测试**在测试期强制——测试遍历代码中的全部事件发布点并与登记表逐项比对，出现未登记事件即测试失败，**受理侧不做运行期校验**；事件只承载「发生了什么」，不得承载「要求谁做什么」（架构案 4.3、7.6、8.4 第 1 至 3 条、8.6 第 10 条）。
- `I-M09-12` 订阅方处理失败不得回滚本单元的受理结果；本单元受理失败也不得依赖订阅方补偿（架构案 8.4 第 4 条）。
- `I-M09-13` 本单元不直接推进世界时间、不申请随机序列、不自行读写存档、不自行写日志、不自行加载资源，一律经 M01 的对应基础设施；含常驻集在内的全部资产经引擎的可寻址资源机制加载与释放，加载路径只有一条，本单元不自行加载任何资源文件（架构案 7.2、第 7 章）。
- `I-M09-14` 跨模块依赖限定在 M01 的基础设施、M10 的阶段只读查询与 M06 的跨局数据局内只读快照之内，不反向依赖调用方，不直接调用 M04、M06 的业务接口；同层只读查询按架构案 3.3 第 5 项的通则成立，不需要逐条登记、不需要逐条例外申报（架构案 3.3 第 5、5.3、8、9、12 项、8.1、3.4 第 12 项）。
- `I-M09-15` 效果求值结果与条件判定结果均为只读内容，不携带写入口；两者均为按来源状态重建的派生缓存、不入档，读取方不得作为数据来源缓存或据以反推来源状态（架构案 5.2.2、8.2 第 2、3 条）。
- `I-M09-16` 三处受理面的拒绝必须返回可判定的失败原因并记录日志，不得静默失败或以空结果代替拒绝，供调用方区分「不成立」与「不可判定」。
- `I-M09-17` 运行期配置的权威载体是**引擎编辑器内的配置资产**；`系统设计文档/` 的扩展配置表是各自系统的**初始素材与迁移来源**，用于设计评审与对照，**程序侧不直接读表**，内容侧不直接改运行期资产；校验失败即拒绝导入（架构案 5.1、7.9、8.6 第 10 条；设计决策记录决策 93）。
- `I-M09-18` 效果实例与来源绑定、物品与容器状态的入档形态采用**判别字段式多态序列化**：序列化结果中只出现自定义的字符串判别值，**不写入运行时类型名**，多态类型按判别值映射；不得使用已被运行时移除实现的二进制序列化机制；单局存档的写入必须原子，读档时未确认的操作不恢复（架构案 7.1、8.6 第 8 条、5.3 第 4、5 项）。
- `I-M09-19` 不得重复实现引擎已提供的能力：对象池与集合池、异步任务、设备到动作的输入映射、音频与本地化与特效动画的播放原语、资产载体与序列化原语、资源加载、场景装卸与日志通道一律使用引擎提供的能力，项目只做架构案 7.12「项目实现」栏登记的部分（架构案 7.12、8.6 第 1 条）。
- `I-M09-20` 权威游戏状态由普通 C# 对象持有，引擎对象只承担承载、呈现与编辑器配置职责；不得把权威状态放在随场景销毁的对象上（架构案 8.6 第 2 条）。
- `I-M09-21` 不依赖引擎的启动回调顺序、脚本执行顺序或帧回调顺序满足初始化与推进的顺序要求；顺序由单元装配声明与显式调用序列决定（架构案 6.1、8.6 第 4 条）。
- `I-M09-22` 本单元在初始化时显式复位自身状态，不依赖引擎的域重载提供初始状态（架构案 6.1、8.3 第 7 条、8.6 第 5 条）。
- `I-M09-23` 影响游戏状态的判定不得使用帧时间；不引入暂停语义（架构案 3.4 第 16 项、8.6 第 6 条）。

其他实现约束：

- 效果施加与移除、物品变更提交均为同步受理：一次受理内完成校验与落库，不留下中间状态。
- 事务记录与求值缓存均为临时运行对象，不跨帧保留、不入档（架构案 6.5、8.3 第 4 条）；本单元不解释效果数值与物品条目的业务含义（前者归 06-75，后者归 05-05）。
- 程序结束时的销毁按初始化逆序执行；进程终止（退出、强制关闭、平台关闭、异常终止同义）**不执行销毁序列、不提交存档、不依赖任何退出回调完成收尾**，单局存档的唯一可靠写路径是时间段推进与战斗轮次推进两类自动保存节点（架构案 6.4、9.4；设计决策记录决策 89）。
- 本单元的接口表、依赖表与事件表按约定 §四.7 的固定列书写，供全库机械核对。
