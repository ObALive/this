## 1. 系统定义

### 1.1 系统目的

在启动阶段一次性把引擎编辑器内的配置资产装载为运行期只读的内存形态，完成跨表校验并生成配置版本标识，使全部模块从唯一入口读取同一份静态配置，并使读档能够判定存档与当前配置版本是否一致（架构案 5.1、7.9）。

### 1.2 系统职责

- 从引擎编辑器内的配置资产装载全部静态配置，形成配置内存形态（`CLS-M01-003`），作为全部模块的只读取数面（架构案 5.1、7.9）。
- 执行跨表校验：标识唯一性、表间引用完整性、契约字段非空；校验失败即中止启动并报出具体资产与条目（架构案 7.9、8.6 第 10 条）。
- 在加载校验通过时生成配置版本标识（`CLS-M01-004`），供存档侧采集入单局存档并参与读档一致性判定（架构案 5.1、5.3、7.9）。
- 提供配置查询（`API-M01-003`）：按定义类别与条目标识返回只读条目，不携带写入面（架构案 7.9）。
- 发布「配置加载完成」，通知各定义模块完成自身定义绑定与自检（架构案 3.1 ARC-M01-001 事件栏、7.9）。
- 拒绝运行期写入与热重载请求（架构案 5.1 第 3 条、7.9「不允许绕过」）。
- **对象承载位置**：本对象是常驻对象，由常驻场景承载，由启动物体按装配声明顺序显式初始化、按逆序销毁；配置内存形态与版本标识在启动阶段建立、进程退出前不销毁（架构案 2.4.1、2.4.2、6.5）。

### 1.3 系统边界

本对象不负责：

- 配置条目的定义、字段含义与业务规则：事件配置归 M02、物品与组件定义归 M04、技能与属性定义归 M05、节点与池与结算组件定义归 M06、效果定义归 M09（架构案 5.1）。
- 设计库 13 张扩展配置表的维护：它们是各自系统的初始素材与迁移来源，用于设计评审与对照，程序侧不直接读表（架构案 5.1、8.6 第 10 条）。
- 资产编辑器内的内容维护：内容侧在编辑器内的资产上维护配置，程序侧不直接读设计库表（架构案 8.6 第 10 条）。
- 设置项清单与设置数据（归成员系统 01-60）；设置数据独立持久化，不随本对象装载（架构案 5.3）。
- 单局存档的结构、写入与迁移规则（归成员系统 01-50）；本对象只提供版本标识与校验结论。
- 输入映射的运行期写入例外（架构案 8.1 已登记的例外，归设置侧与输入映射）。
- 校验清单在资产内的声明方式（待上游补充，见 10.3 `REQ-M01-05`）。

### 2.3 外部数据引用

以下内容由其他单元或引擎侧定义，本对象只登记引用关系，不重定义其结构、职责与规则：

- 引擎侧配置资产与编辑器：运行期配置的权威载体；本对象从该载体装载，装载路径与资产检视由引擎提供（架构案 5.1、7.9、7.12、8.6 第 10 条）。

- 设置项定义：成员系统 01-60 的 `CLS-OPTION-001`，作为配置资产内的定义类别之一按 ID 引用；其内存形态与设置数据归 01-60 与 `CLS-M01-019`。
- 存档侧的版本绑定与版本校验：成员系统 01-50 的 `CLS-SAVE-009`（版本绑定）与 `API-SAVE-005`（版本校验）；本对象只提供标识取值，不定义比对规则。
- 配置版本标识的采集：由 `M01-03_存档服务代码设计案.md` 在自动保存的两类节点驱动。

### 2.4 数据关系

- 派生：`CLS-M01-004` 由 `CLS-M01-003` 派生，其取值在全部静态数据加载校验通过后确定（架构案 5.1 第 2 条）。
- 引用：`CLS-M01-003` 按定义类别引用各定义模块的条目定义；条目定义的所有权不在本对象。
- 包含：`CLS-M01-003` 覆盖全部静态数据类别（架构案 5.1 表内各行），本对象只提供内存形态。
- 并列：配置内存形态与设置数据内存形态（`CLS-M01-019`）相互独立；设置数据不随本对象的装载流程建立（架构案 5.3）。

### 2.5 数据生命周期

- `CLS-M01-003`：在启动阶段阶段 2 创建，运行期只读，进程退出前不销毁；热重载不提供（架构案 6.1 阶段 2、7.9）。
- `CLS-M01-004`：与 `CLS-M01-003` 同生命周期；在加载校验通过时生成，随单局存档提交，读档时参与一致性判定（架构案 5.1、5.3）。
- 校验中间结果：临时运行对象，单次装载与校验内有效，不跨帧保留、不入档（架构案 6.5、8.3 第 4 条）。
- 状态复位：本对象的常驻部分在初始化时显式复位自身状态，不假定引擎已提供初始状态（架构案 6.1、8.3 第 7 条）。
- 跨局与跨档存续：配置内存形态与版本标识不与单局绑定；局切换与开新局不重新装载配置（架构案 5.1「运行期只读」、7.9「不带热重载」）。

## 3. 状态定义

### 3.1 状态

| 对象 | 状态取值 |
| --- | --- |
| 配置服务（CLS-M01-003、CLS-M01-004） | 未加载 → 加载校验中 → 可用；加载校验中 → 中止 |
| 配置条目类别 | 不设运行期状态（装载后只读） |
| 配置版本标识 | 已定／读档时判定为不一致 |

### 3.2 状态转换

```
配置服务：未加载 → 加载校验中 → 可用 ／ 加载校验中 → 中止（中止启动）
配置版本标识：无 → 已定（加载校验通过时生成）
              已定 → 读档时判定为不一致（存档内标识与当前标识不符）
```

### 3.3 状态转换触发条件

转换条件与第 4 节接口表的状态变化列一致。

| 转换 | 触发行为或事件 | 对应接口 |
| --- | --- | --- |
| 未加载 → 加载校验中 | 启动物体在启动阶段阶段 2 发起配置装载（架构案 6.1 阶段 2） | 无（不经对外接口；属内部功能，见第 5 节） |
| 加载校验中 → 可用 | 全部静态数据装载完成，标识唯一性、表间引用完整性与契约字段非空校验通过 | `API-M01-003`（此后可受理查询），事件「配置加载完成」 |
| 加载校验中 → 中止 | 校验失败（标识重复、表间引用断裂、契约字段为空） | 无（中止启动，报出具体资产与条目，架构案 7.9、8.6 第 10 条） |
| 无 → 已定 | 加载校验通过时生成配置版本标识 | 无（内部功能，见 8.3） |
| 已定 → 读档时判定为不一致 | 读档时存档内的配置版本字段与当前标识不符 | `API-SAVE-005`（比对与迁移派发归 01-50） |

### 4.2 接口详细定义

### API-M01-003 配置服务.Query

职责：按定义类别与条目标识返回静态配置的只读内容。

输入：
- 参数输入：定义类别、条目标识或查询范围。
- 状态输入：配置服务加载状态（未加载／加载校验中／可用／中止）。
- 数据输入：`CLS-M01-003` 配置内存形态。
- 外部事件输入：无。

读取：`CLS-M01-003` 配置内存形态、`CLS-M01-004` 配置版本标识。

输出：
- 返回值：只读配置条目或只读视图。
- 状态输出：无。
- 事件输出：无。
- 外部系统调用：无。

产生的状态变化：无。

前置条件：配置服务处于可用状态；定义类别与条目已装载并通过校验。

后置条件：返回内容为只读形态，不携带写入面（架构案 7.9）。

副作用：无。

异常情况：配置尚未加载完成（含加载校验中与中止）；定义类别或条目标识不存在；请求写入（拒绝，运行期配置只读）；请求热重载（拒绝）。待上游补充：新增配置记录所需校验清单在引擎侧资产内的声明方式（承接方：架构设计案 5.1、7.9、8.5.4，见 10.3 `REQ-M01-05`）。

## 5. 内部功能

### 5.1 功能列表

| 功能 | 对外暴露 | 说明 |
| --- | --- | --- |
| 配置装载、校验与版本标识生成 | 部分是（查询经 `API-M01-003`） | 从引擎编辑器内的配置资产装载，含标识唯一性、表间引用完整性与契约字段非空校验；校验通过后生成 `CLS-M01-004` |
| 配置条目绑定与自检通知 | 否（经事件「配置加载完成」） | 通知各定义模块完成自身定义绑定与自检（架构案 7.9、3.1 ARC-M01-001） |
| 配置只读查询受理 | 是（`API-M01-003`） | 按定义类别与条目标识返回只读条目；不提供写入面 |

### 5.2 功能之间的关系

- 启动序：配置装载、校验与版本标识生成 → 配置条目绑定与自检通知 → 配置只读查询受理可用（架构案 6.1 阶段 2、9.1）。
- 输入依赖：装载的输入是引擎编辑器内的配置资产与各定义模块登记的定义类别；绑定与自检通知的输出由各定义模块消费。
- 失败衔接：校验失败即中止启动并报出具体资产与条目，不进入常驻单元初始化阶段（架构案 6.1 阶段 2、8.6 第 10 条）。
- 与存档侧的关系：版本标识生成后由存档侧在两类自动保存节点采集入档（见 `M01-03_存档服务代码设计案.md` 第 8 节）；读档比对由 01-50 的 `API-SAVE-005` 执行。
- 运行期关系：装载完成后本对象不再改变配置内容，只受理查询；不提供热重载与运行期写入路径（架构案 7.9、5.1 第 3 条）。

### 6.4 使用方式

- 装载：在启动阶段阶段 2 从引擎编辑器内的配置资产一次性装载；不使用设计库的扩展配置表作为运行期来源（架构案 5.1、7.9、8.6 第 10 条）。
- 校验：按标识唯一性、表间引用完整性、契约字段非空三类执行；校验失败即拒绝导入并中止启动（架构案 7.9、8.6 第 10 条）。
- 绑定通知：以事件间接获得——发布「配置加载完成」，由各定义模块完成自身绑定，本对象不调用其接口。
- 版本标识：生成后由存档侧采集；读档时由 01-50 的 `API-SAVE-005` 与存档内取值比对，本对象只提供当前取值。
- 查询：全部模块经 `API-M01-003` 只读取数；本对象不提供写入入口。

### 6.5 依赖方向限制

- 被依赖方向：全部模块经 `API-M01-003` 读取静态配置（架构案 3.3 第 9 项）。
- 依赖方向：本对象只从引擎侧的配置资产装载、只发布事件、只经日志服务记录；不依赖任何玩法模块，也不调用其业务入口（架构案 3.4 第 11 项）。
- 硬规则：
  1. 运行期配置只读，任何模块不得修改配置资产，也不得绕过本对象自行读取资产（架构案 7.9、3.4 第 6 项）。
  2. 程序侧不直接读设计库表，内容侧不直接改运行期资产（架构案 8.6 第 10 条）。
  3. 未登记的定义类别不得使用：先登记后使用（架构案 5.1 第 1 条、8.5.4）。
  4. 不重复实现引擎已提供的能力：资产载体与序列化、编辑器内检视归引擎，项目只实现跨表校验、版本绑定与内存形态（架构案 7.12、8.6 第 1 条）。
  5. 不形成循环依赖：本对象对定义模块只发布事件，不反向调用（架构案 3.4 第 12 项）。

## 8. 核心流程

### 8.1 静态配置加载与校验

| 项 | 内容 |
| --- | --- |
| 触发 | 启动阶段阶段 2（架构案 6.1 阶段 2、7.9） |
| 参与者 | 配置服务（M01-04）、各定义模块 |
| 调用顺序 | 从引擎编辑器内的配置资产装载全部静态配置 → 校验标识唯一性、表间引用完整性与契约字段非空 → 生成 `CLS-M01-004` 配置版本标识 → 发布「配置加载完成」 |
| 状态变化 | 配置服务由未加载经加载校验中到可用；`CLS-M01-003` 建立 |
| 产生的事件 | 配置加载完成 |
| 结束条件 | 配置服务可用且各定义模块完成自身定义绑定；校验失败时中止启动并报出具体资产与条目。待上游补充：新增配置记录所需校验清单在引擎侧资产内的声明方式（承接方：架构设计案 5.1、7.9、8.5.4，见 10.3 `REQ-M01-05`） |

### 8.2 配置条目绑定与自检通知

| 项 | 内容 |
| --- | --- |
| 触发 | 配置装载与校验通过之后，阶段 2 结束前（架构案 6.1 阶段 2、7.9） |
| 参与者 | 配置服务、各定义模块 |

### 8.3 配置版本标识的生成与读档一致性判定输入

| 项 | 内容 |
| --- | --- |
| 触发 | 加载校验通过（生成时）；读档路径与阶段 5 的本局装配（比对时） |

| 结束条件 | 读档一致性结论确定；本对象不定义迁移规则本身 |

| 项 | 内容 |
| --- | --- |
| 触发 | 阶段 2 校验发现标识重复、表间引用断裂或契约字段为空（架构案 7.9、8.6 第 10 条） |

| 产生的事件 | 无（中止路径不发布事件） |

## 10. 实现约束

### 10.1 实现约束条目

- 配置在运行期只读、不带热重载；运行期配置的权威载体是引擎编辑器内的配置资产（架构案 5.1 第 3 条、7.9）。
- 程序侧不直接读设计库表；设计库的 13 张扩展配置表只是初始素材与迁移来源（架构案 5.1、8.6 第 10 条）。
- 三类校验必须齐备：标识唯一性、表间引用完整性、契约字段非空；校验失败即拒绝导入并中止启动（架构案 7.9、8.6 第 10 条）。
- 全部静态数据共享一个配置版本标识；该标识必须写入单局存档并参与读档一致性判定（架构案 5.1 第 2 条、5.3）。
- 查询返回的条目必须为只读形态，不携带写入面（架构案 7.9、8.2 第 1 条）。
- 配置条目的定义与业务含义不在本对象内解释；本对象只按类别装载、校验与提供内存形态（架构案 5.1）。
- 不重复实现引擎已提供的能力：资产载体与序列化、编辑器内检视归引擎（架构案 7.12、8.6 第 1 条）。

### 10.2 实现要求

- I-M01-03 配置在运行期只读、不带热重载；运行期配置的权威载体是引擎编辑器内的配置资产，设计库的扩展配置表只是初始素材与迁移来源，程序侧不直接读表；配置版本标识必须写入单局存档并参与读档一致性判定（架构案 5.1、7.9、8.6 第 10 条、设计决策记录决策 93）。

### 10.3 缺口条目

```
编号：REQ-M01-05
提出单元：M01 核心与基础设施（M01）
缺口内容：静态配置新增记录时，校验清单（标识唯一性、表间引用完整性、契约字段非空）**在引擎侧配置资产内的声明方式**与登记格式未定。
影响：4.2 `API-M01-003` 的异常情况、8.1 与 8.4 的校验失败处置。
为何不能自行决定：依据架构案 7.9 与 8.5.4，新增配置记录的登记在权威资产内进行，资产侧的声明约定属架构裁定，本单元不得自行规定。
建议承接方：架构设计案（5.1、7.9、8.5.4）。
建议补充产出：校验清单在配置资产内的声明方式（资产内字段声明或独立的校验清单资产）与登记格式。
优先级：低（不阻塞当前设计阶段）
```

主案的其余三个既有缺口不落在本对象：`REQ-M01-01`（设置项清单）承接方为系统设计文档 01-60；`REQ-M01-03`（日志落点）承接方为架构设计案 7.7 或系统设计文档 01-60；`REQ-M01-06`（世界时间推进时点，已由决策 91 关闭、待复核）落于 `M01-03_存档服务代码设计案.md`。
