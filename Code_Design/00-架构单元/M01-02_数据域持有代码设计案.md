## 1. 系统定义

### 1.1 系统目的

为三个运行期数据域提供唯一持有者：域是全部已提交游戏状态的承载面，持有者负责域的建立、按局重建、释放与承接读写，使「谁拥有数据、谁只能读、谁经谁提交变更」在程序上有唯一落点（架构案 5.2、5.4、8.2）。

### 1.2 系统职责

- 持有世界状态域、单局状态域、玩家状态域三个域的域容器与域内容（架构案 5.2.1 至 5.2.3）。
- 每个域只有唯一持有者；其他模块只持有域标识并通过持有者读取（架构案 5.2、ARC-GAP-018）。
- 承接域内条目的只读查询与变更提交：读取经 01-50 定义的 `API-SAVE-008`，变更经 `API-SAVE-009`（架构案 5.4、8.2）。
- 域内容随单局创建、开新局重建；容器本身常驻、内容按局重建（架构案 6.5、8.3 第 3 条）。
- 在跨局写入提交完成、阶段进入局外时驱动三个域内容释放，域状态由结算封闭转入已释放（架构案 6.6、9.5.6）。
- 配合 01-50 的切面采集与装载：域内容按各域声明的切面被采集入档，恢复按世界状态域 → 单局状态域 → 玩家状态域的次序进行（架构案 7.1、9.3）。
- 派生项不作为数据来源：区域形态推算、背包空间、同名遗物效果、条件求值结果等由来源方按来源状态重建（架构案 8.2 第 3 条）。
- **对象承载位置**：本对象是数据域对象，随单局创建、结算提交完成时释放，容器本身常驻；开新局时全部重建（架构案 6.5、8.3 第 3 条）。

### 1.3 系统边界

本对象不负责：

- 域内条目的业务含义、变更判定与写入时机（归各变更入口模块，架构案 5.4、8.2）。
- 存档结构、切面划分、切面粒度、提交顺序与恢复步骤的定义（归成员系统 01-50）。
- 单局存档的写入、原子性与失败回退（归 01-50，由 `M01-03_存档服务代码设计案.md` 发起）。
- 跨局存档的写入内容与结算流程（写入内容归 M06，流程编排归 M10）。
- 阶段取值的判定与切换（归 M10 的阶段状态机；阶段取值条目由 M10 提交入世界状态域）。
- 派生项的计算与缓存维护（归各来源方）。
- 随机序列位置、设置数据、静态配置（分别归随机服务、01-60、配置服务）。
- 域内容的引用完整性校验与序列化机制（归 01-50）。

- 数据域入口：`API-SAVE-008`（只读查询）、`API-SAVE-009`（变更提交）；两个接口的定义、输入输出分类与失败语义归成员系统 01-50，本对象是承接方。
- 变更入口模块：M02、M03、M04、M05、M07、M09、M10（按模块编号引用，其对象在本对象之外定义）。
- 阶段状态机：M10（阶段取值的判定方；阶段取值条目由 M10 提交入世界状态域）。
- 时间口径：02-10 时间机制（`CLS-TIME-001`、`CLS-TIME-006`），只作为世界时间条目的口径来源引用；世界时间取值的对象（`CLS-M01-006`）归 `M01-06_时间服务代码设计案.md`。

### 2.4 数据关系

- 包含：CLS-M01-016 至 CLS-M01-018 分别包含三个数据域的域内容（架构案 5.2.1 至 5.2.3）。
- 派生：区域形态推算、背包空间、同名遗物效果、条件求值结果、继承效果求值结果、可调取容器范围按来源状态重建，不作为数据来源（架构案 8.2 第 3 条）。
- 引用：三个域持有者被单局存档的三个切面引用；两个事件池同属世界状态域，全局事件池按快照恢复、当前事件池按其快照恢复，读档不重新过滤、不重新抽取（架构案 5.2.5）。
- 并列：三个域互不包含，各自独立提交与恢复，失败语义互不牵连（架构案 5.3 边界规则第 2 条）。
- 跨单元引用：域内条目的读取与变更提交经 01-50 的数据域入口；本对象不向任何模块暴露可变引用（架构案 8.2）。

### 2.5 数据生命周期

- 创建：随单局创建；开新局路径按本局生成输入建立三个域的空结构后写入内容（架构案 6.1 阶段 5、9.5.1）。
- 存续范围：单局内，跨事件与跨场景存在；域内容在结算阶段停止接受改变局内状态的提交（架构案 6.6）。
- 释放：跨局写入提交完成、阶段进入局外时驱动三个域内容释放（架构案 6.6、9.5.6）。
- 重建：开新局时三个域全部重建为空结构；容器本身常驻，不随局销毁（架构案 6.5、8.3 第 3 条）。
- 派生项：不入档，恢复后由来源方按来源状态重建（架构案 8.2 第 3 条）。

### 2.6 持久化要求

| 数据 | 是否入档 | 切面归属 | 恢复时的重建步骤 |
| --- | --- | --- | --- |
| CLS-M01-016 世界状态域内容 | 是 | 单局存档的世界状态域切面（切面划分归 01-50） | 按世界状态域 → 单局状态域 → 玩家状态域的次序装载后，重建派生缓存与事件池；两个事件池按快照恢复 |
| CLS-M01-017 单局状态域内容 | 是 | 单局存档的单局状态域切面 | 同上；战斗未结状态由 M05 按记录重建战场与时间轴 |
| CLS-M01-018 玩家状态域内容 | 是 | 单局存档的玩家状态域切面 | 同上；继承效果求值结果与可调取容器范围按来源状态重建 |
| 域内派生项（区域形态推算、背包空间、同名遗物效果、条件求值结果等） | 否 | 无 | 由来源方按来源状态重建；恢复过程不重新抽取任何随机结果（架构案 7.1、9.3） |

域内容必须可序列化并满足判别字段式多态序列化要求；单局存档的写入原子性由存档侧负责（架构案 5.3 第 4 条、7.1、8.6 第 8 条）。

## 3. 状态定义

### 3.1 状态

| 对象 | 状态取值 |
| --- | --- |
| 数据域持有者（CLS-M01-016 至 CLS-M01-018） | 空结构 → 就绪 → 结算封闭 → 已释放 |
| 域内条目 | 不设独立状态；条目自身的状态取值归各变更入口模块 |

三个域共同使用同一状态集；同一时刻每个域只有一个取值，三个域之间不做联动判定（架构案 5.2、6.6）。

### 3.2 状态转换

```
空结构 → 就绪 → 结算封闭 → 已释放 →（开新局重建）空结构 → 就绪
```

### 3.3 状态转换触发条件

转换条件与第 4 节接口表的状态变化列一致。

| 转换 | 触发行为或事件 | 对应入口 |
| --- | --- | --- |
| 空结构 → 就绪 | 本局装配完成，或读档恢复完成并写入存档内容 | 本局装配（世界状态域 → 单局状态域 → 玩家状态域）；读档经 `API-SAVE-004`，完成后发布「存档恢复完成」 |
| 就绪 → 结算封闭 | 事件结果提交、结局在事件结算环节成立并进入结算阶段 | 无（阶段状态机，架构案 6.6、9.5.5）；域停止接受改变局内状态的提交 |
| 结算封闭 → 已释放 | 跨局写入提交完成、阶段进入局外 | 事件「结算完成」（M06／M10 发布）；释放跨局提交经 `API-SAVE-007` |
| 已释放 → 空结构 | 开新局，三个域全部重建 | 本局装配（架构案 8.3 第 3 条、9.5.1） |

### 4.2 接口详细定义

### API-SAVE-008 数据域只读查询（在本对象中的承接口径）

职责：向读取方提供该域当前已提交状态的只读快照；本对象是三个域的唯一提供面。

输入：
- 参数输入：域标识、读取范围。
- 状态输入：该域持有者状态（空结构／就绪／结算封闭／已释放）。
- 数据输入：域内容（CLS-M01-016 至 CLS-M01-018）。
- 外部事件输入：无。

读取：CLS-M01-016、CLS-M01-017、CLS-M01-018 的域内容。

输出：
- 返回值：只读快照。
- 状态输出：无（查询不改变域状态）。
- 事件输出：无。
- 外部系统调用：无。

产生的状态变化：无。

前置条件：域持有者处于就绪或结算封闭；域标识已登记；读取范围落在该域内容清单内。

后置条件：快照不携带写入口；读取方不得在本地缓存快照结果，也不得把派生结果当作来源状态（架构案 8.2 第 3 条）。

副作用：无。

异常情况：域处于已释放（局外阶段）；本局装配尚未完成；域标识不存在；读取范围含未登记条目。

### API-SAVE-009 数据域变更提交（在本对象中的承接口径）

职责：受理该域登记变更入口模块的变更提交项并写入域内容；本对象是三个域的唯一写入面。

输入：
- 参数输入：域标识、变更提交项、提交来源模块。
- 状态输入：该域持有者状态、当前阶段取值。
- 数据输入：域内容清单（CLS-M01-016 至 CLS-M01-018）。
- 外部事件输入：无。

读取：CLS-M01-016、CLS-M01-017、CLS-M01-018 的域内容。

输出：
- 返回值：提交结果。
- 状态输出：该域内容按提交项变更。
- 事件输出：无。
- 外部系统调用：无（跨域影响由提交方自行经其域入口完成）。

产生的状态变化：域内容按提交项更新；提交不改变该域持有者状态。

前置条件：提交来源模块是该域登记的变更入口模块；域持有者处于就绪；阶段取值允许改变局内状态（架构案 6.6）。

后置条件：域内容反映本次提交；未提交内容不进入任何结构（架构案 5.3、8.2）。

副作用：无；被拒绝的提交经日志服务记录。

异常情况：提交来源模块未登记为该域变更入口；域处于空结构或已释放；结算阶段收到改变局内状态的提交项（拒绝）；物品类变更未经过 M09 的写入服务（拒绝）；提交项落在未登记切面的内容上（不入档，按新增数据域步骤补登记）。

## 5. 内部功能

### 5.1 功能列表

| 功能 | 对外暴露 | 说明 |
| --- | --- | --- |
| 数据域持有 | 否（读取与提交经 `API-SAVE-008`、`API-SAVE-009` 的承接面体现） | 维护三个域的域容器与域内容；容器常驻、内容按局重建（架构案 6.5） |
| 只读快照提供 | 否（经数据域入口受理） | 向读取方提供不带写入口的只读快照（架构案 8.2） |
| 按局重置与开新局重建 | 否（由本局装配驱动） | 空结构重建为就绪；开新局时三个域全部重建（架构案 8.3 第 3 条） |
| 结算提交完成后的释放驱动 | 否（由结算完成事件触发） | 释放三个域内容并由结算封闭转入已释放（架构案 6.6、9.5.6） |

### 5.2 功能之间的关系

- 生命周期序：按局重置与开新局重建 → 数据域持有 → 只读快照提供与变更提交受理（运行期）→ 结算提交完成后的释放驱动。
- 数据面分工：只读快照提供与变更提交受理是两个方向；快照不携带写入口，变更一律经数据域入口（架构案 8.2）。
- 触发衔接：按局重置由本局装配驱动；释放驱动由「结算完成」事件与跨局提交的完成共同触发，两者都成立后阶段进入局外。
- 与存档侧的衔接：切面采集与装载只在本对象处于就绪时进行；恢复完成后本对象写入存档内容并转入就绪（架构案 9.3，流程见 `M01-03_存档服务代码设计案.md` 第 8 节）。
- 与派生项的关系：本对象不保存派生结果，派生项由来源方在域就绪后重建（架构案 8.2 第 3 条）。

### 6.4 使用方式

- 读取：读取方在被授权范围内经 `API-SAVE-008` 取只读快照，不持有可变引用（架构案 8.2）。

- 采集与装载：由存档侧在提交与恢复期间发起，本对象只提供域内容；域内容按各域声明的切面被采集（架构案 7.1）。
- 释放：以事件间接获得——订阅「结算完成」，在跨局提交完成后驱动释放；本对象不主动查询结算流程状态。

### 6.5 依赖方向限制

- 被依赖方向：全部模块经数据域入口读取三个域；变更入口模块经数据域入口提交（架构案 3.3 第 5 项、5.4）。

- 硬规则：
  1. 不直接修改他方数据，不持有对方的可变引用（架构案 8.2 第 1、2 条）。
  2. 派生结果不作为数据来源，读取方不得缓存派生结果（架构案 8.2 第 3 条）。
  3. 结算阶段开始后，任何模块不得创建或销毁单局状态域内的对象（架构案 8.3 第 5 条）。
  4. 不形成循环依赖；与 01-50、M10 之间只经数据域入口与事件接触（架构案 3.4 第 12 项）。

## 8. 核心流程

### 8.1 读档恢复驱动（域侧承接）

| 项 | 内容 |
| --- | --- |
| 触发 | 启动阶段的读档路径，或玩家在局外选择已有存档（架构案 9.3） |
| 参与者 | 存档侧、三个域持有者、M02、M05、M08、M10 |
| 调用顺序 | 存档侧读取单局存档结构与配置版本标识 → 与配置服务的版本标识比对 → 经 `API-SAVE-004` 建立三个域的空结构 → 按世界状态域 → 单局状态域 → 玩家状态域的次序装载 → 域写入存档内容后由空结构转为就绪 → 由来源方重建派生缓存与事件池 → 发布「存档恢复完成」 |
| 状态变化 | CLS-M01-016 至 CLS-M01-018 由空结构转为就绪 |
| 产生的事件 | 存档恢复完成（由存档侧发布） |
| 结束条件 | 三个域均为就绪、派生项已由来源方重建；恢复过程不重新抽取任何随机结果 |

### 8.2 结算提交完成后的释放

| 项 | 内容 |
| --- | --- |
| 触发 | 结局成立进入结算阶段后，跨局写入提交完成、阶段进入局外（架构案 6.6、9.5.6） |
| 参与者 | M10 的结算执行入口、M06、三个域持有者 |
| 调用顺序 | 结局在事件结算环节成立 → 域由就绪转为结算封闭，停止接受改变局内状态的提交 → M10 经 `API-SAVE-007` 提交跨局写入 → 收到「结算完成」→ 驱动世界状态域、单局状态域、玩家状态域三个域内容释放 |
| 状态变化 | 三个域由结算封闭转为已释放 |
| 产生的事件 | 无（本对象不发布事件） |
| 结束条件 | 三个域内容已释放；跨局提交失败时保持结算封闭并保留重试能力，不进入释放 |

### 8.3 开新局的三域重建

| 项 | 内容 |
| --- | --- |
| 触发 | 玩家在局外阶段开新局（架构案 6.1 阶段 5、9.5.1） |
| 参与者 | 本局装配、M02（本局生成）、三个域持有者 |
| 调用顺序 | 由 M02 的本局生成给出生成输入 → 三个域由已释放重建为空结构 → 按域写入初始内容（世界时间与时间段位置、全局事件池快照、区域解锁状态、行情、队伍编制与初始属性等）→ 三个域转为就绪 |
| 状态变化 | 已释放 → 空结构 → 就绪 |
| 产生的事件 | 无（本对象不发布事件） |
| 结束条件 | 三个域就绪且初始内容完整；上一局的域内容不得残留 |

### 8.4 域内变更提交的受理

| 项 | 内容 |
| --- | --- |
| 触发 | 变更入口模块需要改变自身负责的域内条目（架构案 5.4、8.2） |
| 参与者 | 变更入口模块、域持有者、日志服务 |
| 调用顺序 | 变更入口模块经 `API-SAVE-009` 提交域标识与变更提交项 → 本对象校验来源模块是否为该域登记的变更入口、阶段取值是否允许 → 写入域内容并返回提交结果；物品类变更一律经 M09 的写入服务提交 |
| 状态变化 | 该域内容按提交项更新；域持有者状态不变 |
| 产生的事件 | 无 |
| 结束条件 | 提交结果确定；被拒绝的提交经日志服务记录且不改变域内容 |

| # | 判定条件 | 期望结果 |
| --- | --- | --- |
| 1 | 域处于已释放（局外阶段）时收到读取 | 返回空结果或失败结果，不隐式创建域结构 |
| 2 | 本局装配尚未完成时收到读取或提交 | 返回失败结果，不进入就绪 |
| 3 | 结算阶段收到改变局内状态的提交项 | 拒绝（架构案 6.6、8.3 第 5 条） |
| 4 | 结算阶段收到单局状态域内对象的创建或销毁提交 | 拒绝（架构案 6.6） |
| 5 | 提交来源模块未登记为该域变更入口 | 拒绝该次提交并记录日志 |
| 6 | 物品类变更未经过 M09 的写入服务 | 拒绝（架构案 5.4、8.2） |

| 10 | 开新局时上一局域内容未清空 | 判定为违反；已释放到空结构的重建必须覆盖全部域内容 |
| 11 | 域内容含未登记切面的条目 | 不进入任何结构，按新增数据域的接入步骤补登记（架构案 8.5.2） |

| 13 | 恢复后发现派生项未重建或与来源状态不符 | 由来源方按来源状态重建，不按派生结果反推来源状态（架构案 8.2 第 3 条） |

## 10. 实现约束

### 10.1 实现约束条目

- 三个域各有唯一持有者；其他模块只持有域标识，经持有者读取（架构案 5.2）。
- 持有者不承载业务判断，不解释域内条目的业务含义（架构案 5.4）。
- 域内容必须可序列化，并满足判别字段式多态序列化要求；运行期标识不得写入结构（架构案 7.1、8.6 第 8 条）。
- 单局存档的写入必须原子；提交过程中断时整次作废并保留上一份有效存档（架构案 5.3 第 4 条）。
- 派生项不入档，只由来源方按来源状态重建（架构案 8.2 第 3 条）。
- 批量查询与跨域只读遍历属于读取，但不得在读取方缓存结果（架构案 8.2）。
- 结算阶段封闭：不接受改变局内状态的提交，也不接受单局状态域内的对象创建与销毁（架构案 6.6、8.3 第 5 条）。
- 域内容释放后保留重试能力所需的提交结果记录，不因释放丢失跨局提交的失败语义（架构案 9.5.6）。

### 10.2 实现要求

- I-M01-06 三个数据域各有唯一持有者；持有者不承载业务判断，跨域变更经 01-50 定义的数据域入口提交，派生结果不作为数据来源（架构案 5.4、8.2 第 3 条、3.4 第 13 项）。
- I-M01-07 数据域内容必须可序列化：域内条目按 01-50 声明的切面采集，存档对象只在采集与恢复期间存在；存档序列化采用**判别字段式多态序列化**，序列化结果中只出现自定义的字符串判别值、不写入运行时类型名；单局存档的写入必须原子（架构案 6.5、7.1、5.3 第 4 条、8.6 第 8 条）。

I-M01-07 在存档写入与序列化机制上的部分由 `M01-03_存档服务代码设计案.md` 承接，本条在本文档承接域内容侧（域内容的可序列化与切面采集口径），不构成两条编号。

### 10.3 缺口条目

本对象不提出缺口条目。主案的四个既有缺口均不落在本对象：`REQ-M01-01`（设置项清单）承接方为系统设计文档 01-60；`REQ-M01-03`（日志落点）承接方为架构设计案 7.7 或系统设计文档 01-60；`REQ-M01-05`（配置校验清单在资产内的声明方式）落于 `M01-04_配置服务代码设计案.md`；`REQ-M01-06`（世界时间推进时点，已由决策 91 关闭、待复核）落于 `M01-03_存档服务代码设计案.md`。
