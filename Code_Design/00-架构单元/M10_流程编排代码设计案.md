## 1. 系统定义

### 1.1 系统目的

本单元的系统标识为 `SYS-M10-001 流程编排`。

规定「什么时候轮到谁」：持有局内阶段的唯一权威，并把事件的进入与退出、战斗的启动与收束、局末的结算与写入、局外的流转按固定顺序编排成可执行的调用序列。

### 1.2 系统职责

- 持有阶段状态机，维护局内阶段取值（地图阶段、事件执行阶段、战斗阶段、收尾窗口阶段、结算阶段、局外阶段）并执行阶段切换（架构案 6.6）。
- 事件执行：驱动事件实例从进入到退出，编排事件内的战斗、交易与结算调用，并按 9.5.3 的十步收束完成事件退出。
- 战斗执行：接受事件侧的执行请求，启动战斗、驱动轮次推进与自动保存、判定结束并把结果交回事件侧；全队失去行动能力时只产生判定并写入战斗结果，不在战斗内成立结局（架构案 3.1 ARC-M05-001、6.6 第 3 条；设计决策记录决策 90）。
- 结算执行：在事件结算环节的事件结果提交之后读取整局存档快照，按 M06 定义的结算组件清单调度执行并完成跨局写入的一次提交；结算流程末尾（进入局外阶段）释放世界状态域、单局状态域、玩家状态域三个数据域，释放后由开新局全部重建（架构案 5.2、6.6、9.5.6）。
- 局外流转：结算提交后的局外阶段流转，以及开新局与读档恢复两个进入地图阶段的入口编排。
- 三类终止情形的承接：全队失去行动能力、主线中断、关底未达标三种未通关收尾情形由各自判定方只产生判定结果，由本单元的事件执行器在事件收尾时承接，统一在事件结算环节成立与收场（架构案 3.1 ARC-M10-001、9.5.5；设计决策记录决策 90）。

### 1.3 系统边界

流程编排不负责：

- 事件池的生成、刷新、过期剔除、权重与抽取（归 M02；本单元只在收束的第 5 至 9 步调用其刷新入口并等待完成）。
- 事件模板、事件变体、事件实例的数据持有与状态迁移规则（归 M02；本单元只请求其迁移，不改变其取值规则）。
- 战斗内的单条规则：时间轴、行动槽、战场空间、技能、单位状态与战斗结果判定（归 M05；全队失去行动能力在战斗内只产生判定并写入战斗结果，不在战斗内成立结局）。
- 跨局数据的写入内容与结算组件的分工（归 M06；本单元只按组件清单调度，不解释写入项）。
- 结局判定、结局类型与触发起因的取值（归 M06）。
- 界面打开与关闭、场景切换、界面栈层级（归 M08；本单元只发布阶段切换，界面装配由 M08 订阅后执行，见 3.4 第 1 项与 8.4 第 5 条）。
- 存档结构、切面采集、提交点管理与版本迁移（归 M01 的存档服务）。
- 时间口径与事件内记账规则（归 M02 的时间机制）、时间推进的受理实现（归 M01 的时间服务）。
- 条件表达式的定义与组合（归 M02 与 02-30-10）、效果叠加（归 M09）。
- 任何游戏规则的定义；本单元不新增玩法内容。

### 2.3 数据关系

- `CLS-M10-001` 持有对世界状态域阶段取值的引用，并以 `CLS-M10-002` 判定一次切换请求是否成立；两者是引用关系，不是包含关系。
- `CLS-M10-004`、`CLS-M10-005`、`CLS-M10-006` 各自独立，互相之间只通过标识引用（事件实例标识、战斗实例标识、结算执行编号），不互相持有实体。
- 三个执行上下文一律只持有被编排方的**标识**，不持有被编排方的可变对象（架构案 3.4 第 5 项、8.2 第 2 条）。

### 3.2 状态转换

阶段转换：

```
局外阶段 → 地图阶段
地图阶段 → 事件执行阶段
地图阶段 → 战斗阶段
事件执行阶段 → 战斗阶段
事件执行阶段 → 地图阶段

事件执行阶段／收尾窗口阶段的收尾路径（事件结算环节） → 结算阶段
```

装配与执行器转换：

```

```

结算阶段的进入条件是事件结算环节的事件结果提交，不是「结局成立」；战斗阶段不直接退出到结算阶段，全队失去行动能力在战斗内只做判定并写入战斗结果，由事件执行器在事件收尾时承接（架构案 6.6 第 3 条、9.5.5、9.5.6；设计决策记录决策 90）。进入结算阶段的具体来源阶段清单待上游补齐（REQ-M10-02），当前按架构案 9.5.5、9.5.6 与 07-40 3.13 的收场路径执行。「地图阶段 → 战斗阶段」一条依据架构案 9.5.2 第 3 步（战斗事件进入即进入战斗阶段），与 6.6 转换表的地图阶段退出目标（事件执行阶段）待对齐，并入 REQ-M10-02。

### 4.2 接口详细定义

#### API-M10-001 阶段查询

职责：返回当前阶段取值与进入时刻，供全部模块做阶段前置判定。

输入：
- 参数输入：无。
- 状态输入：阶段状态机的当前阶段取值。
- 数据输入：无。
- 外部事件输入：无。

读取：
- 局内阶段取值（世界状态域）。

输出：
- 返回值：阶段取值与阶段进入时刻。
- 状态输出：无。
- 事件输出：无。
- 外部系统调用：无。

产生的状态变化：无。

前置条件：本单元已完成初始化（架构案 6.1 阶段 3、8.3 第 1 条；由启动物体按单元装配声明顺序显式初始化），阶段状态机已创建。

后置条件：返回值等于世界状态域内的阶段取值。

副作用：无。

异常情况：阶段取值缺失（存档损坏或恢复失败）时不返回值，按架构案 7.1 的失败语义停在主界面。

#### API-M10-002 阶段切换执行

职责：受理一次阶段切换请求，校验后更新阶段取值并执行目标阶段的进入动作。

输入：
- 参数输入：目标阶段、起因（开新局／读档恢复／事件进入／战斗开始／战斗结束／事件退出／窗口结束／事件结果提交／结算提交完成）、请求方标识、关联对象标识。
- 状态输入：当前阶段取值、事件实例状态、战斗运行状态、本局结算状态。
- 数据输入：阶段切换登记 `CLS-M10-002`。
- 外部事件输入：本局生成完成、当前事件池刷新完成、存档恢复完成、战斗结束、事件结算环节的事件结果提交。

读取：
- 局内阶段取值、`CLS-M10-002`、事件实例状态（经 `API-M02-001`）、战斗运行状态（经 `API-M05-005`）。

输出：
- 返回值：切换受理结果（受理／拒绝及原因）。
- 状态输出：阶段取值更新；按目标阶段执行进入动作（进入结算阶段封闭局内输入通道；进入局外阶段开放局外操作并释放三个数据域；进入地图阶段按起因触发生成流程或确认恢复结果）。
- 事件输出：阶段切换。
- 外部系统调用：进入地图阶段且起因=开新局时调用 `API-M02-005` 生成流程调用与 `API-M02-002` 事件池刷新；起因=事件退出时调用 `API-M02-002`。

产生的状态变化：
- 局内阶段取值由来源阶段变为目标阶段。
- 目标阶段的进入动作生效（结算阶段封闭输入、局外阶段开放局外操作并释放三个数据域）。

前置条件：
- 请求方是当前阶段的拥有方：地图阶段与事件执行阶段为 M10 的事件执行器，战斗阶段与收尾窗口阶段为 M10 的战斗执行器，结算阶段为 M10 的结算执行器，局外阶段为 M10 的局外流转部分（架构案 6.6 的阶段拥有方）。
- 来源阶段与目标阶段的组合在 `CLS-M10-002` 的允许来源内。
- 起因对应的对象满足目标阶段的进入条件（架构案 6.6：地图阶段需无进行中事件；事件执行阶段需事件实例进入进行中；战斗阶段需战斗执行器启动；收尾窗口阶段需战斗结束；结算阶段需事件结算环节的事件结果提交；局外阶段需结算提交完成）。

后置条件：阶段取值等于目标阶段；阶段切换已发布。

副作用：发布阶段切换；订阅方按各自职责响应，本单元不感知订阅方（架构案 4.3）。

异常情况：
- 非拥有方发起、或来源与目标的组合不在允许清单内：拒绝，不改变阶段取值。
- 目标阶段为结算阶段而事件结算环节的事件结果提交未成立：拒绝。
- 由战斗阶段直接提交切换到结算阶段：拒绝；战斗内只产生判定并写入战斗结果，不在战斗内成立结局（架构案 6.6 硬规则 3；设计决策记录决策 90）。
- 结算阶段内向改变局内状态的模块受理切换：拒绝（架构案 6.6 硬规则 2）。
- 进入局外阶段而三个数据域尚未提交完成：拒绝；数据域释放只发生在跨局写入的一次提交完成之后（架构案 5.2、8.3 第 3 条）。

#### API-M10-003 事件执行入口

职责：受理一次事件的进入或退出，编排事件从进入到退出的执行序列。

输入：
- 参数输入：事件实例标识、执行动作（进入／退出）。
- 状态输入：当前阶段取值、事件实例状态、事件内时间记账、战斗结果标识与达成目标清单。
- 数据输入：事件类型执行登记 `CLS-M10-003`、事件类型契约与事件属性配置（经 `API-M01-003`）。
- 外部事件输入：战斗结束、撤退发生、存档提交完成、时间刻度变化、当前事件池刷新完成。

读取：
- 事件实例与其状态（经 `API-M02-001`）、`CLS-M10-003`、局内阶段取值。

输出：
- 返回值：执行受理结果。
- 状态输出：事件实例状态经 M02 迁移（可进入 → 进行中、进行中 → 已完成）；阶段取值更新；事件退出时世界时间推进。
- 事件输出：阶段切换。
- 外部系统调用：`API-M02-001`、`API-M02-007`（请求 M02 把事件实例置为进行中）、`API-M01-005` 时间服务.Advance、`API-TIME-003` 时间服务.记账（落点归 02-10）、`API-SAVE-002` 存档服务.提交、`API-M02-002` 事件池刷新、`API-M02-004` 事件实例结束、`API-M05-004` 战斗结果查询、`API-M09-004` 条件判定、`API-SETTLE-002` 结局判定（在事件结算环节由本单元向 M06 发起；三类未通关收尾情形的判定结果在此承接，战斗内的判定由战斗执行器轮询战果后转交）。

产生的状态变化：
- 进入：事件实例状态 → 进行中；阶段取值 → 事件执行阶段或战斗阶段。
- 退出：事件实例状态 → 已完成或已错过；世界时间按本事件记账推进；阶段取值 → 地图阶段。
- 事件结算环节：本次事件结果构成本局结束时，阶段取值 → 结算阶段（结算阶段的唯一进入点；不构成本局结束时继续本序列）。

前置条件：
- 动作=进入：当前阶段为地图阶段；事件实例处于可进入。
- 动作=退出：当前阶段为事件执行阶段或收尾窗口阶段；事件实例处于进行中。

后置条件：事件状态已迁移；阶段取值与动作相符；进入时世界时间未推进，事件退出时世界时间已推进一次。

副作用：
- 进入时按事件配置记录一次性事件耗时并建立事件内时间记账（不动世界时间）。
- 事件退出时触发时间段推进节点的单局存档提交，并请求事件池刷新。

异常情况：
- 事件实例不处于动作要求的状态：拒绝，不改变事件状态与阶段取值。
- 同一事件实例重复提交进入：拒绝（同一时间只有一个事件处于进行中，事件系统 4.2）。
- 当前阶段不是地图阶段而提交进入：拒绝。
- 事件结算环节承接判定结果时本局已结算：拒绝重复结算，不改变阶段取值（07-40 3.4）。
- 退出收束过程中依赖不可用（刷新未完成）：保持收束中状态，不发布阶段切换，登记失败原因。

#### API-M10-004 战斗执行入口

职责：受理战斗事件的执行，启动战斗、驱动轮次循环与自动保存，判定结束并把结果交回事件侧；全队失去行动能力时只产生判定并写入战斗结果，不在战斗内成立结局。

输入：
- 参数输入：事件实例标识、战斗配置标识。
- 状态输入：当前阶段取值、战斗运行状态、单位状态（术语表 T-113）。
- 数据输入：事件类型执行登记 `CLS-M10-003`、战斗行为表登记的行为集合。
- 外部事件输入：轮次推进、行为提交完成、单位状态变化、撤退发生。

读取：
- 战斗运行状态（经 `API-M05-005`）、事件实例标识。

输出：
- 返回值：战斗执行受理结果，以及战斗结果标识（术语表 T-131）与达成目标清单（术语表 T-130）。
- 状态输出：战斗运行状态建立与收束；阶段取值更新。
- 事件输出：阶段切换。
- 外部系统调用：`API-M05-001` 战斗启动、`API-M05-002` 轮次推进、`API-M05-004` 战斗结果查询、`API-SAVE-002` 存档服务.提交（战斗轮次推进节点）、`API-M02-004` 事件实例结束（撤退标记随结束结果传入，窗口期延长与周边事件锁定范围在其中登记）。

产生的状态变化：
- 阶段取值 → 战斗阶段；战斗运行状态建立。
- 每次轮次推进后触发一次战斗轮次推进节点的单局存档提交。
- 战斗结束后按结果分派：撤退、终止情形承接、常规三类各自落到对应阶段。全队失去行动能力一类只把判定写入战斗结果，由事件执行器在事件收尾的事件结算环节承接，战斗阶段不直接退出到结算阶段。

前置条件：当前阶段为事件执行阶段，或由事件执行器在地图阶段以战斗事件进入的编排点调用；事件实例处于进行中。

后置条件：战斗结果标识与达成目标清单已取得；阶段按结束分派落定。

副作用：在每次轮次推进后触发自动保存；撤退时请求写入窗口期延长与周边事件锁定范围（撤退后事件在技术上仍为可进入，不新增事件状态取值；设计决策记录决策 92）。

异常情况：
- 战斗结果已提交后重复调用：拒绝。
- 战斗运行状态缺失且无法按存档恢复：拒绝并登记失败原因，停在主界面。
- 战斗配置标识不存在：拒绝，不建立战斗运行状态。
- 战斗内请求直接成立结局或直接切换到结算阶段：拒绝；判定只写入战斗结果（架构案 6.6 硬规则 3；设计决策记录决策 90）。

#### API-M10-005 结算执行入口

职责：受理事件结算环节的事件结果提交，切换至结算阶段，按结算组件清单调度执行并完成跨局写入的一次提交，并在进入局外阶段时释放三个数据域。

输入：
- 参数输入：结局类型（真结局／隐藏关底事件通过／未通关结局）、触发起因（关底未达标／主线中断／全队失去行动能力）、本局标识。
- 状态输入：当前阶段取值、本局结算状态。
- 数据输入：结算组件清单（经 `API-M06-004`）、结算组件表登记的写入边界。
- 外部事件输入：M06 的结算组件执行完成与提交结果登记（`API-SETTLE-001`、`API-SETTLE-003` 的返回）；本单元自己发布的 结算完成 不作为外部输入。

读取：
- 单局存档快照（整局存档快照，经 `API-SAVE-003` 读取）、结算组件清单、本局结算状态（`CLS-SETTLE-003`，07-40 拥有）。

输出：
- 返回值：提交结果（成功／失败待重试）。
- 状态输出：阶段取值 → 结算阶段，再 → 局外阶段；本局结算状态更新；跨局存档更新；进入局外阶段时释放世界状态域、单局状态域、玩家状态域三个数据域。
- 事件输出：结局成立（在事件结算环节承接事件结果提交并落定结算阶段时）、结算完成（一次提交完成后）。
- 外部系统调用：`API-SAVE-003` 存档服务.读取整局存档快照、`API-SAVE-007` 存档服务.提交跨局存档、`API-M06-004`、`API-SETTLE-002` 结局判定执行、`API-SETTLE-001` 结算组件执行、`API-SETTLE-003` 结算提交结果登记、`API-M06-003`、`API-M06-005`。

产生的状态变化：
- 阶段取值 → 结算阶段，局内输入通道封闭，世界时间不再推进。
- 依次执行本次版本启用的结算组件，每个组件从整局存档快照取数并写入跨局存档。
- 一次提交成功后本局标记为已结算，阶段取值 → 局外阶段，并释放世界状态域、单局状态域、玩家状态域三个数据域（由 M01 的数据域侧执行，开新局时全部重建）。

前置条件：
- 事件结算环节的事件结果提交已成立（结局类型与触发起因的判定取值归 M06，经 `API-SETTLE-002` 给出）。
- 本局结算状态为未结算。
- 当前阶段为事件执行阶段或收尾窗口阶段的事件收尾路径；战斗阶段不直接提交到结算阶段（架构案 6.6 硬规则 3；来源阶段清单待上游补齐，REQ-M10-02）。

后置条件：跨局存档已更新；本局结算状态为已结算，或保持未结算并处于提交失败待重试；进入局外阶段时三个数据域已释放。

副作用：发布结局成立与结算完成；结算窗口由 M08 订阅阶段切换后打开，本单元不直接调用界面侧。

异常情况：
- 已结算的本局重复受理：拒绝（同一已结算本局不允许再次结算，07-40 3.4）。
- 提交失败：整笔回滚，保持未结算并保留重试能力，重试不产生重复写入；此时不进入局外阶段、不释放数据域。
- 由战斗阶段直接提交切换到结算阶段：拒绝（架构案 6.6 硬规则 3）。
- 存档快照缺失：拒绝并登记失败原因。
- 结算阶段内收到改变局内状态的受理请求：拒绝。

| API-M10-007 | 阶段进入动作 | 执行目标阶段的进入动作：封闭或开放局内输入通道、按起因触发生成流程或确认恢复结果 | 否（经 `API-M10-002` 间接触发） |

| API-M10-009 | 事件退出收束编排 | 执行 9.5.3 的十步收束；第 2 步即事件结算环节，是承接判定结果与进入结算阶段的唯一入口 | 否（经 `API-M10-003` 间接触发） |

| API-M10-012 | 结算组件调度 | 读取组件清单、按序请求组件执行、汇总提交结果；一次提交完成并进入局外阶段时释放三个数据域 | 否（经 `API-M10-005` 间接触发） |
| API-M10-013 | 执行上下文重建 | 读档或恢复后按来源状态重建三个执行上下文 | 否（在启动与恢复路径中被调用） |

### 5.2 功能之间的关系

- `API-M10-002` 依次调用 `API-M10-006` 与 `API-M10-007`；校验不通过时不再进入动作。
- `API-M10-003` 按动作分派：动作=进入时调用 `API-M10-008`，动作=退出时调用 `API-M10-009`。
- `API-M10-008` 在事件类型为战斗事件时调用 `API-M10-004`；非战斗事件由事件执行器继续持有执行上下文。
- `API-M10-004` 内部由 `API-M10-010` 驱动循环、由 `API-M10-011` 完成分派；分派到撤退、终止情形承接或常规路径时把控制交回 `API-M10-009`。全队失去行动能力的判定由 `API-M10-011` 轮询战果后转交事件执行器，战斗执行器不成立结局。
- `API-M10-009` 在收束的第 2 步（事件结算环节）承接本次事件的判定结果，并按需向 M06 发起结局判定（`API-SETTLE-002`）：事件结果构成本局结束时调用 `API-M10-005`，否则继续后续步骤并回到 `API-M10-002`（回到地图阶段）。
- `API-M10-005` 内部由 `API-M10-012` 完成组件调度与提交；提交完成后调用 `API-M10-002` 进入局外阶段，世界状态域、单局状态域、玩家状态域三个数据域随之释放。
- `API-M10-013` 只被启动与恢复路径调用，不参与局内编排。

### 6.4 使用方式

### 6.5 依赖方向限制

分层与模块是架构案的**描述性分类**，不承担数据隔离、交互隔离与依赖方向约束职责（架构案 1.6）。本节只用于阅读导航：列出本单元实际依赖的模块与方向，以及仍然成立的少量硬规则。调用是否合法的判据是架构案 3.3 的允许清单、3.4 的禁止清单与 8.1 的依赖方向规则；**同层只读查询按 3.3 第 5 项的通则成立，不需要逐条登记、不需要逐条例外申报**（架构案 8.1、8.2）。

阅读导航：

- 依赖方向：本单元向 M01 申请基础设施能力；向 M02、M05、M06 调用其执行入口（本单元是按阶段调用多个模块执行入口的位置）；向 M09 请求条件判定。
- 回指方向：任何模块与界面侧只读查询本单元的当前阶段（`API-M10-001`）；M08 的界面侧经 `API-M10-003` 提交事件进入确认（架构案 9.5.2）；战斗结束与窗口结束的战果由 M05 经 `API-M10-004` 交回，由本单元战斗执行器发起切换。
- 不得依赖：本单元不依赖 M08 及任何表现层对象，不发起界面调用；界面装配由 M08 订阅阶段切换完成。

硬规则：

1. 不写入他方数据、不持有对方的可变引用；跨域变更经持有方入口。三个执行上下文只持有被编排方的标识（架构案 3.4 第 5 项、8.2）。
2. 不绕过统一入口：阶段取值经数据域入口写入，世界时间经 `API-M01-005`，存档经 `API-SAVE-002`、`API-SAVE-003`、`API-SAVE-007`，条件判定经 `API-M09-004`，日志经 `API-M01-010`（架构案 3.4 第 6 至 10 项、第 7 章）。
3. 基础设施不依赖任何具体玩法系统：本单元不得要求 M01 感知阶段语义，也不得把阶段语义写进基础设施（架构案 3.4 第 11 项）。
4. 不形成循环依赖；被编排方不得反向调用本单元的编排内部功能；跨模块状态广播走事件通道（架构案 3.4 第 12 项、8.4 第 1 条）。
5. 不使用系统基础库的随机源、不在游戏状态判定中使用帧时间、不依赖引擎的退出回调完成存档或收尾（架构案 3.4 第 15 至 17 项）。
6. 不重复实现引擎已提供的能力（架构案 7.12、8.6 第 1 条）。

M02、M05、M06 不得依赖本单元的三个执行入口；阶段切换只由当前阶段的拥有方发起（架构案 6.6 硬规则 1），被编排方以战果或结果交回的方式触发编排（战斗结束与窗口结束的战果由 M05 经 `API-M10-004` 交回）。事件状态迁移由本单元调 M02 的 `API-M02-007`／`API-M02-004` 请求（架构案 9.5.3），事件退出由本单元订阅 `事件结算完成` 后自行受理。该方向的登记见 REQ-M10-09。

跨模块事件的契约以**类型契约**的形式确定：登记事件名、唯一发布方、载荷字段类别与失败语义；登记表以可检视的资产承载、按**即用即定**登记（需要新事件时直接在登记表补一行，不设审批、编号申领或版本流程）。契约的强制方式是**一条对账测试**：测试遍历代码中的全部事件发布点并与登记表逐项比对，出现未登记事件即测试失败。事件名不在契约登记表内属于契约缺口，由对账测试在测试期发现，不在运行期拦截（架构案 4.3、7.6、8.4 第 2 条；设计决策记录决策 95）。

一致性说明：结局成立与结算完成两个事件同时登记在 M06 与本单元名下（架构案 3.1 的事件栏）。按架构案 9.5.5 与 9.5.6，两者的唯一发布方是本单元的结算执行器：M06 只提供结局判定取值（`API-SETTLE-002`）与提交结果登记（`API-SETTLE-003`），不发布这两个事件；同一语义不重复发布，该口径由变更 I 直接裁定，07-40 的副作用列与 M06 §7.2 按同一口径对齐。

### 7.3 数据流

- 阶段取值：由 M10 写入世界状态域（M01 持有），其他模块经 `API-M10-001` 只读；不存在第二份权威副本；阶段取值随单局创建，在结算提交完成、进入局外阶段时随三个数据域一并释放，开新局时重建。
- 事件执行数据：事件实例状态由 M02 持有；本单元只传递标识并请求迁移，执行上下文不入档。
- 战斗执行数据：战斗运行状态由 M05 自持并属单局状态域；本单元只读取结果与切面；全队失去行动能力的判定写入战斗结果后由本单元在事件结算环节承接，不在战斗内成立结局。
- 结算数据：输入是存档服务提供的整局存档快照，输出是 M06 按组件写入的跨局存档；本单元不经手写入项内容。一次提交成功后进入局外阶段，世界状态域、单局状态域、玩家状态域三个数据域由 M01 的数据域侧释放，开新局时全部重建（架构案 5.2、8.3 第 3 条；变更 J）。
- 时间数据：事件内只做时间记账（非战斗按事件配置录入并累加，战斗由 M05 以秒累计净时长），事件退出时经 `API-M01-005` 一次性推进世界时间；战斗净时长向上取整对齐到时间段边界（架构案 7.5；设计决策记录决策 91）。

## 8. 核心流程

### 8.1 阶段切换受理（通用）

```
触发：当前阶段的拥有方或本单元执行器提交切换请求
参与：M10（阶段状态机）、请求方、目标阶段的受影响模块
序：
  1 请求方经 API-M10-002 提交目标阶段、起因、请求方标识与关联对象标识
  2 API-M10-006 按 CLS-M10-002 校验请求方、来源与目标的组合、进入条件（结算阶段的进入条件是事件结算环节的事件结果提交，不是结局成立）
  3 校验通过 → 经数据域入口写入阶段取值
  4 API-M10-007 执行目标阶段的进入动作（封闭或开放局内输入通道、按起因触发后续编排；进入局外阶段时三个数据域由数据域侧释放）
  5 经 API-M01-011 发布 阶段切换
状态变化：阶段取值更新；进入动作生效
产生事件：阶段切换
结束条件：目标阶段的进入动作完成
```

### 8.2 事件进入（地图阶段 → 事件执行阶段／战斗阶段）

```
触发：玩家在事件信息面板确认进入，界面侧按架构案 9.5.2 调用 API-M10-003 提交一次进入确认
参与：M10（事件执行器、阶段状态机）、M08（界面侧提交进入确认）、M02、M01（时间服务）
序：
  1 M08 的界面侧提交进入确认（事件实例标识、动作=进入）
  2 API-M10-008 经 API-M02-001 查询事件实例状态，校验当前阶段为地图阶段且事件处于可进入
  3 经 `API-M02-007` 请求 M02 把事件实例置为进行中
  4 按 CLS-M10-003 分派：非战斗事件 → 事件执行阶段；战斗事件 → API-M10-004 启动战斗并进入战斗阶段
  5 非战斗事件经时间服务记账入口记录一次性耗时（不动世界时间；事件内只做时间记账，设计决策记录决策 91）
  6 经 API-M10-002 落定阶段 → 发布阶段切换；M02 发布 事件进入进行中
状态变化：事件状态 → 进行中；阶段取值更新
产生事件：事件进入进行中（M02）、阶段切换（M10）
结束条件：目标阶段的进入动作完成，界面可交互
```

### 8.3 事件退出与十步收束（事件执行阶段 → 地图阶段）

其中第 3 至 10 步即任务书的事件阶段转地图阶段的八步。

```
触发：M02 判定事件达成结束条件并发布 事件结算完成，本单元订阅后由事件执行器受理 `API-M10-003`（动作=退出）
参与：M10（事件执行器、阶段状态机）、M02、M05、M01（时间服务、随机服务、存档服务）、M03、M06、M09
序：
  1 事件执行器收集事件结果：战斗事件经 API-M05-004 取战斗结果标识与达成目标清单
  2 经 API-M02-004 请求事件结算：M02 按结果标识查询事件配置并应用全部结果；需要条件分支时经 API-M09-004 判定。本步即事件结算环节：事件执行器在此承接本次事件的判定结果（战斗中的判定由战斗执行器轮询战果后转交，主线中断与关底未达标由各自系统产生判定结果），并按需向 M06 请求结局判定（`API-SETTLE-002`）；事件结果构成本局结束时转入 8.5，不再继续本序列
  3 时间结算：取出本事件记账的累计值，经 API-M01-005 一次性推进世界时间（战斗净时长先向上取整对齐到时间段边界）。事件内只做时间记账，本次事件退出时一次性推进（架构案 7.5；设计决策记录决策 91）
  4 自动保存：时间段推进节点由时间服务按 `API-M01-005` 的时间刻度变化派生并经 `API-SAVE-002` 提交，本单元只等待 自动保存完成 并核对提交结果（节点归属与提交点见 REQ-M10-08）
  5 至 8 经 API-M02-002 请求事件池刷新：过期剔除、池检查与权重、确认生成数量、抽取生成，全部由 M02 的事件调度执行
  9 呈现：M02 按架构案 3.3 第 5.3 项写入呈现列表，M03 更新呈现并发布 呈现列表更新
 10 经 API-M10-002 回到地图阶段（起因=事件退出）→ 发布阶段切换
 结算阶段的进入条件是事件结算环节的事件结果提交，不是结局成立；战斗阶段不直接退出到结算阶段（架构案 6.6 第 3 条、9.5.5；设计决策记录决策 90）
状态变化：事件状态 → 已完成或已错过；世界时间推进；当前事件池刷新；阶段回到地图阶段
产生事件：事件结算完成、时间刻度变化、自动保存完成、当前事件池刷新完成、呈现列表更新、阶段切换
结束条件：地图界面按新事件池刷新完成
```

### 8.4 战斗执行与结束分派

```
触发：事件执行器在战斗事件编排点调用 API-M10-004
参与：M10（战斗执行器、阶段状态机）、M05、M02、M01（存档服务）
序：
  1 经 API-M05-001 启动战斗（事件上下文与战斗配置标识）
  2 经 API-M10-002 落定战斗阶段（若尚未在战斗阶段）
  3 API-M10-010 驱动轮次循环：每轮经 API-M05-002 请求轮次推进 → M05 按时间轴给出获得行动机会的单位
    → 本单元经 `API-SAVE-002` 提交一次单局存档（战斗轮次推进节点，按 M05 的 `API-M05-002` 注记；提交点归属见 REQ-M10-08）→ 等待 M05 受理玩家行为提交（`API-M05-003`）
  4 API-M10-011 按 API-M05-004 的战斗结果分派：
    撤退 → 经 `API-M02-004` 传入撤退标记并登记窗口期延长与周边事件锁定范围，事件保持可进入（不新增事件状态取值），转入 8.3 收束
    全队失去行动能力 → 战斗内只产生判定并写入战斗结果，不在战斗内成立结局；按常规走完收尾窗口与事件收束，由事件执行器在事件结算环节承接该判定（触发起因=全队失去行动能力），转入 8.3 并在事件结算环节进入 8.5
    其他结果 → 按事件配置进入收尾窗口阶段，或回到事件执行阶段继续编排后转入 8.3
状态变化：战斗运行状态建立与收束；未结状态按切面入档；阶段取值按分派更新；战斗阶段不直接退出到结算阶段
产生事件：战斗开始、轮次推进、行为提交完成、单位状态变化、战斗结束、撤退发生（M05）；自动保存完成（M01）；阶段切换（M10）
结束条件：战斗结果标识与达成目标清单已交回事件侧，阶段按分派落定
```

### 8.5 局末结算与跨局写入（→ 结算阶段 → 局外阶段）

```
触发：事件结算环节的事件结果提交构成本局结束（结算阶段的唯一进入条件；三种未通关收尾情形统一在此成立）
参与：M10（事件执行器、结算执行器、阶段状态机）、M06、M01（存档服务）、M08（订阅阶段切换后打开结算窗口）
序：
  1 判定承接：本单元的事件执行器在事件结算环节承接本次事件的判定结果（战斗中的判定由战斗执行器轮询战果后转交），结局类型与触发起因的判定取值由 M06 经 `API-SETTLE-002` 给出
  2 经 `API-SAVE-003` 读取整局存档快照（结算组件执行的取数来源）
  3 本单元发布 结局成立 并经 `API-M10-005` 受理
  4 经 API-M10-002 落定结算阶段（起因=事件结果提交），封闭局内输入通道；发布阶段切换
  5 经 API-M06-004 查询本次版本启用的结算组件清单
  6 API-M10-012 按清单依次请求 M06 执行组件（`API-SETTLE-001`）：节点解锁检查组件，以及后续版本启用的达成记录与大关进度组件
  7 一次提交（跨局存档，经 `API-SAVE-007`）：成功 → 经 `API-SETTLE-003` 登记为已结算；失败 → 整笔回滚，经 `API-SETTLE-003` 登记为未结算并保留重试
  8 经 API-M10-002 落定局外阶段（起因=结算提交完成）；释放世界状态域、单局状态域、玩家状态域三个数据域（由 M01 的数据域侧执行，开新局时全部重建）；发布 结算完成 与 阶段切换
状态变化：跨局存档更新；本局结算状态更新；阶段取值更新；三个数据域释放（提交失败时不释放、不进入局外阶段）
产生事件：结局成立（M10）、节点解锁、传闻解锁（M06 的写入方发布）、结算完成（M10）、阶段切换（M10）

```

## 9. 异常与边界情况

| 情形 | 判定条件 | 期望结果 |
| --- | --- | --- |
| 非拥有方发起切换 | 请求方不在该阶段的拥有方清单内 | 拒绝，阶段取值不变，登记原因 |
| 非法的来源与目标组合 | 组合不在 `CLS-M10-002` 的允许来源内 | 拒绝，阶段取值不变 |
| 进入条件不满足 | 目标阶段的进入条件未成立（如无进行中事件却切到事件执行阶段；结算阶段未取得事件结算环节的事件结果提交） | 拒绝，阶段取值不变 |
| 结算阶段收到状态变更请求 | 当前阶段为结算阶段且请求会改变局内状态 | 拒绝（架构案 6.6 硬规则 2） |
| 事件状态不匹配 | 进入时事件不处于可进入；退出时事件不处于进行中 | 拒绝，事件状态与阶段取值均不变 |
| 重复进入同一事件 | 同一事件实例已处于进行中 | 拒绝（事件系统 4.2：同一时间只有一个事件处于进行中） |
| 重复结算 | 本局结算状态为已结算 | 拒绝（07-40 3.4） |
| 结算提交失败 | 一次提交未成功 | 整笔回滚，保持未结算并保留重试；不进入局外阶段、不释放数据域；重试不产生重复写入 |
| 存档快照缺失 | 结算受理时读取整局存档快照失败 | 拒绝并登记原因；不改动本局结算状态 |
| 进程在收束过程中终止 | 收束第 4 步提交后、第 5 至 9 步完成前进程终止 | 退出即进程终止：不执行销毁序列、不提交存档、不依赖退出回调；以最近一次自动保存的提交结果为准（架构案 5.3 第 4、5 条、6.4、9.4；设计决策记录决策 89）。重新启动后按存档的阶段取值与事件池快照继续，不重放已提交步骤 |
| 战斗内把判定当作结局成立 | 战斗结果为全队失去行动能力，战斗阶段直接请求切换到结算阶段 | 拒绝；战斗内只产生判定并写入战斗结果，结局只在事件结算环节成立（架构案 6.6 第 3 条、9.5.5；设计决策记录决策 90） |
| 结算提交完成后的数据域访问 | 进入局外阶段后仍有模块读写三个数据域中的内容 | 拒绝；世界状态域、单局状态域、玩家状态域已释放，内容由开新局全部重建（架构案 5.2、8.3 第 3 条；变更 J） |
| 阶段取值缺失 | 读档失败或阶段取值不可读 | 停在主界面，阶段保持局外阶段（架构案 7.1 失败语义） |
| 战斗未结状态恢复 | 存档内存在未结战斗 | 阶段按存档取值落定；战斗执行上下文经 `API-M05-005` 重建，恢复到最近一次行动机会开始的时刻，未确认的选择不恢复（架构案 9.3） |
| 多个终止起因同时成立 | 全队失去行动能力与主线中断同时成立 | 按即时成立的那一刻取一个成因，不产生第二个结局类型（07-40 3.7） |
| 事件未退出时请求推进时间 | 任何模块在事件进行中请求推进世界时间 | 拒绝（架构案 7.5：只在事件退出时推进；事件内只做时间记账，设计决策记录决策 91） |
| 收束中刷新未完成 | 第 5 至 9 步未返回完成 | 保持收束中状态，不发布阶段切换，登记失败原因 |

## 10. 实现约束

### 10.1 功能要求

本单元没有成员系统，以下功能要求取自架构案 6.6、9.5.1 至 9.5.8 与 3.1 ARC-M10-001 的系统级规则，属程序设计约束，无对应的上游游戏设计稿（NR-06 §十.1）。

- `F-M10-01` 局内阶段取地图、事件执行、战斗、收尾窗口、结算、局外六种取值，切换按架构案 6.6 的允许路径执行；结算阶段的进入条件是事件结算环节的事件结果提交，战斗阶段不直接退出到结算阶段。
- `F-M10-02` 事件从进入到退出的全过程由本单元编排，事件退出时按十步收束完成时间推进、自动保存、事件池刷新与回到地图阶段；收束的事件结算环节是结算阶段的唯一进入点。
- `F-M10-03` 战斗事件的启动、轮次推进与结束判定由本单元编排，战斗结果标识与达成目标清单交回事件侧；全队失去行动能力在战斗内只产生判定并写入战斗结果，不在战斗内成立结局。
- `F-M10-04` 事件结算环节的事件结果提交构成本局结束时，按结算组件清单完成一次跨局写入提交，提交失败可重试且不产生重复写入。
- `F-M10-05` 结算提交完成后进入局外阶段，并释放世界状态域、单局状态域、玩家状态域三个数据域；局外提供线索树查看、剪枝提交与开新局入口；开新局与读档恢复均落在地图阶段，开新局时三个数据域全部重建。
- `F-M10-06` 全队失去行动能力、主线中断、关底未达标三种未通关收尾情形由各自判定方只产生判定结果，统一在事件结算环节成立，并按未通关结局与对应触发起因写入（架构案 6.6、9.5.5；07-40 3.7、3.13）。
- `F-M10-07` 世界状态域、单局状态域、玩家状态域三个数据域在跨局写入提交完成、进入局外阶段时释放；释放后由开新局全部重建（架构案 5.2、6.6、8.3 第 3 条；变更 J）。

### 10.2 实现要求

- `I-M10-01` 阶段取值必须入单局存档的世界状态域切面，读档后按存档取值恢复，不依据事件状态或界面位置重新推导。
- `I-M10-02` 三个执行上下文必须按来源状态重建，不入档；被编排方的对象一律只持有标识。
- `I-M10-03` 阶段切换只能经 `API-M10-002` 执行；任何模块不得自行改变阶段，也不得借界面切换隐式改变阶段。
- `I-M10-04` 世界时间的推进只经 `API-M01-005` 且只在事件退出收束的第 3 步发生一次；事件进入与进行中只做时间记账，不动世界时间（架构案 7.5；设计决策记录决策 91）。
- `I-M10-05` 自动保存的两类节点按 01-50 的调用者栏与 M05 的注记分工：时间段推进节点由时间服务经时间刻度变化派生并经 `API-SAVE-002` 提交，本单元只等待 `自动保存完成` 并核对结果；战斗轮次推进节点由本单元经 `API-SAVE-002` 提交（M05 的 `API-M05-002` 注记）；两类的提交点归属待上游对齐（见 REQ-M10-08）。
- `I-M10-06` 跨模块事件的契约以**类型契约**的形式确定：事件名、唯一发布方、载荷字段类别与失败语义在事件契约登记表内按**即用即定**登记（需要新事件时直接在登记表补一行，不设审批、编号申领或版本流程）；契约的强制方式是一条对账测试，事件名不在登记表内属于契约缺口，由对账测试在测试期发现，**不在运行期拦截**（架构案 4.3、7.6、8.4 第 2 条；设计决策记录决策 95）。
- `I-M10-07` 结局判定、结局类型与触发起因的取值归 M06，本单元只受理与编排，不自行判定。
- `I-M10-08` 结算阶段内本单元不受理任何改变局内状态的编排请求，也不创建或销毁单局状态域内的对象（架构案 8.3 第 5 条）。
- `I-M10-09` 需要条件判定时一律经 `API-M09-004`，需要效果表达时一律经 M09 的入口；本单元不自行实现条件判定与效果叠加。
- `I-M10-10` 依赖方向按 6.5 的阅读导航与六条硬规则执行：不得依赖 M08，不得被被编排方反向依赖，不得出现循环依赖。
- `I-M10-11` 常驻对象由常驻场景承载；本单元不自行创建常驻对象，四个常驻对象由启动物体按单元装配声明顺序显式初始化、按逆序销毁，创建顺序按架构案 6.3 第 4 项（架构案 2.4.1、2.4.2、6.1 阶段 3、8.3 第 1、6 条）。
- `I-M10-12` 结算阶段的进入条件是**事件结算环节的事件结果提交**，不是结局成立；战斗模块在全队失去行动能力时只产生判定并写入战斗结果，不在战斗内成立结局；战斗阶段不直接退出到结算阶段；三种未通关收尾情形统一在事件结算环节成立（架构案 3.1 ARC-M05-001 与 ARC-M10-001、6.6 第 3 条、9.5.5；设计决策记录决策 90）。
- `I-M10-13` 结算流程末尾（进入局外阶段）释放**世界状态域、单局状态域、玩家状态域三个数据域**；释放后由开新局全部重建；结算提交失败时不进入局外阶段、不释放数据域（架构案 5.2、6.6、8.3 第 3、5 条；变更 J）。
- `I-M10-14` 退出游戏即**进程终止**，不提交存档、不构成任何提交点、不执行销毁序列、不依赖任何退出回调完成存档或收尾；单局存档的唯一可靠写路径是时间段推进与战斗轮次推进两类自动保存节点（架构案 3.4 第 17 项、5.3 第 4 项、6.4、7.1、9.4；设计决策记录决策 89）。
- `I-M10-15` 不得重复实现引擎已提供的能力：对象池与集合池、异步任务、设备到动作的输入映射、音频与本地化与特效动画的播放原语、资产载体与序列化原语、资源加载、场景装卸与日志通道一律使用引擎提供的能力，项目只做架构案 7.12「项目实现」栏登记的部分（架构案 7.12、8.6 第 1 条）。
- `I-M10-16` 权威游戏状态由普通 C# 对象持有，引擎对象只承担承载、呈现与编辑器配置职责；阶段取值与三个执行上下文不得放在随场景销毁的对象上（架构案 8.6 第 2 条）。
- `I-M10-17` 不依赖引擎的启动回调顺序、脚本执行顺序或帧回调顺序满足初始化与推进的顺序要求；顺序由单元装配声明与显式调用序列决定（架构案 2.4.1、2.4.2、6.1、8.6 第 4 条）。
- `I-M10-18` 本单元在初始化时显式复位自身状态，不依赖引擎的域重载提供初始状态（架构案 6.1、8.3 第 7 条、8.6 第 5 条）。
- `I-M10-19` 影响游戏状态的判定不得使用帧时间；本作为半回合制，玩家不操作时游戏状态不推进，**不设暂停概念**，本单元不得以暂停为由冻结数据或引入暂停语义（架构案 3.4 第 16 项、7.4、8.6 第 6 条；设计决策记录决策 87、88）。

### 10.3 其他实现约束

- 阶段切换是同步受理：一次切换的校验、写入与进入动作在一次受理内完成，不留下中间阶段。

- 本单元不得缓存被编排方的跨域查询结果作为自己的数据来源（架构案 8.2 第 3 条）。
- 结算组件的执行顺序以 M06 的组件清单为准；本单元只按序调度，不解释写入项内容。
