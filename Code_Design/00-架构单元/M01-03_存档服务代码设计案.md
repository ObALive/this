## 1. 系统定义

### 1.1 系统目的

在 M01 侧提供存档的驱动面：在两类自动保存节点判定并发起单局存档提交、在读档路径驱动恢复顺序、受理局末结算的跨局提交并上报结果（架构案 7.1、5.3、9.3、9.5.6）。存档结构、切面模型、提交点管理与校验规则由成员系统 01-50 定义，本对象是这些能力的使用方与触发方。

### 1.2 系统职责

- 受理时间刻度与战斗轮次的推进结果，判定自动保存节点并调用 01-50 的提交能力发起单局存档提交（架构案 5.3、7.1）。
- 驱动读档恢复顺序：按世界状态域 → 单局状态域 → 玩家状态域的次序驱动装载与恢复（架构案 9.3）。
- 受理 M10 结算执行入口的跨局提交请求，并上报提交结果；写入内容归 M06、触发归 M10（架构案 5.3、9.5.6）。
- 登记并采集 `CLS-M01-004` 配置版本标识与 `CLS-M01-005` 随机序列位置（生成类）的入档与恢复关系；两个对象的所有权分别归 `M01-04_配置服务代码设计案.md` 与 `M01-05_随机服务代码设计案.md`。
- 发布「自动保存完成」「存档提交完成」「存档恢复完成」三个事件，发送方为存档侧（架构案 3.1 ARC-M01-001 事件栏、7.1）。
- 拒绝一切以退出为由的提交请求：退出即进程终止，不构成提交点、不依赖退出回调（架构案 6.4、9.4、设计决策记录决策 89）。
- **对象承载位置**：本对象是常驻对象，由常驻场景承载，由启动物体按装配声明顺序显式初始化、按逆序销毁（架构案 2.4.1、2.4.2、8.3 第 1、6 条）。

### 1.3 系统边界

本对象不负责：

- 存档结构、三个切面的划分与切面粒度、提交点管理、引用完整性校验与序列化机制（归成员系统 01-50）。
- 数据域内容的业务含义与变更判定（归 `M01-02_数据域持有代码设计案.md` 与各变更入口模块）。
- 跨局存档的写入内容与结算组件清单（写入内容归 M06，结算流程编排归 M10）。
- 设置项清单与设置数据的持久化提交（归成员系统 01-60，其提交经 `API-SAVE-006`）。
- 版本迁移规则本身；不一致时按 01-50 的迁移规则处理（架构案 7.1）。
- 读档完成后的派生项重建与界面位置恢复（归各来源方与 M08）。
- 自行序列化任何状态、自行读写存档文件（架构案 7.1「不允许绕过」）。

功能要求（编号前缀 `F-`，来源为上游设计）：

- F-SAV-01 游戏只提供自动保存，提交点为时间段推进与战斗轮次推进两类节点，不提供手动保存与多个存档位（01-50 第 6 节、主案 F-M01-02）。
- F-SAV-02 退出即进程终止：退出时不提交存档、不依赖任何退出回调完成存档或收尾；单局存档的唯一可靠写路径是两类自动保存节点（架构案 9.4、设计决策记录决策 89、主案 F-M01-09）。
- F-SAV-03 读档执行全量恢复，恢复后的状态与提交完成时一致；自上一个自动保存节点以来的进度不恢复，未确认的操作不恢复（架构案 5.3 第 5 条、01-50 第 6 节）。
- F-SAV-04 跨局提交与单局提交不做同一次提交，各自失败语义独立（架构案 5.3 边界规则第 2 条）。
- F-SAV-05 恢复过程不重新抽取任何随机结果（架构案 9.3）。

### 2.3 外部数据引用

以下内容由其他单元定义，本对象只登记引用关系，不重定义其结构、职责与规则：

- 存档的对外能力：`API-SAVE-001`（切面登记）、`API-SAVE-002`（存档提交）、`API-SAVE-003`（存档装载）、`API-SAVE-004`（恢复驱动）、`API-SAVE-005`（版本校验）、`API-SAVE-006`（设置数据提交）、`API-SAVE-007`（跨局存档提交）。
- 三个数据域持有者：`CLS-M01-016` 至 `CLS-M01-018`，对象定义归 `M01-02_数据域持有代码设计案.md`；域内读写经 `API-SAVE-008`、`API-SAVE-009`。
- 配置内存形态与配置版本标识：`CLS-M01-003`、`CLS-M01-004`，对象定义归 `M01-04_配置服务代码设计案.md`。

- 跨局写入内容与结算组件清单：归 M06（07-40）；结算流程编排与提交发起归 M10。

### 2.4 数据关系

- 引用：本对象引用三个数据域持有者、配置版本标识与随机序列位置；存档结构与切面按 01-50 的定义引用各域声明的切面。
- 派生：存档索引由提交结果派生、恢复顺序单由切面声明与固定恢复顺序派生（归 01-50）；本对象不保存派生结果。
- 并列：单局存档、跨局存档与设置数据三份结构各自独立提交，单次提交只作用于一个目标结构，失败语义互不牵连（架构案 5.3 第 2 条）。
- 采集与恢复关系：`CLS-M01-004` 与 `CLS-M01-005`（生成类）随单局存档入档与恢复，本对象负责这两个时点的驱动，不拥有其内容。

### 2.5 数据生命周期

- 常驻对象：本对象随常驻场景存活，由启动物体按装配声明顺序显式初始化、按逆序销毁（架构案 2.4.1、8.3 第 1、6 条）。
- 存档对象：三个切面与三份持久化结构只在采集与恢复期间存在，采集完成后即释放（架构案 6.5）；其形态与释放由 01-50 承担。
- 临时运行对象：提交点记录、恢复顺序单、引用完整性校验结果在单次操作内有效，不跨帧保留、不入档（架构案 6.5、8.3 第 4 条）。
- 单局数据的存续：三个域内容随单局创建、结算提交完成时释放；本对象不持有域内容的副本。
- 设置数据：独立于游戏进度，本对象只按其提交入口受理，不因退出或局切换追加提交。

### 2.6 持久化要求

| 需入档的数据 | 切面归属 | 本对象的职责 |
| --- | --- | --- |
| CLS-M01-004 配置版本标识 | 单局存档的配置版本字段 | 驱动采集入档；读档时取该值参与一致性判定，不一致按 01-50 的迁移规则处理 |
| CLS-M01-005 随机序列位置（生成类） | 单局存档的随机状态切面 | 驱动保存与恢复时点；恢复时按存档位置恢复序列，不重新抽取任何随机结果 |
| CLS-M01-016 至 CLS-M01-018 三个域内容 | 单局存档的三个域切面 | 在两类自动保存节点发起提交、在读档路径驱动按域顺序恢复 |

## 3. 状态定义

### 3.1 状态

本对象不新设状态集。运行状态取成员系统 01-50 的口径，本对象是其驱动方与受理方：

| 状态集 | 取值 | 归属 |
| --- | --- | --- |
| 存档服务运行状态 | 空闲／装载中／恢复中／采集中／提交中／失败回退 | 定义归 01-50 的 `CLS-SAVE-001`；本对象是该服务的调用方与事件发布方 |
| 提交点状态 | 待提交／已提交／已作废 | 定义归 01-50 的 `CLS-SAVE-007`；本对象在两类节点取得提交点 |
| 单局存档有效性状态 | 无有效存档／有效／待迁移／不可读 | 定义归 01-50 的 `CLS-SAVE-004` 与 `CLS-SAVE-008`；本对象驱动其判定与比对输入 |
| 常驻对象装配状态（本对象自身） | 未初始化 → 初始化中 → 已初始化 → 已销毁 | 本对象；由启动物体按装配声明驱动（架构案 6.1、6.4） |

### 3.2 状态转换

```
本对象自身：未初始化 → 初始化中 → 已初始化 → 已销毁
提交点：待提交 → 已提交 ／ 待提交 → 已作废
单局存档有效性：无有效存档 → 有效 ／ 有效 → 待迁移 → 有效 ／ 待迁移 → 不可读
```

### 3.3 状态转换触发条件

转换条件与第 4 节接口表的状态变化列一致；运行状态的转换条件以 01-50 的第 3.3 节为准。

| 转换 | 触发行为或事件 | 对应入口 |
| --- | --- | --- |
| 未初始化 → 初始化中 → 已初始化 | 启动物体按装配声明顺序显式初始化；本对象在初始化时完成切面登记受理与版本绑定的取数准备 | 初始化序列（不经对外接口；架构案 6.1 阶段 3） |
| 已初始化 → 已销毁 | 程序结束时的逆序销毁；进程终止不执行销毁序列 | 逆序销毁（架构案 6.4、9.4） |
| 待提交 → 已提交 | 单局存档或跨局存档落库成功并返回提交结果 | `API-SAVE-002`、`API-SAVE-007` |
| 待提交 → 已作废 | 引用完整性校验不通过、落库失败或被并发拒绝 | `API-SAVE-002`、`API-SAVE-007` |
| 无有效存档 → 有效 | 单局存档首次提交成功或首次装载通过校验 | `API-SAVE-002`、`API-SAVE-003` |
| 有效 → 待迁移 → 有效 | 配置版本或结构版本不一致且迁移成功 | `API-SAVE-005` 版本校验 |

### 4.2 接口详细定义

本节记录本对象调用与受理下列三项接口的调用口径，八项字段不省略；职责、输入输出分类与失败语义的权威定义见 01-50 的 `50_存档与持久化代码设计案.md` 第 4.2 节，本文档不重定义。

### API-SAVE-002 存档提交（本对象的发起口径）

职责：在两类自动保存节点受理一次单局存档提交，把三个域切面、配置版本标识与生成类随机序列位置采集入档。

输入：
- 参数输入：提交点类别（时间段推进／战斗轮次推进）、目标结构标识（单局存档）。
- 状态输入：存档服务运行状态、三个数据域持有者状态（就绪）。
- 数据输入：切面声明（`CLS-SAVE-002`）、配置版本标识（`CLS-M01-004`）、随机序列位置（`CLS-M01-005`，生成类）。
- 外部事件输入：「时间刻度变化」（时间服务发布）、「轮次推进」（M05 发布）。

读取：切面声明、三个域内容（经切面采集）、配置版本标识、生成类随机序列位置。

输出：
- 返回值：提交结果。
- 状态输出：提交点由待提交转为已提交或已作废；单局存档与存档索引更新。
- 事件输出：自动保存完成、存档提交完成（发送方为存档侧）。
- 外部系统调用：`API-SAVE-002` 的提交链路（切面采集、装配与校验、落库与索引维护）。

产生的状态变化：单局存档内容与索引更新；上一份有效存档在失败时保持可读。

前置条件：阶段取值允许提交；三个域处于就绪；本对象已完成初始化；节点来自两类自动保存节点之一（退出不构成提交点）。

后置条件：单局存档落库完成或整次作废；提交结果经事件告知订阅方。

副作用：采集期间生成切面快照，采集完成后释放；提交失败经日志服务记录。

异常情况：并发提交（后到请求被拒绝，不排队、不合并）；引用完整性校验不通过（整次作废）；落库失败（保留上一份有效存档）；域未处于就绪；结算阶段收到改变局内状态的提交（拒绝）。

### API-SAVE-004 恢复驱动（本对象的驱动口径）

职责：在读档路径驱动一次全量恢复，按世界状态域 → 单局状态域 → 玩家状态域的次序装载三个域并触发派生项重建时点。

输入：
- 参数输入：装载结果、恢复范围。
- 状态输入：存档服务运行状态、版本校验结论。
- 数据输入：单局存档结构与版本绑定（`CLS-SAVE-004`、`CLS-SAVE-009`）、恢复顺序单（`CLS-SAVE-010`）。
- 外部事件输入：无。

读取：单局存档结构、版本绑定、恢复顺序单、配置版本标识（`CLS-M01-004`）。

输出：
- 返回值：恢复结果。
- 状态输出：三个数据域持有者由空结构转为就绪；运行时状态由恢复中回到空闲或失败回退。
- 事件输出：存档恢复完成（发送方为存档侧）。
- 外部系统调用：数据域入口（装载经 01-50 的切面能力）；随机序列位置由其所有权方按存档位置恢复。

产生的状态变化：三个域内容按存档写入；派生缓存与事件池由来源方重建。

前置条件：装载已完成且版本校验结论为一致或迁移成功；三个域处于空结构。

后置条件：阶段状态机进入地图阶段或战斗阶段、界面可交互；恢复过程不重新抽取任何随机结果，未确认的操作不恢复。

副作用：不可读的旧存档在存档索引中标记；恢复失败经日志服务记录。

异常情况：版本不可迁移（提示存档不兼容并停在主界面）；结构缺失或不可读（保留上一份有效存档）；恢复期收到提交或装载请求（后到请求被拒绝）；恢复中途失败（三个域保持空结构，不进入就绪）。

### API-SAVE-007 跨局存档提交（本对象的受理口径）

职责：受理 M10 结算执行入口的跨局写入提交，落库跨局存档并上报提交结果。

输入：
- 参数输入：跨局写入内容、整局存档快照标识。
- 状态输入：存档服务运行状态、提交点状态、阶段取值。
- 数据输入：跨局存档结构（`CLS-SAVE-005`）、写入内容（由 M06 定义、随提交传入）。
- 外部事件输入：无。

读取：跨局存档结构、版本绑定、整局存档快照标识。

输出：
- 返回值：提交结果。
- 状态输出：跨局存档内容按写入项更新；提交点由待提交转为已提交或已作废。
- 事件输出：存档提交完成（结构类别＝跨局存档；发送方为存档侧）。
- 外部系统调用：`API-SAVE-007` 的落库与索引维护链路。

产生的状态变化：跨局存档落库；失败时整笔回滚并保持提交前内容。

前置条件：结局成立并经玩家在结算窗口确认；阶段处于结算阶段；本局尚无成功的跨局提交记录。

后置条件：跨局存档落库完成或整笔回滚；本局保持未结算并保留重试能力（失败时）。

副作用：提交结果经事件告知订阅方；失败经日志服务记录。

异常情况：同一局重复提交（拒绝，不产生重复写入）；提交期并发（后到请求被拒绝）；写入内容与快照引用完整性问题（整次作废）；提交期间进程终止（整次作废，重新启动后可正常启动与继续游玩）。

## 5. 内部功能

### 5.1 功能列表

| 功能 | 对外暴露 | 说明 |
| --- | --- | --- |
| 自动保存节点判定与提交发起 | 否（节点经事件间接获得，提交经 `API-SAVE-002`） | 受理「时间刻度变化」与「轮次推进」，判定两类节点并发起单局存档提交（架构案 5.3、7.1） |
| 读档恢复顺序驱动 | 否（经 `API-SAVE-004` 的调用口径体现） | 按世界状态域 → 单局状态域 → 玩家状态域的次序驱动装载与恢复（架构案 9.3） |
| 跨局提交的受理与结果上报 | 否（受理经 `API-SAVE-007`，上报经事件） | 受理 M10 的一次提交并上报结果，解耦 M06 的写入内容与 M10 的编排（架构案 9.5.6） |

### 5.2 功能之间的关系

- 时间序：自动保存节点判定与提交发起由「时间刻度变化」「轮次推进」触发；读档恢复顺序驱动由本局装配的读档路径触发；跨局提交受理由 M10 的结算执行入口触发。
- 节点分工：两类自动保存节点是单局存档的唯一调用来源；跨局提交不占用也不依赖单局自动保存节点（架构案 5.3 第 2 条）。
- 提交与恢复互斥：任一时刻只允许一个在途操作；恢复或装载期间收到的提交请求被拒绝（01-50 第 9 节）。
- 结果告知：三项内部功能的结果统一经三个存档事件与日志记录告知外部，订阅方处理失败不回滚本对象已完成的提交或恢复。
- 退出路径的关系：退出路径不触发上述任何功能，也不产生事件（架构案 9.4）。

### 6.4 使用方式

- 节点获得方式：以事件间接获得——订阅「时间刻度变化」与「轮次推进」，不解析其业务含义；「配置加载完成」由版本校验环节受理，不作为提交节点触发（01-50 第 6.4 节）。
- 提交与恢复：两类自动保存节点直接调用 01-50 的提交能力；读档由启动路径调用其装载与恢复能力；跨局提交由 M10 的结算执行入口直接调用。
- 版本一致性：配置版本标识经 `API-M01-003` 只读取得，其权威载体是引擎编辑器内的配置资产；本对象不读取设计库的配置表（架构案 5.1、7.9）。
- 结果告知：每次提交与恢复经事件分发器发布事件，失败与拒绝经日志服务记录。
- 退出路径：不调用任何提交能力，不取得提交点，不注册依赖退出回调的流程（架构案 9.4）。

### 6.5 依赖方向限制

- 被依赖方向：启动物体在初始化序列第 5 步调用装载、恢复与版本校验；M10 的结算执行入口调用跨局提交；01-60 调用设置数据提交。
- 依赖方向：本对象与玩法模块只有两种接触——初始化序列内接收切面声明、提交与恢复完成时发布事件由其订阅；不调用玩法模块的业务入口（架构案 3.4 第 11 项）。
- 硬规则：
  1. 存档是本模块的统一入口，任何模块不得自行读写存档文件或自行序列化状态（架构案 3.4 第 6 项、7.1）。
  2. 不写入他方数据、不持有对方的可变引用；域内容只经数据域入口读写（架构案 8.2）。
  3. 不得把退出当作提交点，不得依赖引擎的退出回调完成存档或收尾（架构案 3.4 第 17 项、8.3 第 8 条）。
  4. 与 M10 之间不构成循环依赖：M10 调用本对象的提交入口，本对象只发布事件、只对阶段做只读查询（架构案 3.4 第 12 项、8.4 第 1 条）。
  5. 不重复实现引擎已提供的能力：使用引擎的持久化数据目录与序列化原语，不另建持久化机制（架构案 7.12、8.6 第 1 条）。

### 7.3 数据流

```
两类自动保存节点（时间刻度变化／轮次推进）
        │ 判定节点
        ▼
存档侧发起提交 ──▶ 切面采集（三个域 + 配置版本标识 + 生成类随机序列位置）──▶ 单局存档 ──▶ 原子写入
        │ 成功
        ▼
自动保存完成、存档提交完成 ──▶ 订阅方（M08、M05）
读档路径 ──▶ 装载与版本比对 ──▶ 世界状态域 → 单局状态域 → 玩家状态域 ──▶ 存档恢复完成
局末结算：M10 结算执行入口 ──▶ 跨局提交 ──▶ 跨局存档 ──▶ 存档提交完成
退出路径：不产生写入、不产生事件、不取得提交点
```

## 8. 核心流程

### 8.1 时间推进受理与自动保存提交

| 项 | 内容 |
| --- | --- |
| 触发 | 事件达成结束条件并退出（架构案 9.5.3 第 3、4 步） |
| 参与者 | M10 事件执行器、时间服务（M01-06）、本对象（存档侧）、M02、M08 |
| 调用顺序 | M10 取出本事件记账上的累计值 → 经 `API-M01-005` 受理推进 → 时间服务发布「时间刻度变化」→ 本对象判定为时间段推进节点 → 经 `API-SAVE-002` 发起单局存档提交（切面采集与装配校验、落库与索引维护）→ 提交成功后发布「自动保存完成」与「存档提交完成」 |
| 状态变化 | 提交点由待提交转为已提交；单局存档与存档索引更新 |
| 产生的事件 | 自动保存完成、存档提交完成 |
| 结束条件 | 提交结果确定；提交失败时整次提交作废并保留上一份有效存档 |

### 8.2 战斗轮次推进的自动保存提交

| 项 | 内容 |
| --- | --- |
| 触发 | 某单位获得行动机会（架构案 5.3、战斗轮次推进节点） |
| 参与者 | M05、本对象（存档侧）、数据域持有侧、日志服务 |
| 调用顺序 | M05 发布「轮次推进」→ 本对象判定为战斗轮次推进节点 → 经 `API-SAVE-002` 发起单局存档提交 → 提交成功后发布「自动保存完成」（提交节点类别＝战斗轮次推进）与「存档提交完成」 |
| 状态变化 | 提交点由待提交转为已提交；战斗未结状态与段内累计时长随单局状态域切面入档 |
| 产生的事件 | 自动保存完成、存档提交完成 |
| 结束条件 | 提交结果确定；读档后由 M05 按记录重建战场与时间轴，恢复到最近一次行动机会开始的时刻 |

### 8.3 读档恢复驱动

| 项 | 内容 |
| --- | --- |
| 触发 | 启动阶段的读档路径，或玩家在局外选择已有存档（架构案 9.3） |
| 参与者 | 启动物体（本局装配）、本对象、三个数据域持有者、M02、M05、M08、M10 |
| 调用顺序 | 经 `API-SAVE-003` 读取单局存档结构与存档索引 → 经 `API-SAVE-005` 比对配置版本标识与结构版本，不一致按 01-50 的迁移规则处理 → 经 `API-SAVE-004` 建立三个域空结构并按世界状态域 → 单局状态域 → 玩家状态域的次序驱动装载 → 恢复生成类序列位置 → 由来源方重建派生缓存与事件池、恢复战斗未结状态 → 发布「存档恢复完成」 |
| 状态变化 | 三个域由空结构转为就绪；本项目运行状态由装载中、恢复中回到空闲 |
| 产生的事件 | 存档恢复完成 |
| 结束条件 | 阶段状态机进入地图阶段或战斗阶段、界面可交互；恢复过程不重新抽取任何随机结果、未确认的操作不恢复 |

### 8.4 跨局提交的受理与结果上报

| 项 | 内容 |
| --- | --- |
| 触发 | 结局成立并经玩家在结算窗口确认，由 M10 的结算执行入口发起（架构案 9.5.6） |
| 参与者 | M10、M06、本对象、三个数据域持有者 |
| 调用顺序 | M10 读取整局存档快照并按组件清单取得写入内容（本对象不读取组件清单）→ 经 `API-SAVE-007` 受理提交 → 引用完整性校验 → 落库并维护存档索引 → 发布「存档提交完成」（结构类别＝跨局存档）→ 跨局提交完成后由 `M01-02_数据域持有代码设计案.md` 驱动三个域释放 |
| 状态变化 | 跨局存档内容按写入项更新；提交点由待提交转为已提交或已作废 |
| 产生的事件 | 存档提交完成 |
| 结束条件 | 跨局存档落库完成；失败时整笔回滚、本局保持未结算并保留重试能力，重试不产生重复写入 |

### 8.5 退出路径（不构成提交点）

| 项 | 内容 |
| --- | --- |
| 触发 | 进程终止：玩家主动退出、强制关闭、平台关闭、异常终止按同一口径处理（架构案 6.4、9.4） |
| 参与者 | 无（退出不做任何收尾承诺） |
| 调用顺序 | 不执行销毁序列、不取得提交点、不调用任何提交能力、不触发任何退出回调驱动的流程 |
| 状态变化 | 无；单局存档保持最近一次自动保存节点的提交结果 |
| 产生的事件 | 无 |
| 结束条件 | 进程结束；任意时刻终止进程后重新启动必须能正常启动并继续游玩 |

## 9. 异常与边界情况

| # | 判定条件 | 期望结果 |
| --- | --- | --- |
| 1 | 提交过程中采集、校验或落库任一环节失败 | 本批内容作废，保留上一份有效存档，提交点记已作废，失败项经日志服务记录 |
| 2 | 引用完整性校验不通过 | 整次提交作废，不落库部分内容 |
| 3 | 采集中或提交中收到新的提交请求 | 后到请求被拒绝，不排队、不合并 |
| 4 | 装载中或恢复中收到提交请求 | 后到请求被拒绝，恢复继续 |
| 5 | 读档时配置版本不一致 | 判定为版本不匹配，交 01-50 的迁移规则处理；无法迁移时提示不兼容并停在主界面 |
| 6 | 读档时结构缺失、不可读或索引与结构不一致 | 保留上一份有效存档，向表现通道给出提示并停在主界面 |
| 7 | 同一局已有成功的跨局提交记录 | 拒绝重复提交，不产生重复写入 |
| 8 | 提交未返回结果时进程被终止 | 整次提交作废，以最近一次自动保存节点为准；重新启动后能正常启动并继续游玩 |
| 9 | 某域未登记切面或声明的入口不可用 | 该域不进入本批次采集与恢复顺序，提交照常完成并记日志 |
| 10 | 恢复过程中发现派生项未重建或与来源状态不符 | 由来源方按来源状态重建，不按派生结果反推来源状态 |
| 11 | 结算阶段收到改变局内状态的提交 | 拒绝（架构案 6.6、8.3 第 5 条） |
| 12 | 存档索引损坏 | 判定为无有效存档，只提供开新局 |
| 13 | 收到以退出为由的提交请求 | 拒绝；退出不构成提交点，也不受理任何退出回调驱动的提交 |
| 14 | 读档未完成时申请生成类随机结果 | 拒绝；序列未初始化，不隐式创建序列（`M01-05_随机服务代码设计案.md`） |
| 15 | 提交失败后再次到达同一类节点 | 正常受理新的提交点；失败不占用节点，重试不产生重复写入 |

## 10. 实现约束

### 10.1 实现约束条目

- 单局存档的写入必须原子：写临时文件后原子替换；提交过程中断时整次作废并保留上一份有效存档（架构案 5.3 第 4 条、7.1）。
- 存档序列化采用判别字段式多态序列化：序列化结果中只出现自定义的字符串判别值，不写入运行时类型名；多态类型按判别值映射，不接受任意类型名；不得使用已被运行时移除实现的二进制序列化机制（架构案 7.1、8.6 第 8 条）。
- 两类自动保存节点是单局存档的唯一调用来源；跨局提交不占用也不依赖单局自动保存节点（架构案 5.3）。
- 退出游戏即进程终止：不提交存档、不构成提交点、不执行销毁序列、不依赖任何退出回调（架构案 6.4、9.4、设计决策记录决策 89）。
- 存档对象与临时运行对象不得跨帧保留，采集完成后释放（架构案 6.5）。
- 本对象不得持有任何玩法模块的对象引用，跨模块接触只经切面声明、事件订阅与提交受理（架构案 3.4 第 11 项）。
- 未登记切面的数据不入档；数据所有者新增可持久化状态时先登记切面再纳入采集范围（架构案 8.5.2）。
- 恢复顺序固定为世界状态域、单局状态域、玩家状态域，派生项在三个域就绪后由来源方重建（架构案 7.1、9.3）。

### 10.2 实现要求

- I-M01-07（存档侧承接部分）数据域内容必须可序列化：域内条目按 01-50 声明的切面采集，存档对象只在采集与恢复期间存在；存档序列化采用**判别字段式多态序列化**，序列化结果中只出现自定义的字符串判别值、不写入运行时类型名；单局存档的写入必须原子（架构案 6.5、7.1、5.3 第 4 条、8.6 第 8 条）。本条在域内容侧的口径由 `M01-02_数据域持有代码设计案.md` 承接，编号不重复占用。

### 10.3 缺口条目

```

提出单元：M01 核心与基础设施（M01）
缺口内容：世界时间推进时点与事件内时间记账的口径在系统设计文档 02-30 与架构案 7.5 之间不一致（系统设计文档写「非战斗事件在进入时一次性推进世界时间」）。
```
