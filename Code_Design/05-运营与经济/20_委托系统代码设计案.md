## 1. 系统定义
### 1.1 系统目的
本系统的对象标识：`SYS-QUEST-001 委托系统`。委托系统把接取事件、跨事件目标、期限与返回结算组织成持续任务（术语表 T-095），使一条委托的要求可以在战斗、交易及其他事件（术语表 T-001）中推进，并在时限内回到接取点位交付结算。它是持续任务与委托结算规则的唯一拥有方；物品与钱的实际变化一律由物品系统经 M09 的写入入口完成。
### 1.2 系统职责
- 持续任务的创建、持有与销毁，以及委托要求的持有与进度推进：接取事件与点位、要求、当前进度、完成时限、押金、报酬与结算规则；接收过程事件（战斗、交易及其他事件）的结果并更新进度（`20_委托系统设计.md` 2.1、2.2、3 过程事件）
- 委托交付登记的维护：与委托交付事件以稳定标识关联，登记点位与签发的窗口期（2.1、3 交付事件、`50_存档与持久化设计.md` 7）
- 交付结算：核验时限与完成情况，接收目标物品，判定圆满完成或按完成率结算，返还押金并发放报酬（2.3）
- 逾期与放弃的同一处置：两条路径都以放弃结束该次委托，都不返还押金，都按完成情况结算报酬；同一委托只结算一次（2.3）
- 委托状态变化的登记与广播，以及单局状态域切面的声明与恢复后的重建（架构案 3.1 ARC-M04-001、01-50 §2、§7）
### 1.3 系统边界
本系统不负责：
- 押金与报酬数值、完成率公式与难度调制（属数值事项，见 2.3、5 与 `00-总览/03_设计决策记录.md` 决策 49）
- 物品与钱的实际扣除、获得与落库（归 05-05 与 M09 的物品与经济写入服务 `API-M09-005`）
- 自动装载顺序、背包空间与溢出落地的执行（归 05-30，经 `API-ITEM-006` 与 `API-M04-006`）
- 事件的生成、刷新、窗口期、过期剔除与事件池维护（归 M02；本系统只读取事件状态并请求创建交付事件）
- 世界时间的推进与自动保存节点（归 M01，时间口径归 02-10）；条件模块的求值与判定（归 M09 的条件求值服务 `API-M09-004`）；存档结构与恢复顺序（归 01-50）
- 委托界面与事件界面的绘制、编辑态与提示呈现（归 M08）；事件入口类奖励进入当前事件池的登记与入池执行（归 M02，入口为 `API-M02-002` 事件池刷新与 `API-M02-003` 事件实例创建；本系统只输出事件入口类奖励的结果标识）
- 局末结算与跨局写入（持续任务随本局废弃，不进入跨局数据）；来源检查（Demo 之后的扩展，见 4）

### 1.5 功能要求
- F-QUEST-01 玩家在委托事件中缴纳押金并接受委托后，系统创建一条持续任务，记录接取事件点位、要求、当前进度、完成时限、押金、报酬与结算规则（2.1）。
- F-QUEST-02 接取后在接取事件点位生成对应的委托交付事件，交付事件的窗口期与委托时限一致（2.1）。
- F-QUEST-03 所有能产出或改变目标状态的事件都通过任务进度接口更新持续任务；任务目标物品遵守物品系统的通用操作规则（2.2）。
- F-QUEST-04 满足任务要求的物品将离开角色时，系统在操作提交前提示玩家；玩家确认后若永久失去目标物品且本局无法重新取得，任务保持未完成，等待窗口期自然过期后按放弃处理（2.2、05-05 §5.3）。
- F-QUEST-05 玩家必须在时限内回到接取事件点位，通过委托交付事件回报；超过时限仍未回报时按放弃处理（2.3）。
- F-QUEST-06 逾期与主动放弃同义：都不返还押金，都按完成情况结算报酬；一次委托只结算一次，系统不处理重复交付（2.3）。
- F-QUEST-07 成果满足全部要求时圆满完成，返还押金并发放完整报酬；成果不完整时按完成率结算报酬（2.3）。
- F-QUEST-08 钱与物品奖励进入自动装载流程，空间不足时使用统一的溢出规则（2.3、05-30 §4）。
- F-QUEST-09 任务状态完整写入存档，并作为事件结果与触发条件的判断依据（3）。
- F-QUEST-10 结算后提供钱、物品或后续事件入口作为报酬；后续事件入口经事件系统进入当前事件池（1、3 后续事件）。本系统只把事件入口类奖励作为结果标识随结算结果输出，登记的发起方是 M02 的执行侧，入口为 `API-M02-002` 事件池刷新（必要时 `API-M02-003` 事件实例创建），本系统不写事件池。

### 2.4 数据关系
- 展开与包含：委托定义 → 持续任务（接取时展开）→ 要求进度项与交付登记；一条任务持有若干要求进度项，至多一条已登记的交付记录。
- 关联：持续任务与委托交付事件以可恢复的稳定标识关联（01-50 §7）；交付事件的窗口期按任务的完成时限签发，窗口期的权威归 M02。
- 引用：要求进度项的条件引用归条件机制（`CLS-CONDITION-001` 条件模块）；押金与报酬清单引用 `CLS-ITEM-001` 元物品定义与 `CLS-ITEM-004` 词条定义与物品池；交付登记引用 `CLS-EVENT-006` 事件实例。
- 判定与归属：结算判定结果由要求进度项、成果提交清单与委托定义的结算规则推出，属临时运行对象与派生判定，不入档、不作为数据来源；物品与钱的定义归 05-05 与 05-10，装载与溢出归 05-30，事件与窗口期归 M02，时间口径归 02-10，本系统只登记归属与访问级别，不重定义其结构。
### 2.5 数据生命周期
按架构案 6.5 分类：
- 常驻对象：本系统无自有常驻数据；能力与依赖声明经服务容器登记与解析（`API-M01-001`、`API-M01-002`）。
- 数据域对象：持续任务、要求进度项、委托交付登记，随单局创建，容器常驻、内容按局重置（架构案 8.3 第 3 条）。
- 场景对象：无。临时运行对象：交付与结算请求、结算判定结果，单次受理内有效，不跨帧保留、不入档（架构案 8.3 第 4 条）。
- 存档对象与静态配置对象：本系统的单局状态域切面只在采集与恢复期间存在，形态归 01-50；委托定义在启动阶段装载，运行期只读。
- 跨局边界：持续任务、进度、押金与尚未领取的报酬随本局废弃，不进入跨局数据；局末结算以整份存档快照为输入，本系统不上报运行时状态（架构案 5.3 第 1 条、01-50 §4）。
- 结算封闭：结算阶段开始后，本系统不得创建或销毁单局状态域内的对象（架构案 8.3 第 5 条）。

## 3. 状态定义
### 3.1 状态
| 状态主体 | 状态取值 | 定义方 |
| --- | --- | --- |
| 持续任务（CLS-QUEST-002） | 进行中、已完成·圆满完成、已完成·按完成率、已放弃 | 本系统（由 2.1 至 2.3 的三条结束路径转出） |
| 要求进度项（CLS-QUEST-003）、委托交付登记（CLS-QUEST-004） | 进度项：未满足、已满足；交付登记：待登记、已登记、已回报、已失效 | 本系统 |
| 交付与结算请求（CLS-QUEST-005）、结算判定结果（CLS-QUEST-006） | 请求：待校验、已校验待提交、已提交、已拒绝；判定结果：已完成情况判定、已交付、已拒绝 | 本系统 |

持续任务的取值清单是本系统对 M04 模块单元 REQ-M04-04 的落点，其上游确认见 REQ-QUEST-03。
### 3.2 状态转换
```
持续任务：进行中 → 已完成·圆满完成 ／ 进行中 → 已完成·按完成率 ／ 进行中 → 已放弃
        已完成·圆满完成、已完成·按完成率、已放弃：终态，不产生后续迁移
要求进度项：未满足 → 已满足
委托交付登记：待登记 → 已登记 →（回报）已回报 ／ 已登记 →（越过窗口期）已失效
请求：待校验 → 已校验待提交 → 已提交 ／ 待校验 → 已拒绝 ／ 判定结果：已完成情况判定 → 已交付 ／ 已拒绝
```
### 3.3 状态转换触发条件
| 转换 | 触发行为或事件 | 对应接口 |
| --- | --- | --- |
| 进行中 → 已完成·圆满完成 | 在交付事件内提交的成果满足全部要求 | `API-QUEST-004` |
| 进行中 → 已完成·按完成率 | 在交付事件内提交的成果不完整，按完成情况结算 | `API-QUEST-004` |
| 进行中 → 已放弃 | 超过完成时限仍未回报，或玩家主动放弃 | `API-QUEST-005`、`API-QUEST-104` |
| 未满足 → 已满足 | 过程事件结果命中该要求项并达到目标量 | `API-QUEST-002` |
| 待登记 → 已登记 | 交付事件创建成功并回填事件实例标识与签发的窗口期 | `API-QUEST-003` |
| 已登记 → 已回报 ／ 已失效 | 玩家在交付事件内提交成果并完成结算；或交付事件越过窗口期转已错过，或事件状态不可读且完成时限已越过 | `API-QUEST-004`、`API-QUEST-104` |
| 终态重复受理 | 已终结任务再次收到推进、交付或放弃请求 | `API-QUEST-002`、`API-QUEST-004`、`API-QUEST-005` 的统一幂等分支 |

### 4.2 接口详细定义
输入与输出按参数输入／状态输入／数据输入／外部事件输入与返回值／状态输出／事件输出／外部系统调用四类分别记录（NR-06 §七）。
#### API-QUEST-001 委托接取受理
职责：受理一次委托接取，完成押金交付与持续任务创建，并给出交付事件创建请求项。
输入：参数输入：委托定义标识或接取事件实例标识、接取事件点位、押金付款请求、接收角色、确认标记；状态输入：单局状态域当前内容、当前阶段取值、付款来源与可调取容器范围；数据输入：CLS-QUEST-001 委托定义、`CLS-ITEM-001` 元物品定义与 `CLS-ITEM-004` 词条定义与物品池、货币媒介口径（`API-TRADE-002` 货币媒介识别）；外部事件输入：无。
读取：CLS-QUEST-001、`CLS-ITEM-005` 物品实例与 `CLS-ITEM-008` 归属引用、局内阶段取值（经 `API-M10-001` 阶段查询）。
输出：返回值：接取结果（任务标识、押金扣除结果、交付事件创建请求项：模板与变体标识、点位、窗口期与完成时限）；状态输出：持续任务新增为进行中，要求进度项按定义展开，交付登记为待登记；事件输出：委托状态变化；外部系统调用：`API-ITEM-005` 物品扣除提交（押金）、`API-SAVE-009` 数据域变更提交、`API-M01-010` 日志服务.Write。
产生的状态变化：持续任务与要求进度项新增；押金对应的物品实例离开角色（归属或数量变化，归零时实例销毁）。
前置条件：委托定义已装载且要求项、完成时限、押金与报酬齐备；押金扣除请求可满足；接取事件实例处于进行中；当前阶段为事件执行阶段；同一接取事件实例尚未创建任务。
后置条件：任务记录与押金交付结果一致；交付事件的窗口期按本任务的完成时限签发，两者同值、不各自计算。一次接取含两次落库，提交顺序为「先经 `API-ITEM-005` 提交押金扣除，再经 `API-SAVE-009` 提交任务、要求进度项与交付登记」：押金扣除失败时拒绝接取、不创建任务、不产生任何状态变化；押金扣除成功后任务创建失败时按撤销押金的补偿提交处理（经 `API-ITEM-006` 把同一批物品返还）并记内容日志，不留下已扣押金而无任务的中间态。
副作用：押金交付经物品系统落库并发布其域级事件（M09 的 物品变更提交）；发布 委托状态变化；订阅方处理失败不回滚该次接取（架构案 8.4 第 4 条）。
异常情况：押金无法从付款来源扣除时拒绝接取且不创建任务；押金扣除成功后任务创建失败时按撤销押金的补偿提交处理并记内容日志；委托定义缺项或未登记时拒绝并记内容日志；结算阶段内受理时返回阶段封闭；同一接取事件重复受理时幂等拒绝并返回既有任务标识；交付事件创建请求项未被受理时任务保持进行中，按完成时限兜底判定（见第 9 节）。
#### API-QUEST-002 委托进度推进
职责：接收一次过程事件的结果，判定其命中的要求项并写入任务进度。
输入：参数输入：任务标识，或作用域（事件实例、点位、事件类别）、过程结果（结束类别、结果标识、达成目标清单、产出与代价）；状态输入：CLS-QUEST-002 至 CLS-QUEST-003、任务当前状态；数据输入：CLS-QUEST-001 的要求项与条件引用；外部事件输入：无（由事件执行方向本系统发起）。
读取：CLS-QUEST-001 至 CLS-QUEST-003、`CLS-CONDITION-001` 条件模块与求值结果。
输出：返回值：推进结果（命中要求项清单、进度增量、是否全部满足）；状态输出：要求进度项当前量与满足标记变化；事件输出：委托状态变化；外部系统调用：`API-M09-004` 条件判定、`API-SAVE-009`、`API-M01-010`。
产生的状态变化：命中项的当前量增长，达到目标量转已满足；未命中项不变。
前置条件：任务处于进行中；过程结果可解析；要求项已按委托定义展开；条件引用已在条件机制登记。
后置条件：同一过程结果重复提交不产生重复计数（幂等）；达到目标量即标记已满足，超出部分不改变满足标记；未命中时不产生任何状态变化。
副作用：发布 委托状态变化；进度写入经数据域变更提交落库；订阅方处理失败不回滚该次推进。
异常情况：任务不存在或已终结时拒绝并返回已结算；过程结果与任务作用域不匹配时不命中、只记分类日志；条件引用未登记或判定不可用时不写入进度并记内容日志；结算阶段内受理时返回阶段封闭。
#### API-QUEST-003 交付事件登记
职责：把交付事件的创建结果回填到委托交付登记，建立任务与交付事件的稳定标识关联。
输入：参数输入：任务标识、交付事件实例标识、签发的窗口期与完成时限；状态输入：任务状态与交付登记当前状态；数据输入：CLS-QUEST-001 的交付事件声明；外部事件输入：无。
读取：CLS-QUEST-002、CLS-QUEST-004、`CLS-EVENT-006` 事件实例与点位绑定。
输出：返回值：登记结果；状态输出：交付登记由待登记转已登记；事件输出：无；外部系统调用：`API-SAVE-009`、`API-M01-010`。
产生的状态变化：交付登记写入事件实例标识、点位与签发的窗口期。
前置条件：任务处于进行中；交付登记为待登记；交付事件实例存在且点位与任务登记的接取点位一致；签发的窗口期与完成时限同值。
后置条件：任务与交付事件以稳定标识关联；同一任务至多一条已登记记录。
副作用：登记不通过时经日志服务记录原因；登记本身不发布事件。
异常情况：任务不存在或已终结时拒绝并返回已结算；点位不一致、窗口期与完成时限不一致时拒绝并记内容日志；重复登记同一交付事件时幂等接受且不覆盖既有记录。
#### API-QUEST-004 委托交付结算
职责：在交付事件内受理成果提交，核验时限与完成情况，并一次性完成成果收取、押金返还与报酬发放的编排。
输入：参数输入：任务标识、成果提交清单（实例标识与数量）、溢出处置结论、确认标记；状态输入：CLS-QUEST-002 至 CLS-QUEST-005、当前世界时间段位置、接收角色、装载与溢出条件；数据输入：CLS-QUEST-001 的结算规则与报酬清单、`CLS-ITEM-001` 元物品定义与 `CLS-ITEM-004` 词条定义与物品池；外部事件输入：无（由交付事件的执行方发起）。
读取：CLS-QUEST-002 至 CLS-QUEST-006、`CLS-ITEM-005` 物品实例与 `CLS-ITEM-008` 归属引用、`CLS-M01-006` 世界时间段位置（M01 持有，口径归 02-10）。
输出：返回值：结算结果（完成情况、押金返还项、报酬清单与奖励交付受理结果：装入量、未装入量、待确认溢出项）；状态输出：持续任务转已完成·圆满完成或已完成·按完成率，交付登记转已回报；事件输出：委托状态变化；外部系统调用：`API-ITEM-005` 收取成果、`API-ITEM-006` 交付押金与报酬、`API-SAVE-009`、`API-M01-010`。
产生的状态变化：持续任务进入终态并记录完成情况；成果物品离开角色；圆满完成时押金返还；报酬清单进入自动装载流程，未装入部分按统一溢出规则落地。
前置条件：任务处于进行中且交付登记为已登记；当前世界时间段位置未越过完成时限（经 `API-TIME-008` 判定）；成果提交清单可解析；确认标记已给出。
后置条件：一次委托只结算一次，终结任务对重复交付返回已结算；成果不完整时按完成率结算；押金返还与报酬在同一笔获得受理内交付。一次交付结算含三次落库，提交顺序为「先经 `API-ITEM-005` 收取成果，再经 `API-ITEM-006` 交付押金返还与报酬，最后经 `API-SAVE-009` 提交任务终态与交付登记」：成果收取失败时拒绝结算、不产生任何状态变化；成果已收取后奖励交付失败时保留待重试标记、按已完成情况继续提交任务终态，任务终态不因奖励交付失败回退、不重复收取成果；任务终态提交失败时按已收取与已交付的实际结果重试终态提交，不重复收取成果、不重复发放奖励。
副作用：成果收取与奖励发放各自经物品系统落库并发布其域级事件；发布 委托状态变化；订阅方处理失败不回滚该次结算。
异常情况：已越过完成时限时拒绝交付结算并转由放弃路径处理；重复交付时拒绝并返回已结算；成果不命中任何要求项时按完成率结算并记录完成情况；溢出处置结论缺失时返回待确认、不提交奖励发放；奖励装载不可用时拒绝奖励发放并保留待重试标记；结算阶段内受理时返回阶段封闭。
#### API-QUEST-005 委托放弃受理
职责：按逾期或主动放弃结束该次委托，按完成情况结算报酬且不返还押金。
输入：参数输入：任务标识、放弃起因（逾期／主动放弃）、溢出处置结论；状态输入：CLS-QUEST-002 至 CLS-QUEST-004、完成时限与当前世界时间段位置；数据输入：CLS-QUEST-001 的报酬清单与结算规则；外部事件输入：无（逾期路径由订阅驱动）。
读取：CLS-QUEST-002 至 CLS-QUEST-006、`CLS-ITEM-005` 物品实例与 `CLS-ITEM-008` 归属引用。
输出：返回值：放弃结果（完成情况、报酬交付受理结果）；状态输出：持续任务转已放弃，交付登记转已失效，要求进度项保持既有进度；事件输出：委托状态变化；外部系统调用：`API-ITEM-006` 交付报酬、`API-SAVE-009`、`API-M01-010`。
产生的状态变化：持续任务进入终态；押金不返还；报酬按完成情况进入自动装载流程。
前置条件：任务处于进行中；放弃起因已给出；主动放弃路径已取得玩家确认（入口形态待上游补充，见 REQ-QUEST-02）；逾期路径由越限判定触发。
后置条件：逾期与主动放弃同义且只结算一次；押金记录随任务废弃，不产生返还项；重复受理幂等跳过。提交顺序为「先经 `API-ITEM-006` 交付报酬，再经 `API-SAVE-009` 提交任务终态与交付登记失效」：报酬交付失败时保留待重试标记并按终态继续结算，任务终态不因奖励交付失败回退（第 9 节）；任务终态提交失败时不重复发放报酬，按已交付结果重试终态提交。
副作用：报酬经物品系统落库并发布其域级事件；发布 委托状态变化；订阅方处理失败不回滚该次放弃结算。
异常情况：任务已终结时幂等跳过并返回已结算；放弃起因未给出时拒绝并记内容日志；报酬交付的溢出处置结论缺失时返回待确认（见 REQ-QUEST-05）；结算阶段内受理时返回阶段封闭。
#### API-QUEST-006 委托状态查询
职责：按任务标识或筛选条件返回持续任务与要求的只读快照，供事件结果、界面取数与关联任务提示使用。
输入：参数输入：任务标识，或按接取点位、状态取值构成的筛选条件；状态输入：CLS-QUEST-002 至 CLS-QUEST-004；数据输入：CLS-QUEST-001 的要求项与结算规则；外部事件输入：无。
读取：CLS-QUEST-001 至 CLS-QUEST-004、`CLS-ITEM-001` 元物品定义与 `CLS-ITEM-004` 词条定义与物品池。
输出：返回值：持续任务只读快照（要求与进度、完成时限、押金、报酬、结算状态）；状态输出：无；事件输出：无；外部系统调用：无。
产生的状态变化：无。
前置条件：本局单局状态域已建立。
后置条件：结果与已提交状态一致；快照不携带写入口，读取方不得缓存为自身数据（架构案 8.2 第 3 条）；条件判定不读取本接口，一律经 `API-M09-004` 读取已提交状态。
副作用：无。
异常情况：任务标识不存在时返回未找到；筛选条件为空时返回空集合；局外阶段返回空结果、不隐式创建域结构。

### 5.2 功能之间的关系
- 接取路径：`API-QUEST-001` → 要求进度项展开 → `API-QUEST-003` 登记交付事件。
- 推进路径：`API-QUEST-002` → `API-QUEST-101` → 进度写入（经 `API-SAVE-009`）。
- 交付路径：`API-QUEST-004` → `API-QUEST-102` → `API-QUEST-103` → `API-ITEM-005`、`API-ITEM-006`。
- 放弃路径：订阅 当前事件池刷新完成 或 时间刻度变化 → `API-QUEST-104` → `API-QUEST-102`、`API-QUEST-103`；玩家的主动放弃经 `API-QUEST-005` 进入同一路径。
- 查询与恢复路径：`API-QUEST-006` 只读，`API-QUEST-105` 只由 存档恢复完成 触发，两者都不产生事件。事件入口类奖励路径：结算时由 `API-QUEST-004`、`API-QUEST-005` 输出结果标识 → M02 的执行侧按标识经 `API-M02-002` 登记入池；本系统不发起登记、不持有事件池。
- 内部功能只在本系统内被调用；跨系统入口以 `API-QUEST-001` 至 `API-QUEST-006` 为准，`API-QUEST-101` 至 `API-QUEST-105` 不对外暴露。

### 6.4 使用方式
- 直接调用：押金扣除、成果收取、奖励获得、条件判定、数据域读取与提交、事件状态读取、阶段与时间读取，均为同步调用，调用点集中在 `API-QUEST-001` 至 `API-QUEST-006` 与内部功能。

### 6.5 依赖方向限制
- 允许的依赖：本系统归 M04（L3），向 L1 申请基础设施属架构案 3.3 第 9 项；调用 M09 的条件判定属第 8 项；对 M02 事件状态的读取属第 5 项的同层只读查询；对 M10 的阶段读取属第 12 项；对数据域与存档入口的使用属 5.4 与 8.2；对 05-05、05-10、05-30、02-10 的使用落在同模块协作与允许清单内。
- 被依赖方向：M02 在事件结果与条件取数时读取本系统的委托状态；M08 经意图与命令提交调用本系统（架构案 3.4 第 3 项）；M10 的事件执行器经本系统接口编排接取、推进、交付与放弃；05-05 经 `API-QUEST-006` 读取任务要求用于离开角色前的提示；M06 的局末结算以整份存档快照为输入，不读取本系统运行时对象。
- 禁止方向：不得创建、刷新或结束事件实例——交付事件的创建由调用方经 `API-M02-003` 受理（架构案 3.3 第 5 项只允许只读查询，创建经第 11 项由 M10 编排）；不得调用 M05 的战斗推进、M06 的跨局写入；不得自行推进世界时间（3.4 第 10 项）；不得自行实现效果叠加、条件判定与物品写入（3.4 第 7、8 项与 7.11）；不得持有 M01、M02、M05、M09 的可变对象。
- 交付结算提交方的一致性：委托交付事件内的成果提交与结算一律由本系统的 `API-QUEST-004` 受理，物品变化经 `API-ITEM-005`／`API-ITEM-006`（上游 `20_委托系统设计.md` 3 交付事件）；需要对方同步的点：M04 模块单元文档的 `API-M04-004` 调用者列含「M02（事件配置的交易动作与委托交付结算）」，与本口径不一致，收口时须同步为「交易动作经 `API-M04-004`、委托交付结算经 05-20 的 `API-QUEST-004`」；05-10 的 §4.1 调用者列与 §7.1 的委托交付行已按本口径改写（本轮已改）。
- 反向依赖标注：本系统与 05-05 之间存在相互只读（本系统经 `API-ITEM-001` 读取物品与词条定义，05-05 经 `API-QUEST-006` 读取任务要求），两者均为查询语义且不写入对方状态，按架构案 4.2 判定为同模块内允许的查询，不构成 3.4 第 12 项的循环依赖；本系统与 M02 之间是单向只读。无其他环。

### 7.3 数据流
委托定义（静态配置）→ 接取受理 → 持续任务与要求进度项（单局状态域）→ 过程事件结果推进进度 → 交付事件内提交成果 → 完成情况判定 → 押金返还项与报酬清单 → 物品获得受理与自动装载溢出 → 单局状态域（物品归属与落地物）→ 自动保存（单局存档·单局状态域切面）→ 读档按快照恢复并重建派生。任务状态同时作为事件结果与触发条件的判断依据，经已提交状态读取，本系统不另建副本。本系统不产生跨局数据：局内进行中的委托进度、押金与尚未领取的报酬随本局废弃（01-50 §4）。
## 8. 核心流程
### 8.1 委托接取（押金交付与交付事件创建）

| --- | --- |

| 参与者 | M10 事件执行器、M08（确认界面）、本系统、05-05（押金扣除）、M02（交付事件创建）、M01（配置、日志、事件分发） |

| 项 | 内容 |
| --- | --- |
| 触发 | 玩家在委托交付事件内提交已经取得的成果 |

| 项 | 内容 |
| --- | --- |

| 调用顺序 | 1 订阅 当前事件池刷新完成 或 时间刻度变化 后经 `API-QUEST-104` 复核时限与交付登记；2 越限时经 `API-M02-001` 读取交付事件状态确认失效；3 交付登记转已失效；4 经 `API-QUEST-102` 判定完成情况并按放弃路径组装报酬；5 经 `API-ITEM-006` 交付报酬；6 任务转已放弃并经 `API-SAVE-009` 提交 |

| --- | --- |
| 押金无法从付款来源扣除 | 拒绝接取且不创建任务，不产生任何状态变化（2.1） |
| 委托定义缺要求项、完成时限、押金或报酬 | 拒绝接取并记内容日志，由事件侧按接取失败处理 |
| 交付事件创建失败或长期未登记、状态不可读 | 任务保持进行中，按完成时限兜底判定逾期后按放弃结算；不得据不可读结果直接结算（见 REQ-QUEST-04） |
| 重复交付同一委托、或对终态任务再次推进 | 拒绝并返回已结算；一次委托只结算一次（2.3、第 10 节） |
| 超过完成时限后提交成果 | 拒绝交付结算并转入放弃路径，不返还押金（2.3） |
| 目标物品永久失去且本局无法重新取得 | 不新增失败判定，任务保持进行中，等待窗口期自然过期后按放弃处理（2.2） |
| 结算阶段内收到接取、推进、交付或放弃请求 | 拒绝并返回阶段封闭（架构案 6.6、8.3 第 5 条） |
| 过程结果与任务作用域不匹配、或进度超过目标量 | 不命中要求项、进度不变，只记分类日志；达到目标量即标记已满足，超出部分不改变满足标记 |
| 溢出处置结论缺失、或奖励装载能力不可用 | 返回待确认、不提交奖励发放；装载不可用时保留待重试标记，任务终态不因奖励交付失败回退 |
| 放弃路径下玩家不在交付事件内 | 报酬交付的确认方式与落点承接方待上游补充（见 REQ-QUEST-05） |
| 读档恢复 | 按快照恢复任务、进度与交付登记关联；不重新签发时限、不重新抽取、不重复结算 |
| 局外阶段查询委托状态 | 返回空结果或不可用，不隐式创建单局状态域结构 |
| 当前版本访问来源检查 | 判定为实现范围越界；来源检查不进入 Demo（4） |
## 10. 实现约束
实现约束条目：
- 持续任务、要求进度项与交付登记必须可序列化并随单局存档完整保存与恢复；本系统不得自行序列化状态或读写存档文件（架构案 7.1、3.4 第 6 项）。
- 任务、进度与交付登记的变更一律经 `API-SAVE-009` 提交；押金与报酬的物品变化一律经 05-05 与 M09 的写入入口完成，本系统不得直接改物品状态（架构案 3.4 第 7 项、9.5.7）。
- 条件判定一律经 `API-M09-004`；本系统不得自行实现要求项的求值（架构案 7.11）。
- 世界时间不由本系统推进；完成时限与越限判定经 `API-TIME-001`、`API-TIME-008` 现场判定，不在任务内各自计算（架构案 3.4 第 10 项、7.5）。
- 交付事件的创建、刷新与过期剔除归 M02；本系统只请求创建、登记标识并读取状态，不得自行改写事件状态（架构案 3.3 第 5、11 项）。
- 一次委托只结算一次：终结任务对推进、交付与放弃请求一律幂等拒绝；逾期与主动放弃走同一结算路径（2.3）。
- 交付事件的窗口期与任务完成时限以同一值签发，权威归 M02；本系统的时限登记只用于界面取数与交付事件缺失时的兜底判定。
- 随机一律经 `API-M01-004`；当前版本的委托不引入随机消费点，后续引入时不得自行创建随机源（架构案 3.4 第 9 项）。
- 跨模块状态广播一律经 `API-M01-011`，载荷只承载已发生的事实；订阅方处理失败不回滚发布方状态（架构案 8.4 第 1 至 4 条）。
- 界面不得直接修改任务状态：接取、交付与放弃一律经意图与命令提交（架构案 3.4 第 3 项、9.5.8）；派生项不得入档、不得作为数据来源，进度汇总、逾期判定与可用报酬清单按来源重建（架构案 8.2 第 3 条）。
- 结算阶段开始后不得创建或销毁单局状态域内的对象，不得受理改变局内状态的委托请求（架构案 8.3 第 5 条、6.6）。
- 本系统不重复定义 05-05、05-10、05-30 与模块单元已登记的对象与接口；能力与依赖声明在启动阶段经 `API-M01-001` 登记，成环即在启动时报错（架构案 6.1、8.5.1 第 4 步）。

实现要求（编号前缀 `I-`）：
- I-QUEST-01 持续任务必须能通过唯一任务标识定位，并与委托交付事件以稳定标识关联（01-50 §7）。
- I-QUEST-02 委托定义（静态）与持续任务（运行期）必须分离；运行期不得改写委托定义（架构案 5.1 第 1、2 条）。
- I-QUEST-03 其他系统不得直接修改持续任务与要求进度项，必须经本系统接口修改（架构案 8.2 第 1、2 条）。
- I-QUEST-04 要求进度项的进度只能经 `API-QUEST-002` 写入，且必须可重复提交而不产生重复计数。
- I-QUEST-05 逾期与主动放弃必须共用同一结算路径与同一判定入口，不得分成两套结算规则。
- I-QUEST-06 押金不返还的路径不得留下可返还记录；押金返还与报酬发放必须在同一笔获得受理内交付。
- I-QUEST-07 委托状态变化必须在每次状态迁移后发布一次，载荷中的变化前后状态必须与任务实际状态一致。
