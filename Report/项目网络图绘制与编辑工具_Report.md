## 1. 任务目标

构建「项目网络图（Project Network Diagram）绘制与编辑工具」，落在 `Tool/` 下新建的目录内，满足六条要求：

1. 以 `Task/CO系列任务/CO05.md` 为测试案例；
2. 同二级标题下的数字编号项依次向上依赖；
3. 正文是「实现目标概要 + 实现目标说明」，括号内是「其他开发路线中的依赖项」与「需要一并构建实现的对象」，对象的实现路径是可选项；
4. 支持插入，并处理插入后后续编号的顺位偏移与引用问题；
5. 成品图中每个节点只写实现目标概要与章节索引，点击节点打开详情编辑框，成品图实时渲染；
6. 工具在 `Tool/` 目录下新建文件目录构建，不阅读其他工具。

## 2. 任务书摘要

`CO05.md` 给出一份自制的增量功能清单：`## 瓦片地图` 5 条、`## 角色技能` 3 条（第 3 条仅「制作」两字）、`## 角色移动` 0～3 共 4 条、`# 时间轴` 4 条，共 16 条。每条括号内声明了依赖的前置内容与需要一并实现的对象，其中 `（依赖元效果）` 是任务书里唯一一条无法对应到本文件内任何路线的依赖。清单前有任务背景与任务执行要求的编号列表，不属于网络图条目。

## 5. 执行过程

1. **定形**：确认工具形态与既有工具一致——本机 Python 服务 + 静态页面，无外部库（服务侧 CSP 只允许 `'self'`，因此图渲染自行实现，不引第三方图库）。
2. **建模**：先把规则落成可测的纯 Python 模型（`model.py`）：标题切路线、编号切条目、正文/括号拆分、引用解析、依次向上依赖成链、插入重编号与引用改写、校验。
3. **校正解析**：首轮跑 `CO05.md` 出现三处偏差并逐一修正——任务书前置编号列表被误当成条目、`依赖…` 因括号剥除写法错误全部落入说明、`元对象-A、元对象-B` 的第二个对象被并进第一个对象的备注。
4. **对齐既有结论**：以 `Output/CO05/CO05_项目网络图依赖空缺核对_v1.md` 为对照，工具自动解出 16 个条目、12 条同路线链式边、6 条显式跨路线依赖，并把 `依赖元效果` 判为未解析——与那轮人工核对的结论一致。
5. **落服务与前端**：`store.py` 负责工作区定位、自动存档与备份；`server.py` 只监听回环地址，提供状态、操作、导入、导出接口；前端用原生 SVG 做增量渲染（按 id diff 而不是整图重建），节点只画章节索引与概要。
6. **验证**：三层测试——模型单测 27 项、布局纯函数测试 14 项、前端冒烟 26 项（用极简 DOM 垫片加载真实页面脚本，打真实接口，覆盖渲染、详情框增删行、保存、悬停高亮、校验联动）。
7. **收口**：写使用说明；生成初始数据（由 `CO05.md` 导入）；清理样例导出与缓存。

## 11. 后续建议

### 11.1 遗留问题

1. `依赖元效果` 在工具里显示为未解析依赖——这不是工具缺陷，而是任务书里确实不存在名为「元效果」的路线；需要一个人工裁定：要么新增一条名为「元效果」的路线，要么把该引用改指到实际承载对象所在的路线。
2. 导入会把每条路线的编号按出现顺序顺排；若原任务书编号本身不连续，导入会用提示条列出偏差，需要人工确认。
3. 导出 Markdown 会规范化括号写法（依赖合并为一个括号、多个对象用 `；` 分隔），语义等价但排版与原文不同；原任务书不被覆盖。

### 11.2 待人工确认项

1. 节点是否需要显示「待实现对象数量」之类的角标。当前为遵守「只写概要与章节索引」，只用描边与侧栏承担状态提示。
2. 是否需要把工具产出的网络图 JSON 纳入版本管理（当前 `数据/` 会随每次编辑变化，备份保留最近 30 份）。
3. 是否需要按 `Output/CO05/CO05_代码设计案遗漏对象与程序集清单_v1.md` 的 28 个对象预填「实现路径」——本轮遵守「不擅自设计」，未写入任何推测内容。

### 11.3 下一轮建议

1. 用本工具把 `CO05.md` 里人工补出的隐含依赖（例如瓦片 3 对「地格占用组件」的对象级前置）录成显式依赖，再对照 `CO05_缺口登记表_v1.md` 检查是否还有成环或孤立段。
2. 把裁定后的缺口结论回填进网络图，让图成为增量构建顺序的唯一事实来源；后续每批对象补齐后在图上看「下一步是否已解锁」。
3. 如果条目规模继续增长，可以考虑给节点加「按程序集/系统着色」的第二套配色，直接复用现有 `routeColor` 的分配机制。
