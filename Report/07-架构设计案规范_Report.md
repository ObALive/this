## 2. 任务书摘要

任务书是一份 841 行的规范设计稿，给出架构设计案的精确定义与章节模板。归纳为十七节：

| 节 | 内容 |
| --- | --- |
| 一 | 精确定义：依据整体游戏设计与技术约束，规定程序整体结构、模块划分、职责边界、依赖关系、通信机制、数据流、生命周期和基础设施约束 |
| 二 | 核心问题六问，判据是「是否整个项目都需要遵守」 |
| 三 | 与代码设计案的最本质区别：架构解决系统之间怎么组成一台机器，代码设计解决某个部件需要具备什么 |
| 四 | 应该规定什么，分为程序总体分层与模块及系统划分 |
| 五 | 依赖方向是架构文档最重要的职能之一 |
| 六 | 通信机制属于架构，「某系统提供某接口」属于代码设计 |
| 七 | 全局生命周期：初始化顺序、对象分类、常驻与多实例 |
| 八 | 数据的整体组织方式与代码设计案的分工 |
| 九 | 基础设施而非具体业务 |
| 十 | 不应该做的四件事 |
| 十一 | 为什么要单独编写：避免几十个系统各自正确但组合起来错误 |
| 十二 | 三个实际用途：上级约束、指导组合、控制长期复杂度 |
| 十三 | 六层文档的精确定义表 |
| 十四 | 信息流关系图，架构设计案与代码设计案是两个并列维度 |
| 十五 | 建议的十章章节结构与架构约束检查清单 |
| 十六 | 归属判断法五问 |
| 十七 | 上游依赖关系：架构决定代码设计案能够怎样设计 |

| 九 | 自检清单十二项 |

归纳时对任务书做了三处细化，理由是任务书只给了方向，落盘需要可核对的判据：

1. **接口在架构层的落点**（§三.8）。任务书第十节说架构不应定义单个系统的全部接口，但基础设施接口、跨模块服务接口与跨系统事件契约必须在架构层出现，否则代码设计案之间无法对齐。本条写明这三类各写到什么程度。
2. **依赖方向要逐条列出禁止项**（§三.3）。任务书给了禁止依赖的例子，本规范进一步要求逐条列出，理由是允许清单无法穷尽错误组合。
3. **模块划分与设计库域划分的关系**（§八.6）。任务书的模块划分示例与 `系统设计文档/` 的 7 域 32 系统不是同一套划分，两者是两个维度，必须写明对应关系，否则会出现同一个系统两套归属。

## 11. 后续建议

### 11.1 架构设计案应先于代码设计案的批量编制

NR-07 §六 已写明架构设计案是代码设计案的上级约束。当前 `架构设计文档/` 与 `Code_Design/` 均为空，两个库都尚未开始编制。建议的推进顺序是先完成架构设计案定稿，再批量编制代码设计案，理由是架构决定了代码设计案能够怎样设计；若先编制代码设计案，架构定稿后需要逐份核对返工，成本更高。

NR-06 §十二.5 保留了先行编制的合法路径：架构未定稿时可按系统设计稿编制，架构定稿后按 NR-07 §六.4 统一核对一次。

### 11.2 模块划分与设计库域划分的对应

NR-07 §八.6 要求写明架构的模块划分与 `系统设计文档/` 域划分的对应关系。这两套划分的维度不同：设计库的域按玩法主题归并，架构的模块按程序结构归并。编制架构设计案时需要逐系统建立这张对应表，建议作为第 2 章模块划分表的一列，避免同一系统两套归属造成引用混乱。

### 11.3 两个库的库说明有待补充实例

`架构设计文档/README.md` 与 `Code_Design/README.md` 的文档清单目前都为空。首个文档定稿后，两份 README 的清单表与当前状态节需要同步更新，此项按 NR-05 §七.3 与 §八.4 执行。

### 11.4 伪代码层尚未建立

NR-03 §七.0.1 的落点表把第 5 层伪代码标为「尚未建立」。按当前进度，架构设计案与代码设计案两份规范已齐备，伪代码层是该链条上的下一个空缺。建议在代码设计案开始批量编制后再确定伪代码的落点与规范。
