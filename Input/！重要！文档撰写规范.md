作为独立游戏制作人，有下面几个游戏策划阶段

1. 创意需求稿：一篇文档诠释游戏的设计理念，有哪些核心设计
2. 系统设计稿：对创意需求稿的内容进行详细释义，将游戏涉及到的不论是独特的还是通用的系统细节都详细描述。偏向于让人能够完备理解游戏全部内容
3. 架构设计稿：面向代码开发的系统设计稿，为代码设计提供上层指导。偏向于让代码工程师能理解代码设计的架构
4. 功能需求拆分&文案编写与数值设计：基本是伪代码的形态，是所有设计转化成代码前的最后一步

第一步属于聊天交流时能让人理解明白的概念文档，第四步几乎来到了伪代码的范畴
中间两步应该包含什么样内容，能充分完成承接上下两步的任务，文档应该有着什么样的编写规范

为了让智能体协助编排二三两步的文档，应该拆分哪些步骤，怎样构造提示词


你的四阶段可以形成一条非常清晰的“**理念 → 规则 → 软件结构 → 实现任务**”链条。

真正需要补强的是：**第二、第三阶段必须承担不同的抽象职责**。很多团队的问题恰恰是：

* 系统设计稿写成了“创意需求稿的扩写版”
* 架构设计稿写成了“程序员开始写代码后的类图”
* 最后第四阶段又重新解释一遍前面的东西

这样会导致文档越来越厚，但信息并没有真正完成传递。

我更建议把四个阶段明确成下面这样：

| 阶段                          | 核心问题                                                 | 主要读者                             | 抽象层级 |
| ----------------------------- | -------------------------------------------------------- | ------------------------------------ | -------- |
| 1. 创意需求稿                 | **为什么做、想让玩家体验什么、游戏由什么构成**           | 制作人、策划、美术、程序、外部合作者 | 概念     |
| 2. 系统设计稿                 | **这个游戏规则究竟是什么，玩家实际会遇到什么行为和结果** | 策划、主程、相关制作人员             | 规则     |
| 3. 架构设计稿                 | **这些规则在软件中应该由什么结构承载，各模块如何协作**   | 程序、技术策划                       | 软件结构 |
| 4. 功能需求拆分 / 文案 / 数值 | **具体要做哪些东西，每个东西具体怎么实现**               | 程序、美术、文案、数值、测试         | 实现     |

可以把中间两份文档直接理解成：

> **系统设计稿 = 游戏规则层**
> **架构设计稿 = 软件结构层**

这是最重要的一条边界。

---

# 一、创意需求稿 → 系统设计稿：完成“概念到规则”的转换

创意需求稿回答的是：

> “玩家应该经历一个什么样的游戏？”

系统设计稿应该回答：

> “那么这个游戏在任何情况下，具体应该如何运作？”

所以系统设计稿**不是代码文档**，也不应该过早讨论 `class`、`interface`、数据库表之类的问题。

它应该把游戏中的概念转换成：

* 对象
* 状态
* 规则
* 条件
* 输入
* 输出
* 资源
* 流程
* 边界情况

也就是说，它需要建立一套**完整且无歧义的游戏规则体系**。

---

# 二、系统设计稿应该包含什么

我建议你的系统设计稿采用下面的结构。

## 2.1 系统目的与范围

先定义：

**这个系统是什么。**

例如：

> 背包系统负责管理玩家持有的物品，并提供物品存储、移动、使用、整理和丢弃功能。

然后明确：

**这个系统不是什么。**

例如：

> 装备属性计算由角色系统负责，背包仅负责装备物品的存储与转移。

这个“范围边界”非常重要。

否则后面系统之间一定会互相吞功能。

---

# 2.2 核心概念

把创意阶段中的模糊概念定义成正式概念。

例如：

### 物品

物品是玩家可以持有、移动、使用、出售或丢弃的游戏对象。

### 物品实例

同一种物品的不同持有对象。

例如：

> “治疗药剂”是物品类型。
> 玩家背包中的第 17 个治疗药剂是一个物品实例。

然后继续定义：

* Item
* ItemInstance
* Inventory
* Slot
* Stack
* Equipment

这些词一旦定义，就应该成为整个项目的**术语标准**。

---

# 2.3 系统实体

列出这个系统中有哪些对象，以及它们拥有的属性。

例如：

| 实体         | 含义     | 核心属性             |
| ------------ | -------- | -------------------- |
| Inventory    | 玩家背包 | 容量、格子           |
| Slot         | 背包格   | 类型、位置           |
| Item         | 物品定义 | ID、名称、重量、标签 |
| ItemInstance | 物品实例 | ItemID、数量、耐久   |

这里依然**不讨论 C# 类怎么写**。

只讨论：

> 游戏世界中存在什么东西。

---

# 2.4 状态

这是系统设计稿最容易缺失、但实际上最重要的部分之一。

每一个重要实体都应该说明：

> 它有哪些状态？
> 状态如何变化？

例如物品：

```text
不存在
↓
生成
↓
被拾取
↓
进入背包
↓
被使用
↓
消耗
↓
销毁
```

例如角色：

```text
正常
→ 受伤
→ 濒死
→ 死亡
→ 复活
```

再复杂一点，可以明确状态转换条件：

| 当前状态 | 行为 | 条件           | 下一状态 |
| -------- | ---- | -------------- | -------- |
| 地面物品 | 拾取 | 背包有空间     | 背包内   |
| 地面物品 | 拾取 | 背包无空间     | 地面物品 |
| 背包内   | 使用 | 满足使用条件   | 背包内   |
| 背包内   | 使用 | 消耗品且数量=1 | 销毁     |

这样系统设计稿就开始具有“**规则可执行性**”。

---

# 2.5 行为规则

这是系统设计稿的核心。

每个系统都应该把主要行为写成：

> **输入 → 判断 → 结果**

例如：

### 拾取物品

1. 玩家发起拾取。
2. 系统检查物品是否仍存在。
3. 检查玩家是否有可用背包空间。
4. 若有空间，则转移物品。
5. 若无空间，则拾取失败。
6. 拾取成功后，地面物品被删除。
7. 背包容量更新。
8. UI刷新。

注意这里已经比创意稿具体很多，但仍然没有进入：

```csharp
InventoryManager.PickupItem(...)
```

这类实现。

这就是**策划规则**。

---

# 2.6 系统之间的关系

这是第二阶段非常重要的一块。

例如：

```text
玩家
 ↓
交互系统
 ↓
拾取系统
 ↓
背包系统
 ↓
物品系统
```

更重要的是写清：

> 谁负责什么。

例如：

> 交互系统负责判断玩家是否能够与目标进行交互。
> 拾取系统负责完成物品从世界对象向玩家持有物的转移。
> 背包系统负责确定物品应该进入何处。
> 物品系统负责提供物品的基础属性。

这样第三阶段才能知道应该怎么拆模块。

---

# 2.7 异常与边界情况

这是我尤其建议你在系统设计稿中强化的一部分。

每个系统至少应该有：

### 正常流程

### 失败流程

### 边界情况

### 非法状态

例如：

> 玩家拾取物品时背包突然满了怎么办？

> 两个系统同时修改物品数量怎么办？

> 玩家使用物品过程中角色死亡怎么办？

> 物品已经被另一个行为销毁，但 UI 仍然尝试使用怎么办？

这些东西如果系统设计稿不规定，最终都会变成程序员自己决定。

一旦程序员开始自行定义**游戏规则**，设计稿和代码就会逐渐分裂。

---

# 2.8 玩家可感知表现

系统设计稿还应该定义：

> 这个系统最终在游戏里表现为什么。

包括：

* UI
* 音效
* 特效
* 动画
* 反馈
* 提示
* 操作方式

例如：

> 物品拾取成功后，角色播放拾取动画；背包图标增加；播放拾取音效；若堆叠，则显示数量变化。

但这里主要描述：

> **应该发生什么**

而不是：

> Unity 中应该调用哪个 API。

---

# 2.9 系统数据

这里可以开始定义数据层面的概念，但不要进入具体数据库设计。

例如：

```text
物品：
- ID
- 名称
- 类型
- 最大堆叠数
- 重量
- 标签
```

这已经可以为第三阶段提供输入。

---

# 2.10 系统设计稿最终应该达到什么程度

一个很实用的判断方式：

> **如果一个经验丰富的游戏设计师拿到系统设计稿，他不写代码，也应该能够完全模拟这个系统。**

例如：

你拿着一份背包系统设计稿，可以直接问：

> “玩家拿着 3 个苹果，背包只剩 2 格，再拾取一个 5 个一组的矿石，会发生什么？”

如果文档无法明确回答：

> 那么系统设计稿还不完整。

---

# 三、系统设计稿最重要的写作规范

我建议你制定几条非常硬的规范。

## 3.1 禁止使用没有定义的术语

第一次出现：

> “背包容量不足时禁止拾取。”

应该已经有：

> 背包容量：背包可以容纳的最大物品数量。

否则术语会越来越模糊。

---

## 3.2 使用“必须 / 应该 / 可以”区分强制程度

例如：

> **必须**：物品无法放入背包时不得完成拾取。

> **应该**：拾取成功后播放反馈动画。

> **可以**：支持自动整理。

这样后面的程序才能区分：

> 什么是需求，什么是建议。

---

## 3.3 不写实现方案，只写行为约束

例如不推荐：

> 使用 Dictionary 保存物品。

这是架构层甚至实现层的内容。

而推荐：

> 通过唯一 ID 可以快速定位任意物品定义。

至于 Dictionary、数据库还是 Addressables，由第三阶段决定。

---

## 3.4 不允许“理所当然”

比如：

> 玩家死亡后掉落装备。

这其实不完整。

必须说明：

* 掉落哪些装备？
* 装备是否包括绑定物？
* 掉落概率？
* 掉落在哪里？
* 玩家死亡期间能否被其他玩家拾取？
* 重登之后是否保留？
* 同时掉落多少个？
* 装备损坏是否影响掉落？

系统设计稿的核心价值就在于**消灭这种隐含规则**。

---

# 四、系统设计稿 → 架构设计稿：完成“规则到软件结构”的转换

到了第三阶段，问题发生了变化。

系统设计稿说：

> 玩家可以拾取物品。

架构设计稿开始关心：

> 哪个模块负责处理“拾取”？

系统设计稿说：

> 物品可以堆叠。

架构设计稿关心：

> 堆叠规则由谁实现？
> 物品数据放哪里？
> Inventory 和 Item 怎么关联？
> UI 从哪里获得状态变化？

也就是说：

> **第二阶段描述“游戏是什么”。**
> **第三阶段描述“程序应该如何承载这个游戏”。**

---

# 五、架构设计稿应该包含什么

我建议第三阶段至少包含下面九类内容。

## 5.1 模块划分

先把整个系统拆成模块。

例如：

```text
Inventory
├── InventoryModel
├── InventoryService
├── InventoryPersistence
├── InventoryUI
└── InventoryEvents
```

但是这里的重点不是“类名”。

重点是：

> **为什么要拆成这些模块。**

例如：

### InventoryModel

负责保存背包当前状态。

### InventoryService

负责执行背包相关业务操作。

### InventoryPersistence

负责存档和读取。

### InventoryUI

负责将背包状态呈现给玩家。

---

# 5.2 模块职责

每个模块都必须回答：

> 负责什么？

以及更重要的：

> 不负责什么？

例如：

### InventoryService

负责：

* 添加物品
* 删除物品
* 移动物品
* 合并堆叠

不负责：

* UI显示
* 物品图标加载
* 存档文件格式

后面这个“反向边界”非常重要。

否则所有东西最后都会进入一个 God Class。

---

# 5.3 模块依赖关系

比如：

```text
InventoryUI
   ↓
InventoryService
   ↓
InventoryModel
   ↓
ItemRepository
```

并定义：

> 谁可以依赖谁。

例如：

```text
UI → Service
Service → Model
Model → Data

Data × UI
```

这实际上是在防止项目架构腐化。

---

# 5.4 数据结构

这里才可以正式开始讨论：

* class
* struct
* interface
* enum
* ScriptableObject
* JSON
* 数据库
* Addressables

例如：

```csharp
ItemDefinition
ItemInstance
InventorySlot
Inventory
```

但还是不要写具体函数逻辑。

---

# 5.5 生命周期

第三阶段必须明确：

> 对象什么时候创建？
> 什么时候销毁？
> 谁拥有它？

例如：

```text
ItemDefinition
游戏启动前加载
        ↓
ItemRepository
        ↓
Inventory
        ↓
ItemInstance
```

这种生命周期问题对 Unity 尤其重要。

例如：

> Inventory 是场景对象，还是 Persistent Manager？

> ItemDefinition 是运行时对象，还是静态资源？

这些应该在架构阶段决定。

---

# 5.6 接口和通信方式

这里开始定义：

> 模块之间怎么说话。

例如：

```text
InventoryService
        ↓
InventoryChanged Event
        ↓
InventoryUI
```

或者：

```text
InventoryService
        ↓
IItemRepository
```

这里可以出现：

```csharp
interface
event
delegate
command
service
repository
factory
```

因为这些属于软件结构，而不是游戏规则。

---

# 5.7 数据流

例如：

```text
玩家点击物品
 ↓
UI
 ↓
InventoryService.UseItem()
 ↓
ItemEffectService
 ↓
CharacterService
 ↓
CharacterStateChanged
 ↓
UI
```

这部分对后续程序开发非常有价值。

程序员看到这里，应该知道：

> 一个完整行为经过哪些模块。

---

# 5.8 错误处理与非法状态

架构层需要解决：

> 如果一个模块失败，怎么通知其他模块？

例如：

```text
UseItem
 ├── Success
 ├── ItemNotFound
 ├── InvalidTarget
 └── InsufficientQuantity
```

但这里依然不应该写：

```csharp
if (item == null)
```

这种具体代码。

---

# 5.9 扩展机制

这是架构稿与普通“程序实现说明”最大的区别之一。

需要考虑：

> 以后会不会增加东西？

例如：

当前有：

```text
HealingItem
ManaItem
BuffItem
```

以后可能出现：

```text
TeleportItem
QuestItem
RandomEffectItem
```

那么架构是应该：

```text
大量 if/else
```

还是：

```text
IItemEffect
```

这种决策就是架构设计。

---

# 六、架构设计稿不应该写什么

这是很关键的反向约束。

第三阶段不要变成第四阶段。

例如下面这种东西就已经越界：

```csharp
public bool AddItem(ItemInstance item)
{
    for (...)
    {
        if (...)
        {
            ...
        }
    }
}
```

这属于实现层。

架构层只应该写：

> `InventoryService` 提供物品添加能力。添加操作必须经过容量检查、堆叠检查和合法性验证；成功后产生 InventoryChanged 事件。

具体循环怎么写，由第四阶段决定。

---

# 七、第四阶段应该成为前三阶段的“编译结果”

这是我非常建议你建立的概念：

> **第四阶段不是新的设计阶段，而应该是前三阶段经过转换后的“执行规格”。**

因此理想的信息流应该是：

```text
创意需求
    ↓
系统规则
    ↓
软件架构
    ↓
实施规格
    ↓
代码
```

而不是：

```text
创意需求
 ↓
系统设计
 ↓
架构设计
 ↓
大家重新想一遍
 ↓
代码
```

---

# 八、因此第四阶段应该拥有“追溯关系”

这是独立开发项目尤其值得做的一件事。

给设计内容分配 ID。

例如：

```text
SYS-INV-001
```

表示：

> Inventory 系统 / Requirement 001

然后：

### 系统设计稿

> SYS-INV-001：玩家可以将获得的物品放入背包。

### 架构设计稿

> ARC-INV-003：InventoryService 负责执行物品添加。

并建立：

```text
SYS-INV-001
    ↓
ARC-INV-003
    ↓
TASK-INV-011
TASK-INV-012
TASK-INV-013
```

这样第四阶段就能追溯：

> 这个功能为什么存在？

程序员也能反向检查：

> “这个需求有没有漏实现？”

---

# 九、四阶段可以进一步明确成四种不同的问题

这是我认为你这套流程最适合固定下来的核心框架：

## 第一阶段：Why

> **为什么做？**

描述：

* 设计理念
* 玩家体验
* 核心循环
* 产品目标
* 特色
* 核心取舍

---

## 第二阶段：What

> **游戏究竟是什么规则？**

描述：

* 系统
* 实体
* 状态
* 流程
* 条件
* 规则
* 数学关系
* 边界情况
* 玩家可见行为
* 系统之间关系

---

## 第三阶段：How（Software）

> **程序应该怎样承载这些规则？**

描述：

* 模块
* 职责
* 数据结构
* 生命周期
* 接口
* 依赖
* 数据流
* 事件
* 持久化
* 扩展点

---

## 第四阶段：How（Implementation）

> **具体做什么？怎么交付？**

描述：

* 功能拆分
* 函数
* 参数
* 伪代码
* 文案
* 数值
* 配置表
* 资源
* UI节点
* 测试条件
* 开发任务

所以你可以非常简单地把它记成：

> **1 = Why**
> **2 = What**
> **3 = How the software works**
> **4 = What developers actually implement**

---

# 十、四份文档的边界最好规定成这样

| 内容     | 创意 | 系统 | 架构 | 功能拆分 |
| -------- | ---: | ---: | ---: | -------: |
| 设计理念 |  ★★★ |      |      |          |
| 玩家体验 |  ★★★ |    ★ |      |          |
| 游戏规则 |    ★ |  ★★★ |      |          |
| 系统流程 |    ★ |  ★★★ |    ★ |          |
| 状态机   |      |  ★★★ |   ★★ |        ★ |
| 数值公式 |      |  ★★★ |      |      ★★★ |
| 模块职责 |      |    ★ |  ★★★ |        ★ |
| 类/接口  |      |      |  ★★★ |       ★★ |
| 数据结构 |      |    ★ |  ★★★ |       ★★ |
| 函数     |      |      |    ★ |      ★★★ |
| 伪代码   |      |      |      |      ★★★ |
| UI文案   |      |    ★ |      |      ★★★ |
| 具体资源 |      |    ★ |    ★ |      ★★★ |
| 开发任务 |      |      |      |      ★★★ |

这样写文档时就有一个很实用的判断标准：

> **一个内容如果出现在某一层，就必须尽量让它承担这一层应该承担的职责，而不是提前替下一层做决定。**

---

# 十一、我尤其建议系统设计稿采用“规则单元”写法

不要整篇都是大段叙述。

最好是：

```text
SYS-INV-001 物品拾取

目的：
玩家可以将世界中的物品转移到自身背包。

前置条件：
1. 玩家处于可拾取状态。
2. 物品处于可拾取状态。

处理规则：
1. 检查物品是否存在。
2. 检查背包是否存在可用空间。
3. 若物品可堆叠，则优先寻找已有堆叠。
4. 剩余数量无法容纳时，继续寻找空槽。
5. 无法完全容纳时，剩余部分保留在世界中。

成功结果：
物品数量增加，世界物品数量减少。

失败结果：
玩家持有状态不发生改变。

玩家反馈：
播放拾取音效并刷新背包界面。

边界情况：
...
```

这种格式对于后续自动化处理也非常好。

尤其是你后面提到的那种**让智能体读取“已有系统设计稿 + 针对问题的补充回答，再把回答归纳回原稿”**的工作流，这种规范化结构会非常有利。

---

# 十二、架构设计稿则适合采用“模块单元”写法

例如：

```text
ARC-INV-001 InventoryService

职责：
负责所有背包业务操作。

负责：
- 添加物品
- 删除物品
- 移动物品
- 堆叠计算

不负责：
- UI显示
- 数据持久化
- 物品静态数据加载

依赖：
ItemRepository
InventoryModel

对外接口：
AddItem()
RemoveItem()
MoveItem()

事件：
InventoryChanged

生命周期：
由 GameContext 创建，游戏会话期间持续存在。
```

它和系统设计稿有一个非常重要的区别：

### 系统设计

> “玩家拾取后物品进入背包。”

### 架构设计

> “由 PickupService 调用 InventoryService 完成物品转移。”

前者描述游戏规则，后者描述软件职责。

---

# 十三、还可以给四层规定不同的“禁止项”

这会比单纯规定“应该写什么”更有效。

### 创意需求稿禁止

* 过多实现细节
* 类设计
* 函数设计
* 技术选型
* 具体任务拆分

### 系统设计稿禁止

* 代码实现
* Unity API
* 类层级
* 具体工程目录
* 过早绑定技术方案

### 架构设计稿禁止

* 重新定义游戏规则
* 大量具体 UI 文案
* 每个函数的算法细节
* 逐行伪代码

### 第四阶段禁止

理论上这里已经没有“不能太细”的问题了。

它就是：

> **把已经确定的设计，拆成机器和人都可以执行的工作。**

---

# 十四、最终可以把它理解成“逐层降低歧义”

这个模型可能最适合你现在的独立开发流程：

```text
创意需求稿
     │
     │ 消除“为什么做”的歧义
     ▼
系统设计稿
     │
     │ 消除“游戏规则是什么”的歧义
     ▼
架构设计稿
     │
     │ 消除“程序由谁负责什么”的歧义
     ▼
功能拆分
     │
     │ 消除“具体要写什么”的歧义
     ▼
代码
```

每向下一层，都应该减少一种歧义。

因此，一份设计文档是否合格，不应该用“写得详细不详细”衡量，而应该问：

> **下一阶段的人是否还需要自行做决策？**

例如：

**系统设计稿交给架构设计者：**

> 不应该再需要架构设计者自行决定游戏规则。

**架构设计稿交给程序员：**

> 不应该再需要程序员自行决定模块职责和主要数据流。

**第四阶段交给程序员：**

> 不应该再需要程序员自行猜测具体需求。

但同时也不要反过来追求“把所有东西提前规定死”。

好的设计文档应该是：

> **上层规定下层必须遵守的约束，下层自行决定不影响上层约束的实现细节。**

这句话其实可以成为你整套策划文档体系的总原则。

---

## 我会建议你最终把“系统设计稿”和“架构设计稿”的目录固定下来

### 系统设计稿

```text
1. 系统概述
2. 系统目标与范围
3. 核心概念与术语
4. 系统实体

6. 状态与状态转换

9. 条件与限制

11. 玩家反馈
12. 异常与边界情况
13. 数据定义
14. 数值规则
15. 待定问题
16. 需求追踪ID
```

### 架构设计稿

```text
1. 架构概述
2. 架构目标与原则
3. 系统模块划分
4. 模块职责
5. 模块依赖关系
6. 核心数据结构
7. 对象生命周期
8. 核心流程与数据流
9. 接口与事件
10. 状态管理
11. 持久化
12. 配置与数据驱动
13. 扩展机制
14. 异常处理
15. 性能/并发/资源约束
16. 技术选型
17. 与系统设计稿的需求映射
18. 待定技术问题
```

另外有一点很值得你采用：

> **每份文档都保留“待定问题”，不要为了让文档看起来完整而强行补全。**

因为“明确知道这里还没决定”远比“写了一个其实未经思考的临时方案”更有价值。

如果把这套流程进一步做成适合**AI 自动整理、补全、检查一致性**的规范，我会建议下一步直接把这四个阶段设计成一套统一的 **ID、字段、状态、引用关系和文档模板体系**。这样你的智能体不仅可以“把补充回答归回系统设计稿”，还可以自动检查哪些系统规则没有对应架构、哪些架构没有对应开发任务。







# 提示词

你是一名**独立游戏制作流程与游戏系统设计文档专家**，需要帮助我建立一套能够由“游戏创意”稳定过渡到“可执行代码需求”的游戏设计文档体系。

我目前将游戏开发前期的设计过程划分为四个阶段：

### 第一阶段：创意需求稿

定位：**概念层 / 设计意图层**

用于在团队交流或策划讨论中，让人快速理解“这个游戏是什么、为什么这样设计”。

主要回答：

* 游戏想做什么？
* 核心体验是什么？
* 有哪些核心设计？
* 玩家将经历什么？
* 各核心系统大致承担什么作用？
* 不同设计之间存在什么关系？

这一阶段强调**设计理念、核心体验和整体概念**，不要求完整描述所有实现细节。

---

### 第二阶段：系统设计稿

定位：**完整规则层 / 游戏设计规格层**

它是第一阶段向实际开发之间的主要承接文档。

目标不是简单扩写创意需求稿，而是让一个**没有参与前期讨论的游戏策划、程序、美术或其他开发人员，仅通过阅读这份文档，就能够完整理解游戏中各个系统“是什么、为什么存在、如何运作、与什么发生关系”**。

需要明确：

* 系统的目标和职责
* 系统包含哪些组成部分
* 玩家能够进行什么操作
* 系统有哪些状态
* 系统的运行规则
* 状态如何变化
* 系统之间如何交互
* 各种正常流程、异常流程和边界情况
* 数据之间的逻辑关系
* 系统与其他系统的依赖关系
* 哪些内容属于设计规则，哪些只是实现方式
* 哪些地方仍然需要进一步决策

这一阶段**不应该过早进入具体代码、类、函数、数据结构或引擎 API 设计**。

---

### 第三阶段：架构设计稿

定位：**软件架构层 / 技术设计层**

它承接第二阶段的完整游戏规则，并将其转化为能够指导程序开发的技术架构。

目标是让程序员能够明确：

* 系统应该如何拆分
* 模块之间如何组织
* 模块之间如何通信
* 核心职责应该由谁承担
* 数据应该如何组织和流动
* 哪些对象拥有状态
* 哪些对象负责行为
* 哪些逻辑应该独立
* 哪些模块需要复用或扩展
* 系统生命周期如何管理
* 关键流程如何在程序层面实现
* 如何控制模块之间的耦合
* 哪些地方需要接口、事件、服务、管理器等架构机制

但第三阶段仍然应该停留在**架构设计**，而不是直接写具体业务代码。

---

### 第四阶段：功能需求拆分 & 文案编写与数值设计

定位：**实现准备层 / 可执行需求层**

这一阶段已经非常接近伪代码和具体实现。

需要将前面的架构和系统规则进一步拆解成程序员可以直接执行的任务，例如：

* 功能点拆分
* 具体接口
* 具体数据字段
* 具体数值
* 状态机
* 事件
* 输入输出
* 条件判断
* 业务流程
* UI 文案
* 道具描述
* 数值表
* 伪代码
* 开发任务清单

最终目标是：**程序员无需重新理解设计意图，即可依据这些内容开始实现。**

---

# 第三部分：设计 AI 辅助编写这两份文档的工作流

要求不要设计成：

> “把创意需求稿丢给 AI，让 AI 直接生成系统设计稿。”

而是设计成一个**分阶段、可检查、可回溯的文档工程流程**。

1. 分析现有创意需求
2. 提取已有设计事实
3. 建立游戏术语表

5. 建立系统依赖关系
6. 识别信息缺口
7. 向设计者提出问题
8. 处理设计者回答
9. 将答案归档到正确的系统位置
10. 形成系统设计稿
11. 检查系统设计稿的一致性
12. 从系统设计稿提取架构需求
13. 建立模块划分
14. 建立模块依赖和数据流
15. 形成架构设计稿
16. 检查架构是否覆盖系统设计
17. 检查架构是否过度进入代码实现

请根据实际需要增加、删除或重新组织这些步骤。

对于每一个步骤，请明确：

* 输入
* 输出
* AI 应该做什么
* AI 不应该做什么
* 需要用户参与什么
* 如何检查结果是否正确
* 出现冲突时如何处理
* 该步骤产生的中间产物是什么

最终形成一套能够实际执行的**AI 游戏设计文档生产流水线**。
