# 1. 文档定义

## 1.1 文档目的

本文件规定游戏程序作为一个整体如何成立：程序由哪些层与模块组成、各部分负责什么、部分之间允许与禁止怎样依赖、系统之间怎样通信、数据怎样分类与流动、对象与系统的生命周期顺序、有哪些统一的基础设施，以及整个项目必须遵守的全局技术规则。

它以引擎为既定技术环境：凡引擎已提供且满足需求的机制，本架构直接采用并写明由谁在什么时机使用，不另行建设功能重复的基础设施。因此本文件同时回答「哪些能力直接来自引擎」「哪些能力必须由项目实现」。

它回答的问题是"整个程序应该怎样组织"，不回答"玩家应该经历什么"（那是 `系统设计文档/` 系统设计稿的内容），也不回答"某个系统为了实现要求需要哪些程序实体与接口"（那是 `Code_Design/` 代码设计案的内容）。

## 1.2 适用范围

本架构覆盖下列内容。

| 范围 | 内容 |
| --- | --- |
| 程序大循环 | 启动 → 主界面与局外界面 → 开新局或读档 → 局内循环（地图阶段与事件阶段往复）→ 结局成立 → 局末结算与跨局写入 → 回到局外界面 |
| 玩法系统 | `系统设计文档/` 的 6 个系统域共 31 个系统，清单见 2.3 的映射表 |
| 基础设施 | 存档、配置与数据资产、随机、时间、输入、资源、场景、日志、事件分发共 9 项，另加 7.8 表现通道与 7.11 其他公共能力，见第 7 章 |
| 数据 | 静态配置资产、运行时数据、持久化数据三类，见第 5 章 |
| 引擎侧全局约束 | 由采用引擎机制而派生的、对全部系统成立的技术约束，见 8.6 与第 10 章 |

未覆盖的内容与承接方如下。

| 未覆盖部分 | 承接方 |
| --- | --- |
| 界面内部的布局、字段排版、视觉样式与操作细节 | `系统设计文档/` 各系统设计文档的界面章节（设计决策记录决策 4：界面与操作规格归各系统设计文档承接） |
| 数值取值、难度调制、公式与数值落点 | 后续数值设计阶段（设计决策记录决策 49） |
| 单个系统对外提供的全部接口及其逐项契约 | `Code_Design/` 各系统的代码设计案 |
| 接口内部的执行步骤与算法 | 伪代码层（该层尚未建立） |
| 第三方插件与包的逐项选型、部署方式与版本号 | 实际代码与技术实现。本架构只规定「某类能力统一经哪个机制」，不规定具体包名与版本 |
| 剧情与叙事编排、引导提示与事件内容的具体编排 | 关卡与内容策划 |
| 界面的一览清单 | `架构设计文档/界面索引.md`；本架构只规定界面栈的职责与层级语义 |
| 覆盖范围之外的两个库级系统 | `00-总览` 的四份库级台账属文档治理，不是程序系统；本架构只在引用处按编号引用 |
| 05-40 仓库与银行的实现 | 远期占位，当前版本不实现；本架构只在 2.3 的映射表中为其保留归属 |
| 事件结果配置的字段级结构 | 设计决策记录决策 76 悬置，到期日为事件结果落点进入实现设计环节时；本架构只固定结果标识这一层接口 |

## 1.3 与其他设计文档的关系

六层文档的信息流如下。

```
创意需求          系统设计文档/ 系统设计稿     本架构设计案        Code_Design/ 代码设计案     伪代码        实际代码
为什么做      →    玩家规则是什么       →    程序整体怎么组织  →   某系统需要什么      →      怎么执行  →   可运行实现
```

| 文档层 | 与本架构的关系 |
| --- | --- |
| `系统设计文档/` 系统设计稿 | 本架构的上游依据。本架构引用其中的系统名与系统编号，不重新定义游戏规则 |
| 本架构设计案 | 规定整个程序允许怎样组织，并规定每项能力由引擎提供还是由项目实现 |
| `Code_Design/` 代码设计案 | 本架构的下游约束对象。代码设计案必须服从本架构的第 3 章与第 8 章；第 2 章的模块划分决定代码设计案的归属范围 |
| 伪代码与实际代码 | 经代码设计案间接约束 |

架构设计案与代码设计案是两个并列维度，不是同一维度的上下层：架构管"系统之间怎样组成一台机器"，代码设计案管"这台机器中的某个部件具体需要具备什么"。冲突处置按《架构设计案编辑规范》第六章第 3 节执行，不得由下游自行选择更方便执行的一条。

## 1.4 术语的四层归属

本架构使用的词汇分四类，**四类之间不要求同名**。

| 类别 | 定义 | 例 | 谁使用 |
| --- | --- | --- | --- |
| 玩家面向术语 | `系统设计文档/00-总览/02_术语表.md` 登记的标准术语，回答玩家看到与经历什么 | 事件、事件状态、元物品、元效果、背包空间、行动槽 | 策划案、界面文案、面向玩家的说明 |
| 架构术语 | 本文件定义的程序结构用语，回答程序里由什么承担什么 | 事件模板、事件实例、事件变体、元对象、组件、数据域、阶段状态机、意图、表现通道、常驻场景、程序集 | 本架构设计案、代码设计案、伪代码与实际代码 |
| 引擎术语 | 引擎自有的机制与概念名 | 场景、预制体、配置资产、资源引用、帧回调 | 本架构设计案、代码设计案、实际代码 |
| 代码术语 | 代码设计案与实际代码中使用的实体名、接口名与字段名 | 由代码设计案定义 | 代码设计案、实际代码 |

四条使用规则：

1. **架构术语可以与玩家面向术语同名，也可以不同名，不要求一一对应。** 例如架构层的「元对象」对应设计库的「元物品」概念并把它扩展到全部局内对象；架构层的「事件实例」在设计库中没有对应术语，但在 `01-50` 的单局状态范围内已隐含存在。
2. **同名不等于同义。** 架构层凡是复用设计库词汇的地方，以第 1.5 节的对应表为准；对应表未登记的同名词，其含义限定在本架构内部，不得反向用于解释游戏规则。
3. **本架构不新增玩家面向术语。** 游戏规则需要新术语时，走 `系统设计文档/00-总览/02_术语表.md` 的登记流程，不由本文件登记。
4. **引擎术语只在需要区分「谁提供机制」时出现。** 本架构写到机制与职责归属一级，不写引擎的接口名、方法名与类名。

## 1.6 分层与模块的定位

**第 2 章的分层与模块划分是本架构的描述性分类，不是强制性隔离。**

它们的作用是：把「这个程序一共有哪些要实现的职责」分类列清楚，让读者与下游文档能按类别定位内容，提升代码与文档的可读性。它们**不承担**下列职责：

| 分层与模块不承担 | 由谁承担 |
| --- | --- |
| 数据隔离 | 第 5 章的数据所有权与 8.2 的数据访问规则 |
| 交互隔离 | 3.3 的允许依赖清单与 3.4 的禁止依赖清单 |
| 依赖方向约束 | 8.1 的依赖方向规则与 8.6 的引擎侧约束；编译期强制由 2.1.2 的程序集引用关系承担 |
| 编译期强制 | 2.1.2 的程序集划分 |

因此：

1. 一个单元属于哪一层、哪个模块，是**分类标注**，不构成它「只能被谁调用」或「只能调用谁」的依据；
2. 判断一次调用是否合法，唯一依据是 3.3 的允许清单、3.4 的禁止清单与 8.1 的依赖方向规则；
3. 新增单元时，必须标注它的分类（哪一层、哪个模块），但不需要为迁就分类而改动既有依赖关系；
4. 分类发生变化（例如某个单元从一层挪到另一层）**不构成架构变更**，不需要按 8.5.6 登记；只有依赖关系与程序集划分发生变化才需要登记。

## 1.8 编号与命名规则

| 对象 | 规则 | 例 |
| --- | --- | --- |
| 模块 | `M{两位序号}`，序号即模块清单顺序 | `M04` |
| 模块单元 | `ARC-M{模块序号}-{三位序号}`，同一模块内递增 | `ARC-M04-001 对象与经济` |
| 层 | `L{一位序号}`，序号即自下而上的层序 | `L1` 基础设施层 |
| 系统引用 | 沿用 `系统设计文档/` 的 `{域编号}-{系统编号}` | `06-30` 战场与战棋规则 |
| 事件 | 中文事件名，登记在各模块单元的「事件」栏与事件登记表内 | 轮次推进 |

约束四条：

1. **系统编号与系统名一律沿用 `系统设计文档/`**，架构不另行编号、不改名、不改动系统的归属域（《架构设计案编辑规范》第八章第 6 节）；
2. **模块编号与系统编号互不复用**，模块撤销后编号保留空缺；
3. 模块单元的「对外接口」一栏登记模块对外暴露的能力名，用于说明模块之间怎样通信；这些能力内部的逐项契约属于代码设计案；
4. **事件名与模块单元编号是下游文档的引用锚点**，一经登记不因承载方式变化而改名；确需变更时按 8.5.6 登记影响面。

# 2. 总体程序架构

## 2.1 整体分层与程序集划分

### 2.1.1 分层

程序分五层。分层的定位见 1.6：它是把职责分类列清楚的自然语言标注，用于提升可读性，不强制各类之间的数据隔离与交互隔离。判断调用是否合法一律按 3.3、3.4 与 8.1。

| 层 | 编号 | 职责 | 不负责 |
| --- | --- | --- | --- |
| 基础设施层 | L1 | 提供与玩法无关的公共能力：存档、配置与数据资产、随机、时间、输入、资源、场景、日志、事件分发，以及 7.8 表现通道 | 任何游戏规则；任何具体玩法状态 |
| 数据层 | L2 | 持有运行期数据（三个数据域）、静态配置的内存形态与持久化数据的读写 | 业务判断；界面呈现；效果的结算规则 |
| 领域层 | L3 | 实现玩法系统的核心规则：事件、时间、日程、探索、战斗、物品、经济、委托、技能、对象与效果、队伍、线索树、概率池、局生成 | 界面呈现；资源加载；输入采集 |
| 游戏逻辑层 | L4 | 编排跨系统的流程与阶段：局内阶段状态机、事件执行与结算、战斗执行、局末结算、局外流程 | 单条规则的实现（由领域层提供）；界面绘制 |
| 表现层 | L5 | 界面栈与场景的生命周期、状态呈现、意图到操作命令的转换 | 直接修改任何游戏数据；业务判断 |

### 2.1.2 程序集划分

分层是描述性的，**编译期强制靠程序集划分**。程序集分四个。

| 程序集 | 内容 | 允许引用的程序集 |
| --- | --- | --- |
| 纯逻辑程序集 | 领域层与数据层：元对象与组件内核、事件状态机、战斗规则、经济规则、线索树、数据域与切面 | 纯逻辑程序集自身；**不引用**表现程序集与承载程序集，也不引用引擎的表现与运行时 API |
| 承载程序集 | 基础设施层：存档、配置加载、数据资产、随机、时间受理、输入采集、资源、场景、日志、事件分发 | 纯逻辑程序集；引擎 API |
| 表现程序集 | 表现层：界面栈、界面实体、场景对象、表现驱动 | 纯逻辑程序集、承载程序集；引擎 API |
| 装配程序集 | 常驻场景的启动物体与编辑器侧工具（资产导入、校验、对账测试） | 全部程序集；编辑器 API 只在编辑器侧引用 |

四条规则：

1. **纯逻辑程序集不得引用表现程序集与承载程序集**，这是 3.4 第 1、2、4 项在编译期的强制形式；
2. 依赖方向与跨程序集调用是否符合 3.3 与 3.4，以**程序集引用关系为第一道核对**，人工核对为第二道；
3. 程序集划分发生变化（增删程序集、调整引用关系）属于架构变更，按 8.5.6 登记；
4. 单元属于哪个程序集由它的内容决定，不由 2.2 的模块划分决定。

## 2.4 核心运行时组成

程序运行时由下列常驻部分组成。常驻部分在启动阶段建立，跨场景存在，进程退出时一并结束。

### 2.4.1 承载方式

| 承载方式 | 内容 | 说明 |
| --- | --- | --- |
| 常驻场景 | 一个专门承载常驻对象的场景 | 该场景在启动阶段加载并全程保留，**其管理方式不等同于普通场景**：它不参与阶段切换、不作为界面承载、不被卸载。常驻对象挂载其上，由引擎在场景装配时一并处理其加载（ENG-GAP-013） |
| 常驻对象 | 2.4.2 表内全部单元 | 由常驻场景承载；其中数据与规则部分为普通 C# 对象，不依赖场景，可脱离场景运行与测试 |
| 启动物体 | 常驻场景内的一个启动物体 | 按 6.1 的显式调用序列完成六阶段启动；**不设统一的持有容器，也不设独立的启动引导单元**（ENG-GAP-003、ENG-GAP-012） |
| 单元装配声明 | 编辑器内维护的声明 | 常驻单元清单与依赖关系的唯一依据，决定初始化顺序与校验结果（ENG-GAP-003） |

| 随单局创建的部分 | 三个数据域的内容 | 随单局创建，结算提交完成时释放（见 5.2 与 6.6） |

事件属性配置的五个字段类（ARC-GAP-036）：**刷新规则组**（入池条件、权重、上限、一次性与延时）、**呈现配置**（出现方式、点位约束、图标与显示）、**时间配置**（窗口期、持续时间与取整规则）、**界面配置**（界面开放状态、面板展示项）、**锁定配置**（撤退后的窗口期延长与周边事件锁定范围）。字段类之内允许按事件类型扩展字段，新增字段必须先登记字段类。

# 3. 模块与系统边界

## 3.1 各模块职责

各模块按固定字段写成一个单元。字段中「不负责」与「负责」同等重要。本节是职责登记，不是调用限制（见 1.6）。

### ARC-M01-001 核心与基础设施

职责：
提供与玩法无关的公共能力，并持有三个运行期数据域。

负责：
- 常驻单元清单与依赖声明的维护，以及初始化顺序依据的提供
- 存档的分域、切面采集、提交与恢复驱动
- 静态配置资产的加载、校验与版本绑定
- 随机源与确定性序列
- 世界时间的受理与广播
- 输入采集与意图分发
- 资源与场景的加载释放、常驻场景的维护
- 分级日志
- 跨系统事件的登记与分发
- 三个数据域的持有与释放

不负责：
- 任何游戏规则的判断
- 战斗、事件、经济等玩法状态的业务含义
- 界面绘制与文案

依赖：
无（本模块是最底层）

对外接口：
存档提交与恢复、配置查询、随机序列申请、时间推进受理与订阅、意图订阅、资源请求、日志写入、事件收发

事件：
时间刻度变化、自动保存完成、存档提交完成、存档恢复完成、配置加载完成

生命周期：
常驻单元的清单在编辑器内维护；运行期由启动物体在启动阶段按声明顺序显式初始化。三个数据域随单局创建，结算提交完成时释放。**不设统一的持有容器**，各单元由常驻场景承载并相互持有引用。

### ARC-M02-001 事件与生成

职责：
承载事件从配置到运行、从生成到退出的完整链路，并负责时间刻度与日程记录、本局环境的生成输入。

负责：
- 事件模板、事件变体与事件实例三层结构的数据持有与状态迁移
- 事件池的两层语义：全局事件池的内容集合与当前事件池的刷新集合
- 事件调度：过期剔除、入池判定、配额核算、按权重抽取、变体抽取、点位查重与重试
- 事件的状态迁移规则：进入、推进、达成结束条件、退出与结算条件
- 事件配置的五个字段类与事件类型契约的读取
- 触发条件的模块组合与求值调用
- 世界时间刻度、窗口期与持续时间的时间口径
- 日程记录与事件的界面配置声明
- 种子到本局四项产物的生成流程

不负责：
- 战斗内部的推进（归 M05）
- 事件内执行流程的编排（归 M10）
- 事件内的经济动作（归 M04）
- 事件的界面绘制（归 M08）
- 池成分的内容集合计算（归 M06）

依赖：
M01、M06、M09

对外接口：
事件实例的创建与结束、事件状态查询、事件池刷新、生成流程调用、时间推进请求、日程记录查询

事件：
本局生成完成、事件进入当前事件池、事件刷新到点位、事件进入进行中、事件结算完成、当前事件池刷新完成

生命周期：
常驻。事件实例随事件生命周期创建与销毁。

### ARC-M03-001 探索与推进

职责：
承载地图层的空间规则与事件的呈现取数。

负责：
- 区域的划分、区域形态的推算与区域封锁规则
- 事件点位的布局与绑定
- 基点与活动范围
- 事件在地图上的呈现列表取数
- 跨区域位移事件（转移事件与载具租赁事件）的空间语义
- 地图界面所需的点位与区域数据
- 区域解锁状态的写入：本局生成与本局推进对区域解锁状态的变化由本模块提交（ENG-GAP-017）

不负责：
- 事件的生成与状态（归 M02）
- 地图界面的绘制（归 M08）
- 战斗内的空间判定（归 M05）

依赖：
M01、M02、M06

对外接口：
区域与点位查询、区域形态查询、呈现列表查询、位移事件参数、区域解锁状态提交

事件：
区域形态转变、周边事件锁定、呈现列表更新、基点变化

生命周期：
常驻。区域与点位为静态配置，形态与呈现列表为单局状态。

禁止项逐条列出。违反禁止项不会让某个系统立刻出错，但会让整个程序的结构腐化，因此按第 10 章核对。

| 1 | 下层依赖上层：纯逻辑程序集引用表现程序集 | 反向依赖会让底层能力无法脱离界面复用，也使界面成为事实上的逻辑层。由 2.1.2 的程序集引用关系在编译期强制 |

| 10 | 任何模块直接推进世界时间 | 时间推进只有一个受理入口，且只在事件退出时发生（ARC-GAP-013、ARC-GAP-025） |

| 16 | 任何模块在游戏状态判定中使用帧时间 | 判定必须与帧率无关且可复现（ENG-GAP-022） |
| 17 | 任何模块依赖引擎的退出回调完成存档或收尾 | 退出是进程终止，不做任何收尾承诺；存档的唯一可靠写路径是两类自动保存节点（ENG-GAP-018） |

# 4. 系统通信机制

本章按 S01 裁定 ARC-GAP-024 的口径编写：**架构层只约束禁止的依赖方向（见 3.4），不强制规定通信方式的分类与选择规则。** 各系统与模块在实现层可以按自身特点选择合适的调用方式。

为使各行其是的调用仍能有共同的理解基础，本节列出项目内**可用**的四种通信方式并给出适用场合说明。它们是可选手段，不是强制分类，任何跨模块调用都不要求必须先归入某一类。

## 4.1 直接调用

适用：调用方明确要求被调用方完成一件它职责内的事，且调用方需要立即知道结果。

写法：调用方持有被调用方的引用并同步调用。引用的取得方式由装配声明与单元的初始化顺序决定（见 6.1 与 6.3），不设统一的解析入口。

约束：
- 被调用方必须是调用方允许依赖的模块（见 3.3）
- 被调用方不得反向调用调用方（见 3.4 第 12 项）
- 一次调用的直接链不跨越两层以上；跨多层的场景通过逐层委托表达，不直接穿透

## 4.2 查询

适用：一方需要读取另一方的状态，但不要求对方做任何事。

写法：向持有方请求只读结果；持有方返回快照、值或只读视图。

约束：
- 查询不得产生状态变化
- 读取方不得缓存跨域结果作为自己的数据（派生缓存只能由来源方维护）
- 同层只读查询不需要逐条登记，但同样受本节约束（3.3 第 5 项的通则）
- 高频查询（战斗内每轮次）由持有方提供只读快照，避免每次穿透到对象内部

## 4.3 事件

适用：一次状态变化需要被多个不特定的接收方知晓，或发布方不应感知接收方。

写法：经 M01 的事件分发器发布与订阅。

约束：
- 事件的语义以**类型契约**的形式确定：每个跨模块事件登记事件名、唯一发布方、载荷字段类别与失败语义，登记表以可检视的资产承载，便于在编辑器内查看全部事件
- **未在契约中登记的事件不得发布。** 该约束的强制方式是一条**对账测试**：测试遍历代码中全部事件发布点，与登记表逐项比对，出现未登记事件即测试失败（ENG-GAP-006）
- **登记按「即用即定」执行**：需要新事件时直接在登记表补一行即可，不设额外的审批、编号申领或版本流程；登记表本身是契约的权威载体（ENG-GAP-020）
- 事件只承载"发生了什么"，不承载"要求谁做什么"；要求做事走直接调用
- 订阅方处理失败不得回滚发布方的状态

## 4.4 数据共享

适用：双方约定共读同一份数据，且该数据有明确的所有者。

写法：由所有者持有，其他方按 3.3 与 8.2 的规则读取。

约束：
- 共享数据的写入权只属于所有者
- 只读快照允许跨模块传递，但快照不携带写入口
- 共享数据的分类与所有者见第 5 章

## 4.5 通信选择规则

本节给出可直接判定的选择规则。强制部分在 8.4；本节回答「默认该用哪一种」，用于在实现时快速定位。

| 情形 | 采用 | 依据 |
| --- | --- | --- |
| 调用方要求对方完成一件属于对方职责的事，且需要立即结果 | 4.1 直接调用 | 明确的命令关系 |
| 只需读取对方状态、不需要对方做任何事 | 4.2 查询 | 同步只读；同层只读不需登记 |
| 需要读取的数据有明确所有者且双方约定共读 | 4.4 数据共享 | 数据所有权见 5.4 |
| 一次状态变化需要被多个不特定接收方知晓，或发布方不应感知接收方 | 4.3 事件 | 状态广播 |
| 跨模块的状态广播 | **必须** 4.3 | 8.4 第 1 条 |
| 界面要求变更游戏状态 | **必须**经意图与命令提交，不得直接调用领域模块改数据 | 8.4 第 5 条 |

判定顺序：先看是否有 8.4 的强制项；没有强制项时，按「要对方做事 → 4.1；只要状态 → 4.2 或 4.4；要多人知道 → 4.3」选取。任一选择都必须同时满足 3.4 的禁止项。

**规范偏离登记。** 《架构设计案编辑规范》第五章第 4 节要求第 4 章给出通信机制的分类与选择规则；S01 裁定 ARC-GAP-024 选择了「只约束禁止项、不规定通信方式分类」的口径。本文件的处置是：把架构层**强制**的部分完整落在 8.4，把第 4 章的四种方式与上表作为**默认指引**保留，两者都不强制要求把每次跨模块调用归入某一类。该偏离在此登记，供后续评审核对。

| 商人原型定义 | 商人差异维度的配置契约 | 配置资产（商人原型） | M04 |
| 地图模板 | 区域划分、区域连接、事件点位布局、点位的战斗瓦片地图标识 | 配置资产（地图模板） | M03 |
| 基础配置 | 世界观包装、文本、音频、表现资源索引 | 配置资产与资源引用 | M01、M08 |

`系统设计文档/` 下的 13 张扩展配置表在定位上是**各自系统的初始素材与迁移来源**，用于设计评审与对照；**运行期读到的一切配置以引擎编辑器内的配置资产为准**。表的内容结构与枚举契约不变，程序侧不直接读表，内容侧不直接改运行期资产。内容侧与程序侧的分工按 8.6 第 10 条执行。

**过渡口径**：在引擎侧资产建立起来之前，设计库的配置表仍是唯一的配置内容载体，表内容不提前废弃（`系统设计文档/00-总览/03_设计决策记录.md` 决策 93）。新增配置记录时按 8.5.4 执行。

**设计表与运行资产的角色分工**：

| 角色 | 载体 | 承担什么 |
| --- | --- | --- |
| 设计侧登记 | 设计库的配置表与类型契约表 | 设计评审、枚举契约的登记、跨系统引用的对照；内容是权威资产的迁移来源 |
| 运行期权威 | 引擎编辑器内的配置资产 | 运行期实际读到的一切配置；校验、版本绑定与内存形态都以它为准 |

部分表除承载配置内容外，还承担**设计侧的契约登记**职责，改动它们属于设计变更而非资产更新，包括：`30_事件类型表.csv`（事件类型契约）、`40_结算组件表.csv`（结算组件的划分与写入边界）、`10_角色属性表.csv`（属性的上级认领台账）。这三张表在 8.5.3 至 8.5.5 的接入步骤中按名登记。

静态数据的三条统一约束：

1. **先登记后使用。** 枚举会持续增长的类别必须先在其权威资产内登记再使用。
2. **版本绑定。** 全部静态数据共享一个配置版本标识，写入单局存档；读档时版本不一致按 7.1 的规则处理。
3. **运行期只读。** 资产在运行期不得被修改；唯一的登记例外是输入映射（见 7.4 与 8.1）。

### 5.2.5 两个事件池

事件池在本架构中是两个独立的数据集合，分属两层职责（ARC-GAP-027）。两者都属世界状态域，但计算时机与用途不同。

| 池 | 含义 | 计算时机 | 用途 |
| --- | --- | --- | --- |
| 全局事件池 | 本局游戏中**哪些事件可以出现**的内容集合，即本局允许出现的事件标识清单 | 开新局时按线索树解锁与剪枝状态计算一次并快照入档，局内不再变化 | 为当前事件池提供内容范围的上界 |
| 当前事件池 | **下一次事件刷新时哪些事件可能出现**的刷新集合 | 由 M02 的事件调度在每次刷新时按区域形态与事件属性规则组对全局集合过滤后生成，局内随刷新变化 | 生成抽取的直接输入 |

三条规则：

1. **上界与刷新分离。** 全局集合只回答"能不能出现"，当前集合回答"这次刷新时哪些可能被抽中"；线索树进度作用于全局集合，区域形态与事件属性作用于当前集合，两个过滤条件正交。
2. **形态转变不需要重算全局集合。** 区域形态在局内转变后，下一次刷新即按新形态从全局集合中取子集，全局快照不变。
3. **两个集合都入档。** 全局集合按快照恢复；当前事件池按其快照恢复，读档不重新过滤、不重新抽取。

### 5.2.6 三个域的访问规则

见 8.2 的全局技术约束。核心是三条：不直接修改他方数据、跨域变更经过持有方入口、派生结果不作为数据来源。

## 5.3 持久化数据

持久化数据分三份独立结构（ARC-GAP-019），序列化机制见 7.1。

| 结构 | 内容 | 提交时机 | 恢复归属 |
| --- | --- | --- | --- |
| 单局存档 | 世界状态域、单局状态域、玩家状态域三个切面，加配置版本标识 | **自动保存的两类节点：时间段推进、战斗轮次推进。退出不提交存档**（ENG-GAP-018） | 由 M01 的存档服务驱动，按域顺序恢复 |
| 跨局存档 | 线索树节点状态、传闻解锁状态、事件解锁状态、封锁集合与封锁标记、达成记录与大关进度；另含剪枝的封锁集合与封锁标记 | 局末结算的一次提交 | 由 M10 的结算执行器写入，写入内容由 M06 定义，随跨局存档独立提交 |
| 设置数据 | 键位映射、音量分轨、字幕与语言；输入映射的覆盖项 | 设置变更时提交 | 由 M01 的配置与设置侧持有，独立于游戏进度 |

三类持久化数据的边界规则：

1. **局内进行中的交易、委托进度、押金、落地物与未领取奖励不进入跨局数据**，随本局结束废弃；落地物在单局存档内完整保存与恢复（`系统设计文档/01-通用系统/50-存档与持久化/50_存档与持久化设计.md` 第 3、4 节）。
2. **跨局与单局不做同一次提交**：结算写入跨局存档与最近一次自动保存写入单局存档是两个提交点，各自的失败语义独立。
3. **版本号按结构分别维护**，迁移由声明了该切面的域负责。
4. **单局存档的写入必须原子**：写临时文件后原子替换；提交过程中断时整次作废并保留上一份有效存档。任意时刻终止进程后重新启动，必须能正常启动并继续游玩，这是本项设计的验收标准（ENG-GAP-018）。
5. **读档口径**：自上一个自动保存节点以来的进度不恢复，未确认的操作不恢复。这是有意为之的设计决策，不是缺陷。

# 6. 生命周期

## 6.1 程序生命周期

程序生命周期分六个阶段，由启动物体按固定顺序显式调用各单元的初始化方法（ENG-GAP-012）。**不设独立的启动引导单元，也不设统一的服务容器**；初始化顺序的依据是 2.4.2 的单元装配声明。前一阶段失败即中止启动并给出可读原因，不进入下一阶段。

| 阶段 | 输入 | 动作 | 输出 | 失败处置 |
| --- | --- | --- | --- | --- |
| 1 装配声明就绪 | 常驻场景已加载 | 启动物体读取单元装配声明，校验声明完整性（无缺失引用、无循环依赖） | 初始化顺序与单元清单 | 声明不完整或存在循环依赖时中止，报出冲突项 |
| 2 配置装载 | 初始化顺序 | 加载静态配置资产、校验标识唯一性与表间引用、确定配置版本标识 | 配置服务可用 | 配置缺失或校验失败时中止，报出具体资产与条目 |
| 3 常驻单元初始化 | 配置服务 | 按装配声明顺序初始化各常驻单元并完成相互引用 | 常驻单元就绪 | 初始化失败时中止，报出单元与阶段 |
| 4 设置与存档索引读取 | 常驻单元 | 读取设置数据与存档索引；设置独立持久化，不随游戏进度 | 主界面可呈现 | 设置损坏时回落默认值；存档索引缺失时只提供开新局 |
| 5 本局装配 | 存档索引或生成输入 | 读档路径：按 9.3 恢复；新开局路径：调用本局生成 | 三个数据域就绪 | 读档失败时保留上一份有效存档并提示；生成失败时回到本局装配入口重试 |
| 6 进入可玩状态 | 数据域就绪 | 阶段状态机进入局外阶段，界面栈打开主界面 | 可玩 | — |

**静态状态的重建（ENG-GAP-013）**：各常驻单元在阶段 1 之前显式复位自身状态，**不依赖引擎的域重载提供初始状态**。较新引擎版本的新项目默认只重载场景，静态字段与非序列化字段会跨播放会话存活；因此各单元必须在初始化时自行复位，不得假定「本次启动时字段已是初始值」。

## 6.2 场景生命周期

### 6.2.1 常驻场景

| 与阶段的关系 | 常驻场景的存在与阶段无关；阶段由阶段状态机持有（见 6.6） |

### 6.2.2 普通场景

| 阶段 | 动作 | 负责方 |
| --- | --- | --- |

## 6.3 单元初始化与销毁顺序

初始化顺序的依据是装配声明中「我要用谁」，被依赖者先初始化。**顺序由声明决定，不由硬编码顺序决定，也不依赖引擎的启动回调顺序**（同一启动阶段内的执行顺序引擎不作保证）。

大致顺序：

1. 基础设施：日志 → 配置 → 随机 → 时间受理 → 事件分发 → 资源 → 场景 → 输入 → 存档；
2. 数据层：三个数据域的容器；
3. 领域层：M09 三处全局能力 → M04 对象与经济 → M07 队伍与角色 → M02 事件与生成（含静态配置绑定）→ M03 探索与推进 → M05 战斗 → M06 元进度与结算；
4. 游戏逻辑层：M10 阶段状态机 → M02 事件调度器 → M10 事件执行器 → M10 战斗执行器 → M10 结算执行器；
5. 表现层：界面栈。

销毁按初始化的逆序执行，依据同上。新增单元时按 8.5.1 登记，不在本节改动顺序。

## 6.4 系统销毁

销毁按初始化的逆序执行。职责边界：

- 表现层先销毁：界面栈关闭，编辑态按各自规则提交或丢弃，状态订阅解除；
- 游戏逻辑层次之：阶段状态机停止，正在进行的战斗与事件按"退出即结算"或"保留未结状态"规则处理；
- 领域层次之：各模块释放非持久资源；
- 数据层次之：数据域随单局结束释放；
- 基础设施最后：存档服务收尾，日志服务刷新缓冲，资源释放，常驻场景结束。

**进程退出不做任何收尾承诺（ENG-GAP-018）**：退出与强制关闭同义，不执行上述销毁序列，也不提交存档；不依赖任何退出回调完成存档或收尾。任意时刻终止进程后重新启动，必须能正常启动并继续游玩；进度的可靠边界是最近一次自动保存节点。

## 6.5 对象分类

| 分类 | 对象 | 约束 |
| --- | --- | --- |
| 常驻对象 | 2.4.2 表内全部单元 | 由常驻场景承载，跨场景存在；不依赖任何普通场景 |
| 数据域对象 | 世界状态域、单局状态域、玩家状态域 | 随单局创建，结算提交完成时释放；容器本身常驻，内容按局重建 |
| 场景对象 | 普通场景实例、战场实例、界面实体 | 随场景与界面的生命周期创建与销毁 |
| 临时运行对象 | 战斗内的结算中间量、条件求值的中间结果、抽样的中间集合 | 单次操作内有效，不跨帧保留，不入档 |
| 存档对象 | 三个切面与三份持久化结构（单局存档、跨局存档、设置数据） | 只在采集与恢复期间存在，采集完成后即释放 |
| 静态配置对象 | 5.1 表内全部定义 | 随构建产出，运行期只读，不销毁直到进程退出 |

## 6.6 阶段状态机

阶段状态机是全部阶段的唯一权威（ARC-GAP-032），与事件状态联动。阶段取六种：地图、事件执行、战斗、收尾窗口、结算、局外。阶段取值属世界状态域，见 5.2.1。

| 阶段 | 进入条件 | 允许的操作 | 退出到 |
| --- | --- | --- | --- |
| 地图阶段 | 无进行中事件 | 按事件类型与界面属性声明（如事件属性配置的界面开放状态） | 事件执行阶段 |
| 事件执行阶段 | 事件实例进入进行中 | 事件类型声明允许的操作（交易操作、物品交付、装备调整等） | 战斗阶段、收尾窗口阶段、地图阶段 |
| 战斗阶段 | M10 的战斗执行器启动 | 按战斗行为表登记的行为集合 | 收尾窗口阶段、事件执行阶段 |
| 收尾窗口阶段 | 战斗结束 | 按战场与战棋规则声明的窗口内操作 | 地图阶段、事件执行阶段 |
| 结算阶段 | **事件结算环节的事件结果提交**（ENG-GAP-018） | 无（本阶段不接受任何改变局内状态的输入） | 局外阶段 |
| 局外阶段 | 结算提交完成 | 线索树查看、剪枝提交、规划下一局、开新局 | 地图阶段 |

阶段拥有方：地图阶段与事件执行阶段的拥有方为 M10 的事件执行器；战斗阶段与收尾窗口阶段的拥有方为 M10 的战斗执行器；结算阶段的拥有方为 M10 的结算执行器；局外阶段的拥有方为 M10 的局外流转部分。

三条硬规则：

1. **阶段切换只能由当前阶段的拥有方发起，由阶段状态机执行。** 任何模块不得自行切换界面以隐式改变阶段。
2. **结算阶段是封闭的。** 结局成立之后世界时间不再推进，本局不再接受任何改变局内状态的输入（`系统设计文档/07-线索树与元进度/40-局末结算与写入/40_局末结算与写入设计.md` 的 3.13）。
3. **战斗阶段不直接退出到结算阶段。** 结局只在事件结算环节成立，战斗只退回收尾窗口阶段或事件执行阶段；全队失去行动能力在战斗内只做判定（ENG-GAP-018）。

## 7.5 时间

时间推进由两段构成，缺一不可（ARC-GAP-025）：**事件内记录**把时间消耗记在事件自己的账上，**事件退出时推进**才把它写入世界时间。

| 项 | 内容 |
| --- | --- |
| 能力 | 提供事件内时间记账与退出时的推进受理，维护世界时间，广播刻度变化，派生自动保存节点与日程记录更新 |
| 提供方 | 项目实现（引擎的时间机制只提供帧钟、真实钟与固定步，不提供逻辑钟与刻度调度） |
| 是否允许绕过 | **不允许。** 任何模块不得直接改世界时间 |
| 事件内记录 | 非战斗事件在进入时按事件配置记录一次性耗时，并在事件进行中把每一项操作或行为各自配置的耗时累加到本事件的记账上；战斗事件由 M05 以秒为单位累计战斗净时长并持有（ENG-GAP-022）。此阶段**不动世界时间** |
| 退出时推进 | 事件退出时把累计值一次性推进：非战斗事件按整个时间段累加，最小推进单位为**一整个时间段**；战斗事件把以秒计的净时长**向上取整对齐**到时间段边界 |
| 三段刻度的关系 | 世界时间是唯一持久化刻度，只在事件退出时被写入；事件内的两条记录路径是它的输入：非战斗事件按「进入时的一次性耗时 + 事件内各项操作／行为各自配置的耗时」累加，战斗事件按 M05 持有的净时长累加。两个累计量随事件实例与战斗状态入档 |
| 广播 | 每次推进一步广播刻度变化；自动保存节点与界面时间显示由该广播派生 |
| 帧时间的边界 | 帧时间只用于表现、动画与界面计时；**任何影响游戏状态的判定都不得使用帧时间**（ENG-GAP-022、3.4 第 16 项） |

## 8.1 依赖方向规则

3. 引擎侧的强制约束按 8.6 执行。

禁止清单以 3.4 的 17 条为准。**例外必须登记在本节**：写明例外双方、理由、失效条件与复核时点；未登记的例外在架构核对时按违反处理。

已登记的例外：

## 8.2 数据访问规则

按 S01 裁定 ARC-GAP-033 的口径，只规定三条通用原则，不逐数据域列举读写方。

| # | 原则 | 具体含义 |
| --- | --- | --- |
| 1 | 不直接修改他方数据 | 只允许数据所有者写入自己的数据；其他模块只能读取，或经所有者提供的写入能力提交变更 |
| 2 | 跨域变更经过持有方入口 | 任何跨域的状态变化必须经持有方的提交入口，不得直接改对象字段、不得持有对方的可变引用 |
| 3 | 派生结果不作为数据来源 | 派生缓存（背包空间、同名遗物效果、条件求值结果、区域形态推算结果）只能由来源方维护与重建，读取方不得把派生结果当作来源状态使用或缓存 |

**粒度不设严格限制（ENG-GAP-015）**：哪个模块在什么粒度写入哪一条数据，按功能实现需要确定；本架构只登记各数据域的变更入口清单（5.4），不逐条目规定写入方，也不规定切面的采集粒度。具体访问关系由各系统的代码设计案自行声明，并在代码设计案评审时按本节三条核对。评审时的判断基准：

- "直接修改"指持有对方的可变对象并改其字段，或持有对方的内部集合并在其上增删；
- 只读快照的传递不视为直接修改，但快照不得携带写入口；
- 批量查询、跨域只读遍历属于读取，但不得在读取方缓存结果。

# 9. 关键全局流程

全局流程写到模块与能力调用一级，不写能力内部的执行步骤。

## 9.1 游戏启动

```
触发：可执行程序启动
参与：装配侧（常驻场景、启动物体、装配声明）、M01、M10（阶段状态机）、M08（界面栈）
序：
  1 常驻场景加载 → 启动物体就绪
  2 各常驻单元显式复位自身状态（不依赖域重载）→ 读取装配声明并校验（缺失引用或循环依赖即中止）
  3 日志服务就绪 → 配置服务加载并校验静态配置资产 → 记录配置版本标识
  4 按装配声明顺序初始化常驻单元并完成相互引用
  5 读取设置数据（损坏则回落默认值）→ 读取存档索引
  6 阶段状态机置为局外阶段 → 界面栈打开主界面
状态变化：无游戏状态变化
产生事件：配置加载完成
结束条件：主界面可交互
```

## 9.2 进入场景

```
触发：界面栈发起界面打开请求
参与：M08（界面栈）、M01（资源机制、场景机制）、M10（阶段状态机，提供当前阶段供界面判定）
序：
  1 界面栈解析目标界面与其层级 → 判定是否需要新场景
  2 需要时：经统一资源机制加载场景与所需资源 → 场景机制加载场景
  3 界面实体创建 → 建立状态订阅 → 转换为编辑态（若为可编辑界面）
  4 若是地图与战斗之间的一次性切换：先加载目标场景，再替换界面栈顶，再释放来源场景的非共享资源
状态变化：界面栈变化；不改变任何游戏数据
产生事件：界面打开
结束条件：界面可交互
失败处置：资源或场景加载失败时保留当前界面，向表现通道给出提示
约束：常驻场景不参与本流程
```

## 9.3 存档加载

```
触发：启动阶段的读档路径，或玩家在局外选择已有存档
参与：M01（存档服务、数据域）、M06、M02、M03、M05、M07、M09、M10（阶段状态机）、M08（界面栈）
序：
  1 存档服务读取单局存档结构与配置版本标识
  2 版本一致则继续；不一致则按迁移规则处理，无法迁移时提示不兼容并停在主界面
  3 装载静态配置资产（已在启动阶段完成）
  4 创建三个数据域的空结构
  5 按序恢复：世界状态域 → 单局状态域 → 玩家状态域
  6 重建派生缓存：背包空间、同名遗物效果、条件求值结果、区域形态推算
  7 恢复事件池：全局事件池内容集合按快照恢复，当前事件池按快照恢复
  8 恢复战斗未结状态（若有）
  9 恢复界面位置：局内恢复到地图阶段；战斗未结时恢复到最近一次行动机会开始的时刻
状态变化：三个数据域由空转为存档内容
产生事件：存档恢复完成
结束条件：阶段状态机进入地图阶段或战斗阶段，界面可交互
约束：恢复过程不重新抽取任何随机结果；未确认的操作不恢复；上一个自动保存节点之后的进度不恢复
```

## 9.4 游戏退出

```
触发：进程终止（玩家主动退出、强制关闭、平台关闭、异常终止均按同一口径处理）
参与：无（退出不做任何收尾承诺）
序：
  不执行销毁序列，不提交存档，不触发任何退出回调驱动的流程
状态变化：无
产生事件：无
结束条件：进程结束
约束：
  1 单局存档的唯一可靠写路径是两类自动保存节点（时间段推进、战斗轮次推进）；退出不构成提交点（ENG-GAP-018）
  2 任意时刻终止进程后重新启动，必须能正常启动并继续游玩；不能保证这一点即为设计失败
  3 由此要求单局存档的写入必须原子（写临时文件后原子替换），且提交过程中断时按 7.1 的失败语义整次作废并保留上一份有效存档
  4 读档口径：自上一个自动保存节点以来的进度不恢复，未确认的操作不恢复；这是有意为之的设计决策，不是缺陷
```

## 9.5 关键跨系统流程

### 9.5.1 开新局

```
触发：玩家在局外选择开新局
参与：M02（局生成）、M06、M01、M07、M09、M10（阶段状态机）、M08（界面栈）
序：
  1 读取输入：全局事件池内容集合（按线索树解锁与剪枝状态计算）、剪枝状态、已解锁的大关进度
  2 生成四项产物：本局事件池快照、事件的窗口期与出现顺序、区域解锁状态、行情
  3 计算并快照全局事件池的内容集合（本局允许出现的事件标识清单）
  4 重建三个数据域（结算提交完成时已释放）：队伍编制按生成结果重置，技能配置重置，物品与容器按生成结果建立
  5 初始化当前事件池：由事件调度器执行一次刷新
  6 界面栈切到地图界面，阶段状态机进入地图阶段
状态变化：三个数据域由空转为初始状态
产生事件：本局生成完成、当前事件池刷新完成
结束条件：地图界面可交互且存在可进入的事件
```

### 9.5.2 事件阶段转换（地图 → 事件）

```
触发：玩家在事件信息面板上点击进入
参与：M08（面板）、M10（事件执行器与阶段状态机）、M02（事件状态与数据）、M01（时间受理、输入）
序：
  1 玩家点选事件点 → 面板原地展开（窗口期、参考持续时间、强制标记）
  2 点击进入 → 阶段状态机校验当前阶段为地图阶段且事件实例处于可进入
  3 M10 的事件执行器把事件实例置为进行中 → 阶段切换为事件执行阶段（若为战斗事件则进入战斗阶段）
  4 界面栈打开事件界面或战斗界面
状态变化：事件状态迁移；世界时间不在此刻推进
产生事件：事件进入进行中、阶段切换
结束条件：事件界面或战斗界面可交互
```

### 9.5.3 事件阶段转换（事件 → 地图）与十步收束

```
触发：事件达成结束条件并退出
参与：M10（事件执行器与阶段状态机）、M02（事件调度器）、M01（时间受理、随机、存档）、M05、M04、M09、M06、M03、M08
序：
  1 M10 的事件执行器收集事件结果：战斗事件取战斗结果标识与达成目标清单
  2 事件结算：按结果标识查询事件配置，应用本次事件对玩家与世界状态的全部结果
  3 时间结算（ARC-GAP-025）：取出本事件记账上的累计值——非战斗事件为按行为与操作累计的时间之和，战斗事件为 M05 以秒计的净时长；由时间服务在事件退出时一次性推进世界时间（战斗净时长先向上取整对齐到时间段边界）
  4 本步骤是**事件结算环节**：若本事件的结果构成本局结束（含三类终止情形），结局在此刻成立，随后进入结算阶段（见 9.5.5 与 9.5.6）。这是本局结束的唯一入口
  5 自动保存：时间推进触发单局存档提交（时间段推进节点）
  6 过期剔除：事件调度器把越过窗口期的事件状态转为已错过并从地图呈现中移除
  7 事件池检查：按事件属性配置判定哪些事件进入、哪些移除、哪些保留，并计算权重；权重由每个事件自己的配置数据填写，抽取时不做难度体系式的层权重调制（ARC-GAP-028）
  8 确认生成数量：按每种事件的当前在场数量与配置上限核算本轮各类别的生成数量
  9 抽取生成：随机服务提供确定性序列 → 按权重抽取模板 → 抽取变体 → 点位查重，冲突则重试，重试超限记为生成失败且不占用点位
  10 呈现：生成结果写入当前事件池 → M03 更新呈现列表 → 界面刷新地图 → 阶段状态机回到地图阶段
状态变化：事件状态收尾、世界时间推进、当前事件池刷新、事件实例销毁（已完成或已错过）
产生事件：事件结算完成、时间刻度变化、自动保存完成、当前事件池刷新完成、阶段切换
结束条件：地图界面按新事件池刷新完成
```

### 9.5.4 撤退后的收场

```
触发：玩家在战斗中发起撤退并成功
参与：M05（撤退判定）、M10（事件执行器）、M02（事件属性配置与状态）、M03、M08
序：
  1 战斗以撤退收场 → 撤退结果写入战斗结果标识
  2 事件状态：技术上仍为可进入状态（ARC-GAP-026），保留战斗内敌人的状态与位置，玩家可以重新进入
  3 事件退出并把控制权交回地图
  4 M10 的事件执行器按事件配置执行两条地图侧结果：该事件的窗口期延长；以该事件为中心锁定一定范围内的其他事件
  5 被锁定的其他事件在该事件完成或过期之前不可进入
状态变化：事件仍可进入；周边事件进入锁定；已获得的战利品保留；世界时间按实际战斗时长推进
产生事件：撤退发生、周边事件锁定
结束条件：回到地图界面
```

### 9.5.5 三类终止情形与结局成立

```
触发：全队失去行动能力、主线中断、关底未达标三种情形之一发生
参与：M05（判定）、M10（事件执行器、结算执行器、阶段状态机）、M06（结局判定）、M01（存档服务）
序：
  1 判定：全队失去行动能力由 M05 在战斗内即时判定并写入战斗结果；主线中断与关底未达标由各自系统即时判定
  2 承接：M10 的事件执行器在事件收尾时承接判定结果（战斗内的判定由战斗执行器轮询战果后转交）
  3 收场：事件按常规流程打完收尾窗口、按常规退出与结算规则处理本场战斗
  4 结局成立：在 9.5.3 第 4 步的事件结算环节成立；结局类型与触发起因按 `系统设计文档/07-线索树与元进度/40-局末结算与写入/40_局末结算与写入设计.md` 的 3.7 与 3.13 与 `06-A0` 的 3.4 取值
  5 阶段状态机进入结算阶段，关闭本局输入通道，世界时间停止推进
  6 M10 的结算执行器接管：收集整局存档快照 → 调度结算组件 → 写入跨局存档
状态变化：本局终止；跨局数据按未通关结局写入
产生事件：结局成立、结算完成
结束条件：结算提交完成并转入局外阶段
约束：战斗内不成立结局，只做判定；结局成立的唯一入口是事件结算环节（ENG-GAP-018）
```

### 9.5.6 局末结算与跨局写入

```
触发：结局成立（真结局、隐藏关底事件通过、或未通关结局的三种收尾情形）
参与：M10（结算执行器）、M06（跨局写入内容）、M01（存档服务）、M02、M04、M05、M07、M08（结算窗口）
序：
  1 结算执行器读取整局存档快照（不由各系统另行上报）
  2 按结算组件表依次执行本次版本启用的组件
  3 节点解锁检查组件：判定本局解锁的节点与传闻，写入跨局存档
  4 达成记录与大关进度组件（后续版本启用）：写入结局类型、触发起因与大关进度
  5 一次提交完成；提交成功即标记本局已结算，并随最近一次自动保存写入存档
  6 提交失败则整笔回滚，本局保持未结算并保留重试能力，重试不产生重复写入
  7 界面栈打开结算窗口：变更清单 + 结局提示 + 局外循环入口
  8 阶段状态机进入局外阶段 → 释放三个数据域（ENG-GAP-016）
状态变化：跨局数据更新；本局标记为已结算；三个数据域释放
产生事件：节点解锁、传闻解锁、结算完成
结束条件：结算窗口可交互
约束：场景变化包装事件默认不写入（事件配置显式声明时才产生节点解锁项）；剪枝的封锁集合与封锁标记不经结算组件
```

### 9.5.7 交易提交

```
触发：玩家在交易事件内确认一笔交易
参与：M08（界面与编辑态）、M09（物品写入服务）、M04（交易与物品）、M01（存档服务）
序：
  1 界面持有玩家选择形成的编辑态
  2 玩家确认 → 界面把编辑态提交给物品写入服务
  3 写入服务按"变更一项一落库"执行（ARC-GAP-010）：逐项校验并落库，任一项无法完成时整笔交易回滚，不产生部分提交
  4 提交成功后界面按新状态刷新
状态变化：物品归属、数量与容器格位变化；撤回与退款的规则见 `系统设计文档/05-运营与经济/10-金钱与货物/10_金钱与货物设计.md` 的 4.1
产生事件：物品变更提交、交易提交完成
结束条件：界面反馈完成
边界：确认前不改变任何物品状态；未确认的选择不产生状态变化
```

### 9.5.8 界面交互与提交

```
触发：玩家在界面上进行操作
参与：M08、M01（输入采集）、M09、各领域模块
序：
  1 输入方案把物理输入映射为动作 → 输入服务把动作语义化为意图 → 分发给当前界面
  2 界面把意图转为编辑态变化，或转为一次操作命令
  3 提交位置按粒度判定（ARC-GAP-017）：粗粒度在界面退出指令处提交；细粒度在每次交互处提交；复杂交互在确认处提交
  4 提交经服务（含 M09 的写入服务）执行，数据变化由持有方落库
  5 界面按新状态刷新
状态变化：按提交内容而定
产生事件：界面打开、界面关闭、编辑态提交
结束条件：界面回到可交互状态
约束：界面不直接修改任何游戏数据；本流程不含任何暂停语义
```

# 10. 架构约束检查

每个新增或修订的系统在进入代码设计前逐项自查。**前六项为必备项，不得删减**；后十二项为本项目按自身架构补充的检查项。

```
[ ] 1  是否产生跨层依赖？
       （对照 2.1.1 的分层标注与 3.3 的允许清单；分层是标注，实际判据是 3.3、3.4 与 8.1）

[ ] 2  是否产生循环依赖？
       （对照 3.4 第 12 项；两模块互相直接调用即为违反）

[ ] 3  是否绕过统一存档系统？
       （对照 7.1；任何自行序列化状态或自行读写存档的行为均为违反）

[ ] 4  是否直接修改其他系统的内部状态？
       （对照 8.2 三条原则；持有对方可变引用并改其字段即为违反）

[ ] 5  是否违反对象生命周期规则？
       （对照 6.5 与 8.3；自行创建常驻单元、临时对象跨帧保留、结算后仍创建数据域对象均为违反）

[ ] 6  是否创建了重复的基础设施？
       （对照第 7 章与 7.12 的能力归属汇总；自行实现随机源、日志落点、资源加载、
         事件通道、效果叠加、条件判定、物品写入、输入采集、时间推进、通用对象池
         中的任何一项均为违反）

[ ] 7  是否绕过 M09 的物品写入服务改动物品状态？
       （对照 3.4 第 7 项与 7.11）

[ ] 8  是否在界面层直接改动了游戏数据？
       （对照 3.4 第 3 项与 8.4 第 5 条）

[ ] 9  是否由非持有方推进了世界时间，或在事件未退出时推进了时间？
       （对照 7.5 的推进入口与 8.4）

[ ] 10 是否落在已登记的扩展路径内？
       （对照 8.5 的六类接入步骤；不属于六类之一的扩展先登记再实施）

[ ] 11 是否把派生结果当成了数据来源？
       （对照 8.2 第 3 条；自行缓存跨域结果、或按派生缓存反推来源状态均为违反）

[ ] 12 是否发布了未登记的事件，或把「要求谁做什么」写进了事件？
       （对照 8.4 第 2、3 条与 7.6；对账测试必须通过）

[ ] 13 是否让订阅方处理失败回滚了发布方状态？
       （对照 8.4 第 4 条）

[ ] 14 是否存在未登记的依赖例外？
       （对照 8.1；例外必须写明双方、理由、失效条件与复核时点）

[ ] 15 是否重复实现了引擎已提供的能力？
       （对照 7.12；把权威游戏状态放在随场景销毁的对象上、自建通用对象池、
         自建设备到动作的映射均为违反）

[ ] 16 是否让游戏状态判定依赖了帧时间，或引入了暂停语义？
       （对照 3.4 第 16 项、7.4 与 7.5）

[ ] 17 是否依赖了引擎的启动回调顺序、脚本执行顺序或域重载来保证初始化与复位？
       （对照 8.6 第 4、5 条；常驻单元必须在初始化时显式复位）

[ ] 18 是否在存档里写入了运行时类型名，或依赖退出回调完成存档？
       （对照 7.1、8.6 第 8 条与 3.4 第 17 项）
```
