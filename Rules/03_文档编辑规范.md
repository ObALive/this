# 一、文档库的承载体裁

本库承接策划流程第 2 至 5 步的全部落盘文档，回答三个问题：

1. **做什么**：游戏整体与每个系统的设计内容；
2. **有哪些系统**：全量系统清单与分层结构，目录结构即该清单的物理载体；
3. **有哪些注意的交互逻辑和细节**：跨系统的关键交互逻辑与每个界面的交互方式细节。

本阶段的范围约束：本库当前只承载**系统级设计**，即各系统做什么、系统间如何交互。属性定义、数值规格与代码实现落地细节不属于本阶段讨论内容，禁止写入本库文档正文与待设计清单。

代码实现落地细节由代码设计案承接，其库为 `Code_Design/`，编制规则见《代码设计案编辑规范》。六层文档的分工见第七章。

# 二、编辑动作

## 1. 新建文档

1. 复制 `系统设计文档/_模板/系统设计文档模板.md`；
2. 按节填充，删除全部「（填写说明）」；
3. 元信息表七项全部填写，状态按第三节的状态约定取值；
4. 放入所属系统目录，文件名按《目录维护规范》的命名规则。

## 2. 修订文档

**修订直接在原文件上进行。** 历史由 git 提交记录承载，本库不另存历史版本、不保留归档副本、不在文档内登记版本号与更改历史。

修订前先读现行文档与对应索引，确认改动落在哪个章节、影响到哪些引用点。

## 3. 每次任务的边界

每次任务只在任务书授权的系统范围内新建或修订文档。跨系统的交互逻辑与设计原则发生变更时，同步登记到 `系统设计文档/00-总览/01_设计原则与跨系统交互逻辑.md`。

## 4. 修订后的沿革措辞复核

修订任务收口前，必须对本次改动的内容做一次沿革措辞复核，判定标准见第四章第 8 节。

| 项 | 内容 |
| --- | --- |
| 复核对象 | 本次任务改动的全部文档内容，按份逐句读取 |
| 对照基线 | 版本管理的最近一次提交；`Rules/` 未纳入版本管理时，以本任务输出目录内的留档为对照 |
| 判据 | 改动内容中的每一处措辞都能按第四章第 8 节归入游戏内状态变化或设计状态陈述，读者只读当前文档即可理解完整设计 |
| 越界处置 | 发现沿革措辞时按第四章第 8 节改写；无法判断属于哪一类时上报，不自行删改 |

复核必须逐句读取改动内容。判定取决于语境，同一个词在游戏内状态变化中是合法表述，在设计沿革中是违例表述，关键词检索只能用于复核末尾的查漏，不能用于定位问题。

复核范围以本次改动的内容为界。未纳入本次改动的既有文字不追溯改写；确需清理时另立任务，并在任务报告中登记为遗留问题。

# 三、文档头与文档状态

## 1. 元信息表

每张设计文档头部必须有元信息表，七项如下：

| 项目 | 内容 |
| --- | --- |
| 系统名 | 与目录名一致 |
| 所属域 | 域目录名，例如 `06-战斗` |
| 状态 | 占位 / 草稿 / 评审中 / 定稿 |
| 设计依据 | 列出全部上游依据，写到章节号 |
| 关联文档 | 本系统目录内子文档、上下游系统文档、全景图条目 |
| 维护人 | 首席主策划 |
| 更新日期 | `yyyy-mm-dd`，每次修订同步更新 |

元信息表**不设版本字段**。文件名与文档标题同样一律不带版本号。

## 2. 状态取值

| 状态 | 含义 |
| --- | --- |
| 占位 | 结构已建、要点已摘录，完整设计待填充 |
| 草稿 | 设计已展开，未评审 |
| 评审中 | 提交总监或顾问评审 |
| 定稿 | 评审通过，可作为下游架构与功能拆分的依据 |

# 四、正文写什么

## 1. 只写已敲定

文档正文只写已敲定的内容。存在争议或有候选方案的，一律不列入正文，另建文档编写并在正文附链接方便定位争议点。

## 2. 肯定式陈述

文档陈述「我们是什么」。用陈述句式介绍清楚系统，不得用否定句式堆砌来承担定义职责。需要说明边界时，正面写出该边界由谁承担。

## 3. 消灭隐含规则

不允许「理所当然」的写法。凡写出一条规则，就要把与之相连的条件写全。

以「玩家死亡后掉落装备」为例，合格的写法需要回答：掉落哪些装备、是否包括绑定物、掉落概率、掉落在哪里、死亡期间能否被其他角色拾取、重登之后是否保留、同时掉落多少个、装备损坏是否影响掉落。系统设计稿的核心价值就在于消灭这种隐含规则。

## 4. 区分强制程度

用三类词区分需求的强制程度，让下游能分辨什么是需求、什么是建议：

| 用词 | 含义 |
| --- | --- |
| **必须** | 硬性规则，例如物品无法放入背包时不得完成拾取 |
| **应该** | 推荐做法，例如拾取成功后播放反馈动画 |
| **可以** | 可选能力，例如支持自动整理 |

## 5. 写行为约束，不写实现方案

系统设计稿只写行为约束。例如写「通过唯一 ID 可以快速定位任意物品定义」，而不写「使用 Dictionary 保存物品」。至于用 Dictionary、数据库还是 Addressables，由架构阶段决定。

## 6. 举例的处理

草稿当中的举例仅作辅助说明。应当理解举例要表达的含义，用简洁无歧义的语言总结成规则，再写进正文。举例、比喻、临时描述都不进入正文。

## 7. 来源可追溯

来源标注是库内既有惯例，予以保留。设计依据、依据栏与设计依据节中的任务编号与裁定编号引用都要保留。

## 8. 只陈述当前状态

正文只陈述当前版本的设计状态。判据是读者不需要对照前后版本，只读当前文档就能得到完整的设计。任何需要对照前后版本才能理解的表述都属违例。

**适用面**按文档体裁区分：

| 文档 | 是否受本节约束 |
| --- | --- |
| `系统设计文档/` 下的设计文档、索引、总览与库级 README | 受约束 |
| 任务报告、决策库、留档文件与 `Rules/` 下的规范文件 | 不受约束，这几类文档的体裁就是过程记录，按各自体裁写 |

**两类表述的判定**：

| 类别 | 判定 | 例 |
| --- | --- | --- |
| 游戏内的状态变化 | 属于设计内容，保留 | 区域形态随事件结果转变、事件状态迁移、物品归属改变、剪枝封锁与撤销、落地物随本局结束废弃 |
| 设计本身的沿革 | 不属于设计内容，清除 | 系统更名、条款撤销或移除、结构升级，以及用「原」「本次」「不再」「取代」「修订」指代前后版本的写法 |

**违例措辞清单**：降维、更名、升级为、收缩为、退化为、撤销、移除、废弃、取代、修订、回填、迁移、原有的、原本的、此前的。清单用于提示常见写法，判据仍然是有没有指代前后版本的差异，不限于清单内的词。

**反向表述同样违例**：用「不存在某事物」「不再有某事物」「没有某事物」陈述边界的写法按第四章第 2 节改为正面陈述。例如「不存在独立的确认弹窗」应当改为直接写进入操作发生的位置。

**两处台账例外**：`系统设计文档/00-总览/03_设计决策记录.md` 的裁定栏与理由栏，以及 `系统设计文档/00-总览/02_术语表.md` 的停用术语表，其职能就是登记取舍与停用，按下列写法填写：

* 决策记录的裁定栏取库内既有取值，即定案、砍掉、不做、撤销与悬置一类；理由栏写这条决策为什么这样定，不写这次改动了什么；
* 停用术语行的停用原因写该表述被停用的理由，承接方写标准表述或其位置，依据登记对应的决策编号。

来源标注按第四章第 7 节保留，不受本节约束。

本节清除的沿革信息不丢失：设计沿革的权威落点是 `系统设计文档/00-总览/03_设计决策记录.md` 的决策条目与 git 提交记录，正文只承载结论。

## 9. 不强行补全

每份文档保留待定问题。明确知道「这里还没决定」远比写一个未经思考的临时方案更有价值。禁止为了让文档看起来完整而强行补全待定问题。

## 10. 不擅自设计

智能体不得自行创造游戏设计。撰写与编排文档时，只使用三类内容：已知事实、用户明确决定的内容、从已有内容可以直接推导出的内容。智能体的建议与尚未决定的问题必须明确标记，不得伪装成正式设计写入正文。

# 五、用词与术语

## 1. 唯一术语

`系统设计文档/00-总览/02_术语表.md` 是全库术语的权威清单。同一概念只使用一个标准术语，禁止同义词、别名与缩写混用。新术语必须先登记入表，再用于各系统文档。

## 2. 定义优先级

术语的定义以文档正文为准。正文已有定义的，术语表只做一句话概括并标注概念来源，即首次给出定义的文档与章节；正文没有定义的，才由术语表补充一句话定义，并标注「定义来源：术语表补充」。

## 3. 引用标注

凡跨文档、跨章节引用，或某术语在当前处出现而其定义在别处时，必须在引用处加注术语表编号，写作 `术语名（术语表 T-XXX）`。

## 4. 反向可追溯

术语表条目必须标明概念来源并给出一句话简介，使任意引用点都能回溯到定义处。

## 5. 停用术语

术语表的停用术语一节登记已撤销或已更名的表述，全库禁止再使用，其位置以标准术语或承接方为准。

## 6. 允许的简称

仅当术语表条目显式标注「文档中可简称」时，正文才可使用该简称，且须在同一文档内标准术语首次出现之后使用。未标注的写法一律改为标准术语。

# 七、六层文档的职责边界

策划文档分六层，每层承担一种抽象职责。前六层的关系是「理念 → 规则 → 软件结构 → 程序契约 → 执行步骤 → 技术实现」。

| 阶段 | 核心问题 | 主要读者 | 抽象层级 |
| --- | --- | --- | --- |
| 1. 创意需求稿 | 为什么做、想让玩家体验什么、游戏由什么构成 | 制作人、策划、美术、程序、外部合作者 | 概念 |
| 2. 系统设计稿 | 这个游戏规则究竟是什么，玩家实际会遇到什么行为和结果 | 策划、主程、相关制作人员 | 规则 |
| 3. 架构设计案 | 这些规则在软件中应该由什么结构承载，各模块如何协作 | 程序、技术策划 | 软件结构 |
| 4. 代码设计案 | 某个游戏系统在程序里必须具备什么，与其他系统如何协作 | 程序员 | 程序契约 |
| 5. 伪代码 | 这些程序功能具体按什么步骤执行 | 程序员 | 执行步骤 |
| 6. 实际代码 | 最终用什么语言和技术实现 | 程序员 | 技术实现 |

**系统设计稿 = 游戏规则层，架构设计案 = 软件结构层，代码设计案 = 程序契约层。** 这是三条最重要的边界。

第 4 层与第 5 层的关系是：代码设计案确定「要有什么」，伪代码确定「这些东西具体怎么运行」。

## 0. 架构设计案与代码设计案的关系

第 3 层与第 4 层都从系统设计稿取得输入，但两者是两个不同维度：

```
                  系统设计稿
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
        架构设计案            代码设计案
             │                   │
             │ 全局约束           │ 系统实现规格
             └────────┬──────────┘
                      ▼
                    伪代码
                      ▼
                   实际代码
```

| 文档 | 解决的问题 |
| --- | --- |
| 架构设计案 | 系统之间怎么组成一台机器 |
| 代码设计案 | 这台机器中的某一个部件具体需要具备什么 |

架构设计案决定代码设计案能够怎样设计，代码设计案决定伪代码能够怎样编写。架构设计案是代码设计案的上级约束，代码设计案必须服从。

工作流上的先后是「系统设计 → 架构设计 → 代码设计 → 伪代码」，因为架构定下的全局规则必须在具体系统进入代码设计之前确定；两者在文档体系上是并列的两个维度，不是同一维度的上下层。

分工细则见《架构设计案编辑规范》第六章与《代码设计案编辑规范》第二章。

| 阶段 | 禁止内容 |

| 系统设计稿 | 代码实现、引擎 API、类层级、具体工程目录、过早绑定技术方案 |
| 架构设计案 | 重新定义游戏规则、大量具体 UI 文案、每个函数的算法细节、逐行伪代码 |
| 代码设计案 | 具体算法步骤、程序语言语法、容器类型选择、重新解释游戏规则。细则见《代码设计案编辑规范》第三章 |
| 功能需求拆分与伪代码 | 无。该层的职责是把已经确定的设计拆成机器和人都可以执行的工作 |

## 3. 逐层降低歧义

每向下一层，都应该减少一种歧义：

```
创意需求稿
     │ 消除「为什么做」的歧义
     ▼
系统设计稿
     │ 消除「游戏规则是什么」的歧义
     ▼
架构设计案
     │ 消除「整个程序由谁负责什么」的歧义
     ▼
代码设计案
     │ 消除「某个系统的程序契约是什么」的歧义
     ▼
伪代码
     │ 消除「具体按什么步骤执行」的歧义
     ▼
实际代码
```

一份设计文档是否合格，不用「写得详细不详细」衡量，而应问：**下一阶段的人是否还需要自行做决策？**

总原则：**上层规定下层必须遵守的约束，下层自行决定不影响上层约束的实现细节。**

# 八、系统设计稿的写法

## 1. 合格判据

一个经验丰富的游戏设计师拿到系统设计稿，不写代码也应该能够完全模拟这个系统。用文档回答一个具体情形，例如「玩家拿着 3 个苹果，背包只剩 2 格，再拾取一个 5 个一组的矿石，会发生什么」，答不出来就说明文档还不完整。

## 2. 应包含的结构

| # | 章节 | 回答什么问题 |
| --- | --- | --- |
| 1 | 系统概述 | 这个系统是什么 |
| 2 | 系统目标与范围 | 这个系统是什么，以及不作为哪些职责的承担方 |
| 3 | 核心概念与术语 | 把创意阶段中的模糊概念定义成正式概念 |
| 4 | 系统实体 | 游戏世界中存在什么东西 |
| 5 | 实体属性 | 每个实体拥有哪些属性 |
| 6 | 状态与状态转换 | 实体有哪些状态，状态如何变化 |
| 7 | 核心流程 | 主要流程的完整链路 |
| 8 | 行为规则 | 输入 → 判断 → 结果 |
| 9 | 条件与限制 | 规则的触发条件与边界 |
| 10 | 系统间关系 | 谁负责什么 |
| 11 | 玩家反馈 | 这个系统最终在游戏里表现为什么 |
| 12 | 异常与边界情况 | 正常流程、失败流程、边界情况、非法状态 |
| 13 | 数据定义 | 数据层面的概念，不进入具体数据库设计 |
| 14 | 数值规则 | 数学关系，不含最终取值 |
| 15 | 待定问题 | 还没决定的事 |
| 16 | 需求追踪 ID | 规则的编号与上下游映射 |

## 3. 规则单元写法

行为规则不要写成大段叙述，每条规则写成固定字段的单元：

```
SYS-INV-001 物品拾取

目的：
玩家可以将世界中的物品转移到自身背包。

前置条件：
1. 玩家处于可拾取状态。
2. 物品处于可拾取状态。

处理规则：
1. 检查物品是否存在。
2. 检查背包是否存在可用空间。
3. 若物品可堆叠，则优先寻找已有堆叠。
4. 剩余数量无法容纳时，继续寻找空槽。
5. 无法完全容纳时，剩余部分保留在世界中。

成功结果：
物品数量增加，世界物品数量减少。

失败结果：
玩家持有状态不发生改变。

玩家反馈：
播放拾取音效并刷新背包界面。

边界情况：
...
```

这种结构化写法对后续自动化处理有利，尤其适合「读取已有设计稿加补充回答，再把回答归纳回原稿」的工作流。

## 4. 边界与异常

每个系统至少写清四类情形：正常流程、失败流程、边界情况、非法状态。典型问题例如玩家拾取物品时背包突然满了怎么办、两个系统同时修改物品数量怎么办、玩家使用物品过程中角色死亡怎么办、物品已被另一个行为销毁而界面仍尝试使用怎么办。

这些内容若不由系统设计稿规定，最终都会变成程序员自己决定。一旦程序员开始自行定义游戏规则，设计稿和代码就会逐渐分裂。

## 5. 系统之间的关系

写明「谁负责什么」，例如交互系统负责判断玩家是否能够与目标进行交互，拾取系统负责完成物品从世界对象向玩家持有物的转移，背包系统负责确定物品应该进入何处，物品系统负责提供物品的基础属性。系统之间的关系写清之后，架构阶段才知道应该怎么拆模块。

# 九、架构设计案的写法

架构设计案有独立的编制规范，见 `Rules/07_架构设计案编辑规范.md`。本章只写它在本规范体系中的位置，不重复其条款。

## 1. 分工

| 文档 | 编制规范 |
| --- | --- |
| 架构设计案 | 《架构设计案编辑规范》，十章结构与验收标准见该规范第五章与第七章 |
| 代码设计案 | 《代码设计案编辑规范》 |

本章原先承载的十八节结构，已由《架构设计案编辑规范》第五章的十章结构取代。两份结构的取舍以该规范为准，避免同一规则两个落点。

## 2. 与系统设计稿在判据上的区别

系统设计稿写「玩家拾取后物品进入背包」，描述游戏规则。架构设计案写「由 PickupService 调用 InventoryService 完成物品转移」，描述软件职责。

架构层可以出现 `interface`、`event`、`delegate`、`command`、`service`、`repository`、`factory` 这类概念，因为它们属于软件结构而不是游戏规则。架构层不写具体业务代码，只写模块提供了什么能力、这些能力受哪些约束、成功后产生什么事件。

架构层是否越界，按《架构设计案编辑规范》第二章的归属判断法与第四章的禁止项核对。

# 十、需求追踪

给设计内容分配 ID，建立上下游映射：

```
SYS-INV-001    系统设计稿：玩家可以将获得的物品放入背包
    ↓
ARC-INV-003    架构设计案：InventoryService 负责执行物品添加
    ↓
TASK-INV-011   功能拆分：具体开发任务
TASK-INV-012
TASK-INV-013
```

有了映射，下游可以追溯「这个功能为什么存在」，也可以反向检查「这个需求有没有漏实现」。

# 十一、缺口与裁定

文档编写过程中发现的缺口不直接写进正文，走缺口呈报流程。流程说明见 `Tool/缺口决策系统/建库说明.md`、`读库说明.md` 与 `迭代使用说明.md`，本节只写与文档编辑相关的对接要求。

## 1. 一轮迭代的五步

| 步骤 | 动作 | 责任 | 产物 |
| --- | --- | --- | --- |
| 1 出题 | 分析现状，把信息缺口写成缺口记录与候选方案 | 分析负责人 | 决策库中的未裁定项 |
| 2 提问 | 导出候选清单与作答模板，交给总监 | 分析负责人 | `{base}_候选清单_v{n}.md`、`{base}_作答模板_v{n}.md` |
| 3 回收 | 把总监的裁定导入决策库 | 工具 | `decisions` 表更新 |
| 4 归档 | 已裁定项移入归档表，主表只留未澄清项 | 工具 | `gaps_archived` 表更新 |
| 5 落地 | 按裁定回填设计稿，登记设计决策记录 | 分析负责人 | 新版设计稿与决策记录 |

第 5 步是归档的前提：`landed_at` 字段应当在设计稿回填完成后填写，只有结论真正落到文档里，一条缺口才算闭合。

## 2. 回填的三项强制要求

1. 正文只写已敲定内容；
2. 停用术语一律替换为标准表述；
3. 跨文档引用与索引同步更新。

## 3. 落定后的登记

重大取舍必须登记 `系统设计文档/00-总览/03_设计决策记录.md`。「不做」与「砍掉」须记录理由与复活条件，「悬置」须记录到期日。

# 十二、任务书的写法

任务书放在 `Task/` 下，文件名与任务编号一致。任务书至少写清四节：

| 节 | 内容 |
| --- | --- |
| 任务背景 | 为什么做这件事 |
| 核心指导理念 | 本次任务的取舍方向，用于判断边界情形 |
| 工作方向指导 | 逐条列出要做的事 |
| 工作方法 | 读什么、术语在哪里查、产物怎么交付、哪些动作需要先请示 |

任务书只写授权与目标，不写实现细节。需要约束产物格式时，在「工作方法」一节写明产物路径与命名。
