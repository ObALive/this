## 一、目标与完成尺度

代码设计案是现有代码的解释文档。沿用“代码设计案”“代码设计稿”的名称和 `Code_Design/` 落点，正文回答现有代码由什么组成、各部分如何归属和协作、服务什么功能目的，以及它如何产生当前结果。

文档必须让具备项目基本概念、尚未阅读目标源码的读者能够说明：

1. 该功能解决什么问题，对玩家、调用方或维护者有什么作用。
2. 在什么条件下进入，接收什么输入，产生什么结果或状态变化。
3. 主要过程如何推进，各参与部分分别负责什么。
4. 哪些条件会改变结果，现有代码如何处理拒绝、失败和结束。
5. 当前说明覆盖哪些实现，哪些能力尚未实现或无法确认。
6. 相关程序集、类与方法分别属于哪里，关键类型之间怎样继承、组合，统一入口位于何处。

完成依据是代码结构与功能行为均解释清楚且忠于现有代码。禁止以能否据此编写伪代码、重新实现类型或独立实施单类作为验收门槛。

## 二、文档关系与事实责任

| 材料 | 在解释文档中的作用 |
| --- | --- |
| 现有源码及相关工程配置、资产 | 当前实现行为的主要事实依据 |
| 系统设计稿 | 说明预期功能、业务概念与规则背景 |
| 架构设计案 | 说明全局职责、依赖与技术约束，供对照实际实现 |
| 伪代码与待实施方案 | 表达拟采用的逻辑；不能证明功能已经实现 |
| 测试与运行记录 | 支撑已经实际核验的结果，须注明验证范围 |

代码设计案不承担新增类、字段、签名、技术选型或算法方案的决策职责，也不作为伪代码的前置规格。需要改动实现时，按相应开发任务处理，解释文档在实现变化后同步。

设计与代码不一致时，分别写清预期要求与当前实现及其影响，不能把源码改写成符合设计的理想行为。不得借解释文档擅自修改代码、游戏规则或架构约束。

## 三、解释单位与阅读结构

### 1. 以程序集、方法、类为对象

代码设计文档必须以程序集、方法、类为对象，解释声明范围内的实际代码结构。功能目的用于串联结构与行为；仅写功能流程、在文末附源码位置，不能代替结构说明。

| 解释对象 | 必须说明的结构事实 |
| --- | --- |
| 程序集 | 实际程序集名称及工程依据、范围内类的归属，以及理解协作所需的程序集引用方向；区分程序集、命名空间、源码目录与架构模块 |
| 类 | 所属程序集与命名空间、承担的职责、直接基类与实现的接口；存在继承层级时交代相关基类和派生类，存在组件组合时交代持有方、被持有对象和创建/释放责任 |
| 方法 | 关键方法的声明类、是否继承或重写，以及在协作中的入口或内部步骤地位；说明主要调用方、调用目标及其作用，不把被调用关系写成声明归属 |

结构说明必须区分继承、接口实现、组合持有、配置引用与方法调用。类型派生与定义创建实例是不同关系；对象持有组件与组件继承基类也是不同关系，不能以一张未注明关系含义的层级图混写。

存在统一调度或生命周期入口时，必须明确承接该职责的类和方法、由谁持有和调用、统一管理的实际范围，以及它与上游请求方和下游执行方的关系。每实例持有的执行器、场景控制器和全局调度器的作用域须据源码区分，不能只描述它所参与的一段流程而省略结构地位。

程序集中未单独拆分的部分按工程现状说明；源码中的类名与业务术语有差异时，说明对应关系。程序集归属、派生关系、持有关系或统一入口缺乏依据时，按第十二章与第十四章登记缺失证据和影响，不猜测补全，也不标为已核对。

### 2. 文档组织与阅读顺序

文档可以按程序集、类或一组相关类组织，也可以由功能专题串联多个类，不强制一类一稿或一方法一节。跨文档出现的同一类型应明确主要结构说明位置，其他位置引用；拆分后仍须能沿“程序集 → 类 → 关键方法”定位，并查明必要的继承与组合关系。

每份文档开头先用一至两段概括解释对象、功能目的、核心行为和结果。正文按“目的与范围 → 代码结构与归属 → 入口与条件 → 主要过程 → 结果与边界 → 实现定位”的阅读顺序展开。

标题应明确解释的程序集、类或功能范围。类名、方法名可以作为结构组织与定位信息，并须配合职责和关系说明。禁止按文件顺序堆砌符号，禁止用全量字段或方法清单代替结构与行为解释。

## 四、功能目的与覆盖范围

目的必须落到实际作用，不能只写“提供管理”“执行处理”或把方法名翻译成中文。面向基础设施的能力，可以说明它为调用方提供的价值，无需虚构玩家可见效果。

功能目的优先依据明确的系统需求与实际使用方式。只能从代码推断用途时，标明“根据调用关系推断”，并说明依据；无法确认的动机保留为待核实，不编造设计理由。

范围说明覆盖的入口、子功能与外部协作边界。上游计划但尚未实现的能力单独登记，不能混入当前能力总结。

## 五、入口、输入与可见结果

解释功能由什么操作、事件、生命周期或调用触发，什么条件下生效，以及调用方能得到什么结果。输入用业务含义描述，只有影响理解时才补充类型、单位、范围或标识。

必须区分“请求被接收”与“功能已经完成”。输出可以是返回结果、状态变化、事件、界面反馈、资源变化或文件写入；只描述代码能够支持的结果。

公共入口的源码符号应注明所属类，并与结构说明和实现定位表一致。完整签名仅在重载区分或参数语义确有需要时补充，不要求全量 API 清单。

## 六、主要流程与关键判断

用连贯的自然语言归纳从触发到结束的主要过程，写清关键判断为何会改变功能结果。顺序关系明显的流程可以使用简短编号列表。

多步校验可以归并为有共同目的的阶段，但决定成功、拒绝、部分完成或失败的条件必须保留。不能把只检查了部分条件的代码概括为“完成全部校验”。

禁止逐行翻译、照搬分支循环、为每条语句配一段中文。必要的算法说明应解释它解决的问题及对结果的影响，不展开为待执行的伪代码。

## 七、数据、状态与生命周期

只解释理解功能所需的关键数据：它表示什么、由谁维护、何时变化，以及变化怎样影响后续行为。派生数据和缓存要说明其来源与实际更新时机。

创建、就绪、挂载、替换和释放会影响功能可用性时，说明相应条件与责任。配置、运行状态和存档数据必须分清，不因类型可序列化就推断它已被保存。

不要求穷举字段、访问修饰符、容器类型或实例数量。缺少某项技术细节会导致读者误解行为时，才补充该细节及源码位置。

## 八、可读性与总结性

1. 先说明功能目的和结论，再解释关键过程。每段围绕一个功能问题展开。
2. 以项目通用概念和自然语言为主，首次出现的必要技术术语应说明其含义。
3. 归并相同目的的处理，保留改变结果的差异；不能用“按需处理”“正常完成”等空泛表述替代解释。
4. 结构关系可以用有关系标注的图或简表呈现，并配自然语言解释；符号应准确表达声明归属与关系。禁止用整页签名、字段表或调用箭头替代结构和功能说明。
5. 可以使用有源码依据的简短情境帮助理解，情境不得暗示尚未实现的行为。
6. 正文描述当前实现；历史差异与修改过程由 git 和任务报告承载。

读者应能仅凭正文说明代码的主要组成与归属、类型层级、关键入口、功能目的、主流程和关键边界；源码用于核对与深入阅读。可读性不意味着省略结构事实或会改变结果的条件。

## 九、协作、调用与事件

跨类或跨模块功能必须说明参与者的职责、传递的信息、交接时机以及最终结果由谁形成。先解释协作目的，再列出必要的调用或事件符号。

事件驱动的流程应区分发布与处理、订阅与解除，以及通知是否代表完成。只读到了发布方而尚未核实接收方时，标明解释范围，不能直接断言后续功能已经发生。

文档描述现有协议的行为含义，不另行定义共享接口、事件载荷或回调契约。

## 十、异步、资源与结束条件

涉及跨帧、异步、取消或资源时，只展开影响功能结果的实际机制。说明等待期间的状态、完成通知、结束清理，以及已实现的取消或失败处理。

代码未实现超时、重试、回滚、线程保证或资源自动释放时，禁止在文档中补写这些能力。相关缺失会影响理解时，如实登记限制及其影响。

纯同步功能无需保留异步章节或空表。

## 十一、配置、组件与持久化

涉及配置或组件时，说明它们如何改变功能行为，以及实际加载、组合或查询方式。无需完整抄录所有配置字段和组件类型。

涉及存档时，说明实际保存的内容范围、保存与恢复的触发，以及已实现的失败行为。源码只提供数据结构而未接入保存流程时，必须区分数据定义与持久化能力。

## 十二、源码依据与可追溯性

每份文档必须登记实际源码位置、关键入口符号、覆盖的程序集与类、功能范围与核对基线。程序集归属须核对工程配置、程序集定义或实际编译信息；命名空间、目录名和架构模块名不能单独证明程序集归属。继承、接口实现和关键方法归属须核对声明，组合与统一入口须继续核对创建、持有、调用和清理代码。基线使用可识别的提交标识；包含未提交改动时，注明工作区状态、核对日期及受影响文件，不能把 HEAD 当作这些改动的身份。

行为依据应覆盖关键判断和必要调用链。仅凭类名、接口声明、注释、旧文档或测试名称，不能断言完整功能已实现。涉及配置、场景或预制体绑定的结果，应核对实际绑定；无法取得时标为待核实。

源码位置可以集中放在文末定位表，关键边界可就近加注。源码及相关工程文件是允许引用的实现依据，不受过程文档引用禁令的排除；一次性任务报告不能替代源码事实来源。

源码缺失、只有空实现或只有伪代码时，注明“未实现”或“待核实”及影响范围。允许先解释已经核实的部分，禁止为补齐文档发明实现。重要限制放入正文，不只藏在状态表中。

阅读代码得到的结论标为源码核对；编译、测试或运行得到的结论写明实际验证方式与范围。未执行的验证不得标为通过。

## 十三、编制与修订方法

1. 确定要解释的程序集、类、关键方法和功能范围，定位现有源码与必要配置。
2. 核实程序集归属、类型继承、组合持有、关键方法声明及统一入口，再阅读关键判断、状态写入和主要协作。
3. 对照系统与架构文档理解功能目的，区分预期与实现。
4. 先写功能总结，再按阅读顺序解释代码结构、归属、流程、结果和边界，补充实现定位。
5. 按第十五章检查事实准确性与可读性，登记未核实范围。

任务仅要求修订规范时，不据此批量改写代码或现有解释文档。既有稿件在后续授权修订时按本规范核验，不自动取得新状态。

## 十四、状态、限制与同步

| 状态 | 含义 |
| --- | --- |
| 草稿 | 正在阅读源码或整理解释，尚未完成自检 |
| 待核实 | 存在影响功能结论的源码、配置或行为证据缺口 |
| 已核对 | 声明覆盖范围内的说明已对照源码，并通过第十五章验收 |
| 待更新 | 实现已变化或发现说明与源码不符，需要重新核对 |
| 停用 | 所述功能或实现已停止使用，已注明承接位置或终止范围 |

“已核对”表示文档在所注明基线和范围内准确，不代表代码已经编译、测试或运行通过。部分已实现、部分未实现的功能应明确分开；如果未核实事项影响正文结论，不能将整篇标为已核对。

限制与待核实项至少记录缺失依据、影响功能、已知范围和核实条件。程序集归属、类型关系、方法归属、源码行为、入口、依赖或配置发生实质变化后，同步受影响说明、定位表、基线和索引；纯排版变化不扩大行为验证范围。

旧“可分发”“定稿”状态须重新核对后转换，不能自动等同于“已核对”。

## 十五、验收标准

| 检查项 | 通过条件 |
| --- | --- |
| 功能目的 | 开篇能回答解决什么问题、服务谁以及带来什么结果 |
| 代码结构与归属 | 读者能定位程序集、类及关键方法的声明归属，说明相关继承、接口实现、组合持有和配置引用，关系有源码或工程依据 |
| 统一入口的地位 | 适用时明确统一调度或生命周期入口的类、方法、持有方、调用方、作用域及下游执行关系；未将每实例执行器误写成全局调度器 |
| 自然语言可读性 | 未读源码的读者能够复述主要结构、主流程和关键边界，必要符号与关系说明准确易懂 |
| 总结性 | 内容按功能归纳，无逐行翻译、字段堆砌或重复调用清单 |
| 行为完整性 | 主要触发、输入、关键判断、状态变化、输出及适用失败路径清楚 |
| 事实准确性 | 关键结论可追到实际实现，未把需求、注释、占位和推测当成已实现能力 |
| 范围与限制 | 源码缺失、未实现、未核实和设计差异已明确，不用理想行为掩盖限制 |
| 可追溯性 | 源码位置、入口符号、核对基线、状态和日期齐全且一致 |

验收采用正文阅读与源码对照，不要求读者据此编写伪代码、复刻实现或声明完整类型。仅做解释文档修改时无需为文档新增镜像测试；需要确认运行行为时采用与疑点相适应的验证，并如实记录结果。

## 附录 A：功能解释文档模板

章节可按内容合并，不适用的条件节删除。所有填写提示在交付前替换为实际内容。

```markdown
# {功能名}代码设计案

| 项目 | 内容 |
| --- | --- |
| 解释范围 | {覆盖的程序集、类、关键方法及功能；说明结构详解的主要位置} |
| 源码依据 | {源码位置与关键入口符号} |
| 核对基线 | {提交标识；适用时注明工作区改动与核对日期} |
| 关联设计 | {功能背景与架构约束} |
| 状态 | {按第十四章填写} |
| 更新日期 | {日期} |

## 功能目的与概述
用一至两段说明解决的问题、主要行为和可见结果。

## 代码结构与归属
说明实际程序集及其依据、命名空间和类的归属；写明相关基类、接口、派生类型与组件持有关系。适用时注明统一入口、持有方和调度范围。可用带关系类型的结构图辅助说明。

| 类或关键方法 | 所属程序集与声明类 | 继承、组合或调用关系及职责 |
| --- | --- | --- |
| {实际类名} | {程序集、命名空间} | {相关基类/接口、持有者或被持有对象，以及结构职责} |
| {关键方法名} | {程序集、声明类；适用时注明重写来源} | {主要调用方与调用目标；是否为统一入口及其范围} |

## 入口与生效条件
说明谁在何时触发、输入的含义及生效条件。

## 主要过程与协作
按功能阶段解释关键判断、状态变化和参与者分工。

## 结果、边界与当前限制
说明成功、拒绝、失败及其他会改变结果的条件；区分已实现与待核实内容。

## 实现定位
| 功能环节 | 源码位置与符号 | 对应职责 |
| --- | --- | --- |

## 待核实项
记录缺失依据、影响范围与核实条件；没有待核实项时删除本节。
```

## 附录 B：写法示例

以下仅为写法示例，假定已核对的代码会先检查目标地格能否进入，允许时更新角色位置并发出位置变化通知，拒绝时保留当前位置。它不声明本项目已经具备这些能力。

> 这段代码负责让角色移动到允许进入的地格，并使其他部分获知位置变化。收到移动请求后，它先检查目标地格能否进入；检查通过便更新角色位置，再发布位置变化通知。目标不可进入时，角色保持原位。位置通知给后续显示更新提供了触发入口；是否实际播放移动动画，需要继续核对接收该通知的表现代码。

此写法先交代功能目的，再归纳关键判断与结果，并明确通知与最终表现之间的证据边界。实际文档仍需按第十二章补充源码位置与核对基线。
