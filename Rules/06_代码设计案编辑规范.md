# 一、定位与边界

## 1. 一句话定位

**代码设计案 = 面向单个游戏系统的程序实现规格与接口契约。**

它的最小闭环是：

```
系统职责 → 数据 → 状态 → 功能 → 接口 → 输入输出
        → 状态变化 → 外部依赖 → 系统交互 → 实现约束
```

它最核心的目的不是让人理解代码，而是**让人可以无歧义地开始设计代码**。

## 2. 边界压缩成一句话

**规定「必须有什么、负责什么、接受什么、产生什么、依赖什么」，但不规定「每一步具体怎么算」。**

## 3. 适用的判据

写完一份代码设计案后，读者应当能够回答：

> 我要实现系统 X，打开代码设计案 X 章节，知道 X 需要什么、提供什么、调用谁、被谁调用、有哪些状态、有哪些规则、有哪些接口，然后直接进入伪代码。

达不到这条判据时，该章节按第十一章的标准判定为未完成。

# 二、文档体系中的位置

## 1. 六层文档的分工

| 文档 | 回答的问题 | 面向对象 | 核心产物 |
| --- | --- | --- | --- |
| 创意需求稿 | 这个游戏想让玩家体验什么，为什么这样设计 | 项目组、外部人员 | 核心体验、设计理念、产品特征 |
| 系统设计稿 | 玩家具体会怎么玩，游戏规则是什么 | 策划、设计、程序、美术 | 完整游戏规则与系统行为 |
| 架构设计案 | 整个程序应该如何组织 | 程序、技术人员 | 软件整体结构、模块边界、基础设施 |
| 代码设计案 | 某个游戏系统在程序里必须具备什么，与其他系统如何协作 | 程序员 | 数据、对象、接口、职责、依赖、流程契约 |
| 伪代码 | 这些程序功能具体按什么步骤执行 | 程序员 | 函数级算法与执行逻辑 |
| 实际代码 | 最终用什么语言和技术实现 | 程序员 | 可执行程序 |

## 2. 架构设计案是上级约束

架构设计案与代码设计案都从系统设计稿取得输入，两者是两个不同维度：

```
                  系统设计稿
                       │
             ┌─────────┴─────────┐
             ▼                   ▼
        架构设计案            代码设计案
             │                   │
             │ 全局约束           │ 系统实现规格
             └────────┬──────────┘
                      ▼
                    伪代码
                      ▼
                   实际代码
```

| 文档 | 解决的问题 |
| --- | --- |
| 架构设计案 | 系统之间怎么组成一台机器 |
| 代码设计案 | 这台机器中的某一个部件具体需要具备什么 |

架构设计案决定代码设计案能够怎样设计，代码设计案决定伪代码能够怎样编写。**代码设计案必须服从架构设计案**：架构规定 UI 不得直接修改游戏逻辑时，背包系统的代码设计案不得设计出经界面反向控制背包的结构。

架构设计案尚未定稿时，代码设计案可按系统设计稿先行编制，架构定稿后按《架构设计案编辑规范》§六.4 统一核对一次。

架构设计案是什么、写什么、怎么写，见 `Rules/07_架构设计案编辑规范.md`。

## 3. 与相邻层的分界

| 分界 | 判据 |
| --- | --- |
| 与系统设计稿 | 系统设计稿规定游戏规则；代码设计案规定程序契约。系统设计稿说「玩家发现传闻后该传闻进入已发现状态」，代码设计案回答这个状态在程序里是什么、谁保存、谁负责改变、行为从哪里进入、调用什么接口、条件系统如何读取、内容系统如何被通知、哪些数据要存档、哪些对象属于本系统 |
| 与伪代码 | 代码设计案确定「要有什么」，伪代码确定「这些东西具体怎么运行」。代码设计案写 `InvestigateRumor(RumorID) → InvestigationResult` 加前置条件与成功后结果；伪代码写函数体内的算法步骤 |
| 与实际代码 | 代码设计案不涉及具体语言与工程编码细节 |

## 4. 与策划书的职责分界

`Design/` 设计库承载「系统做什么、系统间如何交互」，`Code_Design/` 代码设计案承载「某个系统在程序里有什么、负责什么、依赖什么」。两者各自的文档互不重复对方的内容。

# 三、应该规定什么，不规定什么

## 1. 应该规定

| # | 项目 | 说明 |
| --- | --- | --- |
| 1 | 系统职责 | 系统负责什么，不负责什么 |
| 2 | 程序实体 | 系统需要哪些类、对象、数据结构、状态实体 |
| 3 | 数据定义 | 每个数据是什么、意义是什么、来源是什么、生命周期是什么 |
| 4 | 接口 | 系统对外提供哪些功能，含每项功能的输入、输出、副作用与前置条件 |
| 5 | 输入 | 外部系统传入的数据、玩家行为、配置数据、查询结果、状态信息 |
| 6 | 输出 | 返回值、状态变化、创建与销毁对象、产生事件、通知其他系统、存档变化 |
| 7 | 依赖 | 本系统实现时会使用其他哪些已经设计好的类、对象和函数 |
| 8 | 系统交互 | 谁调用谁，谁通知谁，谁读取谁的数据 |
| 9 | 状态变化 | 实体有哪些状态，什么行为导致状态变化 |
| 10 | 实现约束 | 只有会影响程序设计的规则才写进来 |

## 2. 不规定

| # | 禁止项 | 判据 | 应当写成 |
| --- | --- | --- | --- |
| 1 | 具体算法 | 出现遍历、查找、排序等具体执行步骤，就进入伪代码 | 系统必须根据玩家的当前状态判断该传闻是否满足调查条件并返回调查资格。具体怎么判断由伪代码决定 |
| 2 | 具体语法 | 出现程序语言的类声明、容器类型、引擎基类 | 传闻系统持有所有运行时传闻进度，通过 RumorID 唯一定位传闻。技术选择属于架构约束时另在架构设计案规定 |
| 3 | 重新解释游戏规则 | 上游已定的规则被改写成另一套 | 把规则转换成程序契约，例如内容系统需要通过 ConditionEvaluator 查询条件是否满足 |

禁止第 3 项的后果最严重：系统设计稿是一套规则，代码设计案又改成另一套规则。

## 3. 实现约束的写法

只有影响程序设计的约束才写。

| 写法 | 判定 |
| --- | --- |
| 传闻状态必须可序列化，因为需要存档 | 合格，这是影响程序设计的约束 |
| 使用 `Dictionary<int, Rumor>` 保存 | 越界，已经进入具体实现选择 |

# 四、基本单位是系统，不是类

代码设计案以**系统**为基本单位，一个系统章节即一个可实现单元。

一个游戏系统很可能对应多个程序对象。例如传闻系统可能对应 `RumorDefinition`、`RumorProgress`、`RumorService`、`RumorRepository`、`RumorConditionAdapter`，这些对象共同属于传闻系统。

因此章节划分的判据是：

| 划分方式 | 判定 |
| --- | --- |
| 一个系统 = 一个章节 | 正确。先以系统为单位描述职责、输入、输出、状态、数据对象、对外接口、内部组件、外部依赖、交互关系与核心流程 |
| 一个类 = 一个章节 | 错误。类名属于实现选择，提前固定会把章节切碎并锁死实现空间 |

系统名称与系统编号沿用 `Design/` 设计库中的定义，两者一一对应。

# 五、系统章节的标准结构

每个系统章节严格套用下列结构。各节按系统规模增减条目，十节本身不得省略。

```
# XXX系统

## 1. 系统定义
### 1.1 系统目的
### 1.2 系统职责
### 1.3 系统边界
### 1.4 上游需求

## 2. 数据定义
### 2.1 本系统拥有的数据
### 2.2 外部数据引用
### 2.3 数据关系
### 2.4 数据生命周期
### 2.5 持久化要求

## 3. 状态定义
### 3.1 状态
### 3.2 状态转换
### 3.3 状态转换触发条件

## 4. 对外接口
### 4.1 接口列表
### 4.2 接口详细定义

## 5. 内部功能
### 5.1 功能列表
### 5.2 功能之间的关系

## 6. 外部依赖
### 6.1 依赖系统
### 6.2 依赖对象
### 6.3 依赖函数与接口
### 6.4 使用方式
### 6.5 依赖方向限制

## 7. 系统交互
### 7.1 调用关系
### 7.2 事件关系
### 7.3 数据流

## 8. 核心流程

## 9. 异常与边界情况

## 10. 实现约束
```

## 1. 系统定义

| 小节 | 写法 |
| --- | --- |
| 系统目的 | 一两句，这个系统为什么存在 |
| 系统职责 | 逐条列出负责的事项 |
| 系统边界 | 逐条列出**不负责**的事项。这一项与职责同等重要，缺了它职责会持续漂移 |
| 上游需求 | 引用系统设计稿中本系统的章节与需求编号 |

系统边界示例：

```
传闻系统负责：
- 管理传闻定义
- 管理传闻运行状态
- 处理传闻发现
- 处理传闻调查完成

传闻系统不负责：
- 内容解锁
- UI 展示
- 存档文件读写
```

## 2. 数据定义

### 2.1 本系统拥有的数据

每个实体登记八项：

| 项 | 说明 |
| --- | --- |
| 名称 | 实体名 |
| 用途 | 这个数据解决什么问题 |
| 数据来源 | 静态游戏数据、运行时产生、外部系统传入 |
| 所有权 | 哪个系统拥有它 |
| 生命周期 | 何时创建、何时销毁 |
| 状态 | 它自身携带哪些状态 |
| 与其他对象的关系 | 引用、包含、派生 |
| 是否持久化 | 是否需要存档 |

### 2.2 数据所有权

数据所有权是本规范的核心概念，作用是避免代码架构混乱。每个数据对象必须标明所有者系统，以及本系统对它的访问级别：

| 访问级别 | 含义 |
| --- | --- |
| 拥有 | 本系统负责创建、修改与销毁 |
| 只读 | 本系统可以读取，不得修改 |
| 经接口修改 | 本系统需要通过所有者系统提供的接口修改 |

示例：

```
RumorDefinition
所有者：传闻系统
来源：静态游戏数据

PlayerProgress
所有者：玩家进度系统
传闻系统仅读取
```

### 2.3 外部数据引用

引用其他系统的数据时只写引用关系，不重新定义该数据的职责与结构。

### 2.4 数据生命周期

写明数据的创建时机、存续范围与销毁时机。跨局持久的数据与单局内的数据分别标注。

### 2.5 持久化要求

需要存档的数据逐项列出，并标明存档粒度。

## 3. 状态定义

### 3.1 状态

列出实体状态的完整取值。

### 3.2 状态转换

用箭头或表格写明转换路径，例如：

```
Locked
→ Unlocked
→ Completed
```

### 3.3 状态转换触发条件

每条转换写明由什么行为或事件触发。转换条件与第 4 节接口表中的「状态变化」列必须一致。

## 4. 对外接口

### 4.1 接口列表

每个系统都必须有一张接口表：

| 接口 | 调用者 | 输入 | 输出 | 状态变化 | 副作用 |
| --- | --- | --- | --- | --- | --- |
| DiscoverRumor | 调查系统 | RumorID | 发现结果 | Rumor → Discovered | 产生发现事件 |
| InvestigateRumor | 玩家交互系统 | RumorID | 调查结果 | Progress 更新 | 可能产生线索 |
| GetRumorState | UI 与条件系统 | RumorID | RumorState | 无 | 无 |

对外接口指跨系统可调用的功能。仅系统内部使用的功能归第 5 节，不进入本表。

### 4.2 接口详细定义

每项接口按第六章的函数契约模板展开。

## 5. 内部功能

### 5.1 功能列表

列出系统内部的执行能力，标明是否对外暴露。

### 5.2 功能之间的关系

写明功能之间的调用顺序与依赖，以及哪些功能由哪项对外接口间接触发。

## 6. 外部依赖

外部依赖表是本规范要求中最容易漏写的一项，必须单列。写法见第八章。

## 7. 系统交互

三类关系分开写，并在章内保持一致：

| 小节 | 写明 |
| --- | --- |
| 调用关系 | 谁主动调用谁，调用哪项接口 |
| 事件关系 | 谁发出什么事件，谁监听，监听后的响应职责 |
| 数据流 | 数据从哪个系统产生、经过谁、流向谁 |

事件关系与接口表中的「副作用」列必须一致。

## 8. 核心流程

每个系统选出最重要的若干条流程，逐条按固定骨架写：

| 项 | 说明 |
| --- | --- |
| 触发 | 流程由什么触发 |
| 参与者 | 涉及哪些系统与对象 |
| 调用顺序 | 依次调用哪些接口，接口之间怎么衔接 |
| 状态变化 | 每一步改变什么状态 |
| 产生的事件 | 过程中发出哪些事件 |
| 结束条件 | 流程何时算完成 |

核心流程只写到接口调用一级，不写接口内部的执行步骤。

## 9. 异常与边界情况

逐条列出正常路径之外的情形：非法输入、状态不允许、依赖不可用、重复调用、并发修改、数据缺失。

每条写明判定条件与期望结果。异常的**判定**属于本规范，异常的**处理步骤**属于伪代码。

## 10. 实现约束

只写影响程序设计的约束，例如：数据必须可序列化、状态修改必须经接口、某项数据在系统间必须保持一致、性能或容量上限。

不写具体的数据结构选择、容器类型与语言特性。

# 六、函数契约模板

接口详细定义与内部功能说明统一使用本模板。八项不得缺项，确实不适用时写「无」，不省略字段。

```
### {接口名}

职责：
一句话，这项功能完成什么。

输入：
- 参数输入：来自调用者的参数
- 状态输入：读取哪些运行时状态
- 数据输入：读取哪些静态配置数据
- 外部事件输入：接收其他系统的哪些事件

读取：
- 明确列出读取的数据对象

输出：
- 返回值：返回什么
- 状态输出：改变哪些状态
- 事件输出：产生哪些事件
- 外部系统调用：调用其他系统的哪些接口

产生的状态变化：
- 逐条列出

前置条件：
- 逐条列出

后置条件：
- 逐条列出

副作用：
- 逐条列出

异常情况：
- 逐条列出
```

写作要点：

1. 前置条件、后置条件与异常情况用来约束契约，不用来描述处理流程；
2. 「异常情况」只写判定条件，处理步骤留到伪代码；
3. 「读取」与「输入」不重复，读取用于列全数据访问面，输入用于分类说明来源；
4. 状态变化、事件输出与副作用三处不得互相矛盾。

# 七、输入与输出的四类划分

输入输出不得只理解为函数参数，按四类分别写明。

## 1. 输入四类

| 类别 | 含义 | 例 |
| --- | --- | --- |
| 参数输入 | 调用者直接传入 | RumorID |
| 状态输入 | 读取的运行时状态 | PlayerState、RumorProgress、WorldState |
| 数据输入 | 读取的静态配置数据 | RumorDefinition |
| 外部事件输入 | 接收其他系统发出的事件 | PlayerInvestigatedEvent |

## 2. 输出四类

| 类别 | 含义 | 例 |
| --- | --- | --- |
| 返回值 | 直接返回给调用者 | InvestigationResult |
| 状态输出 | 改变了哪些状态 | RumorProgress 已变更 |
| 事件输出 | 产生了哪些事件 | RumorInvestigatedEvent |
| 外部系统调用 | 主动调用了其他系统 | ClueService.UnlockClue() |

四类划分的作用是把「本系统做了什么」与「本系统让别的系统做了什么」分开记录，避免接口表看起来完整、实际漏掉了跨系统影响。

# 八、外部依赖

## 1. 依赖表

每个系统章节必须单列外部依赖表：

| 依赖对象 | 所属系统 | 依赖类型 | 用途 | 使用接口 |
| --- | --- | --- | --- | --- |
| PlayerState | 玩家系统 | 读取对象 | 获取玩家状态 | GetState |
| ConditionEvaluator | 条件系统 | 函数 | 判断条件 | Evaluate |
| ClueService | 线索系统 | 服务接口 | 解锁线索 | UnlockClue |
| SaveService | 存档系统 | 服务接口 | 保存进度 | Save |

依赖类型取三类：读取对象、数据、函数或接口。

这张表的作用是：实现某个系统时不需要重新搜索整个项目去找「这个系统依赖什么」。

## 2. 跨系统引用必须引用，不得重定义

依赖其他系统的内容时，代码设计案必须引用其已定义的程序对象、接口或函数，**不得重新定义其职责**。

## 3. 使用方式

写明每条依赖的调用时机与调用方式，区分直接调用与经事件间接获得。

## 4. 依赖方向限制

写明本系统允许依赖谁，以及不得被谁依赖或不得反向依赖谁。允许出现环时必须在章内显式标注并说明理由。

---

# 九、编号与依赖对象索引

## 1. 唯一 ID

代码设计案中的对象分配唯一 ID，前缀区分对象类型：

| 前缀 | 对象 |
| --- | --- |
| `SYS-` | 系统 |
| `CLS-` | 类、数据结构、实体 |
| `API-` | 接口与函数 |

示例：

```
SYS-RUMOR-001     传闻系统
CLS-RUMOR-001     RumorDefinition
CLS-RUMOR-002     RumorProgress
API-RUMOR-001     DiscoverRumor()
API-RUMOR-002     InvestigateRumor()

SYS-CLUE-001      线索系统
API-CLUE-001      UnlockClue()
```

## 2. 依赖按 ID 书写

外部依赖按 ID 书写，使依赖关系可机械检索：

```
外部依赖：

SYS-CLUE-001
    API-CLUE-001 UnlockClue()

SYS-CONDITION-001
    API-CONDITION-001 Evaluate()
```

## 3. 依赖关系图谱

全部代码设计案合起来构成一张程序设计关系图谱，支持反向查询，例如：

- 哪些系统依赖 `UnlockClue()`；
- `PlayerProgress` 被哪些系统读取。

反向查询由各章节的依赖表与 ID 汇总得出，当前不单独维护一份全局索引表。跨系统引用量增长到难以人工检出时，再按《规范目录维护规范》的流程评估是否新增索引表。

## 4. 编号唯一

同一 ID 在全库唯一，不得复用。对象撤销后其 ID 不重新分配。

# 十、功能要求与实现要求

两类要求分开列出，编号前缀区分。

## 1. 功能要求

来源于游戏设计，编号前缀 `F-`。

```
F-RUMOR-01
玩家完成调查后，传闻必须进入已调查状态。

F-RUMOR-02
调查结果可能产生一个或多个线索。

F-RUMOR-03
传闻状态必须能够被条件系统查询。
```

## 2. 程序实现要求

来源于程序设计，编号前缀 `I-`。

```
I-RUMOR-01
传闻必须能够通过唯一 ID 定位。

I-RUMOR-02
传闻运行状态必须与传闻静态定义分离。

I-RUMOR-03
其他系统不得直接修改 RumorProgress，
必须通过传闻系统提供的接口修改。
```

这一区分把「游戏要求」与「程序为了实现游戏要求而产生的结构约束」分开，便于核对上游覆盖情况与实现自由度。

# 十一、验收标准

## 1. 系统独立实现完备性

一个系统章节只有满足下列条件才算完成：

> 程序员读取该系统章节后，可以明确知道该系统：
>
> 有什么数据；
> 这些数据由谁拥有；
> 有哪些状态；
> 有哪些可执行功能；
> 每个功能接受什么输入；
> 产生什么输出；
> 会改变什么状态；
> 会产生什么副作用；
> 依赖哪些外部系统、对象、接口和函数；
> 其他系统通过什么接口与它交互；
> 有哪些必须满足的功能规则与程序约束；
>
> 并且能够以此为依据继续编写伪代码，而无需重新推测系统的程序行为。

## 2. 逐项核对

| # | 检查项 |
| --- | --- |
| 1 | 十节结构齐备，各节的必填字段无省略 |
| 2 | 系统边界写出了不负责的事项 |
| 3 | 每个数据对象标明了所有者与访问级别 |
| 4 | 接口表齐备，每项接口有详细契约 |
| 5 | 输入输出按四类写明 |
| 6 | 外部依赖表齐备，跨系统引用按 ID 书写 |
| 7 | 状态转换与接口表的状态变化列一致 |
| 8 | 事件输出与系统交互的事件关系一致 |
| 9 | 核心流程写到接口调用一级，未进入算法 |
| 10 | 功能要求与实现要求分开编号 |
| 11 | 未出现具体算法、具体语法与被改写的游戏规则 |
| 12 | 上游需求回指到系统设计稿的章节与编号 |

# 十二、文档组织

## 1. 目录与命名

代码设计案放在 `Code_Design/` 下，一个系统一份，文件名写：

```
{系统编号}_{系统名}代码设计案.md
```

系统编号与系统名沿用 `Design/` 设计库中的定义。文件名、文档标题与元信息表一律不带版本号，历史由 git 提交记录承载。

## 2. 元信息表

每份代码设计案头部必须有元信息表：

| 项目 | 内容 |
| --- | --- |
| 系统名 | 与设计文档中的系统名一致 |
| 所属域 | 域目录名，例如 `06-战斗` |
| 系统编号 | 设计库中的系统编号 |
| 对应设计文档 | `Design/` 中本系统设计稿的路径 |
| 状态 | 占位 / 草稿 / 评审中 / 定稿 |
| 关联文档 | 本系统依赖的其他代码设计案、架构设计案 |
| 维护人 | 首席主策划 |
| 更新日期 | `yyyy-mm-dd` |

## 3. 状态取值

| 状态 | 含义 |
| --- | --- |
| 占位 | 章节骨架已建，内容待填充 |
| 草稿 | 内容已展开，未按第十一章核对 |
| 评审中 | 已通过核对，提交评审 |
| 定稿 | 评审通过，可直接作为伪代码设计的输入 |

## 4. 与设计文档的一一对应

代码设计案的章节与 `Design/` 中的系统一一对应，不合并、不拆分。一个系统在代码实现上确实需要拆成两个独立单元时，先在设计库中评估该系统是否应当拆分，再在代码设计案中同步。

## 5. 落定后的同步

1. 代码设计案定稿后，回写对应系统设计文档的元信息表，在该文档的关联文档栏标明本系统已有代码设计案；
2. 新增或定稿的代码设计案登记到索引，索引由代码设计案的建设任务维护，建设任务开始后再按《规范目录维护规范》的流程确定索引文件的落点与格式；
3. 架构设计案存在时，核对代码设计案是否落在架构允许的结构内，核对项见《架构设计案编辑规范》§六.4。

架构设计案尚未定稿时，代码设计案按系统设计稿先行编制；架构定稿后按上一条统一核对一次，超出架构约束的部分先修订架构设计案或回退到系统设计稿确认。

## 6. 引用其他系统

引用其他系统时写其 ID 与出处章节，不复制对方内容。

# 十三、自检清单

编制或修订代码设计案时，收口前逐项核对：

| # | 检查项 |
| --- | --- |
| 1 | 章节结构与第五章的十节一致 |
| 2 | 未出现具体算法步骤、程序语言语法、容器类型选择 |
| 3 | 未重新定义或改写系统设计稿中的游戏规则 |
| 4 | 引用的跨系统内容使用引用而非重定义 |
| 5 | 每个数据对象有所有者与访问级别 |
| 6 | 每项接口有完整契约，八项字段无省略 |
| 7 | 依赖表按 ID 书写，反向依赖已标注 |
| 8 | 状态转换表与接口表、事件关系三处一致 |
| 9 | 全部对象有唯一 ID，无重复无复用 |
| 10 | 功能要求与实现要求分别编号 |
| 11 | 元信息表八项齐备，系统名与设计库一致 |
| 12 | 按第十一章的十二项核对通过 |
