# 规范目录维护规范

| 项目 | 内容 |
| --- | --- |
| 规范编号 | NR-04 |
| 定位 | 规范目录自身的元规范。规定新规范如何从其他任务中落盘进本目录，以及现有规范如何修订、废弃与检索 |
| 适用范围 | 对 `Rules/` 目录的任何写入动作，包括新增规范、修订条款、拆分或合并规范、登记外部规范来源、废弃条款 |
| 不适用范围 | 设计文档正文的写法见《文档编辑规范》；任务的授权、产物落点与报告见《任务执行规范》 |
| 维护规则 | 本规范约束自身。修订本规范同样走本文第三章的流程，不允许绕过 |
| 更新日期 | 2026-10-05 |

# 一、规范目录的构成

## 1. 目录内容

```
Rules/
├── README.md                规范索引：任务到规范的适用性路由
├── BaseRules.md             入口指针：指向本目录的规范集
├── 01_规范总则.md           顶层原则、目录边界与冲突优先级
├── 02_任务执行规范.md       任务全生命周期与权限边界
├── 03_文档编辑规范.md       策划文档写作规范与文档库编辑规则
└── 04_规范目录维护规范.md   本文件
```

## 2. 文件的三类角色

| 角色 | 文件 | 约束 |
| --- | --- | --- |
| 入口指针 | `BaseRules.md` | 只写指针与优先级摘要，不承载细则，不参与细则修订 |
| 索引 | `README.md` | 只做定位与路由。每条规范只登记一次，不在索引里复制正文 |
| 正文 | `01` 至 `04` | 每条规范条款的**唯一权威落点**。同一规则不得在两个文件里各写一份 |

## 3. 唯一事实来源

一条规则只在一个文件里定义。其他文件需要引用它时，写文件名与章节号，不复制内容。

判断一条规则该放在哪个文件的依据是它的**适用面**：

| 规则的适用面 | 落点 |
| --- | --- |
| 所有任务 | `02_任务执行规范.md` |
| 所有涉及策划文档编写或修订的任务 | `03_文档编辑规范.md` |
| 规范目录自身的写入动作 | `04_规范目录维护规范.md` |
| 跨规范的原则与冲突裁定 | `01_规范总则.md` |
| 仅在某个目录内成立的细则 | 该目录的 README，由本目录登记出处 |

# 二、触发条件

出现下列任一情形，视为产生了需要落盘的新规范：

| # | 触发情形 | 典型来源 |
| --- | --- | --- |
| 1 | 任务执行中经用户确认，形成了新的通用约束 | 用户的追加指令、总监的裁定 |
| 2 | 某个反复出现的问题经裁定后形成固定做法 | 缺口决策的裁定结论 |
| 3 | 现有规范在本次任务中暴露出歧义或漏洞，经裁定补充 | 任务报告的遗留问题 |
| 4 | 用户直接要求把某项规范写入规范目录 | 用户指令 |
| 5 | 某条规范被裁定失效、被取代或需要合并 | 结构治理类任务 |

只影响单份文档、单次任务的局部约定不构成新规范，不落盘，按《文档编辑规范》留在该文档或该任务的产物内。

# 三、写入流程

## 1. 流程七步

| 步 | 动作 | 判据 |
| --- | --- | --- |
| 1 识别 | 判定是否满足第二章的触发条件 | 找到触发的指令或裁定原文 |
| 2 归类 | 判定规则的适用面，选定落点文件 | 按第一章第 3 节的适用面对照表 |
| 3 查重 | 检索规范目录与索引，确认没有同类条款 | 已有条款时改为修订，不新建 |
| 4 起草 | 按第五章的条款写法写出条款 | 条款可被独立理解，不含临时上下文 |
| 5 确认 | 取得用户或总监的确认 | 未确认前只作为候选登记，不写入正文 |
| 6 落盘 | 写入落点文件，同步更新该文件的元信息表日期 | 唯一事实来源不出现两份 |
| 7 登记 | 更新规范索引的条目与触发信号表 | 索引能路由到新条款 |

第 3 步与第 5 步不得跳过。查重跳过会造成同一规则两处定义，确认跳过会把未经批准的约束变成事实规范。

## 2. 索引登记项

每新增或修订一条规范，在规范索引中更新对应条目：

| 字段 | 填写要求 |
| --- | --- |
| 编号 | `NR-xx`，新增时按现有最大号递增 |
| 名称 | 与文件标题一致 |
| 权威文件 | 相对路径 |
| 适用场景 | 一句话写明什么任务需要读它 |
| 触发信号 | 任务书或任务内容中出现哪些词或哪些情况时需要读它 |
| 状态 | 生效 / 已废弃 |
| 生效日期 | `yyyy-mm-dd` |
| 更新日期 | `yyyy-mm-dd` |

## 3. 条款编号

正文内的条款一律用章节号定位，写作 `《文档编辑规范》§四.2`。不用条款级 ID，原因是条款会被拆分与合并，章节号在拆分时同步调整一次即可，条款 ID 调整会牵动全库引用。

需求追踪类的 ID（`SYS-`、`ARC-`、`TASK-`）属于文档内容，不属于规范条款，按《文档编辑规范》第十章执行。

# 四、修订、废弃与合并

## 1. 三类变更动作

| 动作 | 适用情形 | 动作要求 |
| --- | --- | --- |
| 修订 | 条款表述不清、边界需要补充 | 直接改条款正文，更新文件元信息表日期 |
| 废弃 | 条款失效，且无承接方 | 条款从正文移除，索引条目标记为已废弃，在索引的废弃登记表写明时间与原因 |
| 合并 | 两条规范覆盖同一件事 | 保留适用面更广的一条，另一条移除并在索引写明合并去向 |

## 2. 覆盖前留档

规范文件被改写或拆分之前，把原文件复制到当次任务的输出目录留档，命名格式为：

```
规则文件名_v{序号}_{日期}.md
```

复制后核对源文件与副本的校验值一致，再动原文件。`Rules/` 目录未纳入 git，其中的文件被覆盖后无法靠版本管理复原，留档是本目录唯一的历史凭证。

## 3. 禁止动作

* 禁止在未留档的情况下覆盖规范文件；
* 禁止直接删除规范文件，废弃只改索引状态与移除条款，文件本身保留；
* 禁止把同一规则同时写进两份规范文件；
* 禁止智能体自行修改自身权限类条款，该类修订必须有用户明确授权，见《任务执行规范》§四.1。

# 五、条款写法

## 1. 条款必备信息

一条可执行的规范条款写清四项：

| 项 | 说明 |
| --- | --- |
| 约束 | 必须做什么、禁止做什么 |
| 适用面 | 在什么条件下生效 |
| 判据 | 怎么算做到了 |
| 越界处置 | 做不到时怎么办 |

四项中「判据」最容易缺。缺了判据的条款在验收时无法核对，等于没有约束。

## 2. 写法要求

* 用肯定式陈述。禁止类条款直接写「禁止做某事」，不用「不建议」「尽量避免」这类软化措辞；
* 用「必须 / 应该 / 可以」区分强制程度，含义与《文档编辑规范》§四.4 一致；
* 条款脱离起草时的临时上下文仍然可以独立理解。不出现「上一条说的那种情况」「本次任务中提到的」这类依赖上下文的指代；
* 举例只用于说明，不作为条款本体。条款本体要能覆盖同类情形；
* 一条条款只约束一件事。一件事需要多条约束时拆成多个条款，不写成一段长句。

## 3. 来源标注

条款不写来源任务编号，来源留在索引的条目与任务报告中。原因是正文需要长期稳定可读，任务编号与裁定编号属于过程信息。

例外：条款的依据是库内某条设计决策（`Design/00-总览/03_设计决策记录.md` 中的决策编号）时，登记到索引的条目里，便于回溯裁定。

# 六、与任务流程的对接

## 1. 规范变更类任务

任务属性中要求新增或修订规范的，在任务书的「工作方法」一节写明：待落盘的规范内容、来源裁定或指令、预期落点。任务执行时按第三章的七步流程处理，并在任务报告的文件变更列表中单列规范目录的改动。

## 2. 任务执行中发现规范不适用

任务执行中发现某条规范与任务书冲突，或规范本身存在歧义时，不得自行绕过：

1. 按《任务执行规范》§五上报，评定等级；
2. 在任务报告中登记为遗留问题；
3. 取得裁定后按第三章流程写入规范，或按第四章废弃条款。

冲突当下的执行顺序按《规范总则》的优先级判定，不按「哪条更方便」判定。

## 3. 规范变更后的同步

规范条款被修订后，检查三处是否需要同步：

| 检查对象 | 检查内容 |
| --- | --- |
| 规范索引 | 条目的适用场景、触发信号、更新日期 |
| 规范正文 | 引用该条款的其他条款是否仍然指向正确的章节号 |
| 目录 README | 承载该规则的目录 README 是否留有重复副本 |

# 七、审计要求

## 1. 变更登记

每次规范目录的写入动作在任务报告中登记，内容为：改动文件、改动类型、来源依据、影响面。

## 2. 索引与正文一致

索引登记完成后核对一次：索引列出的每个权威文件都存在，正文里的每个规范文件都在索引中有条目。两处数量不一致时以正文为准补齐索引。

## 3. 定期比对

规范目录与外部来源定期比对一次，比对对象为登记在索引「外部来源」一节的规范。外部来源发生变化而本目录未跟进时，在索引条目上标注待同步，并在下一次规范变更类任务中处理。
