# 一、文档库类型

工作区的文档分五类，组织规则各不相同。

| 类型 | 目录 | 性质 | 组织依据 |
| --- | --- | --- | --- |
| 设计文档库 | `系统设计文档/` | 全局、持续维护、跨任务共享的系统 wiki | 本规范第二章至第五章 |
| 架构设计案库 | `架构设计文档/` | 全篇一份、持续维护的全局程序结构规格 | 本规范第八章；编制规则见《架构设计案编辑规范》 |
| 代码设计案库 | `Code_Design/` | 按功能与模块组织、持续维护的现有代码解释文档 | 本规范第七章；编制规则见《代码设计案编辑规范》 |
| 任务过程库 | `Output/{任务编号}/` | 一次性的过程产物，任务结束即冻结 | 本规范第六章 |
| 报告库 | `Report/` | 每份任务书对应唯一报告 | 本规范第六章 |

三个长期维护的库分工：

| 库 | 承载 |
| --- | --- |
| 设计文档库 | 系统做什么、系统间如何交互 |
| 架构设计案库 | 程序整体由什么组成、如何连接、如何依赖 |
| 代码设计案库 | 现有代码的功能目的、主要过程、协作、结果与行为边界 |

系统与架构库维护设计定义；代码设计案库依据现有源码形成解释视图，不另立实现定义。源码依据见《代码设计案编辑规范》第十二章，架构对照关系见《架构设计案编辑规范》第六章。

`Task/` 下任务书的放置与命名见《任务执行规范》§二.3.1。

# 二、设计文档库的分层

设计文档库按四层组织，每一层承担一种职责。

```
系统设计文档/
├── README.md              库定位、分层说明与实例清单，不是规则的落点
├── _模板/                 统一模板
├── 00-总览/               域目录：库级全局文档
├── {域编号}-{域名}/        域目录
│   └── {系统编号}-{系统名}/  系统目录
│       ├── {子系统编号}-{子系统名}/  子系统目录
│       └── {系统编号}_{系统名}{文档类型}.md
└── ...
```

| 层 | 形态 | 职责 | 组织依据 |
| --- | --- | --- | --- |
| 域目录 | `{域编号}-{域名}` | 按独特系统、通用系统、局外系统、支撑系统归并的系统域，编号即稳定排序 | 第二章第 1 节 |
| 系统目录 | 域内 `10`、`20`、`30`…… | 一个系统一个目录，为该系统的后续多文档扩展预留空间 | 第二章第 2 节 |
| 子系统目录 | 系统内 `{系统编号}-{序号}` | 子系统在设计上从属于宿主系统、两者设计不可分割时使用 | 第二章第 3 节 |
| 文档 | `{序号}_{名称}{文档类型}.md` | 每系统当前一张主设计文档，后续可拆分子文档放在系统目录内 | 第二章第 4 节 |

## 1. 域目录

域目录的编号是两位数字 `00` 至 `99`。其中 `0X` 只是单位数时的补零对齐，`00` 保留给库级总览文档。第 10 个及以后的域直接使用 `10`、`11`……，词典序天然正确，`09` 排在 `10` 之前。

域可以使用补零编号，原因是域数量少、新域只会追加在末尾，不存在在两个域之间插入新域的需求，因此不需要为中段插入预留编号空间。

已停用的域编号不复用，避免与已失效的旧域指向混淆。停用登记在库级 README 与设计决策记录中。

## 2. 系统目录

系统目录的编号是域内的两位数字，以 `10`、`20`……`90` 为锚点，共 9 个锚点。

新增系统插在相邻锚点之间取中值，例如 `15`、`25`，避免整域重编号。

系统不使用 `0X` 连续编号，原因是 `01` 与 `02` 之间没有任何整数插入位，插入新系统必然引发整域重编号与全库引用更新。锚点编号把插入成本降为取一个中值，不波及既有系统。

已停用的系统编号不复用。

## 3. 子系统目录

子系统目录写 `{系统编号}-{系统内序号}`，例如 `30-10-触发条件`。

子系统目录的使用条件是：子系统在设计上从属于宿主系统，两者设计不可分割。不满足该条件的内容应当独立成立系统，不建子系统目录。

## 4. 文档

每个系统当前一张主设计文档。后续可以拆分出子文档，例如规则表、界面规范，放在该系统目录内。

每份文档都需要元信息表，七项字段与状态取值见《文档编辑规范》§三。

## 5. 扩展配置表

扩展配置表写 `{序号}_{表名}.csv`，放在所属系统目录内。

使用条件是同时满足两项：枚举会持续增长，且被多个系统共同引用。不满足的内容不建表，写在设计文档正文内。

建表契约三项：

1. 表内以 ID 标识每条记录；
2. 保留一条「待补充」记录，声明扩展契约；
3. 新增条目时同步登记到所属系统的设计文档。

当前全部实例登记在设计库 README 第二节。

## 6. 界面与交互规格的归属

界面与操作规格不单独成立章节，由各系统设计文档承接本系统的界面与操作。

跨系统的全局交互规范由 `系统设计文档/00-总览/01_设计原则与跨系统交互逻辑.md` 维护。

# 三、命名与版本控制

## 1. 命名式样

| 对象 | 式样 | 例 |
| --- | --- | --- |
| 域目录 | `{域编号}-{域名}` | `06-战斗` |
| 系统目录 | `{系统编号}-{系统名}` | `10-战斗总览` |
| 子系统目录 | `{系统编号}-{系统内序号}-{子系统名}` | `30-10-触发条件` |
| 设计文档 | `{序号}_{名称}{文档类型}.md` | `10_战斗总览设计.md` |
| 扩展配置表 | `{序号}_{表名}.csv` | `10_角色属性表.csv` |

## 2. 不带版本号

文件名、文档标题与元信息表一律不带版本号。

设计文档库采用 git 版本控制，修订历史、修订原因与历史版本全部由提交记录承载。库内不保留归档文件，不在文档内登记版本号与更改历史。

该条与《文档编辑规范》§二.2 的修订规则一致：修订直接在原文件上进行。

## 3. 系统编号扩容

域内系统数达到 10 个时，按下列顺序处置：

1. 优先拆分该域。10 个系统挤在一个域是复杂度过高的信号；
2. 不拆分时，整域重编号为三位补零，即 `010`、`020`……`100`，保证字典序等于数字序。

禁止两位与三位混排：混排时 `100` 会排在 `90` 之前，排序失效。

三位编号仍不足以容纳时，按上一条的同一原理继续扩展位数，保持全库同一域内位数一致。

## 4. 编号停用

域编号与系统编号一经停用即不复用。停用的编号保持空缺，不填补新内容，避免既有引用指向错误对象。

# 四、术语与引用

## 1. 唯一术语来源

`系统设计文档/00-总览/02_术语表.md` 是全库术语的权威清单。同一概念只使用一个标准术语，禁止同义词、别名与缩写混用。新术语必须先登记入表，再用于各系统文档。

## 2. 定义优先级

术语的定义以文档正文为准。正文已有定义的，术语表只做一句话概括并标注概念来源，即首次给出定义的文档与章节；正文没有定义的，才由术语表补充一句话定义，并标注「定义来源：术语表补充」。

## 3. 引用标注

凡跨文档、跨章节引用，或某术语在当前处出现而其定义在别处时，必须在引用处加注术语表编号，写作 `术语名（术语表 T-XXX）`。

## 4. 反向可追溯

术语表条目必须标明概念来源并给出一句话简介，使任意引用点都能回溯到定义处。

## 5. 撤销术语的处置

术语被撤销或更名后，其编号不复用；全库一律使用标准术语，指向旧表述的引用直接改写为标准术语或其所指的对象。

## 6. 允许的简称

仅当术语表条目显式标注「文档中可简称」时，正文才可使用该简称，且须在同一文档内标准术语首次出现之后使用。未标注的写法一律改为标准术语。

## 7. 文档引用的边界

三个长期维护的设计库（`系统设计文档/`、`架构设计文档/`、`Code_Design/`）按设计约束与实现解释区分：系统设计文档 → 架构设计案提供设计背景，现有源码 → 代码设计案提供实现事实。库内文档的引用必须落在下面的圈层之内。

| 库 | 允许引用 | 禁止引用 |
| --- | --- | --- |
| `系统设计文档/` | 本库文档（含 `00-总览/` 的库级文档与扩展配置表） | `架构设计文档/`、`Code_Design/`、过程文档目录 |
| `架构设计文档/` | `系统设计文档/`、本库文档（架构设计案与界面索引） | `Code_Design/`、过程文档目录 |
| `Code_Design/` | `系统设计文档/`、`架构设计文档/`、本库文档、实际源码及必要工程文件 | 过程文档目录 |

**过程文档目录**指 `Task/`、`Output/`、`Report/`、`Input/`、`Tool/`，以及已停用的旧目录前缀。禁止引用它们，原因是过程文档是一次性产物、按《任务执行规范》第六章冻结或按第六章第 3 节归档，以其为引用对象会使设计文档依赖一份可以失效的文件。

术语表编号、库内相对路径、上游章节号与创意需求文档的章节号不受本表约束，可以照常书写。

引用边界约束设计定义的依赖方向。`Code_Design/` 允许引用实际源码及必要工程配置、场景和资产作为实现依据，按《代码设计案编辑规范》第十二章登记。程序类型、包和引擎机制可以引用核实过的官方技术资料，不因资料位于外部网站而将其视为内部过程文档；游戏规则来源的库边界不因此改变。

## 8. 过程编号不进设计文档

任务编号（`C-01-10-01` 一类）、规范文件名与编号（`NR-xx`）、裁定编号（`S01`、`S02`、`R01` 一类）、问答轮次标记（`回答 N`、`第一轮` 一类）与缺口编号（`SMP-GAP-nn`、`ARC-GAP-nn`、`ENG-GAP-nn` 一类）都属于过程信息，只落在 `Task/`、`Output/`、`Report/` 与 `Rules/` 内，**不得写进三个设计库的正文、元信息表或台账**。

两处例外，其一是缺口条目，其二是术语表条目对库内既有条目的承接说明；两处登记的是现行结论与承接方，不是过程痕迹。

判据：设计库文档中出现上述任一编号即判为违例，包括写在「设计依据」「依据」「设计依据节」等出处栏内的写法。

## 9. 越界引用的处置

发现越界引用时按下述两步处置，不得只删引用、留下语义缺口。

1. **判定被引内容是否已被现版本正文覆盖。** 已被覆盖的，直接删除该引用；未被覆盖的，进入第 2 步。
2. **把被引内容的实质归纳后搬入引用位置。** 按《文档编辑规范》第四章第 1 节的写法，把该内容总结为当前状态的陈述写入本处；归纳后必须能独立理解，不保留对原载体的指路。

越界引用清空后，原位置不得留空括号、孤立标点或断句。**引用不可用时正文仍应完备**是本节唯一的验收标准：删除越界引用后，读者只读本库文档即可得到完整设计。

# 五、台账与维护流程

设计文档库有四处库级台账，一次任务改动设计内容时按本章同步更新。台账的落点与职责：

| 台账 | 路径 | 登记内容 |
| --- | --- | --- |
| 系统全景图 | `系统设计文档/00-总览/00_系统全景图.md` | 全量系统清单、系统关系、各系统状态列、后续版本路线 |
| 设计原则与跨系统交互逻辑 | `系统设计文档/00-总览/01_设计原则与跨系统交互逻辑.md` | 跨系统的关键交互逻辑与全局设计原则 |
| 术语表 | `系统设计文档/00-总览/02_术语表.md` | 术语的权威清单、概念来源、定义来源与停用术语 |
| 设计决策记录 | 上游设计稿与架构设计案 | 重大取舍：做、不做、砍掉、悬置（含到期日） |

## 1. 维护流程八条

1. 每次任务只在其任务书授权的系统范围内新建或修订文档；
2. 修订文档前先读现行文档与对应索引，修订直接在原文件上进行，历史由 git 提交承载，不另存历史版本、不保留归档副本；
3. 同步更新所属域索引与系统全景图中的状态列；
4. 跨系统的交互逻辑与设计原则变更，同步登记到设计原则与跨系统交互逻辑；
5. 新术语写入术语表，并按第四章维护编号、概念来源与定义来源；
6. 重大取舍登记到设计决策记录。「不做」与「砍掉」记录理由与复活条件，「悬置」记录到期日；
7. 任务的过程性产出放 `Output/{任务编号}/`，设计文档库只存放长期维护的设计文档；
8. 设计文档库只承载系统级设计，即各系统做什么、系统间如何交互。属性定义、数值规格与代码实现落地细节不属于本阶段讨论内容，禁止写入文档正文与待设计清单。

## 2. 台账的写法

四处台账的体裁是记录，按各自体裁写，不受《文档编辑规范》§四.8 只陈述当前状态的约束。具体边界：

| 台账 | 写法 |
| --- | --- |
| 设计决策记录 | 裁定栏取库内既有取值，即定案、砍掉、不做、撤销与悬置；理由栏写这条决策为什么这样定 |
| 系统全景图 | 状态列按任务改动同步，跨域关注点保留决策轮次标注 |
| 设计原则与跨系统交互逻辑 | 逐条正向陈述当前规则，不写沿革 |

# 六、过程文档的组织

## 1. 任务过程库

任务的过程性产物放在 `Output/{任务编号}/` 内，一个任务一个子目录。

任务结束即冻结：后续任务不修改其他任务的过程文件，需要引用时在本任务输出目录内建立副本。

## 2. 命名与版本

过程文档的命名按《任务执行规范》§二.3.2 执行。

过程文档可以带版本号，与设计文档库不带版本号的规则不同。原因是过程文档的版本号标识的是**并列交付物**，同一任务的不同轮次产出同时存在、各自独立，不是同一份文件的历史版本。

## 3. 归档子目录

任务内自行产生、不再进入后续流程的中间文件，放在任务输出目录内的归档子目录下，由任务报告登记。工作区不设全局归档目录。

## 4. 报告

任务报告放在 `Report/` 下，文件名与任务书一致，结构按《任务执行规范》第六章。

# 七、代码设计案库的组织

代码设计案库位于 `Code_Design/`，内容、交付与验收按《代码设计案编辑规范》执行。本章规定目录、命名与索引。

## 1. 目录结构

`Code_Design/README.md` 为库索引，正文按实际程序集、相关类或功能域组织。解释对象、结构归属和拆分后的阅读要求按《代码设计案编辑规范》第三章执行，不强制按类型拆文件。

需要增加层级时按程序集或功能范围建立子目录。总览承载范围与阅读入口，专题文档承载实际结构与功能解释；不要求每模块建立固定名称的 Types、Contracts 目录。

## 2. 命名

文件名使用 `{编号}_{功能名}代码设计案.md`，既有有效编号可沿用。同目录同名时增加明确的范围限定。文件名、标题与元信息不带历史版本号，历史由 git 承载。

## 3. 索引与状态

库索引至少登记解释对象或功能名称、覆盖的程序集与主要类、说明文件、关键源码位置、核对基线、文档状态与更新日期。状态含义见《代码设计案编辑规范》第十四章，完成判据见第十五章。

新增、拆分、改名、停用、源码位置改变或状态改变时同步索引。一个功能的主要说明位置应明确，其他位置引用它，避免重复维护。

## 4. 与系统及源码的关系

玩法系统、解释文档与源码允许多对多对应。系统编号用于定位规则背景，模块归属用于说明协作，源码位置用于核对当前实现。解释文档不承担类型、接口或共享契约的唯一声明职责。

## 5. 既有稿件与过渡

既有目录、文件名和状态在实际修订前据实保留；后续授权修订时按新定位核验并更新索引。旧实施稿不能自动视为已完成的代码解释文档；缺少源码依据时标明待核实，不凭旧稿推定功能已实现。

批量迁移、重命名或改写文档须在相应任务授权范围内执行。

# 八、架构设计案库的组织

架构设计案库位于 `架构设计文档/`，其内容规则见《架构设计案编辑规范》，本章只写组织规则。

## 1. 目录结构

架构设计案是全篇一份的全局文档，不按系统拆分：

```
架构设计文档/
├── README.md              库定位、清单与当前状态，不是规则的落点
└── 架构设计案.md
```

需要按主题拆成多份时，在库 README 中登记主文档与子文档的关系，主文档保留全局章节，子文档只承载被拆出的主题。

库当前为空，架构设计案开始编制时建立本目录。

## 2. 命名

主文档命名为 `架构设计案.md`；拆分的子文档命名为 `{主题}架构设计案.md`，例如 `数据架构设计案.md`。

文件名、文档标题与元信息表一律不带版本号，历史由 git 提交记录承载。

## 3. 与两个相邻库的关系

| 关系 | 说明 |
| --- | --- |
| 上游 | 架构设计案以 `系统设计文档/` 的系统设计稿为依据，引用其中的系统名与系统编号 |
| 实现解释 | `Code_Design/` 以架构为对照背景，忠于源码并登记差异 |

架构设计案引用的系统名与系统编号沿用 `系统设计文档/` 的定义。架构的模块划分与设计库的域划分是两个不同维度，两者的对应关系写在架构设计案第 2 章的模块划分表中，不改变系统在设计库中的编号与归属域。

## 4. 索引与状态

架构设计案是单份文档，无需按系统建立索引。库 README 登记本库的文档清单、状态与覆盖范围。

主文档拆分为多份时，库 README 同时登记子文档清单与各自的覆盖主题。
