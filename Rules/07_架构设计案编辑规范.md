# 一、定位与边界

## 1. 一句话定位

**架构设计案 = 游戏程序整体结构与全局技术约束的规格。**

它规定程序整体由哪些部分组成、各部分负责什么、各部分如何连接、依赖方向是什么，以及系统必须遵守哪些全局技术规则，以保证各个具体游戏系统能够在统一的软件结构下被实现、组合、运行和维护。

## 2. 边界压缩成一句话

**架构设计案描述「程序作为一个整体如何成立」，不描述「某一个游戏系统具体怎么实现」。**

## 3. 职责八类

| # | 职责 | 回答什么 |
| --- | --- | --- |
| 1 | 程序总体分层 | 项目采用什么样的整体程序组织方式 |
| 2 | 模块与系统划分 | 哪些系统属于哪一层、哪个模块，各模块承担什么职责 |
| 3 | 依赖方向 | 谁可以依赖谁，谁不能依赖谁 |
| 4 | 通信机制 | 系统之间通过什么方式沟通 |
| 5 | 全局生命周期 | 什么时候初始化、创建、销毁，哪些对象跨场景存在 |
| 6 | 数据的整体组织方式 | 数据总体怎么分类、怎么流动、谁拥有 |
| 7 | 基础设施 | 多个游戏系统共同依赖的基础设施由谁统一提供 |
| 8 | 全局技术约束 | 整个项目必须遵守哪些统一规则 |

## 4. 核心问题六问

只要某个问题属于「整个项目都需要遵守」，它就适合进入架构设计案。

1. 程序由什么组成？
2. 每一部分负责什么？
3. 部分之间允许怎样依赖？
4. 它们通过什么方式通信？
5. 数据在程序中如何流动和持久化？
6. 整个项目必须遵守哪些统一规则？

## 5. 与代码设计案的最本质区别

| 文档 | 解决的问题 |
| --- | --- |
| 架构设计案 | 系统之间怎么组成一台机器 |
| 代码设计案 | 这台机器中的某一个部件具体需要具备什么 |

举例说明这一区别：

| 内容 | 归属 |
| --- | --- |
| 背包系统需要调用存档接口 | 代码设计案 |
| 所有 Gameplay 系统只能通过 Save 层提供的统一持久化接口访问存档 | 架构设计案 |
| 传闻系统提供 `InvestigateRumor()` | 代码设计案 |
| 同步状态查询使用接口，命令使用服务调用，跨多个系统的状态广播使用事件 | 架构设计案 |
| `RumorProgress` 保存某条传闻的运行状态 | 代码设计案 |
| 所有运行时进度统一归属于玩家进度数据域，并由统一的持久化机制负责保存 | 架构设计案 |

## 6. 为什么单独编写

架构设计案解决的是一个实际问题：**避免几十个系统各自正确，但组合起来错误。**

典型情形是每个系统单独设计都没有问题，但传闻系统认为线索系统可以直接读取它的内部数据，线索系统认为剧情系统可以直接修改线索状态，剧情系统认为存档系统负责保存整个 Gameplay 对象，存档系统又认为每个系统自己提供存档数据，最后形成大量交叉依赖。

架构设计案的作用是在具体代码设计开始之前把这些全局规则定下。

## 7. 三个实际用途

| # | 用途 | 说明 |
| --- | --- | --- |
| 1 | 作为所有代码设计案的上级约束 | 代码设计案服从架构设计案。架构规定 UI 不得直接修改游戏逻辑，背包系统代码设计案就不能设计出经 UI 反向控制背包的结构 |
| 2 | 指导系统之间的组合 | 开发新系统时先检查它属于哪一层、应该依赖谁、谁可以依赖它、使用哪种通信方式、生命周期是什么、使用哪种数据管理机制 |
| 3 | 控制项目长期复杂度 | 真正的架构问题通常不是某个函数写错了，而是某个系统正在逐渐承担不属于它的责任。代码仍然能运行，但架构已经腐化 |

# 二、适用判据

## 1. 归属判断法

判断一项内容该放哪份文档，用下列五问：

| 内容在回答 | 归属 |
| --- | --- |
| 玩家应该经历什么 | 系统设计稿 |
| 整个程序应该怎样组织 | 架构设计案 |
| 这个具体系统为了实现要求，需要哪些程序实体和接口 | 代码设计案 |
| 这个接口内部具体按照什么步骤执行 | 伪代码 |
| 用什么具体代码技术实现 | 实际代码与技术实现 |

## 2. 全局规则的判据

一项规则满足下列任一条时属于架构设计案：

1. 它对全部模块或全部系统成立；
2. 它约束的是模块之间或系统之间的关系，而不是某个系统内部；
3. 它规定了某项能力必须统一经过同一入口；
4. 它规定了对象的生命周期或数据的归属与流动；
5. 违反它不会让某个系统出错，但会让整个程序的结构腐化。

## 3. 完成判据

一份架构设计案完成后，应当能够回答：

> 一名程序员拿到它，可以判断任意一个新系统属于哪一层、应该依赖谁、谁可以依赖它、使用哪种通信方式、生命周期是什么、数据放在哪里，并且不需要回头猜测全局规则。

# 三、应该规定什么

## 1. 程序总体分层

明确项目采用什么样的整体程序组织方式。

分层可以取例如「表现层 → 游戏逻辑层 → 领域与系统层 → 数据层 → 基础设施层」这样的形态，具体层数与命名按项目实际确定。

分层本身不是目的，需要写清的是每一层的职责与层与层之间的允许关系。

## 2. 模块与系统划分

规定模块清单，以及哪些系统属于哪一层、哪个模块。

模块划分的粒度是**划分边界**，写到「哪些系统属于哪个模块、该模块承担什么职责」为止，不写某个系统内部有哪些函数。

## 3. 依赖方向

这是架构设计案最重要的职能之一。逐条写明：

1. 允许的依赖方向，例如模块 A 可以依赖模块 B；
2. 禁止的依赖方向，例如 UI 不得直接修改游戏逻辑数据、游戏逻辑不得依赖具体界面实现、底层基础设施不得依赖具体剧情系统。

禁止的依赖必须逐条列出。只写允许的依赖不足以防止结构腐化，因为允许清单无法穷尽错误组合。

## 4. 通信机制

系统之间如何沟通，在架构层确定。可用的通信方式分类：

| 方式 | 适用 | 例 |
| --- | --- | --- |
| 直接调用 | 明确的命令关系 | 背包系统调用物品服务 |
| 查询 | 读取另一方状态 | 条件系统查询玩家状态 |
| 事件 | 状态广播给多个接收者 | 传闻系统发出发现事件，界面、任务与成就系统接收 |
| 数据共享 | 双方约定共同读取同一数据 | 按数据所有权规则约定 |

并规定通信选择规则，例如同步状态查询使用接口、命令使用服务调用、跨多个系统的状态广播使用事件。

通信模式属于架构设计案。某个系统提供哪些具体接口属于代码设计案。

## 5. 全局生命周期

| 项 | 写明 |
| --- | --- |
| 程序生命周期 | 程序启动、初始化、进入场景、退出与销毁的顺序 |
| 场景生命周期 | 场景创建、切换与销毁时各部分的处理 |
| 系统初始化 | 初始化顺序，以及初始化顺序的依据 |
| 系统销毁 | 销毁顺序与资源释放职责 |
| 对象分类 | 常驻对象、场景对象、临时运行对象、存档对象、静态配置对象 |
| 对象约束 | 哪些对象跨场景存在，哪些对象允许创建多个实例，哪些数据在启动时加载，哪些按需加载 |

## 6. 数据的整体组织方式

数据的总体分类、流动与归属属于架构设计案，某个系统的字段清单属于代码设计案。

按三类划分并写明各自的来源、生命周期与持久化归属：

| 类别 | 说明 |
| --- | --- |
| 静态数据 | 配置与定义 |
| 运行时数据 | 游戏状态 |
| 持久化数据 | 存档数据 |

写明数据所有权：每类数据由哪一层、哪个模块拥有，其他模块以何种方式访问。

## 7. 基础设施

多个游戏系统共同依赖的基础设施，统一在架构层确定。典型的候选：

输入系统、事件总线、资源管理、场景管理、存档框架、配置管理、日志系统、时间系统、随机数系统、异步任务机制、对象生命周期管理。

每一项写明：它提供什么能力、谁负责实现、其他模块以什么方式使用、是否允许绕过。

统一入口类是典型架构约束，例如所有系统不得自行写文件而必须经过统一的存档服务，所有资源请求必须经过统一的资源服务。

具体的第三方技术选型可以留到实际技术方案，但「程序需要统一经过某个基础设施」这一条属于架构约束。

## 8. 接口在架构层的落点

架构设计案不定义单个系统的全部接口，但下列三类接口需要在架构层出现：

| 类别 | 为什么在架构层 | 写到什么程度 |
| --- | --- | --- |
| 基础设施的对外接口 | 多个模块共同使用，接口形态决定全局耦合 | 写明能力、约定与调用约束，不写逐参数契约 |
| 跨模块的服务接口 | 架构约束要求某类调用必须经过服务层 | 写明服务的存在、职责与使用规则，逐项契约由代码设计案给出 |
| 跨系统事件的契约 | 事件的发送方与接收方分属不同模块 | 写明事件的语义与收发规则，载荷结构由代码设计案给出 |

除这三类之外，接口的逐项契约由代码设计案给出。

## 9. 全局技术约束

逐类写明整个项目必须遵守的统一规则：

| 类别 | 内容 |
| --- | --- |
| 依赖方向规则 | 允许与禁止的依赖 |
| 数据访问规则 | 谁可以读写哪类数据，修改他方数据必须经过什么 |
| 生命周期规则 | 对象的创建、存续与销毁约束 |
| 通信规则 | 什么场景用哪种通信方式 |
| 扩展规则 | 新增系统、新增数据、新增事件时应当遵循的接入方式 |

## 10. 模块单元写法

第 3 章描述模块时，每个模块写成固定字段的单元：

```
ARC-INV-001 InventoryService

职责：
负责所有背包业务操作。

负责：
- 添加物品
- 删除物品
- 移动物品
- 堆叠计算

不负责：
- 界面显示
- 数据持久化
- 物品静态数据加载

依赖：
ItemRepository
InventoryModel

对外接口：
AddItem()
RemoveItem()
MoveItem()

事件：
InventoryChanged

生命周期：
由 GameContext 创建，游戏会话期间持续存在。
```

「不负责什么」这一反向边界与「负责什么」同等重要。缺了它，职责会持续漂移，最终所有东西都进入一个模块。

本单元写法描述模块这一层的职责与边界。单元中「对外接口」一栏登记的是模块对外暴露的能力名，用于说明模块之间如何通信；这些能力内部的逐项契约属于代码设计案。

## 11. 与系统设计稿的区别

系统设计稿写「玩家拾取后物品进入背包」，描述游戏规则。架构设计案写「由 PickupService 调用 InventoryService 完成物品转移」，描述软件职责。

架构层可以出现 `interface`、`event`、`delegate`、`command`、`service`、`repository`、`factory` 这类概念，因为它们属于软件结构而不是游戏规则。架构层不写具体业务代码，只写模块提供了什么能力、这些能力受哪些约束、成功后产生什么事件。

# 四、不应该规定什么

| # | 禁止项 | 判据 | 应当写在架构层的内容 |
| --- | --- | --- | --- |
| 1 | 详细描述游戏规则 | 出现「收集三个线索后解锁某剧情节点」这类玩家规则 | 剧情系统可以读取或订阅进度变化，并通过统一条件机制判断解锁状态 |
| 2 | 定义单个系统的全部接口 | 出现某系统的完整接口清单 | 该系统作为某模块的一部分，对外通过公开服务接口提供功能。具体有哪些接口交给代码设计案 |
| 3 | 描述具体算法 | 出现遍历、深度优先搜索这类执行步骤 | 该项判定为伪代码设计的内容 |
| 4 | 过早规定具体代码形式 | 出现类声明、容器类型等语言层面选择 | 只有当该选择本身是全局架构要求时才写，例如所有运行时系统对象不得继承引擎的场景对象基类。这类全局约束可以写 |
| 5 | 写某一系统的内部字段 | 出现某系统的实体字段列表 | 该系统的数据定义交给代码设计案 |

第 4 项的判据是「这个选择是否对全部系统成立」。对全部系统成立的是架构约束，只对某一个系统成立的是实现选择。

## 1. 第 1 章 文档定义

写明这份架构设计案的目的、适用范围，以及它与系统设计稿、代码设计案、伪代码的关系。

适用范围要写清本架构覆盖哪些系统与哪些技术边界，未覆盖的部分标明由谁承接。

## 2. 第 2 章 总体程序架构

| 小节 | 写明 |
| --- | --- |
| 整体分层 | 层清单、每层职责、层间允许关系 |
| 模块划分 | 模块清单、每个模块包含哪些系统 |
| 核心运行时组成 | 程序运行时由哪些常驻部分组成，各自的作用 |

## 3. 第 3 章 模块与系统边界

| 小节 | 写明 |
| --- | --- |
| 各模块职责 | 每个模块负责什么、不负责什么 |
| 模块所有权 | 每个模块拥有哪些系统、哪些数据 |
| 模块之间允许的依赖 | 逐条列出允许的依赖方向 |
| 禁止的依赖 | 逐条列出禁止的依赖方向与理由 |

## 4. 第 4 章 系统通信机制

按四种方式分节，并在最后一节给出通信选择规则。每种方式写明适用场景、写法与约束。

## 5. 第 5 章 数据架构

按静态、运行时、持久化三类分节，再写数据所有权与数据流向。数据所有权要写到「哪类数据由哪个模块拥有、其他模块以什么方式访问」，逐字段的定义属于代码设计案。

## 6. 第 6 章 生命周期

按程序、场景、初始化、销毁、常驻对象分节。初始化与销毁要写明顺序以及顺序的依据。

## 7. 第 7 章 基础设施

逐项写明本项基础设施提供什么能力、由哪个模块实现、其他模块如何使用、是否允许绕过。项目未采用的基础设施写「本项不单独设立」并说明由什么替代。

## 8. 第 8 章 全局技术约束

五类规则分节。第 8 章是代码设计案与伪代码的直接约束来源，写法要可直接核对，避免口号式表述。

## 9. 第 9 章 关键全局流程

逐条流程写明触发、参与模块、调用顺序、状态变化、产生的事件与结束条件。全局流程写到模块与接口调用一级，不写接口内部的执行步骤。

## 10. 第 10 章 架构约束检查

以核对清单形式给出，供每个新增或修订的系统在进入代码设计前自查：

```
[ ] 是否产生跨层依赖？
[ ] 是否产生循环依赖？
[ ] 是否绕过统一存档系统？
[ ] 是否直接修改其他系统的内部状态？
[ ] 是否违反对象生命周期规则？
[ ] 是否创建了重复的基础设施？
```

清单可以按项目实际扩充，但不得删减上述六项。

# 六、与代码设计案的分工

## 1. 上游依赖关系

| 文档 | 决定 |
| --- | --- |
| 架构设计案 | 代码设计案能够怎样设计 |
| 代码设计案 | 伪代码能够怎样编写 |

举例说明三层如何衔接：

**架构设计案规定：**

```
Gameplay 系统不得直接访问存档文件，必须通过 SaveService。
```

**传闻系统代码设计案规定：**

```
传闻系统：
依赖 SaveService.SaveProgress()
依赖 ClueService.UnlockClue()
依赖 ConditionService.Evaluate()
```

**伪代码再规定：**

```
InvestigateRumor()
    → Evaluate()
    → 更新自身状态
    → UnlockClue()
    → SaveProgress()
```

每一层都有明确的输入来源，下一层不重新发明上一层已经确定的东西。

## 2. 代码设计案的服从要求

代码设计案必须服从架构设计案。架构规定 UI 不得直接修改游戏逻辑时，背包系统的代码设计案不得设计出经界面反向控制背包的结构。

## 3. 冲突处置

代码设计案与架构设计案冲突时，按《规范总则》§三 的优先级与《规范目录维护规范》§六.2 上报，不得自行选择更方便执行的一条。

冲突的三种合法出路：

1. 修订代码设计案使其符合架构；
2. 确有必要时修订架构设计案，并在设计决策记录中登记该取舍；
3. 上报由用户裁定。

## 4. 覆盖检查

架构设计案存在后，核对全部代码设计案是否落在架构允许的结构内。核对项：

| # | 核对项 |
| --- | --- |
| 1 | 每个代码设计案的所属模块与层级在架构中有定义 |
| 2 | 每个代码设计案的对外依赖符合架构允许的依赖方向 |
| 3 | 每个代码设计案未使用架构禁止的依赖 |
| 4 | 每个代码设计案的持久化行为经过架构规定的统一入口 |
| 5 | 每个代码设计案引用的基础设施在架构中有定义 |
| 6 | 每个代码设计案引用的跨模块事件在架构中有登记 |

# 七、验收标准

## 1. 架构完备性

一份架构设计案只有满足下列条件才算完成：

> 读者读取后，可以明确知道：
>
> 程序由哪些层与模块组成；
> 每一层与每个模块负责什么、不负责什么；
> 模块之间允许怎样依赖，禁止怎样依赖；
> 系统之间通过什么方式通信，什么情况用哪种方式；
> 数据分几类、由谁拥有、如何流动、由谁持久化；
> 对象与系统的生命周期顺序；
> 有哪些统一的基础设施，以及是否允许绕过；
> 整个项目必须遵守哪些统一规则；
> 新增一个系统时应当按什么步骤接入；
>
> 并且能够以此为依据，判断任意一个代码设计案是否落在允许的结构内。

## 2. 逐项核对

| # | 检查项 |
| --- | --- |
| 1 | 十章结构齐备，各节的必填字段无省略 |
| 2 | 禁止的依赖逐条列出，不只写允许的依赖 |
| 3 | 通信选择规则可直接判定，未停留在原则性表述 |
| 4 | 数据所有权写到模块级，未越界写字段 |
| 5 | 生命周期写明顺序与顺序依据 |
| 6 | 每项基础设施写明能力、实现方与是否允许绕过 |
| 7 | 全局技术约束可直接核对 |
| 8 | 第 10 章的六项检查齐备 |
| 9 | 未出现游戏规则、单系统接口清单、具体算法 |
| 10 | 出现具体代码形式时，能说明该选择为何对全部系统成立 |
| 11 | 引用的系统名与系统编号与 `系统设计文档/` 一致 |
| 12 | 与已定稿的代码设计案无冲突，或冲突已登记 |

# 八、文档组织

## 1. 目录与命名

架构设计案放在 `架构设计文档/` 下。全篇一份，不分系统，文件名为：

```
架构设计案.md
```

需要拆成多份时，按主题拆，例如「总体架构」「数据架构」「基础设施」，文件名写 `{主题}架构设计案.md`，并在库 README 中登记主文档与子文档的关系。

文件名、文档标题与元信息表一律不带版本号，历史由 git 提交记录承载。

## 2. 元信息表

每份架构设计案头部必须有元信息表：

| 项目 | 内容 |
| --- | --- |
| 文档名 | 架构设计案 |
| 覆盖范围 | 本架构覆盖的模块与系统范围 |
| 上游依据 | 系统设计稿的库路径与关键章节 |
| 下游文档 | 依本架构编制的代码设计案清单，随编制推进同步 |
| 状态 | 占位 / 草稿 / 评审中 / 定稿 |
| 关联文档 | 系统设计稿、代码设计案、伪代码 |
| 维护人 | 首席主策划 |
| 更新日期 | `yyyy-mm-dd` |

## 3. 状态取值

| 状态 | 含义 |
| --- | --- |
| 占位 | 章节骨架已建，内容待填充 |
| 草稿 | 内容已展开，未按第七章核对 |
| 评审中 | 已通过核对，提交评审 |
| 定稿 | 评审通过，可作为代码设计案的上级约束 |

## 4. 与代码设计案的对应

架构设计案是单份全局文档，代码设计案是每系统一份，两者不是一一对应关系。

架构设计案的第 3 章与第 8 章是代码设计案的直接约束来源，第 2 章的模块划分决定代码设计案的归属与依赖范围。

## 5. 落定后的同步

1. 架构设计案定稿后，回写 `系统设计文档/` 中受影响的系统设计文档的关联文档栏，标明架构设计案的位置；
2. 后续新增或修订代码设计案时，先核对是否符合架构，核对项见第六章第 4 节；
3. 架构发生变更时，逐份核对已定稿的代码设计案是否仍然落在允许的结构内，不满足的登记为待修订项。

## 6. 与 `系统设计文档/` 的一致性

架构设计案引用的系统名与系统编号必须与 `系统设计文档/` 一致。架构把一个系统划入某个模块时，不改动该系统在设计库中的编号与归属域：设计库的域是按玩法主题归并的系统域，架构的模块是按程序结构归并的模块，两者是不同维度的划分。两者的对应关系在第 2 章的模块划分表中写明。
