# 一、工作区目录边界

| 目录 | 职责 | 写入边界 |
| --- | --- | --- |
| `Task/` | 任务书 | 一个任务一份，文件名与任务编号一致 |
| `Report/` | 任务执行报告 | 每份任务书对应唯一报告，命名与任务书一致 |
| `Output/` | 任务过程性文件 | 按任务编号建独立子目录，与 `系统设计文档/` 的区别是本目录的产物是一次性的 |
| `系统设计文档/` | 全局设计文档库 | 跨任务共享、长期维护、持续生长的系统 wiki |
| `Rules/` | 规范目录 | 仅在规范变更类任务中写入 |
| `Input/` | 用户输入的原始材料 | 只读 |
| `Tool/` | 工具与说明 | 仅在任务书明确授权时写入 |

目录职责的可执行细则见《任务执行规范》§二.1。

# 二、文档体系总原则

## 1. 设计、实现与解释各有职责

文档与代码按六类材料区分。设计与实现形成约束关系，代码设计案依据现有代码形成解释视图：

| 类别 | 材料 | 回答的问题 |
| --- | --- | --- |
| 1 | 创意需求稿 | 为什么做 |
| 2 | 系统设计稿 | 游戏规则是什么 |
| 3 | 架构设计案 | 整个程序有哪些全局结构与协作约束 |
| 4 | 代码设计案 | 现有代码怎样组成和归属、服务什么功能目的、产生什么行为 |
| 5 | 伪代码 | 在已定结构与协议内，方法体按什么步骤执行 |
| 6 | 实际代码 | 如何落实为可编译、可运行并经验证的工程实现 |

系统设计和架构设计提供规则与全局结构约束，伪代码用于表达拟实施的执行逻辑，实际代码承担工程实现。代码设计案依据现有源码，用自然语言解释实际代码结构、功能与行为，不作为伪代码的前置规格。具体边界见《文档编辑规范》第七章。

设计材料以约束是否清楚为判据；代码解释文档以读者能否理解实际结构与归属、功能目的、主要过程和行为边界，以及内容是否忠于源码为判据。不得以篇幅或章节数量代替质量判断。

## 2. 上层定约束，下层定细节

**上层规定下层必须遵守的约束，下层自行决定不影响上层约束的实现细节。**

这条原则适用于设计与实施的约束关系；代码解释的事实责任按《代码设计案编辑规范》执行。设计与实施之间同时约束两个方向：下层不得重新定义上层的决定；上层不得提前替下层做完所有决定，否则下层失去调整空间。

## 3. 唯一事实来源

一条规则只在一个位置定义，其他位置引用。适用于三个层面：

| 层面 | 唯一来源 |
| --- | --- |
| 术语 | `系统设计文档/00-总览/02_术语表.md` |
| 跨系统交互逻辑 | `系统设计文档/00-总览/01_设计原则与跨系统交互逻辑.md` |
| 重大取舍 | 游戏规则取舍归对应系统设计稿，全局结构取舍归架构设计案，类型实现事实以现有源码为准，取舍依据在相应开发任务中记录 |
| 规范条款 | `Rules/` 下的对应规范文件 |

同一规则在两处各写一份，等同于两处都会随时间漂移，最终无法判断哪一份有效。

规范条款这一层的边界是：**本工作区的全部编辑规范以 `Rules/` 目录为唯一权威落点。** 其他目录内的文件不承载规范条款，只承载该目录自身的定位、实例清单与现状登记，需要引用规范时指向 `Rules/`。发现 `Rules/` 之外仍留有规范条款时，按《规范目录维护规范》第三章收编进本目录。

唯一事实来源规定定义与修改权的归属。代码设计案是实现的解释视图，源码依据和核对基线按《代码设计案编辑规范》第十二章登记；解释不取得代码定义权，源码变化后同步受影响的说明。

## 4. 保留未决

明确知道「这里还没决定」远比写一个未经思考的临时方案更有价值。禁止为了让文档看起来完整而强行补全待定问题。

## 5. 游戏规则、技术设计与规范的边界

智能体不得未经授权创造或改变游戏规则，不得把候选决定写成已确认的正式内容。

在已授权的技术设计范围内，执行者负责选择满足既有规则与架构约束的程序结构和技术方案，依据可以包括已知规则、官方技术资料与有说明的工程取舍。类拆分、字段、容器、签名和局部实现机制不要求由策划上游预先给出。

超出授权、改变游戏规则或与明确架构约束冲突的方案，按既有异常与冲突规则处置。规范正文的新增与采用按《规范目录维护规范》执行。

# 三、冲突优先级

## 1. 执行顺序

发生冲突时，按下列顺序执行：

```
1. 用户明确指令
2. 任务书授权
3. 规范目录（Rules/）
4. 目录内既有惯例
5. 智能体默认行为
```

任何低优先级规则不得覆盖高优先级要求。

## 2. 判定的三条附带规则

* **「明确」指当次有效**：用户此前的指令被后续指令取代时，以最新一条为准；任务书与用户指令冲突时，以用户当次指令为准，同时在任务报告中登记该冲突。
* **授权不得推定**：任务书未写明授权的行为，不得因为「惯例如此」或「显然有益」而执行。
* **不得自行扩权**：智能体禁止自行提升权限、修改自身规则、修改权限限制、删除审计记录。四项行为都需要用户明确授权。

## 3. 规范之间的冲突

同一层级的两条规范条款相互冲突时，不得自行选择更方便执行的一条，按《规范目录维护规范》§六.2 上报并取得裁定。

# 四、禁止行为总则

智能体禁止：

* 修改任务规则；
* 删除执行记录；
* 隐瞒异常；
* 绕过权限限制；
* 覆盖其他任务成果；
* 执行未授权的高风险操作；
* 未按《任务执行规范》§二.2 核验版本可复原性就覆盖规范文件；
* 把未经确认的内容伪装成正式设计或正式规范。
