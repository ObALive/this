# 一、工作区目录边界

| 目录 | 职责 | 写入边界 |
| --- | --- | --- |
| `Task/` | 任务书 | 一个任务一份，文件名与任务编号一致 |
| `Report/` | 任务执行报告 | 每份任务书对应唯一报告，命名与任务书一致 |
| `Output/` | 任务过程性文件 | 按任务编号建独立子目录，与 `Design/` 的区别是本目录的产物是一次性的 |
| `Design/` | 全局设计文档库 | 跨任务共享、长期维护、持续生长的系统 wiki |
| `Rules/` | 规范目录 | 仅在规范变更类任务中写入 |
| `Input/` | 用户输入的原始材料 | 只读 |
| `Tool/` | 工具与说明 | 仅在任务书明确授权时写入 |

目录职责的可执行细则见《任务执行规范》§二.1。

# 二、文档体系总原则

## 1. 逐层降低歧义

策划文档分四层，每向下一层减少一种歧义：创意需求稿消除「为什么做」的歧义，系统设计稿消除「游戏规则是什么」的歧义，架构设计稿消除「程序由谁负责什么」的歧义，功能拆分消除「具体要写什么」的歧义。

一份设计文档是否合格，不用「写得详细不详细」衡量，而应问：下一阶段的人是否还需要自行做决策？

## 2. 上层定约束，下层定细节

**上层规定下层必须遵守的约束，下层自行决定不影响上层约束的实现细节。**

这条原则同时约束两个方向：下层不得重新定义上层的决定；上层不得提前替下层做完所有决定，否则下层失去调整空间。

## 3. 唯一事实来源

一条规则只在一个位置定义，其他位置引用。适用于三个层面：

| 层面 | 唯一来源 |
| --- | --- |
| 术语 | `Design/00-总览/02_术语表.md` |
| 跨系统交互逻辑 | `Design/00-总览/01_设计原则与跨系统交互逻辑.md` |
| 重大取舍 | `Design/00-总览/03_设计决策记录.md` |
| 规范条款 | `Rules/` 下的对应规范文件 |

同一规则在两处各写一份，等同于两处都会随时间漂移，最终无法判断哪一份有效。

## 4. 保留未决

明确知道「这里还没决定」远比写一个未经思考的临时方案更有价值。禁止为了让文档看起来完整而强行补全待定问题。

## 5. 不擅自设计

智能体不得自行创造游戏设计，也不得自行创造规范。任何写入正式文档的内容，只能来自：已知事实、用户明确决定的内容、从已有内容可以直接推导出的内容。建议与未决事项必须明确标记，不得伪装成正式内容。

# 三、冲突优先级

## 1. 执行顺序

发生冲突时，按下列顺序执行：

```
1. 用户明确指令
2. 任务书授权
3. 规范目录（Rules/）
4. 目录内既有惯例
5. 智能体默认行为
```

任何低优先级规则不得覆盖高优先级要求。

## 2. 判定的三条附带规则

* **「明确」指当次有效**：用户此前的指令被后续指令取代时，以最新一条为准；任务书与用户指令冲突时，以用户当次指令为准，同时在任务报告中登记该冲突。
* **授权不得推定**：任务书未写明授权的行为，不得因为「惯例如此」或「显然有益」而执行。
* **不得自行扩权**：智能体禁止自行提升权限、修改自身规则、修改权限限制、删除审计记录。四项行为都需要用户明确授权。

## 3. 规范之间的冲突

同一层级的两条规范条款相互冲突时，不得自行选择更方便执行的一条，按《规范目录维护规范》§六.2 上报并取得裁定。

# 四、禁止行为总则

智能体禁止：

* 修改任务规则；
* 删除执行记录；
* 隐瞒异常；
* 绕过权限限制；
* 覆盖其他任务成果；
* 执行未授权的高风险操作；
* 未经留档覆盖规范文件；
* 把未经确认的内容伪装成正式设计或正式规范。
