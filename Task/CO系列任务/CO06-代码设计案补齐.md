# CO06-代码设计案补齐

## 一、任务背景

代码设计案的定位是以功能目的为导向，用可读、概括的自然语言解释现有代码。现有 `Code_Design/` 中仍保留面向伪代码实施的规格和索引说明，与当前定位及实际开发进度存在差距。

项目已按网络图逐步实现部分功能，完成范围在 `Tool/项目网络图/` 的现行数据库中标记。本任务以这些实现标记为范围入口，结合实际源码补齐代码设计案，使文档反映当前已经具备的功能、主要过程、协作与行为边界。

## 二、核心指导理念

### 1. 网络图确定核查范围，源码确定实现事实

以节点的“已实现”状态筛选本轮需要解释的功能，读取完整目标及相关对象、备注和依赖，不能仅凭概要或对象声明判定覆盖完整。图上的实现标记不等于已经完成源码核对或运行验证；实际能力、入口和边界以当前源码及必要配置、场景与资产为准。

一个节点可能涉及多个类型，同一个类型也可能承接多个增量节点。按当前功能归纳说明，保留各增量之间的联系，不把每个节点机械转换成一份文档，也不把整个类型的未来能力都算作已实现。

### 2. 解释功能目的，归纳当前行为

按 `Rules/06_代码设计案编辑规范.md` 组织正文，让读者理解功能解决什么问题、如何进入、经过哪些关键判断、怎样协作、最终产生什么结果。现有稿件中与实际代码一致的背景和说明可以保留归纳；未落地的方案不能继续作为当前实现陈述。

对部分实现、证据不足及代码与设计不一致的情况，区分说明当前事实、缺失依据和影响。文档补齐不承担继续开发缺失能力或替代码作技术决定的职责。

## 三、工作方向与授权范围

### 1. 补齐已实现功能的代码说明

对执行开始时现行网络图中全部“已实现”节点核对文档覆盖，补齐缺失内容，修订过时或失真的说明。解释所需的前置能力与协作对象应结合实际使用关系纳入阅读和说明范围；未实现的后续节点仅用于识别边界，不扩展为待实施规格。

按需要在本工作区 `Code_Design/` 中修订现有文档或新增功能专题，并同步 `Code_Design/README.md` 的定位、阅读入口、覆盖范围和状态。保留仍有效的文件与编号，不以本任务为由重构整个文档库。与本轮功能相关的旧实施内容应明确与当前解释区分，无关稿件保持现状，不自动取得“已核对”状态。

### 2. 建立覆盖与证据对应

在本任务过程材料中保留“已实现节点—实际实现—代码说明”的对应关系，能够逐项确认节点已被解释，或已明确记录部分实现、标记与源码不一致、依据缺失等情况。

代码说明正文以源码位置、关键入口和核对基线作为实现依据；网络图数据库路径、节点编号及执行报告等过程引用留在任务记录中，按适用引用规范处理。

任务执行时可以只读查看工程仓库的 Git 提交记录及对应差异，确认实现各个节点时新增、修改或删除了哪些脚本、配置、场景与资产，并辅助建立节点与实际实现的对应关系。结合提交内容和前后调用关系判断改动归属，不仅凭提交标题认定某个节点的全部实现范围。

提交记录用于追溯实现过程，当前功能说明仍须对照工程现状，包含后续提交及尚未提交的相关改动。历史行为已被调整时，以当前实现为准；不能将某次提交中的行为直接视为现状，也不能将提交存在视为运行验证通过。

### 3. 改动边界

授权修改本工作区 `Code_Design/` 中与本轮功能有关的正文、必要总览及库索引，并按执行规范生成本任务记录。网络图工具与数据库、实际代码工程、`Rules/`、`系统设计文档/` 和 `架构设计文档/` 均作为只读资料。

发现代码缺陷、图中标记不准确或上游设计需要调整时，在本任务记录中写明具体事实和影响，不通过本任务修复代码、回写实现状态或改变游戏规则。

### 4. 完成判据

- 本轮基线中的全部“已实现”节点都有覆盖结论，既无遗漏，也未把后续计划写成已经具备的能力。
- 每项已核实功能都有可定位的说明，能够独立读懂功能目的、入口、主要过程、关键协作、结果与适用边界，且符合代码设计案的写法与验收规范。
- 关键行为能追到实际源码和必要工程依据；未实现、待核实及设计差异明确可见，缺少依据的部分不标为已核对。
- 库索引与正文的定位、覆盖、链接、核对基线和状态一致；旧实施稿与已核对解释的身份清楚。
- 覆盖核查记录与任务报告齐备，准确区分文档核对结果和实际执行过的编译、测试或运行验证。
