# 混稿
1. 在游戏系统当中，时间的分划粒度的最小单位为10分钟，自此往上的小时/天/月/年等均与现实一致
2. 有关闰年闰月，游戏内会虚构一个日历，如设定现代的时间为1900年，程序以现实的1900年来计算闰年即可
3. 日程表的UI设计：完全套用现有的手机电脑当中的时间与日期系统。目前的设计方案是参照Ubuntu26桌面系统，点击屏幕上方的时间后显示的页面。会对Notification显示区做出一些改动，用于显示日程表（记录每段时间经历了些什么事件）（具体UI设计方案暂缓）
4. 日程表现实的信息包括：已经经历的事件，正在经历的事件，规划未来的事件。demo阶段先只做已经经历的事件
5. 玩家经历一个事件的流程：到达事件地点->交互目标并确认进入事件->时间才参与事件的过程中逐步推进->到达结束事件的条件，退出事件，结算玩家资源和时间
6. 从事件流程当中可见，同一事件的持续长度是取决于玩家采取的不同操作的
7. 事件的各个状态：未出现、可进入、进行中、已完成、已错过
8. 事件对于世界后续生成内容的影响，以楼房着火隐患排查为例
    1. 错过事件。在事件状态从可进入切换到已错过之后，在游戏时间继续推进一段时间之后，楼房会着火；地图的地点发生变化：楼房区域会变成火场区域，在一段时间过后变成废墟区域；发生在楼房内的事件不再会刷新；发生在废墟的事件会允许进入事件池并刷新；发生在火场区域的事件同样允许进入事件池，但是窗口期更短，不得超过火场场地存在的时间
    2. 进入事件，且玩家在事件当中以激进的方式排除隐患。耗费更少的时间完成事件，但是会有伙伴牺牲；楼房区域不会发生转变；伙伴相关事件不再刷新。
    3. 进入事件，并且玩家谨慎排除隐患。耗费更多的时间完成事件，没有人牺牲
    4. 进入事件，且玩家排除隐患失败，强制进入一个火灾事件。
    5. 其他
   需要注意，这里的所有有关世界场景的变化，在程序上也都是通过包装为事件来实现的。比如错过事件的时候楼房从正常变为着火，代码层面上就是进入了一个没有流程，日程中不可见，没有投入和产出，玩家感知不到的一个强制事件。将所有场景变化包装成事件来执行，便于管理
