# 4.GAP表
1. 物品类别与用途关系未定义，无法判断货物、装备、遗物、消耗品和货币是互斥类别还是可重叠用途
所有的物品都不互斥，共享同一套底层架构，根据其所挂载的组件和赋予的属性而有着不同的功能。面向功能设计组件而非物品类别。物品的功能由组件实现。
2. 首版货币形态没有裁定，创意稿的三形态要求与 B01 的现金单形态建议并存
货币同样与其他物品没有本质区别，只是对一个基础的“元物品”附加组件（如价值组件，物品堆叠组件）来实现货币的功能。货币物品甚至本身不会被打上类似于“money”一类的标签，而是在一个区域内，其广泛被作为等价物和交易媒介使用，给予玩家“这是货币”的印象。在后期游戏地图切换之后，还便于引入各个国家地区不同的货币。
3. 物品化货币的面额、堆叠、找零、拆分合并、支付来源与不足处理均未定义
在Demo阶段暂时不设置货币面额，暂时不引入找零问题。可以先将其设置为一个有着很高堆叠上限的物品。
4. 初期一格一物与整格、单个、一半三种取物粒度的语义尚未统一
此部分内容涉及到有关在容器UI界面移动物品的一系列操作，目前的设计方案：
    鼠标上没有悬挂物品时：
   1. 左键单击格子，格子内的所有物品悬挂在鼠标上
   2. 右键单击格子，格子内的一半物品（向上取整）悬挂在鼠标上
   3. shift+左键单击格子，格子内的所有物品转移到当前UI内的其他容器中（从左往右，从上往下填充）。如果没有另一个容器的UI或者无法放入则动作无效
   鼠标上悬挂物品时：
   1. 左键单击空格子，悬挂的物品全部转移到格子内。如果无法全部放入，剩余部分依旧悬挂在鼠标上。无法放入时动作无效
   2. 右键单击空格子，悬挂的物品会分一个转移到格子内。无法放入时动作无效。
   3. 左键单击物品，如果是同类物品，则悬挂的物品全部转移到格子内。如果堆叠已满（无法堆叠判断为堆叠已满，下同），剩余部分依旧挂在鼠标上。
   4. 左键单击物品，如果是其他物品，则悬挂的物品会全部转移到格子内，格子内原本的物品会悬挂到鼠标上。无法完全放入鼠标上原本的物品时动作无效。
   5. 右键单击物品，如果是同类物品，则悬挂的物品会分一个转移到格子内。如堆叠已满则动作无效
   6. 右键单击物品，如果物品是包含容器格的其他物品，则悬挂的物品会全部进入容器（从左往右，从上往下填充）。如果堆叠已满则剩余部分依旧悬挂在鼠标上。无法放入时动作无效。
   没有提及的操作均无效。
有关物品UI内的鼠标动作后续还会扩展，要预留接口。
5. 各容器中的物品是否可用于付款、前置条件、委托交付和战斗没有统一边界
在队伍中的所有角色的身上的所有容器内的钱均可用于交付物品和付款（由于2的定义，付款本质也是交付物品）
6. 背包满载时会优先由队友身上的容器装载物品。无论何时，角色背包空间内的容器类物品都不会自动装载物品，必须手动装入。部分容器必须在容器UI打开的状态下才能存取物品，这类容器内的物品在交付物品时不会被自动检测。如果可以自动装载的空间全满时，获得物品时会弹窗提示，玩家可以选择是否继续领取，如果继续领取物品会掉落在地上。玩家可以整理好背包空间后拾取
重要定义：背包空间，指的是角色已装备的装备中，所有拥有容器组件的装备的储物空格（含队友）。容器中的容器的空间不会被算作背包空间。

8. 交易的方式多样，包括但不限于指定货物订购，拍卖，市场选购等。这些交易方式的实现主要通过事件来完成，有关交易带来的时间的推进也会在事件当中定义。只有几个挂靠在物品系统域的动作需要定义，以方便在事件的配置中构建出一个交易事件。在交易事件当中，一般不再完全采取通用的“玩家行动决定事件的行进分支”模型，而是采用进入一个“根据玩家行动即时进行相应反馈”的行动状态。例如在这个状态内，玩家可以自由选购物品，自由完成“选择，交付，获得”的循环，直到到达判定退出这个行动状态的条件。
需要在事件系统当中补充内容：事件系统当中设计了“事件里存档状态和玩家行为会决定事件的分支，每个分支的末端有不同的事件结果”的事件结构模型。补充如下：事件由一个个事件片段组成，事件片段串联起来就是整个事件。一个事件片段有时会导向多个事件片段，由存档状态和玩家行为确认进入的下一个事件片段会是哪一个。一个事件片段的内容种类各不相同，目前已有的：对话、“根据玩家行动即时进行相应反馈”的行动状态等。有关片段内容种类需要在事件系统相关文档当中构建一个表格，便于后续扩展和补充
   1. 物品交付。应用场景：物品订购、换取授权等，玩家按照所需要交付的物品提交内容。提交之后的效果包括但不限于：（物品订购）物品到货的事件进入事件池，从事件池生成成功后（失败就是卖方违约）延时发生。（换取授权）交付门票之后，事件往验票员放行玩家的走向发展。
   2. 物品交换。应用场景：市场购买、以物易物等。玩家按照所需要交付的物品提交内容后，对应的交换目标直接进入背包
   3. 其他，后续在开发过程中补充，需要预留便于扩展和补充的表格
