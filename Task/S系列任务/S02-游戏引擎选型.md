基于现有的**系统设计稿**，重新编写/优化**架构设计案**

本项目已经确定使用 **Unity 引擎**作为游戏开发技术基础。

本次工作的目标不是将一套与引擎无关的通用代码架构“适配到 Unity”，而是：

> **以 Unity 作为既定技术环境，在 Unity 提供的程序运行机制、对象模型、资源体系、序列化机制、编辑器能力和生命周期机制之上，自然地设计游戏程序的代码结构。**

### 一、架构设计案的定位

**架构设计案 = 游戏程序整体结构与全局技术约束的规格。**

它规定：

- 程序整体由哪些部分组成
- 各部分负责什么
- 各部分如何连接
- 依赖方向是什么
- 系统必须遵守哪些全局技术规则
- 如何保证各具体游戏系统能够在统一的软件结构下实现、组合、运行和维护

因此，架构设计案需要约束代码设计案，并充分利用 Unity 已有能力。

### 二、Unity 的定位

Unity 不只是代码运行环境，而是本项目基础架构的一部分。

在设计代码结构时，应优先判断：

> **Unity 是否已经提供满足需求的机制。**

如果 Unity 已提供合适的基础能力，应直接将其纳入程序架构，而不是重新构建功能重复的基础设施。

例如（举例，但不限于以下情况）：

- 静态数据可优先使用 `ScriptableObject`
- 场景对象可利用 `GameObject + Component`
- 对象生命周期应结合 Unity 生命周期进行设计
- Prefab 应作为可复用对象的基础组织方式
- Unity Serialization 应作为适当的数据持久化/配置手段
- Unity 的资源体系用于组织和加载游戏资源
- Unity Input、UI、Animation、Physics 等成熟模块，在满足需求时优先直接采用

这意味着：

> **架构设计不应默认“所有基础设施都需要自行实现”，而应优先考虑“哪些能力可以直接由 Unity 提供”。**

尤其是原文中基础设施板块，需要着重审查这些内容在Unity引擎中已有现成的轮子。

### 三、代码设计原则

代码设计过程中遵循以下原则：

1. **Unity 原生能力优先**
   
   对于 Unity 已经提供且能够满足需求的能力，优先直接采用，不重复建设。

2. **以 Unity 的对象模型设计程序结构**
   
   合理区分：
   - `MonoBehaviour`
   - `ScriptableObject`
   - 普通 C# 类
   - Unity Asset
   - GameObject / Component
   - Scene 对象
   
   不得为了形式统一而让所有对象继承 `MonoBehaviour`。

3. **以 Unity 生命周期作为程序运行结构的一部分**
   
   对需要参与 Unity 生命周期的对象，明确其初始化、运行、销毁等阶段，以及与其他系统的执行顺序关系。

4. **自行建设基础设施必须有理由**
   
   只有当 Unity 原生能力无法满足需求，或项目存在明确的特殊需求时，才自行设计对应基础设施，并说明其必要性。

5. **代码设计服从架构设计案**
   
   不得为了使用某项 Unity 技术而无理由改变既有系统职责、依赖方向和整体架构。

6. **优先考虑实际开发与维护**
   
   代码结构应能够直接指导后续功能需求拆分和实际编码，并适合长期在 Unity 项目中维护。

### 四、编写代码设计时重点回答的问题

对于每个程序模块，至少明确：

- 它属于什么程序层次/模块
- 它负责什么
- 它依赖什么
- 谁依赖它
- 它是否需要 Unity 生命周期
- 它是否应该是 `MonoBehaviour`
- 它是否应该是 `ScriptableObject`
- 是否应该使用普通 C# 对象
- 数据应该由谁持有
- Unity 对象与纯逻辑对象如何分工
- 对象如何创建、初始化和销毁
- 系统之间如何通信
- 是否可以直接使用 Unity 已有能力
- 如果不能使用 Unity 原生能力，为什么需要自行实现

### 五、设计方式

不要采用以下方式：

**先设计一套通用、独立于引擎的程序架构 → 再寻找 Unity 对应实现。**

应采用：

**游戏系统需求 + 架构设计案 + Unity 技术环境 → 直接形成代码设计。**

因此，Unity 的技术特点应该自然地体现在最终代码设计中，而不需要额外增加一层“Unity 适配方案”。

### 六、最终目标

最终形成的代码设计稿应当让程序员在阅读后能够明确：

> **在这个已经确定使用 Unity 的项目中，游戏程序具体应该由哪些代码对象、Unity 对象和基础设施组成，它们分别负责什么，如何组织和连接，以及哪些能力直接使用 Unity、哪些能力需要项目自行实现。**

同时，避免为了体现“架构完整”而重复建设 Unity 已经提供的基础能力。

**核心原则：**

> **不是把 Unity 接入既有架构，而是在 Unity 这一既定技术基础上设计架构与代码。**
