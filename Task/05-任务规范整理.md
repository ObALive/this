# 任务背景

工作区内的文档编辑约束分散在多处，分别是 `Rules/BaseRules.md`、`Task/C系列任务/C系列任务通则.md`、`系统设计文档/README.md`、`系统设计文档/_模板/系统设计文档模板.md` 与 `Input/！重要！文档撰写规范.md`。智能体接到任务时没有统一的入口判断本次适用哪些规则，历次任务报告要靠人工经验挑选，容易出现漏读与重复阅读；后续任务中提出的新规范也没有固定的落盘流程。

第一轮把五处来源归并进 `Rules/` 并建立索引与维护规范，其中 `系统设计文档/README.md` 与 C 系列任务通则的重复内容按当时的写入边界未回收，登记为「待收口」。第二轮按指令收口，消除两处并存。

# 核心指导理念

规范目录 `Rules/` 是全部规范的唯一权威落点，由这个目录规范整个工作区。索引负责路由，规范文件负责承载条款，维护规范负责规范自身的增删改。三者职责分开，任何一条规则只在一处定义。

`Rules/` 之外的文件只承载自身目录的定位、实例清单与现状登记，不承载规范条款；需要引用规范时指向 `Rules/`。

# 工作方向指导

## 第一轮：建立规范目录

1. 建立规范索引。智能体接到任务后先读索引，按任务类型与触发信号分析出本次任务适用的规则清单，再按图索骥读取规范文件。
2. 建立规范目录维护规范。规定在新任务中提出的新规范如何落盘：触发条件、归类与查重、确认、写入、索引登记、修订与废弃的完整流程。
3. 把散落在各处的规范全文归并进 `Rules/`，形成按适用面拆分的规范文件集，外部来源在索引中登记出处。
4. 清除原文件中的失效路径前缀。原 `Dsh` 目录的内容已直接挂在工作区根目录下，规范中的 `Dsh/` 前缀与实际不符。
5. `Rules/` 目录未纳入 git，改写既有文件前先把原件复制到本任务输出目录留档。

## 第二轮：全部编辑规范统一到 Rules

第一轮把 `系统设计文档/README.md` 第二节至第六节与 `Task/C系列任务/C系列任务通则.md` 的内容登记为「待收口」，两处规则与 `Rules/` 并存。第二轮按指令收口，使 `Rules/` 成为整个工作区唯一的规范落点：

6. 全部编辑规范统一到 `Rules/` 目录下，由这个目录规范整个工作区。`Rules/` 之外的文件不再承载规范条款。
7. 把 `系统设计文档/README.md` 第三、四、五、六节的规则条款迁入 `Rules/`，该文件保留库定位、分层实例清单、依据对应与当前状态。
8. 把 `Task/C系列任务/C系列任务通则.md` 的六条限制与阶段范围收编进 `Rules/`，原文改为指向规范文件的对照表，保留原路径使历史任务书的引用继续有效。
9. 新增一份承载文档库组织规则的规范文件，与既有四份并列。
10. `Input/！重要！文档撰写规范.md` 位于只读目录，原文不回收，在索引的外部来源登记中标注其规则内容已承接、原文转为参考材料。

# 工作方法

## 第一轮

1. 通读上述五处规范来源，按适用面归类合并，同一条规则只保留一份。
2. 智能体行为与任务流程类规则归《任务执行规范》，策划文档写法类规则归《文档编辑规范》，规范自身的写入流程归《规范目录维护规范》，跨规范的原则与冲突优先级归《规范总则》。
3. 产物分三类：规范目录的改动落在 `Rules/`；任务书落在 `Task/`；报告落在 `Report/`；过程文件与原件留档落在 `Output/05-任务规范整理/`。
4. 写入边界：可以写入 `Rules/`、`Task/`、`Report/` 与本任务输出目录。`系统设计文档/`、`Input/`、`Tool/` 与其他任务目录一律不改动。
5. 本次任务不建决策库。遗留问题写进任务报告的后续建议一节，需要正式呈报时另开一轮缺口分析任务。

## 第二轮

6. 写入边界扩大到 `系统设计文档/README.md` 与 `Task/C系列任务/C系列任务通则.md` 两份承载重复规则的文件。`系统设计文档/` 下的其他设计文档、`Input/`、`Tool/` 与其他任务目录仍不改动。
7. 迁移前逐条建立映射，确认原文件的每一条规则都有承接方，不遗漏、不改写规则内容。
8. 改写既有文件前先把原件复制到 `Output/05-任务规范整理-收口/` 留档，并核对校验值。
9. 迁入 `Rules/` 的规则按现有规范文件的章节体例编写，一条规则只落一个位置。
10. `Input/` 内的重复内容不回收，按文件隔离规则处理。
