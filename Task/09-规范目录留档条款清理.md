# 任务背景

工作区已由 git 托管，`Rules/`、`Task/`、`Output/`、`Report/` 四个目录的文件全部处于 git 跟踪之下。但规范目录内仍残留一套手工版本管理的条款：改写文件前把原件复制到任务输出目录留档、按 `_v{序号}_{日期}` 命名副本、把留档情况写进索引与核验清单。这套机制在版本管理缺位时成立，现在与 git 承载历史的规定并存，形成两处口径：

| 对象 | 现行口径 | 出处 |
| --- | --- | --- |
| 设计文档 | 修订直接在原文件上进行，历史由 git 提交记录承载，**不另存历史版本、不保留归档副本** | `Rules/03_文档编辑规范.md` §二.2；`Rules/05_文档库组织规范.md` §三.2、§五.1 第 2 条 |
| 规范文件 | 改写或拆分之前，把原文件复制到当次任务的输出目录留档 | `Rules/04_规范目录维护规范.md` §四.2、§四.3；`Rules/01_规范总则.md` §四 |

同一个工作区对「要不要留档」给出两套相反口径，执行时只能靠人判断，且留档副本本身又不受清理规则约束，会持续积累。本次任务取消 A、C、D 三类涉及的留档操作，把版本管理的口径统一到设计文档一侧。

# 核心指导理念

**版本管理只有一个权威载体：git。** 凡"为了留下改写前的版本"而复制文件、命名副本、登记留档清单的动作，一律取消；改写前的版本通过 `git show HEAD:{路径}` 取回，不再另存副本。

**边界情形的判据是「这份文件改写前能否用 git 复原」，不是「它属于哪个目录」。**

- 文件已在 `HEAD` 中 → 版本管理已承载，不另建副本；
- 文件尚未进入 `HEAD`（新建未提交、或被忽略）→ 差别不在"要不要留档"，而在"**先提交再改写**"：把文件纳入版本管理是唯一动作，仍不建手工副本。

**要区分留档动作与相邻的三件事**，后三件不属于本次取消范围：

| 事项 | 是否取消 | 原因 |
| --- | --- | --- |
| 留档动作（复制副本、命名 `_v`、登记留档清单） | 取消 | 与 git 重复 |
| 库级台账 | 不取消 | 台账登记「当前有哪些系统、术语、决策、界面」，是内容清单；git 登记文件历史。两者语义不同 |
| 任务结束即冻结、过程文档归档子目录 | 不取消 | 是流程约束与目录组织，不是版本管理 |
| 过程文档名里的 `_v1`、`_v2` 后缀 | 不取消 | 是并列交付物的编号，不是同一文件的历史版本；git 存历史不存并列交付物 |

## 二、订正过时理由（C 类，1 处）

### C1 `Rules/05_文档库组织规范.md` §六.2

现文「过程文档可以带版本号，与设计文档库不带版本号的规则不同。原因是过程文档是一次性产物，不进入 git 承载的长期修订链，版本号是它自身的历史载体」。

理由与实际不符：`Output/` 下的过程文档同样处于 git 跟踪之下。改为：「过程文档可以带版本号，与设计文档库不带版本号的规则不同。原因是过程文档的版本号标识的是**并列交付物**，同一任务的不同轮次产出同时存在、各自独立，不是同一份文件的历史版本」。结论「可以带版本号」不变。

## 三、统一版本管理口径（D 类）

以设计文档一侧为基准，即 `Rules/03_文档编辑规范.md` §二.2 与 `Rules/05_文档库组织规范.md` §三.2、§五.1 第 2 条的现行表述不动。规范文件一侧按第一、二节的改法收敛后，全库对「留档」只剩一种口径：**不留档，历史由 git 承载**。

收敛后核对一次全库：`Rules/` 下不再存在要求复制副本、命名 `_v` 副本或登记留档清单的条款。

# 工作方法

## 1. 本次任务的性质与适用规范

本任务属于规范变更类。执行前按 `Rules/README.md` 第一节四步判定取出适用清单，并按 `Rules/02_任务执行规范.md` §二.1 在任务报告中登记。

## 2. 待落盘的规范内容、来源指令与预期落点

本节按 `Rules/04_规范目录维护规范.md` §六.1 的要求写明三项：

| 项 | 内容 |
| --- | --- |
| 待落盘的规范内容 | 取消留档动作，把版本管理口径统一为 git 承载；订正过程文档版本号的过时理由 |
| 来源指令 | 用户直接指令：修改前文件由 git 管理，以设计文档口径为准；A、C、D 三类涉及的留档操作全部取消 |
| 预期落点 | `Rules/01_规范总则.md`、`Rules/02_任务执行规范.md`、`Rules/03_文档编辑规范.md`、`Rules/04_规范目录维护规范.md`、`Rules/05_文档库组织规范.md`、`Rules/BaseRules.md`、`Rules/README.md` |

## 3. 落盘流程

按 `Rules/04_规范目录维护规范.md` §三 的七步执行。第 1 步的触发情形为「用户直接要求把某项变更写入规范目录」；第 3 步查重必须逐条核对第一至三节列出的 11 处，确认没有同类条款残留；第 5 步的确认以本任务书为凭据；第 7 步在 `Rules/README.md` 的变更记录中登记本次修订。

本次修订属取消与收敛条款，不新增编号，不新建规范文件。

## 4. 读什么

1. `Rules/README.md` 全篇，取适用清单；
2. `Rules/01_规范总则.md` 与 `Rules/02_任务执行规范.md`；
3. `Rules/04_规范目录维护规范.md` 全篇，本次改动的流程依据；
4. 第一至三节列出的六份文件中的对应章节，逐条核对现文。

1. 需要改动 `Rules/02_任务执行规范.md` §四（权限类条款）时先请示，按 `Rules/04_规范目录维护规范.md` §四.3 第 4 条，权限类条款的修订必须有用户明确授权。A5、A6 落在 §二与 §六，属权限判定与核验清单，不在 §四之内，按本任务书授权执行；

3. 发现取消某条后会留下语义缺口（例如删除后读者无法判断改写前该做什么）时，先补出替代表述再请示，不得只删不留。
